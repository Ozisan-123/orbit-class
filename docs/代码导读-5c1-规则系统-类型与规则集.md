## 本模块在系统里的位置

**P2 解决的问题**：加一条约束以前要**改求解器代码并重新部署** ✓ 现在变成**在页面上加一行** ✓

它的机制是「**规则 = 数据 + 实现**」✓：

```
    数据（可编辑）                        实现（开发者写一次）
  ┌──────────────────────┐            ┌────────────────────────┐
  │ constraint_rules     │            │ orbit-solver-core      │
  │   rule_type ─────────┼───────────►│  RuleRegistry          │
  │   params (JSON)      │            │   type → RuleHandler   │
  │   hardness / weight  │            │  （10 个 handler）      │
  │   enabled / scope    │            └────────────────────────┘
  └──────────┬───────────┘
             │ 规范化哈希
             ▼
  ┌──────────────────────────────────────┐
  │ constraint_rule_versions             │
  │   rule_set_hash + **整份规则快照**    │  ← 为什么存快照而不只存 hash：见 §5c1.5
  └──────────────────────────────────────┘
```

**本册三个主题**：

## 5c-1.1 `RuleTypeCatalog` —— 唯一真相来源（75 行）

### 🔴 类注释里那张图：一份 schema，三处消费

```
RuleHandler.params()  →  RuleParamSpec  →  ┬─→ 前端"新建规则"表单（动态渲染，不用为每条规则写页面）
                                            ├─→ 后端保存时的参数校验
                                            └─→ 助手的工具定义（P4/P5，新增规则类型自动可用）
```

> 这三处**必须来自同一个地方**。如果前端自己维护一份表单定义，
> 那么"开发者加了一条新规则"和"前端能配这条规则"就会变成两件事 —— 而它们**本该是同一件事**。

🔴 **最后那句话是全部要点** ✓ —— 它把一个**工程问题**说成了**语义问题** ✓：
"加了一条规则但前端配不了" ✗ 看起来只是"前端忘了改" ✓
**实际上是"系统里有两份关于'有哪些规则'的真相"** ✗ —— 而真相只该有一份 ✓

**这就是"单表驱动"（single source of truth）在业务代码里的具体形态** ✓
而它的**验证方式**很实际：**加一个 handler，重启，前端表单自动多一条 ✓ 不需要改任何其他地方** ✓

### 为什么直接用 `BuiltinRules.registry()` 而不是再列一份

> `BuiltinRules` 已经是"系统内置哪几种规则"的装配点（solver-core 里也这么用它）。
> 这里的职责只是**换个形状暴露出去**（投影成 HTTP 响应用的 DTO），而不是决定有哪些规则。
> 所以它**没有任何 if/else 分支，也没有类型白名单** —— 新增一个 handler，这个接口下次请求就自动多一条。

⚠ **"没有任何 if/else 分支"这句可以当作一个检查标准** ✓：
如果某个"目录 / 清单 / 枚举"类里有 `switch` 或白名单 ✗ 那它就**不是投影** ✗ 而是**第二份真相** ✓

### 逐方法

```java
private final RuleRegistry registry = BuiltinRules.registry();
```

⚠ **字段初始化时直接调用** ✓ —— 而不是构造器注入 ✓
因为 `BuiltinRules.registry()` 是**纯静态构造** ✓（solver-core 不认识 Spring ✓ 不能变成 bean ✓）
**代价**：注册表在**类加载时**建好 ✓ 而且**不可替换** ✓（没有 setter ✓ 也没法 mock ✓）
**收益**：这个类因此**不依赖任何 Spring 容器状态** ✓ 测试时 `new RuleTypeCatalog()` 就行 ✓

| 方法 | 用途 |
|---|---|
| `all()` | **全部**规则类型（含不变量 ✓）→ 供"规则能力清单"接口 ✓ |
| `configurable()` | **只有可配置的** ✓ → 供"新建规则"下拉 ✓ |
| `handlerOf(String)` | 按 type 找 handler ✓ **未知类型抛 400** ✓ |
| `isKnown(String)` | 存在性检查 ✓ |
| `isMandatory(String)` | 是否不变量 ✓（**先 `contains` 再 `get`** ✓ 不会 NPE ✓） |

#### 🔴 `configurable()` 为什么必须排除不变量

> 不变量与数据驱动规则**不该出现在这里**：它们始终生效、不接受参数，
> 让用户"选它"只会产生一条**什么也不做的规则**（甚至误导用户以为关掉它就能改变行为）。

⚠ **"误导用户以为关掉它就能改变行为"** ✓ —— 这是比"产生无用数据"更严重的后果 ✓
**一条永远生效的规则出现在"可开关"的列表里** ✗ 用户会以为他能关 ✓
→ 他关掉了 ✓ 行为没变 ✓ → **他会怀疑整个系统的可靠性** ✗

#### 🔴 `handlerOf` —— "在边界上翻译，而不是在出口处兜底"

```java
public RuleHandler handlerOf(String ruleType) {
    if (!registry.contains(ruleType)) {
        throw BusinessException.badRequest("未知的规则类型: " + ruleType);
    }
    return registry.get(ruleType);
}
```

**注释里的论证非常值得读** ✓：

> ⚠ 「未知类型」是**用户输入错误**，不是服务端故障 —— 所以在这里就把 solver-core 抛的
> `IllegalArgumentException` 翻成 400。
>
> 为什么不直接在全局异常处理器里把 `IllegalArgumentException` 映射成 400：
> 那**太宽了**，会把真正的编程错误（空指针式的前置条件违反）也报成"你的请求有问题"，
> 从此这类 bug **永远以 400 的面目出现、淹没在正常错误里**。
> **在边界上翻译，而不是在出口处兜底。**

🔴 **这是全项目关于"异常处理粒度"最重要的一段** ✓ ——

| 做法 | 对用户输入错误 | 对真正的 bug |
|---|---|---|
| 全局把 `IllegalArgumentException` → 400 ✗ | ✓ 正确 | ✗ **被伪装成"你的请求有问题"** ✓ 从此查不到 ✓ |
| **在边界翻译**（现在 ✓） | ✓ 正确（这里翻 ✓） | ✓ **照旧 500 + 日志** ✓ 保持显眼 ✓ |

> 💡 **可推广**：**异常类型是有语义的** ✓
> `IllegalArgumentException` 在 Java 里既被用来表示"参数不合法（用户输入）"✓
> 也被用来表示"内部前置条件被违反（代码 bug）"✗ —— **它同时承担了两种语义** ✓
> **所以它不该被全局映射** ✗ 只能在知道上下文的地方翻 ✓
>
> 对照第 1 册 `ApiExceptionHandler` 的兜底 ✓ —— 那里把**未预期的 `Exception`** 兜成 500 并**打日志** ✓
> **两者配合起来才是对的**：边界翻已知的 ✓ 出口兜未知的 ✓

⚠ 而**这条规则的价值在于它防的是一类"慢性病"** ✗：
如果 400 里混进了真 bug ✓ 那**监控上"400 率"这个指标就失去意义** ✓
（正常用户输错和程序出错混在一个数字里 ✓ 无法告警 ✓）

## 5c-1.2 `RuleTypeResponse` —— 🔴 两个字段"故意不加"（43 行）

```java
public record RuleTypeResponse(
        String ruleType,
        String displayName,
        boolean mandatory,
        boolean editable,          // = !mandatory
        List<RuleParamResponse> params) { ... }
```

**只有 5 个字段** ✓ 而类注释用了**两大段**解释**为什么没有另外两个字段** ✓ —— 这是全项目最好的"减法论证" ✓

### 为什么不加 `layer`（不变量 / 数据驱动 / 可配置）

> 方案 §6.1 的三层语义很重要，但它**在代码里唯一可判定的后果就是 `mandatory()`**：
> - 不变量 + 数据驱动 → `mandatory = true` → 用户**碰不到**
> - 可配置 → `mandatory = false` → 用户可增删改
>
> 而"某个 mandatory 规则到底是不变量还是数据驱动"**无法从实现推出来**（两者都是"参数为空、始终生效"）。
> 与其在 scheduling 里再硬编码一张映射表（**那就出现了第二个真相，新增 handler 时会静默漏掉**），
> 不如**只暴露代码里真实存在的那个属性**。这个区分留给 `display_name` 与 `describe()` 用人话表达。

🔴 **"第二个真相，新增 handler 时会静默漏掉"** ✓ —— 这句话精确说出了一个**具体的失败模式** ✓：

```
开发者加了一个新的 mandatory handler
        ↓
忘记把它加进 scheduling 里的那张 layer 映射表
        ↓
接口返回 layer = null（或抛异常）
        ↓
前端无法分类显示 —— 但没人会注意到 ✗（因为新规则本来就不常用）
```

**对照 `RuleTypeCatalog` 的"没有任何 if/else 分支"** ✓ —— 两处论证是**同一个原则** ✓：
**能投影的绝不另立** ✓

⚠ **而"留给 `display_name` 用人话表达"是一个很好的替代** ✓：
"教师不撞课" vs "教师周课时上限" ✓ —— 用户**看名字就知道是哪一类** ✓
**不需要一个 `layer` 枚举** ✓ —— 因为**用户的认知是"这句话什么意思"而不是"它属于哪一层"** ✓

### 为什么不加 `supports_hard`

> 同理没有 `supports_hard`：`RuleHandler.apply` 本身就接受 `hard` 参数，
> 任何可配置规则都能当硬约束用。"某条规则只能软"是**设计建议，不是代码约束** ——
> **暴露一个代码里不存在的限制会误导前端**。

⚠ **"设计建议 vs 代码约束"** ✓ —— 这个区分很实用 ✓：
如果前端按 `supports_hard=false` 把"硬度"下拉禁掉 ✗ 用户就**永远试不了**那条规则当硬约束 ✓
**而它其实能跑** ✓ —— **一个不存在的限制比没有限制更糟** ✗

### `editable` 是 `!mandatory` 的冗余表达

```java
handler.mandatory(),
!handler.mandatory(),      // editable
```

⚠ **两个字段互为反义** ✗ —— 有点冗余 ✓ 但**都留着**：
因为前端读 `editable` 更自然（"能不能编辑"✓）✓ 而 `mandatory` 是代码里的原始属性 ✓
**注释也点明了**（`/** {@code !mandatory} —— 前端据此决定… */` ✓）✓

> 💡 这类"语义别名"在 API 设计里是可接受的 ✓ —— 只要**注释说明它是派生的** ✓
> （否则前端会以为两者可以不一致 ✗）

## 5c-1.3 `RuleParamResponse` —— 纯投影（35 行）

```java
public record RuleParamResponse(String name, String type, boolean required,
                                Long min, Long max, List<String> enumValues, String label) {
    public static RuleParamResponse of(RuleParamSpec spec) { ... }   // 逐字段透传，无加工
}
```

**类注释**：
> ⚠ 它是**投影**而不是新定义：字段与 solver-core 的 `RuleParamSpec` **一一对应，一行都不多做解释**。
> 原因见 `RuleTypeCatalog` 的类注释 —— 这份 schema 是"前端表单 + 后端校验 + 助手工具定义"三处的**同一个来源**，
> **一旦在这里"顺手加工"，三处就会各说各话**。

🔴 **"一旦顺手加工，三处就会各说各话"** ✓ —— 这是**投影类**的共同纪律 ✓
（"顺手加工"的典型：把 `min`/`max` 合并成一句中文提示 ✗ 把 `enumValues` 翻译成中文 ✗ ✓
—— 看着更友好 ✓ 但**后端校验和助手工具定义拿不到那些中文** ✗ → 三处语义分叉 ✓）

**`type` 用字符串而不是枚举** ✓：
> 这样前端拿到就能直接 `switch`，**也不用跟着后端枚举改名**。

⚠ **"不用跟着后端枚举改名"** ✓ —— 一个很实际的考虑 ✓：
Java 枚举改名 ✗ 序列化出去的名字就变了 ✗ 前端 `case` 就失效 ✗
**用字符串把"接口契约"和"Java 类型名"解耦** ✓ —— 代价是丢了编译期检查 ✓ 取舍合理 ✓

⚠ 而 `spec.type().name()` 里 `type()` 是个枚举 ✓ —— **所以枚举在 solver-core 里存在** ✓
只是**在 HTTP 边界上被摊平成字符串** ✓ 这正是"投影"该做的事 ✓

## 5c-1.4 `ConstraintRuleEntity` —— 规则表（169 行）

```java
@TableName(value = "constraint_rules", autoResultMap = true)
public class ConstraintRuleEntity {
    @TableId(type = IdType.AUTO) private Long id;
    private Long organizationId;
    private String ruleType;

    @TableField(typeHandler = JacksonTypeHandler.class)
    private Map<String, Object> params;      // MySQL json 列

    private String hardness;                 // hard | soft
    private Integer weight;                  // 仅 soft 有效
    private String scope;                    // org | grade | class | teacher | subject
    private Long scopeId;
    private Boolean enabled;
    private String description;              // 面向用户的人话
    private String source;                   // manual | assistant
    private Integer version;                 // 乐观锁
    private LocalDateTime createdAt, updatedAt;
}
```

**这是 P2 的核心表** ✓ —— 类注释用一句话定义了它在这个架构里的位置 ✓：

> 「规则 = 数据 + 实现」里的那一半**数据**：用户能编辑的就是这张表的 `rule_type` 与 `params`，
> 而 `rule_type` 指向的实现由开发者在 solver-core 里写一次。

### 六处字符串枚举（都没有用 Java 枚举）

| 字段 | 取值 | 注释给了吗 |
|---|---|---|
| `hardness` | `hard` / `soft` | ✓「小写，与 §5.3 的列注释一致」 |
| `scope` | `org` / `grade` / `class` / `teacher` / `subject` | ✓ |
| `source` | `manual` / `assistant` | ✓（**为 P4 的助手预留** ✓） |
| `enabled` | boolean ✓ 真类型 | — |
| **`weight`** | 「仅 soft 有效」 | ✓ |
| **`version`** | 「**乐观锁**列 —— 对应接口里的 `expected_revision`」 | ✓ |

⚠ **六个"取值有限"的字段全用 `String`** ✗ —— 与 4c-2 的 `action`、5d 的 `severity` 是同一族 ✓
**统一的手法**：`String` + **注释里列出取值** ✓
**代价**：拼错不报错 ✗（写 `"Hard"` 会静默变成一个"未知硬度" ✓ 而 `toConstraintRules` 里 `"hard".equalsIgnoreCase(...)` 会把它当 **soft** ✗✓）

🔴 **具体后果**：`hardness` 写成 `"Hard"` ✓ 会被 `equalsIgnoreCase` 正确识别 ✓（有忽略大小写 ✓）
但写成 `"HARD "`（带空格 ✗）→ **被当成 soft** ✗ → **一条本该硬的约束变成软约束** ✗
→ **排课结果变了** ✓ 而且**不报错** ✓ —— 这是"字符串枚举"最典型的代价 ✓

⚠ `source` 的取值 `manual` / `assistant` ✓ —— 而**现在代码里只写 `"manual"`** ✗（见 `ensureInitialized` ✓）
`assistant` 是**给 P4 预留的** ✓ —— 一个**面向未来的字段值** ✓ 好 ✓（文档化了意图 ✓）

**所以时间必须由应用写** ✓ —— 这是一条**贯穿全项目**的约定 ✓

## 5c-1.5 `ConstraintRuleVersionEntity` —— 🔴 为什么存快照而不只存 hash（104 行）

```java
@TableName(value = "constraint_rule_versions", autoResultMap = true)
public class ConstraintRuleVersionEntity {
    @TableId(type = IdType.AUTO) private Long id;
    private Long organizationId;
    private Integer versionNo;
    private String ruleSetHash;

    /** 冻结的规则快照（只含 enabled 的）。 */
    @TableField(typeHandler = JacksonTypeHandler.class)
    private List<Map<String, Object>> rules;

    private Integer ruleCount;
    private String note;
    private LocalDateTime createdAt;
}
```

🔴 **类注释里那段话，是整个 P2 里最有远见的一个决定** ✓：

> ⚠ `rules` 存的是**当时全部生效规则的冻结快照**，不是只存 hash ——
> 因为审计链要求「这版课表用的哪套规则」**任何时候都能点开**，
> **只存 hash 的话规则被删改后历史就还原不出来了**。

**为什么"只存 hash"不够** ✗ —— 这是一个很容易想错的地方 ✓：

| 只存 hash ✗ | 存快照 ✓ |
|---|---|
| 能回答"这两次是不是同一套规则" ✓ | ✓ 同样能 ✓ |
| **不能**回答"那套规则**具体是什么**" ✗ | ✓ 能 ✓ |
| 规则被改/删之后 ✗ → hash 还在 ✓ 但**内容无从得知** ✗ | ✓ 内容还在 ✓ |

⚠ **而"审计链"这个词是关键** ✗ —— 它不是"要不要留个记录"的问题 ✓
而是"**能不能解释清楚这版课表是怎么来的**" ✓
**课表被人质疑时（"为什么周三下午排了体育"✗）你必须能调出当时那套规则** ✓
**只有 hash 是解释不了的** ✗ —— 一个 64 位的十六进制串说明不了任何事 ✓

### 🔴 而它在 P3 意外地救了一次场

`RuleSetService.rulesByHash` 的注释（§5c1.7 ✓）道出了后续 ✓：

```java

 * 使并发的插入阻塞到本事务结束。

 * {@code --transaction-isolation=REPEATABLE-READ} 是**显式写出来**的
```

| **② 机制** | `FOR UPDATE` 在 RR 隔离级别下，对**不存在的行**会加 **gap lock** ✓ |

## 5c-1.7 `RuleSetService` —— 规则集的中枢（385 行）

类注释直接给了三件事 ✓：**载入** ✓ **哈希** ✓ **版本** ✓

### 🔴 `rule_set_hash` 为什么必须确定性

> 同一个规则集**任何时候算出来必须是同一个值**，否则：
> - 「这版课表用的哪套规则」**对不上**（当前 hash 找不到历史版本）
> - 规则改回去之后会被当成"新规则集"，**历史版本无限膨胀**

**规范化规则（原文）**：
```
每行 → rule_type|hardness|weight|scope|scope_id|<params 的键排序 JSON>
全部行**按这个字符串排序**后换行拼接 → sha256 → 小写 hex
```

**⚠ 刻意不含三个字段** ✓ —— 每一个都有理由 ✓：

| 排除 | 理由 |
|---|---|
| `id` | **删掉再建一条一样的规则，应当被认作"没变"** ✓ |
| `description` | **纯展示** ✓ 改个说明不该算"规则变了" ✓ |
| `enabled` | **哈希只覆盖 enabled 的行** ✓ 所以启停会**自然地**改变哈希 ✓ |

🔴 **三个排除标准的共同点：它们都不改变"排课结果"** ✓
`id` 变了但规则一样 → 排课一样 ✓ / `description` 变了 → 排课一样 ✓
`enabled` 变了 → **排课会变** ✓ **所以它必须影响哈希** ✓ —— 而它影响的方式是**那一行整个不参与** ✓

> 💡 **判断"某字段该不该进哈希"的标准**：**它变了，排课结果会变吗** ✓
> 会 → 进 ✓（哪怕只是个 boolean ✓）
> 不会 → 不进 ✓（否则"改个错别字"就会产生一个新版本 ✗ 历史版本无限膨胀 ✓ 正是注释说的 ✓）

**排序的两层** ✓：

```java
canonicals.sort(String::compareTo);              // 行间排序 → 与数据库返回顺序无关
... + canonicalJson(row.getParams());            // 行内：params 的键也排序
```

⚠ **两层都不能少** ✗：
- **行间**：数据库不保证 `SELECT` 的顺序（除非 `ORDER BY` ✓ 而这里没依赖 ✓）
- **行内**：`Map` 的迭代顺序（`HashMap` ✗）会让同一个 params 序列化出不同字符串 ✓

**行内排序靠一个专用 ObjectMapper** ✓：

```java
private static final ObjectMapper CANONICAL = JsonMapper.builder()
        .configure(SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS, true)
        .build();
```

⚠ **注释说**：「规范化哈希专用的 ObjectMapper：**Map 键排序**，输出才可能与输入顺序无关」✓
**"专用"这个词很重要** ✗ —— 它**不是全局的那个** ✓（全局的是 SNAKE_CASE ✓）
→ **改全局 Jackson 配置不会影响它** ✓ **改它也不会影响别的** ✓ 隔离得很好 ✓

⚠ 而 `canonicalJson` 里有个不必要的中间步骤 ✗：
```java
JsonNode node = CANONICAL.valueToTree(params);      // Map → JsonNode
return CANONICAL.writeValueAsString(node);          // JsonNode → String
```
**可以直接 `writeValueAsString(params)`** ✗ —— 两步等价 ✓ 但多一次转换 ✓
（大概是为了"让序列化走 JsonNode 这条确定的路径" ✓ 无害 ✓ 记在案 ✓）

**`sha256Hex`** ✓：`HexFormat.of().formatHex(...)` ✓ —— Java 17+ ✓ 比手写 `String.format("%02x", b)` 简洁 ✓

### 🔴 `currentVersion` —— **按哈希找，不按最大 version_no**

```java
/**
 * <p>⚠ **按哈希找，不按 version_no 找最大的那个**。因为版本是哈希去重的：
 * 把规则改回去（例如把一条规则停用、或把参数改回原值）会让规则集**回到一个更早的版本**，
 * 此时"当前版本"就是那个**编号更小**的版本。
 *
 * <p>实测过这个坑：停用一条规则后，规则集与 v1 完全相同，
 * 但按 {@code ORDER BY version_no DESC} 会报成 v3 —— 等于告诉用户
 * "你现在用的是 v3"，而 v3 的规则内容根本不是当前生效的那一套。
 */
public ConstraintRuleVersionEntity currentVersion(long organizationId) {
    String hash = hashOf(organizationId);
    return findByHash(organizationId, hash);
}
```

🔴 **这是一个"想当然就会写错"的地方** ✓ —— 而且注释里给了**实测的具体场景** ✓：

```
v1: 规则集 A（两条默认规则）
v2: 加了「语文一天最多 2 节」          → 规则集 B
v3: 把那条停用了                      → 规则集又回到 A（= v1 的哈希）

按 version_no DESC 找最大 ✗ → 返回 v3  ✗ 但 v3 的内容是 B + 停用 ✓
按哈希找 ✓                 → 返回 v1  ✓ 内容就是 A ✓ 正确 ✓
```

⚠ **而错误的做法会"看起来合理"** ✗：v3 是最新创建的 ✓ 直觉上"当前"就是它 ✓
**但版本表是"规则集的集合"** ✓（见上 ✓）**不是"操作日志"** ✓
→ **最新的操作 ≠ 当前的状态** ✗ —— 这正是哈希去重带来的语义变化 ✓

> 💡 **两次出现同一个道理** ✓：
> **"最新的一条记录"和"当前的状态"是两回事** ✓
> 当历史记录会**去重 / 回退**时，就必须**按内容（哈希）查当前** ✓ 而不是按时间戳 ✓
>
> 对照 4c-2 册的 `nextVersionNo` ✗ —— 那里是"递增号" ✓ 语义不同 ✓ 没这个问题 ✓

⚠ 而 `findByHash` 用了 `.last("LIMIT 1")` ✓ —— 因为理论上哈希**应该**唯一 ✓
但如果并发插入了两条同哈希的版本 ✗（见 `insertVersion` 的竞态 ✓）→ 取第一条 ✓ **不报错** ✓
**这是一个"用 LIMIT 1 容忍数据异常"的选择** ✓ —— 与 `currentVersion` 的语义一致 ✓（反正内容一样 ✓）

### 🔴 `rulesByHash` —— P3 的冻结路径

```java
@SuppressWarnings("unchecked")
public List<ConstraintRule> rulesByHash(long organizationId, String hash) {
    ConstraintRuleVersionEntity version = findByHash(organizationId, hash);
    if (version == null || version.getRules() == null) {
        throw BusinessException.conflict("规则集版本已不存在（指纹 " + hash + "）—— 该任务无法用当时的规则复现");
    }
    List<ConstraintRule> out = new ArrayList<>(version.getRules().size());
    for (Map<String, Object> item : version.getRules()) {
        Object params = item.get("params");
        out.add(new ConstraintRule(
                String.valueOf(item.get("rule_type")),
                RuleParams.of(params instanceof Map<?, ?> m ? (Map<String, Object>) m : Map.of()),
                "hard".equalsIgnoreCase(String.valueOf(item.get("hardness")))
                        ? ConstraintRule.Hardness.HARD : ConstraintRule.Hardness.SOFT,
                weight instanceof Number n ? n.intValue() : 1,
                true,                       // 👈 enabled 硬编码 true
                item.get("description") == null ? null : String.valueOf(item.get("description"))));
    }
    return out;
}
```

🔴 **这就是"P2 存快照"那个决定的兑现点** ✓（见 §5c1.5 ✓）
**类注释**：
> <p>为什么不能直接用"当前规则集"：任务可能**排队几分钟**才被 worker 领走，
> 期间管理员完全可能改了规则。那样排出来的课表用的就不是任务创建时那一套，
> 而 `rule_set_hash` 却记的是旧指纹 —— **审计链会自相矛盾**。

⚠ **四处防御性转换** ✓ 每一处都在防"JSON 里的类型和预期不符" ✓：

| 代码 | 防什么 |
|---|---|
| `params instanceof Map<?, ?> m ? ... : Map.of()` | JSON 里 `params` 不是对象 ✓ |
| `"hard".equalsIgnoreCase(String.valueOf(...))` | `hardness` 是 null（`String.valueOf` 得 `"null"` ✓ 不匹配 ✓ → SOFT ✓ 安全的默认 ✓） |
| `weight instanceof Number n ? n.intValue() : 1` | `weight` 是 null 或字符串 ✓ |
| `item.get("description") == null ? null : String.valueOf(...)` | — |

🔴 **而 `enabled` 那一行是硬编码的 `true`** ✗ —— 见 §5c1.5 的脆弱点分析 ✓
**回读时无法校验"这条快照里的规则当时是不是启用的"** ✗
（因为快照里根本没存那个字段 ✓ 而写快照时只传了 enabled 的行 ✓）
**记在案** ✓

⚠ **异常选的是 `conflict`（409）而不是 `notFound`（404）** ✗ —— 合理的 ✓：
调用方（worker 领单 ✓）不是"找不到资源" ✓ 而是"**这个任务的前置条件没了**" ✓
409 让 worker 把它当成"不可重试的失败" ✓（hmm ✓ 取决于 `JobRunner` 怎么分类 ✓ 见 2a 册的发现 #6 ✓）
**文案也很准确**：「该任务无法用当时的规则复现」✓

### `ensureInitialized` —— 懒初始化 + gap lock

```java
@Transactional
public void ensureInitialized(long organizationId) {
    // 先加间隙锁：并发的首次访问会在这里排队，而不是各插一份默认规则
    ruleMapper.lockOrganizationRules(organizationId);

    if (currentVersion(organizationId) != null) {
        return;   // 已经初始化过（有版本行 = 规则集存在过）
    }

    List<ConstraintRule> defaults = RuleSets.legacyEquivalent();
    for (ConstraintRule rule : defaults) { ... ruleMapper.insert(entity); ... }
    log.info("首次初始化规则集: org={} 写入 {} 条默认规则", organizationId, defaults.size());
    insertVersion(organizationId, enabledRows(organizationId),
            canonicalHash(enabledRows(organizationId)), DEFAULT_NOTE);
}
```

**四步** ✓：**加锁** → **判存** → **插默认规则** → **记版本** ✓

🔴 **类注释里解释了"为什么默认规则是那两条"** ✓：
> 两条默认规则来自 `RuleSets.legacyEquivalent()` —— 也就是 P1 迁移期用来**复现 Python 行为**的那套。
> **这样 P2 上线不会改变任何一所学校的排课结果**：新组织第一次排课用的还是那两条软约束，
> 只是它们现在**看得见、改得动**了。

**这正是 P2 决策门"用 DB 规则集排课 == 用 legacy 等价规则集"的落地机制** ✓✓
—— 那句决策门不是一个"测试通过"✓ 而是**代码里的一条初始化逻辑** ✓

**注释还解释了它顺带解决的问题** ✓：
> <p>它同时解决了"以后新建的组织怎么办"—— 不需要在 academic 建组织时跨服务写规则
> （**那就违反铁律 2 了**）。

🔴 **"懒初始化"在这里同时是三个问题的解** ✓：
1. **并发**（gap lock ✓）
2. **P2 行为不变**（默认=legacy 等价 ✓）
3. **新组织不改 academic**（铁律 2 ✓）

**判存用的是 `currentVersion(organizationId) != null`** ✓ —— 即"**有没有版本行**" ✓
⚠ 注释说「有版本行 = 规则集存在过」✓ —— 用**版本表**作为"初始化过了"的标志 ✓
**而不是用"规则表有没有行"** ✗ —— 因为**用户可以把所有规则都删光** ✓
那样规则表为空 ✓ 但**已经初始化过了** ✓ 不该再塞回默认规则 ✗✓ **这个选择是对的** ✓

⚠ **`canonicalHash(enabledRows(...))` 被调了两次** ✗（第 356-357 行 ✓）：
```java
insertVersion(organizationId, enabledRows(organizationId),
        canonicalHash(enabledRows(organizationId)), DEFAULT_NOTE);
```
**`enabledRows(organizationId)` 执行了两次查询** ✗ —— 结果必然相同 ✓（同一事务 ✓）
**无害但是多余的两次往返** ✓ 记在案 ✓

### 🔴 一个可能的启动顺序缺口

```java
public List<ConstraintRule> loadForSolve(long organizationId) {
    ensureInitialized(organizationId);        // 👈 会初始化
    return toConstraintRules(enabledRows(organizationId));
}

public String hashOf(long organizationId) {
    return canonicalHash(enabledRows(organizationId));   // 👈 不会初始化
}
```

⚠ **`hashOf` 不初始化** ✗ 而 `loadForSolve` 会 ✓
**类注释解释了 `loadForSolve` 为什么带初始化** ✓：
> 调它会顺带完成首次初始化 —— 因为求解是"**必须有一组规则**"的场景，
> 让它自己保证这个前提，比要求每个调用方先记得调一次初始化可靠。

🔴 **但 `hashOf` 的场景也可能"必须有一组规则"** ✗ —— 它被用来**给任务/快照记指纹** ✓
如果一个**全新组织**的第一次排课 ✓：
```
generate → 记录 rule_set_hash = hashOf(orgId)
                          ↓
                如果这时还没人调过 loadForSolve ✗
                          ↓
                规则表为空 → canonicalHash([]) = sha256("") ✓ 一个"合法"的哈希 ✗
                          ↓
                任务带着这个"空规则集"的哈希入队
                          ↓
                worker 领单 → rulesByHash(orgId, 空哈希)
                          ↓
                版本表里没有这个哈希 ✗ → 抛 409 ✗
```
⚠ **后果链的末端取决于 `generate` 的调用顺序** ✗ —— 它会不会先 `loadForSolve` ✗
**我没有验证这条链** ✓ **标记为"从代码路径推导，未实测"** ✓
（agent 的报告里也提到了这条 ✓ 我把它记为待验证 ✓）

**最小的修法**：`hashOf` 里也调 `ensureInitialized` ✓（一行 ✓）
**或者**让 `generate` 显式先 `loadForSolve` ✓
**记在案** ✓ —— 这是本册**最值得验证的一条** ✓

### `validateParams` / `rejectMandatory` —— 两条校验

```java
public void validateParams(String ruleType, Map<String, Object> params) {
    if (!catalog.isKnown(ruleType)) { throw BusinessException.badRequest("未知的规则类型: " + ruleType); }
    List<String> errors = RuleParams.of(params).validate(catalog.handlerOf(ruleType).params());
    if (!errors.isEmpty()) { throw BusinessException.badRequest(String.join("；", errors)); }
}
```

🔴 **注释说明了为什么只有一份校验** ✓：
> **不在这里实现第二套校验逻辑**：`RuleParamSpec` 是前端表单、后端校验、助手工具定义
> **三处共用的同一份 schema**，校验规则也必须只有一份。

**这就是 §5c1.1 那张图的兑现** ✓ —— `catalog.handlerOf(ruleType).params()` 取的是**solver-core 的 spec** ✓
校验用的是 **solver-core 的 `RuleParams.validate`** ✓
→ **新增一个 handler ✗ 校验自动生效** ✓ **不用改这里** ✓

⚠ **`String.join("；", errors)`** ✓ —— 用**中文分号**连接多条错误 ✓
**为什么不用 `,`** ✗：因为错误消息本身可能含逗号 ✓ 中文分号更不容易歧义 ✓
⚠ 但**前端拿到的是一个字符串** ✗ 而不是数组 ✓ —— 无法逐条高亮 ✓
（对照 422 是数组 ✓ 而这里是 400 + 字符串 ✓ —— **两种校验错误的形状不同** ✓
因为 422 是"请求体不符合 DTO 校验"✓ 而这里是"值不符合业务 schema"✓ 语义不同 ✓）✓

```java
public void rejectMandatory(String ruleType) {
    if (catalog.isMandatory(ruleType)) {
        throw BusinessException.badRequest("该规则是系统不变量，始终生效且不可配置: " + ruleType);
    }
}
```

🔴 **"写成数据行只会产生'看起来能关掉'的假象"** ✓ —— 与 `configurable()` 的注释同一个理由 ✓
**两处防线** ✓：`configurable()` 让它**不出现在下拉里** ✓ `rejectMandatory` 挡住**直接构造请求** ✓
**客户端可以绕过下拉** ✗ 所以服务端这道不能省 ✓

## 本册小结

**把这一册串成一句话**：

> P2 把「有哪些约束」拆成 **数据（`constraint_rules` 表）+ 实现（solver-core 的 handler）** ✓
> 而**"有哪些类型"这件事只能有一个真相** ✓ —— 所以 `RuleTypeCatalog` **投影** `BuiltinRules.registry()` ✓
> 一份 schema 同时喂**前端表单 / 后端校验 / 助手工具定义** ✓
> 规则集则要能被**规范化哈希**（可复现 ✓）并**冻结成快照**（可回放 ✓）✓

**最该带走的三件事**：

1. 🔴 **"一份 schema 三处消费"必须真的是同一份**（§5c1.1 / §5c1.3）✓
   `RuleParamResponse` 是**纯投影，一行不加工** ✓ —— 因为"一旦顺手加工，三处就会各说各话" ✓
2. 🔴 **两个字段"故意不加"的论证**（§5c1.2）✓
   不加 `layer`：「**那就出现了第二个真相，新增 handler 时会静默漏掉**」✓
   不加 `supports_hard`：「**暴露一个代码里不存在的限制会误导前端**」✓
3. 🔴 **冻结快照而不只是 hash**（§5c1.5）✓
   P2 的理由是审计链 ✓；**P3 顺带解决了"排队期间规则被改"** ✓
   —— **在"记录一次决策"时把输入一起冻住** ✓ 因为你无法预知将来要不要重放 ✓
