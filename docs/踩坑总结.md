# 踩坑总结

> 供以后参照。收录 **本项目实际踩到**的坑 —— 每条都是「构建通过、但运行时出错或静默失效」那一类，
> 也就是**只看编译/文档发现不了**的问题。
>
> 写法统一为：**现象 → 根因 → 修法 → 教训**。
> 带 🔴 的是「静默失效」——不报错但功能没生效，最危险。

## A. 环境与工具链

### A1. PowerShell 读 UTF-8 文件按 GBK 解码

**现象**：用 `Get-Content -Raw` 读 UTF-8 的 pom.xml / .py 文件，中文字符串变成乱码，
导致基于内容的检查**误报**（当时误判了 6 个 pom「XML 格式错误」，实际文件完全正常）。

**根因**：Windows PowerShell 5.1 的 `Get-Content` 默认按系统 ANSI 代码页（中文机器是 936/GBK）解码，
不认 UTF-8（无 BOM）。

**修法**：
```powershell
$text = [IO.File]::ReadAllText($path, [Text.Encoding]::UTF8)
# 写回时不要 BOM：
[IO.File]::WriteAllText($path, $text, (New-Object Text.UTF8Encoding($false)))
```

**教训**：**只要涉及非 ASCII 内容，读写文件一律走 `[IO.File]::*` + 显式编码。**
`Get-Content`/`Set-Content` 只适合纯 ASCII 或纯展示。

### A2. `.cmd` 脚本：编码必须 GBK、换行必须 CRLF

**现象**：写了个 `.cmd` 启动脚本，运行时满屏
`'E' is not recognized`、`'%I' is not recognized`、`'_ready' is not recognized`。

**根因**：两个原因叠加
1. 文件写成 **UTF-8**，而 cmd.exe 按 **GBK** 读 → 中文注释被解析成命令
2. 文件是 **LF** 换行 → `goto`/标签/`for` 的解析出错

**修法**：文件用 **GBK（代码页 936）+ CRLF** 保存：
```powershell
$content = $content -replace "`r`n","`n" -replace "`n","`r`n"   # 先归一，再统一成 CRLF
[IO.File]::WriteAllText($path, $content, [Text.Encoding]::GetEncoding(936))
```
自检：
```powershell
$b = [IO.File]::ReadAllBytes($path)
"CRLF: $(([regex]::Matches([Text.Encoding]::ASCII.GetString($b), "`r`n")).Count)"
"裸 LF（应为 0）: $(([regex]::Matches([Text.Encoding]::ASCII.GetString($b), "(?<!`r)`n")).Count)"
```

**教训**：**Windows 批处理脚本与「UTF-8 通行」是两回事。** 项目里原有的 `start-dev.cmd` 之所以能跑，
是因为它**通篇纯英文**。

### A3. `timeout` 在 stdin 被重定向时立刻失败

**现象**：`.cmd` 里用 `timeout /t 2 /nobreak >nul` 做延时，输出
`ERROR: Input redirection is not supported, exiting the process immediately.`

**根因**：`timeout.exe` 在 stdin 不是交互终端时拒绝工作（CI、被管道捕获、后台运行时都是这种情形）。

**修法**：用 `ping` 做延时（GNU 时代的经典技巧，与 stdin 无关）：
```bat
ping -n 3 127.0.0.1 >nul      rem 约 2 秒
```

**教训**：脚本里**不要用依赖交互终端的命令**（`timeout`、`pause`、`choice`）做与终端无关的事。

### A4. `[IO.File]` 的相对路径不认 PowerShell 的 `Set-Location`

**现象**：变异实验脚本里 `Set-Location` 切到了 `backend-java`，紧接着 `[IO.File]::ReadAllText("some/relative.java")`
报 `Could not find a part of the path ...\orbit\some\relative.java`。

**根因**：`Set-Location` 只改 PowerShell 的「当前位置」，
而 `[IO.File]` 用的是**进程的工作目录**（两者不是一个东西）。

**修法**：给 .NET API 传绝对路径；`Set-Location` 只影响 cmdlet（`Get-ChildItem` 等）。

**教训**：**同一个脚本里混用 cmdlet 和 .NET API 时，路径语义要分开对待。**

### A5. `Start-Process -UseNewEnvironment` 会把 pwsh 进程搞崩

**现象**：想用它验证「新开终端能不能看到新写的环境变量」，结果**整个 pwsh 进程无输出退出、退出码 -1**，
连之前 `Write-Output` 的缓冲都丢了 —— 导致我误判「环境变量没写进去」，白折腾一轮。
（后来确认变量其实写成功了。）

**修法**：不要用它。要验证环境变量是否生效，**直接读注册表**：
```powershell
[Environment]::GetEnvironmentVariable('JAVA_HOME','User')
```
或者拼出「机器 PATH + 用户 PATH」模拟全新终端。

**教训**：**验证手段本身也可能是坑。** 当验证脚本莫名崩溃时，
先怀疑验证手段，而不是被验证的对象。

### A6. Java 直连 Maven Central 下载大 jar 会挂死

**现象**：Maven 下载 OR-Tools 的 25 MB 平台 jar 时卡在 **0 字节**，等了几分钟毫无进展，
连 `HttpRequest.timeout(30s)` 都不触发。同一台机器：

| 方式 | 结果 |
|---|---|
| `curl` 直连 repo.maven.apache.org | 1.85 MB/s ✅ |
| `Invoke-WebRequest`（走系统代理） | 1.6 MB/s ✅ |
| **Java 直连**（Maven 默认，不走系统代理） | **0 MB/s，挂死** ❌ |
| Java 走本机代理 127.0.0.1:7890 | 1.95 MB/s ✅ |
| **Java 直连 maven.aliyun.com** | **4.37 MB/s** ✅ |

小 POM 能过、大 jar 挂死 —— 典型的链路对大文件传输不友好。

**修法**：`~/.m2/settings.xml` 配国内镜像（又快又不依赖代理是否开着）：
```xml
<mirrors>
  <mirror>
    <id>aliyun-public</id>
    <url>https://maven.aliyun.com/repository/public</url>
    <mirrorOf>central</mirrorOf>
  </mirror>
</mirrors>
```

**教训**：
1. **「网络慢」和「特定程序网络慢」是两件事**，要用同一条 URL、不同客户端对比才能定位。
2. Java 默认**不读** Windows 系统代理设置（除非 `-Djava.net.useSystemProxies=true`）。

## B. Maven / Spring Boot

### B1. `java -jar` 报「没有主清单属性」

**现象**：`mvn package` 成功，但 `java -jar xxx.jar` 报 `no main manifest attribute`。
查 jar：只有 **11.7 KB**，**没有 `BOOT-INF/`、没有 `.jar.original`**。

**根因**：`spring-boot-maven-plugin` 的 `repackage` **执行**是由 `spring-boot-starter-parent`
提供的。本项目用「**BOM 导入**」（`spring-boot-dependencies`）而不是继承 starter-parent，
所以 `repackage` **不会**自动绑定。

**修法**：在父 pom 的 `pluginManagement` 里显式绑定：
```xml
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <version>${spring-boot.version}</version>
  <executions>
    <execution><id>repackage</id><goals><goal>repackage</goal></goals></execution>
  </executions>
</plugin>
```
放 `pluginManagement` 而不是各模块 `plugins` 有个额外好处：
**只有声明了该插件的模块才会被 repackage** —— 库模块（`orbit-solver-core`）
不声明它，因此不会被破坏成不可依赖的 fat jar。

**教训**：**「用 BOM」和「继承 starter-parent」不是等价的。** 前者只管理依赖版本，
后者还会带来一堆默认插件配置。

### B2 🔴 Flyway 完全不工作，而且不报错

**现象**：服务启动正常、日志干净，但**表没建、history 表也没有、一行 Flyway 日志都没有**。

**根因**：**Spring Boot 4 把自动配置拆成了独立模块。**
拆开 fat jar 检查发现：
- `spring-boot-autoconfigure-4.1.1.jar` 里**没有任何 flyway 类**
- 依赖里有 `flyway-core`，但**没有** `spring-boot-flyway`

也就是说 `flyway-core` 只是「库在 classpath 上」，**没有任何东西去驱动它**。

**修法**：改用 starter（它会带进 `spring-boot-flyway` 自动配置模块）+ 数据库方言模块：
```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-mysql</artifactId>
</dependency>
```

**教训**：
1. **Spring Boot 4 时代，「引了依赖」≠「功能生效」**，要引对应的 starter。
   同理还有 `spring-boot-jdbc` / `spring-boot-webmvc` / `spring-boot-security` / `spring-boot-data-redis`。
2. **每个「按文档引入了却没动静」的功能，都必须有一次「它真的工作了吗」的验证。**
   这次是靠 `/api/health` 里暴露 `flyway.version` 才抓到的 ——
   **如果 health 只返回 `ok: true`，这个坑会一直埋着。**

### B3. `mvn -pl <模块>` 报找不到内部构件

**现象**：`mvn -pl orbit-academic spring-boot:run` 报
`Could not find artifact com.orbit:orbit-common:jar:0.1.0-SNAPSHOT`。

**根因**：`-pl` 只把指定模块放进反应堆，它的依赖（`orbit-common`）既不在反应堆里、
也没装进本地仓库。

**修法**（两种，视场景）：
- 一次性构建多个相关模块：`mvn -pl orbit-academic,orbit-scheduling -am package`
  （`-am` = also make，把依赖模块一起构建）
- **常规前置：先 `mvn install` 一次**，之后 `mvn -pl <模块> <goal>` 就能用

**教训**：多模块工程里，**`mvn install` 是一次性的必要动作**（把内部构件装进 `~/.m2`），
不装的话每次都要靠 `-am`。这也是 IDE 能识别多模块工程的原理。

### B4. 两个 Maven 进程写同一个日志文件

**现象**：明明配置改对了，构建还是立刻以 exit 1 失败，而日志内容像是**旧配置**的输出。
stderr 里有 `The process cannot access the file because it is being used by another process.`

**根因**：我**忘记杀掉一个更早启动的后台构建**，它还在跑并占着同名日志文件；
新构建的 `> log 2>&1` 重定向失败，于是立刻退出 —— **它根本没跑 Maven**，
我读到的是旧进程写的日志。为此白绕了一整圈（误判「镜像没生效」）。

**修法**：后台任务用**唯一日志名**；启动新任务前先确认没有旧任务在跑同一份产物。

**教训**：**看到「配置改了但行为没变」时，先怀疑「我看到的输出是不是当前这次运行的」。**

### B5. 🔴 MyBatis-Plus 3.5.9 在 Spring Boot 4 下**完全不生效**，而且报错指向错误方向

**现象**：Mapper 接口注册上了，但创建 Bean 时失败：
```
Error creating bean with name 'userMapper':
    Property 'sqlSessionFactory' or 'sqlSessionTemplate' are required
```
这句话把人往「配置写错了 / 少加了个 Bean」的方向带，于是去查 yml、查 `@MapperScan`、
查 DataSource 配置 —— **全都对**。用 `--debug` 打出条件评估报告才看到真相：
```
MybatisPlusAutoConfiguration:
   Did not match:
      - @ConditionalOnSingleCandidate (types: javax.sql.DataSource; SearchStrategy: all)
        did not find any beans        ← 连 DataSource 都没有？
```
可 DataSource 明明是好的（P0 时 `/api/health` 就报过 `db.available: true`）。

**根因**：**Spring Boot 4 把自动配置按模块拆开了，类的包名也跟着变了**：

| | Spring Boot 3.x | Spring Boot 4.1 |
|---|---|---|
| 类 | `org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration` | `org.springframework.boot.**jdbc.autoconfigure**.DataSourceAutoConfiguration` |
| 所在 jar | `spring-boot-autoconfigure` | `spring-boot-**jdbc**` |

而 MyBatis-Plus 3.5.9 的 `MybatisPlusAutoConfiguration` 上写的是：
```java
@AutoConfigureAfter(org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration.class)
```
（用 `javap -v` 能看到常量池里就是这个旧名字）

**这个类在 Boot 4 里已经不存在了。** 而 `@AutoConfigureAfter` 指向一个不存在的类时
**不会报错**，只是这条排序提示**被静默忽略** —— 于是 `MybatisPlusAutoConfiguration`
可能在 `DataSourceAutoConfiguration` **之前**就被评估，`@ConditionalOnSingleCandidate(DataSource)`
当然找不到 Bean，整个 starter 直接不激活。

**修法**：换成为 Spring Boot 4 出的 starter，并升版本：
```xml
<mybatis-plus.version>3.5.17</mybatis-plus.version>
<artifactId>mybatis-plus-spring-boot4-starter</artifactId>
```
`mybatis-plus-spring-boot4-starter` 从 **3.5.13** 起才有（3.5.9 时代还不存在）。
校验方法：`mvn dependency:tree` 后确认拿到的是 `boot4` 那个 artifact。

**教训（两条，都很通用）**：

1. **Spring Boot 大版本升级会改变自动配置类的包名，进而静默破坏所有第三方 starter 的排序。**
   症状是「starter 完全不生效」，但报错信息通常指向别处。
   判断方法只有一个：**`--debug` 看条件评估报告**，看那个 `Did not match` 的真实原因。

2. **「某个类在 classpath 上」与「它按预期被装配」是两件事。**
   这与 B2（Flyway 静默失效）是同一类问题的两次现身：
   依赖坐标对、构建通过、启动成功，**功能却从未运行**。
   凡是「按文档引入了却没动静」，都要有一次「它真的工作了吗」的验证。

### B6. 🔴 `mvn package` 构建成功，但源码其实编译不过

**现象**：接口在运行时抛出一个从未见过的错误：
```
java.lang.Error: Unresolved compilation problems:
        RequestBody cannot be resolved to a type
        at com.orbit.common.error.ApiExceptionHandler.handleBodyValidation(ApiExceptionHandler.java:87)
```
而在它之前，`mvn -q package` **一直是 BUILD SUCCESS**。

**根因（两层）**：

1. **源码确实错了**：我编辑 `ApiExceptionHandler` 时加了
   `ex.getParameter().hasParameterAnnotation(RequestBody.class)`，
   **但忘了加 `import ...annotation.RequestBody;`**。代码根本编译不过。

2. **为什么构建还成功**：`target/classes` 里的 `.class` 文件**不是 Maven 写的**。
   VS Code 的 Java 语言服务器（redhat.java / JDT，用 **ECJ** 编译）在保存时就往
   `target/classes` 写过一份。Maven 的增量编译按**时间戳**判断
   「`.class` 比 `.java` 新 → 不需要重编」，于是跳过编译，
   直接把这堆 class 打进 jar。

   `Unresolved compilation problems` 是 **ECJ 特有的产物** ——
   javac 遇到编译错误会直接失败，**永远不会**生成一个"运行时抛错的 class"。
   所以只要看到这句话，就能确定这个 class 不是 javac 产的。

**修法**：
- 补上 import；
- **改用 `mvn clean package`**（清掉 IDE 写入的 class，强制全部重编）。

**教训（这条最容易反复踩）**：

> **「构建成功」不等于「源码能编译」。**
> 当 IDE 的语言服务器和 Maven 共用 `target/` 时，Maven 的增量判断会被 IDE 污染。

两个实用信号：
- 运行时报 **`java.lang.Error: Unresolved compilation problems`** → 一定是陈旧/错误 class，
  直接 `mvn clean`，不要去读业务逻辑；
- 一次「本该失败却成功」的构建之后，**怀疑产物而不只是怀疑配置**。

（这与 G1「旧进程占着文件、我读到旧日志」是同一主题：
**先确认「我看到的产物/输出是这一次的」。**）

### B7. 用 `@Select` 标注 UPDATE 语句 → 运行时 `BindingException`

**现象**：点"排课"后接口 500，日志里是：
```
org.apache.ibatis.binding.BindingException: Mapper method
  'ScheduleWorkerSlotMapper.tryAcquire attempted to return null
   from a method with a primitive return type (int)'
```

**根因**：抢容量槽位的那条是 **UPDATE** 语句（靠受影响行数判断"抢到了吗"），
但我把它标成了 `@Select`。MyBatis 会**按查询执行**它，拿不到 rowcount，
于是返回 null → 撞上 `int` 返回类型 → 异常。

**修法**：写操作（UPDATE/INSERT/DELETE）必须用
`@Update` / `@Insert` / `@Delete`。改完就好了。

**教训**：**注解名就是语句类型，不能靠"能编译"判断。**
`@Select` 标 UPDATE **构建期完全正常**，只有真的调用到那个方法才会炸 ——
所以「编译通过」对这类错误零信息量。凡是用 rowcount 做判断的写法
（本项目的并发控制全靠它），都要有一次"真的点到那个按钮"的验证。

## C. 运行时依赖

### C1. `Unsupported character encoding 'utf8mb4'`

**现象**：应用启动正常，但一取数据库连接就抛
`java.sql.SQLException: Unsupported character encoding 'utf8mb4'`。

**根因**：JDBC URL 的 `characterEncoding` 要的是 **Java 字符集名**，
而 `utf8mb4` 是 **MySQL 的字符集名**。两者不是一回事。

**修法**：
```
?useUnicode=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_0900_ai_ci
```
`characterEncoding` 负责 Java ↔ 驱动的映射，**utf8mb4（4 字节）靠 `connectionCollation` 指定**。

**教训**：**跨层传递的「编码」参数，每一层用的名字体系不同。**
（Python 的 PyMySQL 接受 `charset=utf8mb4`，所以照着 Python 的 URL 抄就错了。）

### C2. Spring Cloud 与 Spring Boot 版本不兼容，且只在运行时校验

**现象**：构建完全正常，服务一启动就被拒：
```
Spring Boot [4.1.1] is not compatible with this Spring Cloud release train
action = 'Change Spring Boot version to one of the following versions [4.0.x]'
```

**根因**：Spring Cloud 自带 compatibility verifier，在**启动时**检查版本配对。
Maven 能解析 BOM **不等于**兼容。

**修法**：两者必须成对，照官方 compatibility matrix 走。
本例：Spring Cloud 2025.1.1 → **2025.1.3** 后与 Boot 4.1.1 兼容。

**教训**：
1. **「BOM 能解析」是最弱的验证**，只能说明坐标存在。
2. **升级 Spring Boot 或 Spring Cloud 任何一个，都必须真的启动一次服务。**
   这也是为什么「P0 决策门 = 一条命令跑通」是有意义的 —— 它强制你做这件事。

### C3. Spring Security 默认返回 403，而前端只认 401

**现象**：未认证访问受保护接口，返回不是预期的 401。

**根因**：Spring Security 的默认 `AuthenticationEntryPoint` 对未认证请求走
`AccessDeniedHandler` 分支，返回 **403**。而前端 axios 拦截器**只对 401 触发登出** ——
收到 403 会当成普通业务错误弹窗，用户会卡在「明明没登录却退不出去」。

**修法**：
```java
.exceptionHandling(h -> h.authenticationEntryPoint((req, res, ex) -> {
    res.setStatus(401);
    res.setContentType("application/json;charset=UTF-8");
    res.getWriter().write("{\"detail\":\"请先登录\"}");   // 与 Python 版逐字一致
}))
```
另外：**`spring-boot-starter-security` 一上 classpath，所有请求默认都要认证**，
健康检查必须显式 `permitAll`，否则探针探不到、负载均衡把实例摘掉。

**教训**：**「契约」这种东西要在最早的时候钉住**，否则等前端接上来才发现，
改的就是两边。

## D. 数据库与迁移

### D1 🔴 共享库下 Flyway 静默跳过 V1，表根本不建

**现象**：scheduling 启动成功，但它的 6 张表**一张都没建**，只多出一张**空的** history 表。
**不报错。**

**根因**：Flyway 的基线判断依据是「**整个 schema 是否为空**」，
而在共享库里 schema 非空是因为**别的服务**建了表。
配置 `baseline-on-migrate: true` + `baseline-version: 1`（默认值）时，
scheduling 看到 schema 非空，就**误判「我的 V1 早就应用过了」**，直接跳过。

**修法（走了三版才对）**：

| 版本 | 配置 | 结果 |
|---|---|---|
| 1 | `baseline-on-migrate: true` + `baseline-version: 1` | 🔴 静默跳过 V1，表不建 |
| 2 | 关掉 `baseline-on-migrate` | ❌ Flyway 安全拒绝：`Found non-empty schema but no schema history table` |
| 3 | `baseline-on-migrate: true` + **`baseline-version: 0`** + 幂等脚本 | ✅ 四种场景全对 |

**为什么 `baseline-version: 0` 是对的**：基线只抑制「版本 ≤ 基线」的迁移。
基线设 0，**V1 照常执行**；而 V1 写成 `CREATE TABLE IF NOT EXISTS`（幂等），
在已有表上就是 no-op。四种场景：

| 场景 | 行为 |
|---|---|
| 现有库（表已在） | 基线 0 → V1 空跑 → 记为已应用 |
| 空库，先起的服务 | 无基线 → V1 建表 |
| 空库，后起的服务 | 基线 0 → V1 建自己的表 |
| **顺序颠倒** | V1 因外键指向不存在的表而**响亮失败** |

**代价（要记住）**：幂等的 V1 对「已存在的表」不做结构比对，
**因此它不具备漂移检测能力**。这是「采纳遗留 schema」的固有性质，漂移检测从 V2 开始生效。

**教训**：**Flyway 的「schema 是否为空」是库级概念，不支持「按服务划分」的语义。**
共享库 + 按属主拆表时，必须意识到这个错配。

### D2. 手工容器与 compose 容器不能混管

**现象**：`docker compose up -d` 报
`container name "/orbit-mysql" is already in use`。

**根因**：容器是 `docker run` 创建的，**没有 compose 的项目标签**，
compose 不认它是「自己的」容器，但名字又被占了。

**修法**：**删容器（不删卷）再让 compose 重建**：
```powershell
docker rm -f orbit-mysql orbit-redis   # 只删容器
docker compose up -d                    # 用同一个具名卷重建
```
前提是先确认数据在**具名卷**里（`docker inspect` 看 `Mounts[].Type == "volume"`），
而不是匿名卷或容器内路径。

**教训**：**迁移前先确认数据落在哪。** 数据在具名卷 → 删容器无损；
数据在匿名卷 → 删容器等于丢数据（要先 dump）。

### D3 🔴 compose 卷名不加 `name:` → 看起来数据全丢了

**现象**：compose 起来后进数据库，发现**空的**。

**根因**：compose 默认给卷加**项目名前缀**。
写 `orbit-mysql-data:` 会创建 `backend-java_orbit-mysql-data` —— **一个空的新卷**，
而原数据还在 `orbit-mysql-data` 里。

**修法**：
```yaml
volumes:
  orbit-mysql-data:
    name: orbit-mysql-data     # 显式指定，覆盖前缀
```
（会有 warning：`volume ... was not created by Docker Compose. Use external: true`。
这是**无害的** —— 用 `name:` 的好处是「首次创建」和「复用已有」两种场景都能工作，
而 `external: true` 要求卷必须预先存在。）

**教训**：**compose 会自动加前缀的东西有两类：容器名（除非 `container_name`）和卷名（除非 `name`）。**
两个都要显式管住。

### D4. 按属主拆表 → 跨边界外键锁死启动顺序

**现象/事实**：把 16 张表按服务属主拆开后发现，scheduling 的 6 张表有
**16 个外键**指向 academic 的 5 张表（`organizations` / `users` / `classes` / `subjects` / `teachers`）。

**后果**：
- **启动顺序被数据模型绑死**：academic 必须先起来完成迁移
- 将来「每个服务一个独立库」时，这 16 个外键是**第一个要处理的障碍**
- 无论顺序怎么排，两个服务在数据库层面是耦合的

**当前选择**：**让它响亮失败**，而不是 `SET FOREIGN_KEY_CHECKS=0` 静默建表 ——
后者会得到一个没有外键的库，**问题推迟到运行期才暴露，那时更难查**。

**附带发现**：MySQL 的 DDL 会**隐式提交**，所以「迁移失败」未必等于「什么都没建」。
本例因为第一张表就有跨边界外键，所以在第一句就失败了，业务表 0 张。
但如果失败发生在中间，会留下部分表 —— **好在幂等脚本让「修好后重跑」是安全的**。

**失败后恢复流程**（已验证）：
```
1. 把顺序改对（先起 academic）
2. 清掉失败记录：DELETE FROM flyway_schema_history_xxx WHERE success = 0
   （等价于 flyway repair；不做这步 Flyway 会拒绝继续，报 "Detected failed migration"）
3. 重跑
```

**教训**：**「共享库 + 按服务划分表所有权」是半吊子方案** ——
它把 DDL 的属主分开了，但引用关系还在。要么接受这个耦合（当前选择），
要么真正做「每服务独立库」，那就要处理这 16 个外键。

### D5. `mysqldump` 是字母序，不能直接当迁移脚本

**现象**：dump 出来的 SQL，`classes` 排在 `organizations` 前面 ——
直接执行会因外键指向还不存在的表而失败。

**修法**：按外键依赖**拓扑排序**后重新生成（用脚本解析 dump、抽取每张表的
`CREATE TABLE` 块、按预定顺序拼接），不要手工誊抄。

**教训**：**dump 是「快照」不是「迁移脚本」。** 当迁移脚本用之前要问：
顺序对吗？有数据残留吗（`AUTO_INCREMENT=5`）？可重复执行吗？

### D6. MySQL 到底能不能回滚 —— 「回滚」有三个层次，别混着说

**背景**：说过「Python 那套 `create_all` + 手写 ALTER 不能回滚」，
被问「MySQL 不是可以回滚吗」。**两边都没错，是三个不同的东西被同一个词盖住了。**

下面是 MySQL 8.4.11 / InnoDB 上的**实测结果**（不是查文档得来的结论）。

#### 层次 1 · 行级事务回滚：**支持**

```sql
START TRANSACTION;
INSERT INTO t VALUES (1, 'a');
SELECT COUNT(*) FROM t;   -- 1
ROLLBACK;
SELECT COUNT(*) FROM t;   -- 0   ✅ 回滚成功
```
**前提**：InnoDB 引擎 + **DML**（INSERT/UPDATE/DELETE）+ 显式事务
（或 `autocommit=0`）。MyISAM 表不支持事务，回滚无效。

#### 层次 2 · DDL 回滚：**不支持，而且比「不支持」更糟**

```sql
START TRANSACTION;
INSERT INTO t VALUES (2, 'b');
SELECT COUNT(*) FROM t;   -- 1   （还没提交）
CREATE TABLE t2 (id INT); -- ← DDL：隐式提交点
ROLLBACK;                 -- ← 想撤销一切
SELECT COUNT(*) FROM t;   -- 1   ❌ 本该回滚的 INSERT 被提交了！
SELECT id, note FROM t;   -- 2 | b   ← 它还在
-- t2 这张表也还在
```

**关键结论**：DDL **不但自己回滚不了，还会把事务里挂着的 DML 一起提交掉**。
这是最容易反直觉的一点 —— 你以为 `ROLLBACK` 能兜底，实际上它什么也没兜住。

**MySQL 8.0+ 的「原子 DDL」是另一回事**（容易望文生义）：

```sql
ALTER TABLE t ADD COLUMN c1 INT, ADD COLUMN c2 INT, ADD COLUMN c1 INT;
-- ERROR 1060 (42S21): Duplicate column name 'c1'
-- 失败后 t 的列仍然只有 id / note —— 中间的 c2 也没有残留
```

原子 DDL 保证的是「**单条** DDL 语句要么全成功要么全失败」（以及崩溃安全），
**不等于「DDL 可以被 ROLLBACK」**。

#### 层次 3 · 迁移回滚：**工具层面的概念，跟 MySQL 无关**

前面说的「不能回滚」指的是这一层：**没有版本记录，所以你不知道该退回到哪个状态**。
而且换成 Flyway **也一样回滚不了 DDL** —— Flyway 社区版**没有 undo**，
它的模型是 **forward-only**（只前进）。要「回滚」就得**再写一个反向迁移**，
比如 `V2__revert_xxx.sql` 把 V1 改回去。

#### 那 DDL 出问题到底怎么办（四种实际做法）

| 做法 | 说明 | 适用 |
|---|---|---|
| **补偿迁移** | 写 V2 把 V1 改回去 | 通用，也是 Flyway/git 的思路：只前进 |
| **备份/快照** | 迁移前 `mysqldump` 或卷快照 | 大改动、不可逆改动 |
| **幂等 + 可重跑** | 脚本写成 `IF NOT EXISTS` 之类，失败后修好重跑 | 采纳遗留 schema（本项目 V1 用的就是这个） |
| Flyway Teams 的 `undo` | 付费功能 | 一般不必要 |

#### 这件事在 P0 里的实际影响：迁移不是原子的

**实测**：一个文件里两条 DDL，第一条成功、第二条失败 ——

```sql
CREATE TABLE mig_step1 (id INT);                                        -- 成功
CREATE TABLE mig_step2 (id INT, FOREIGN KEY (id) REFERENCES no_such_table(id));  -- 失败
-- 结果：mig_step1 残留下来了
```

所以：

1. **一个迁移文件里多条 DDL，中间失败会留下半成品**（MySQL 逐句隐式提交，没有整体事务）
2. P0 那次「顺序颠倒」的失败之所以是**干净的**（业务表 0 张），
   纯属**凑巧** —— 第一张表就带着跨边界外键，第一句就失败了。
   如果它失败在中间，就会留下一半的表
3. **幂等脚本在这里救了场**：重跑时已建的表被跳过，所以「修好顺序 → 清掉失败记录 → 重跑」
   是安全的
4. **写 V2/V3 时的纪律**：一个迁移**只做一件事**；
   写下每一句 DDL 之前先想「如果这句失败，会留下什么」

**教训**：
> 「回滚」在数据库语境里至少有三种意思：**事务回滚 / DDL 回滚 / 迁移回滚**。
> 说「能回滚」之前先问是哪个 —— 而且**DDL 那层是 MySQL 的硬性质**，
> 换任何工具都改变不了，只能靠「补偿迁移 + 备份 + 幂等」去管理风险。

## E. 求解与建模

### E1. OR-Tools 的 Java API 不能凭直觉猜

**现象**：写第一版建模代码时凭直觉写了几个方法名，编译全错。

**实测到的真实 API**（与直觉不同的地方）：

| 直觉 | 实际 |
|---|---|
| `addNotEqual` | **`addDifferent`** |
| `newBoolVar` 返回 `IntVar` | 返回 **`BoolVar`**（同时实现 `IntVar` 和 `Literal`） |
| `addEquality(var, value)` | 参数是 **`LinearArgument`** |
| `LinearExpr.sum(vars)` | 参数是 **`LinearArgument[]`** |
| `solver.numBooleans()` | **`solver.response().getNumBooleans()`** |

**修法**：**用 `javap` 读已下载的 jar 里的真实签名**，而不是猜测或翻博客：
```powershell
javap -classpath ortools-java-9.15.6755.jar com.google.ortools.sat.CpModel | Select-String "addEquality|addDifferent"
```

**教训**：**对没把握的第三方 API，先探再写。** 探一次的成本远低于反复编译试错。

### E2. 模型指纹不能做跨语言等价判据

**现象**：Python 与 Java 两边 `model_stats()` 的统计行**一字不差**
（变量数、约束数、目标项数全同），但 `model_fingerprint` **不同**。

**根因**：定位到 proto 的 `objective.scaling_factor`：
Python 的 `minimize()` 会写 `1.0`，Java 留空 `0.0`。**语义相同，指纹不同。**

**修法**：跨语言等价性要**逐字段比对 `CpModelProto`**
（变量名/定义域/约束逐条序列化后对比），而不是比指纹。

**指纹的正确用途**：**同语言内的回归护栏** ——
它敏感于变量创建顺序与记账字段，这对「改了代码要立刻发现模型变了」是优点，
对跨语言比对则是噪音。

**教训**：**要清楚「一个校验手段测的到底是什么」。** 指纹测的是「是否一模一样地构建」，
不是「是不是等价的问题」。

### E3. JDK 23 上 `CpSolver.solve()` 段错误

**现象**：建模、指纹、`model.validate()` 全部正常，一调 `solve()` 就
`EXCEPTION_ACCESS_VIOLATION ... msvcp140.dll`。

**误判过程**：一开始怀疑「缺 MSVC 可再发行组件」—— 查了发现本机 redist 是新的（14.51），
**排除**。后来在另一台环境用 **JDK 21** 试，**完全正常**。

**修法**：项目统一 **JDK 21 LTS**。

**教训**：
1. **JNI 类库对 JDK 版本敏感**，「同版本号的新 JDK」也可能不兼容。
2. **遇到 JNI 段错误，换 JDK 试是最便宜的排查手段之一。**

## F. 验证方法论（这一节最值得反复看）

### F1 🔴 测试通过了，但通过的原因与被测对象无关（假绿）

**现象**：为验证规则「不排当天最后一节」，构造了「周五只有 3 节」的输入，
断言「把某科目排到周五第 3 节 → 不可行」。测试**通过**了。
但另一个测试却失败在**前提断言**上：
`前提：不带规则时这个强制是可满足的 ==> expected: not equal but was: <INFEASIBLE>`

**根因**：原夹具是 6 节 × 5 天 = **30 个座位**，而周课时合计 **28 节** ——
**只有 2 个富余**。我把周五压到 3 节后总座位变成 **27 < 28**，
**模型本来就无解**。也就是说，那个「不可行」跟规则**没有任何关系**。

**修法**：两条
1. 加宽其他天，保证容量充足（保留富余）
2. **在下结论前先断言前提**：不带规则时同一个构造必须**可行**

**教训**：
> **「不可行」是一个多因一果的结论。**
> 断言「某个约束导致了不可行」之前，必须先证明「去掉这个约束，它就可行了」。

这条对所有「负向测试」都成立（校验失败、权限拒绝、限流触发……）。

### F2. 「能解」证明不了「编码正确」

**现象**：空档约束（教师课表不留空档）写完，测试「能解、目标值合理」全绿。
但这个测试**证明不了编码是对的** —— 空洞定义写错也会「能解」，只是惩罚项算错。

**修法**：加**独立校验器**：从**排出来的课表反推**空档数，断言等于模型报告的目标值。
```java
int actualGaps = countTeacherGaps(outcome.entries());   // 独立实现，不复用建模代码
assertEquals(actualGaps, outcome.objectiveValue());
```

**并且用变异实验证明它有牙齿** —— 把空洞定义里的 `NOT busy[p]` 去掉后：
```
模型目标值应当等于独立统计的空档数 ==> expected: <3> but was: <34>
```
独立统计 **3** 个空档，变异模型报 **34** —— 立刻变红。

**教训**：
1. **复杂编码要用「独立实现」验收，不能只测「能解」。**
2. **测试写完要做变异实验**：故意改坏一行，确认对应测试变红。
   全绿但没做过变异的测试套件，你**不知道它是不是永远绿**。
3. 同类做法：给每条规则配一个**灵敏度反证** ——
   「把这条规则从注册表拿掉后，同一个违反解必须被接受」。
   没有它，反例测试可能因为**别的原因**恰好不可行而永远绿。

### G4. 验证脚本自己出错，却看起来像被测系统出错

**现象**：影子对比里 Python 侧返回 `{"detail":"登录已失效，请重新登录"}`，
一度以为是 token 过期或密钥不匹配。单独打印 payload 才发现 **token 完全有效**
（`exp` 还在 8 小时之后）。

**根因**：我在 PowerShell 里写的是
```powershell
$out = & python -c "..." 2>&1        # ← 把 stderr 也合并进来了
$tok = $out | Select-Object -Last 1  # ← 抓到的其实是最后一行 stderr
```
于是 `Authorization: Bearer <一条 Python 报错>` → 401。

**修法**：**让子进程把结果写文件，主流程读文件**，不要靠"取 stdout 的最后一行"。
（影子对比工具本身用的是 `subprocess.run(capture_output=True)`，
stdout/stderr 分开，所以它一直是对的 —— 出错的只是我临时的探测脚本。）

**教训**：**"被测对象报错"之前，先确认"我发出去的请求真的是我想发的"。**
同类问题在本项目里出现过三次：G1（读到旧日志）、B6（读到旧 class）、G4（读到 stderr）——
**都是"我看到的输入/产物不是这一次的"。**

## H. Web 层：契约类静默错误

这一节是 P1「用两个最简单资源走通全链路」时一次性抓出来的 6 个问题。
它们的共同点：**接口"能用"，但语义/字段/顺序与预期不同，且不报错**。
单个看都是小事，但漏掉任何一个，要么污染 12 个接口，要么在几百行后才发现。

### H1. 查询参数用原始类型 `int` → 不带参数时**全部 422**

**现象**：`GET /api/subjects?page=1&size=1` 正常，
但 `GET /api/subjects`（不带任何参数）返回
```
422 {"detail":[{"type":"value_error","loc":["query","page"],
     "msg":"Failed to convert value of type 'null' to required type 'int'"}]}
```

**根因**：Spring 对 record 做**构造器绑定**时，请求里没带的参数会传 **null**。
而 `record PageQuery(int page, int size, ...)` 的组件是**原始类型**，null 转不进去 → 绑定失败。
**如果照这样写 12 个列表接口，它们全都会在"不带参数"时失败** —— 而带上参数又都好，
所以最容易被漏测（我确实先漏了）。

**修法**：用包装类型 `Integer`，在紧凑构造器里归一化：
```java
public PageQuery {
    page = (page == null || page <= 0) ? 1 : page;
    size = (size == null || size <= 0) ? DEFAULT_SIZE : Math.min(size, MAX_SIZE);
}
```

**教训**：**框架的"可省参数"必须以 null 能进来为前提设计。**
原始类型表达不了"没传"，凡是来自外部输入的参数，默认用包装类型。

### H2. record 组件名与查询参数名对不上 → **静默不绑定**

**现象**：`GET /api/subjects?order_by=organization_id`（一个**非法**字段）
返回 **200 正常列表**，而不是白名单校验的 400。
换句话说：白名单校验代码写了，但**从没被触发过**。

**根因**：record 组件叫 `orderBy`，查询参数叫 `order_by`。
Spring 构造器绑定按**名字字面匹配**（除非显式指定），
`orderBy` 找不到 `order_by` → 该参数**永远是 null** —— **不报错、不警告**。

**修法**：显式绑定参数名：
```java
public record PageQuery(
        @BindParam("page") Integer page,
        @BindParam("order_by") String orderBy,
        ...) { }
```

**教训**：**camelCase 字段 ↔ snake_case 参数之间的映射不会自己发生。**
凡是"我传了参数但好像没生效"，第一件事是确认它**真的绑定上了**（把值打到日志/响应里看）。

### H3. `orderBy(condition, isAsc, column)` 参数传反 → 排序方向相反且不报错

**现象**：`?order=asc` 出来是**降序**，`?order=desc` 出来是升序。

**根因**：MyBatis-Plus 的第二个参数是 **`isAsc`**（是不是升序），不是 `isDesc`。
我顺手把 `query.desc()` 传了进去 —— 语义整个反过来。
默认排序与显式排序**都有结果**，只是一个正一个反，所以不会报错。

**修法**：显式提供语义正确的方法，别在调用处做心算：
```java
public boolean ascending() { return !desc(); }   // 名字就是给 isAsc 用的
...
wrapper.orderBy(true, query.ascending(), SORTABLE.get(column));
```

**教训**：**布尔参数的调用点最容易出错**，因为它没有编译期语义。
给布尔参数包一层**名字即含义**的方法（`ascending()` 而不是 `!desc()`）。

### H4. `isEmpty()` 被 Jackson 当成 getter → 响应多出一个 `empty` 字段

**现象**：列表响应变成
```
{"items":[...],"total":6,"empty":false}
```
而 Python 侧是 `{"items":[...],"total":6}`。

**根因**：Jackson 把任何 `isEmpty()` 视为属性 `empty` 的 getter。
我为了调用方便加了这个方法，却不知道它会参与序列化。

**修法**：`@JsonIgnore`。

**教训**：**DTO 上的"便利方法"可能悄悄改变对外契约。**
凡是会序列化的类型，加任何 `getXxx()` / `isXxx()` 之前先想一下它会不会变成字段。

### H5. `LocalDateTime.now()` 带纳秒 → 同一个接口两次调用格式不一致

**现象**：
```
POST /api/organizations → "created_at":"2026-09-27T06:23:11.0585571"   ← 7 位小数
GET  /api/organizations → "created_at":"2026-09-27T06:21:25"           ← 干净的秒
```

**根因**：MySQL 的 `datetime`（无精度声明）只存到**秒**，
但 `insert` 之后返回给客户端的是**内存里的对象**，它带着纳秒。
Python 侧没这个问题，因为它在 commit 后调了 `db.refresh()` 重新读库。

**修法**：写入前就截断到秒：`LocalDateTime.now(ZoneOffset.UTC).truncatedTo(ChronoUnit.SECONDS)`。

**教训**：**"刚写进去的对象"和"从库里读回来的对象"可能不是一回事。**
要么写前归一，要么写完重读 —— 但必须选一个，否则同一个接口会有两种输出格式。

### H6. MyBatis-Plus 不注册分页拦截器 → **静默不分页**

**现象**：`selectPage(page, wrapper)` 不报错，但返回**全部**记录（SQL 里根本没有 `LIMIT`），
`page.getTotal()` 也拿不到正确总数。看起来像"分页参数没生效"。

**根因**：MyBatis-Plus 把分页实现放在 `PaginationInnerInterceptor` 里，
它负责**改写 SQL** 加 `LIMIT`。不注册这个 Bean，`selectPage` 就退化成普通查询。
而且 3.5.9+ 把它依赖的 jsqlparser **拆到了独立构件**（`mybatis-plus-jsqlparser`），
只引 starter 时这个类根本不在 classpath 上（编译期就报错，算运气好）。

**修法**：注册拦截器 + 显式引 `mybatis-plus-jsqlparser`。

**教训**：**"调用了分页 API" ≠ "分页真的发生了"。**
实测一条 `?size=1` 只返回 1 条、而 `total` 仍是总数，才算验证过。
（与 B2 / B5 同一主题：**引入了依赖 ≠ 功能在运行**。）

### H7. 422 的**嵌套路径**与 `type` 与 Pydantic 不一致

**现象**：批量接口（`items` 是数组）参数越界时，两边 422 的 `loc` 与 `type` 都不同：

```
Python: {"type":"less_than_equal",     "loc":["body","items",0,"weekly_hours"]}
Java  : {"type":"value_error",         "loc":["body","items[0].weeklyHours"]}
```

**根因**：两处都是"两边表达方式天生不同"：
- **路径**：Spring 给的是一整串 `items[0].weeklyHours`；Pydantic 把**数组下标当成独立的一段**。
- **类型**：Pydantic 对数值边界用 `less_than_equal` / `greater_than_equal`；
  Spring 只给约束码 `Max` / `Min`。

**修法**：在 `ApiExceptionHandler` 里做两个映射：
1. 解析字段路径 → 遇 `[n]` 就把 `n` 作为独立的整型段插进去，字段名逐段转 snake_case；
2. 约束码 → Pydantic 的类型名（`Max`→`less_than_equal`、`Min`→`greater_than_equal`、
   `NotNull/NotBlank/NotEmpty`→`missing`、其余→`value_error`）。

**教训**：**"两边都返回 422"不等于"契约一致"。**
错误体的**结构**（位置怎么表达、类型怎么命名）也是契约的一部分，
而且这类差异**只能靠逐字段比对发现**，肉眼看"都是 422"会直接放过。

### H8. 列表接口的**默认页大小**会在契约比对里造成"假差异"
**现象**：`GET /api/assignments` 两边"条数不同"（Python 24 / Java 20），
看起来像 Java 少返回了数据。

**根因**：不是 bug —— Java 的列表接口默认 `size=20`（§9.2 定的），
而 Python 没有分页、返回全量。**两边都没错**，是比对方法错了。

**修法**（工具侧）：列表用例**自动补 `size=200`**（Python 忽略该参数、Java 全量返回），
再完整比对；另外单留一个用例用 `first_page` 模式验证"默认页确实是 20 条 + total 是全量"。

**教训**：**引入新能力（分页）之后，与旧实现的"全量返回"不能直接比。**
要么把新能力**调到等价于旧行为**再比（这里就是 `size=200`），
要么显式声明这条用例的基线语义（`superset` / `first_page`）。
这也是 §9 说的"分页让迁移期不再是零改动"在**验证侧**的镜像。

### H9. 必填查询参数"没传"与"传错"是**两条不同路径**（422 vs 400）

**现象**：`DELETE /api/system/storage/schedules`（防误触的 `confirm` 参数）：
```
不带 confirm     → Python 422 {"detail":[{"type":"missing","loc":["query","confirm"],"msg":"Field required"}]}
confirm=WRONG    → Python 400 {"detail":"缺少安全确认参数"}
```
我最初把两种情况都写成 400（用 `required = false` + 自己判空）。

**根因**：FastAPI 里 `def f(confirm: str)`（**没有默认值**）会把这个查询参数当成**必填**，
缺失时由框架返回 422；而"传了但值不对"才是业务代码的 400。
Spring 默认是 `MissingServletRequestParameterException`，不处理会掉进兜底 500。

**修法**：参数声明为必填（`@RequestParam(name = "confirm")`，**不加** `required = false`），
并在全局异常处理器里加一条 `MissingServletRequestParameterException → 422 + ["query", 参数名]`。

**教训**：**参数校验分三层，别用一层糊过去**：
框架层缺失（422）→ 业务层值非法（400）→ 权限层（403）。
这三层的状态码是契约的一部分，前端会据此区分"我少传了"和"我传错了"。
（这条也是影子对比工具抓出来的 —— 它构造了"完全不带参数"的请求。）

### H10. 「报第一个冲突」依赖**遍历顺序** → 同一输入给出不同答案

**现象**：一次会造成教师冲突的换课，Python 与 Java **都正确地拒绝**了（409），
但报的是**不同的冲突**：
```
Python: {"detail":"王老师在周1第2节存在班级冲突"}
Java  : {"detail":"钱老师在周1第1节存在班级冲突"}
```
两边都对（确实存在多处冲突），但**同一个输入给出了不同的回答** —— 契约上这就是不一致。

**根因**：校验器在找一个"第一个冲突"：
```python
conflict = next(((k, v) for k, v in teacher_slots.items() if len(v) > 1), None)
```
Python 的 `dict` 是**插入序**（构建时按条目顺序逐个插入），而 Java 侧我用了 `HashMap` ——
**无序**，迭代顺序取决于哈希值。于是"第一个"就成了两回事。

**修法**：换成 `LinkedHashMap`（保持插入顺序 = 条目的读取顺序），
并且条目的查询顺序也要与 Python 一致（都没有 `ORDER BY`，走主键序）。

**教训**：**凡是"取第一个/只报一个"的逻辑，都要问一句"顺序谁来定"。**
这类 bug 不会崩、不会报错，只会在**某些数据**上表现不一致 ——
而契约测试如果只比对状态码，就会完全放过它。
（这次能发现，是因为影子对比工具连**响应体文案**一起比。）

## J. 前端（React 19 + antd 6 + TypeScript 6）

### J1. `tsc --noEmit` 通过了，`npm run build` 却失败 —— 两者不是同一份配置

**现象**：
```
npx tsc --noEmit   → exit 0        （"类型检查通过"）
npm run build      → error TS2322  （build 的脚本是 `tsc -b && vite build`）
```

**根因**：`tsc --noEmit` 走根 `tsconfig.json`，而 `tsc -b` 走**项目引用**
（`tsconfig.app.json` / `tsconfig.node.json`）—— 两者的 `include` 与严格度可以不同。

**教训**：**验证要用 CI 真正执行的那条命令。**
"我本地类型检查过了"如果指的不是构建脚本里的那条，就没有说服力。
本项目一律用 `npm run build`（它含 `tsc -b`）。

### J2. antd 6 把 `Divider` 的 `orientation` 改成了"方向"，标题位置改叫 `titlePlacement`

**现象**：`<Divider orientation="left">` 编译报错
`Type '"left"' is not assignable to type 'Orientation'`，换成 `"start"` **还是报错**。

**根因**：antd 6 里 `Orientation = 'horizontal' | 'vertical'` —— 它现在是**分割线的方向**，
不再是标题位置。标题位置搬到了新 prop：

```ts
export type TitlePlacement = 'left' | 'right' | 'center' | 'start' | 'end';
export interface DividerProps {
  orientation?: Orientation;       // horizontal | vertical
  titlePlacement?: TitlePlacement; // ← 想要的是这个
}
```

**修法**：`orientation="left"` → `titlePlacement="start"`。

**教训**：**升级大版本时，报错说"类型不对"要去看类型定义，而不是猜同义词。**
`'left'` 不行就试 `'start'` 是在猜；读一眼
`node_modules/antd/es/divider/index.d.ts` 一眼就看清了。

## K. P3：分布式任务队列与独立求解进程

> P3 把"排课"从**进程内线程**改成**持久任务队列 + 独立求解进程**。

### K1. 迁移一段"清理逻辑"时按功能点搬，漏掉了大半 ⭐

P1 的旧 `ScheduleRunner` 在一个 `finally` 里统一做三件事：
**释放资源 + 收尾对外状态 + 落库**。P3 把它拆到任务路径时我**按功能点分散搬**，
于是漏了 4 处：

| # | 漏了什么 | 症状 |
|---|---|---|
| 1 | Redis 锁没人释放 | **第一次排课之后这所学校被永久锁死** —— 每次 generate 都 409「本校已有排课任务正在运行」 |
| 2 | 容量槽位不交还、对外状态不更新 | 任务显示 `done`，但**产能被一点点吃掉**（槽位永久被占）、**前端一直显示"正在排课"** |
| 3 | 失败/取消后不收尾状态 | 任务已 `failed`，而 `scheduling_state` 仍是 `running` → **再也发不起新排课** |
| 4 | **接管时没释放死掉 worker 的槽位** | 槽位按 token 记、接管换了 token → 旧槽位**永久泄漏** |

**前 3 个是跑测试时撞出来的；第 4 个只有真 `kill -9` 才暴露** ——
用"把 `lease_until` 改到过去"模拟租约过期时，永远不会走到"一个 worker 死了、
另一个接管"这个完整过程，于是那份槽位谁也不去释放。

**教训**：迁移一段清理逻辑时，**先列出它原本做的所有事**，再逐项确认新路径是否都做了。
按功能点分散搬很容易漏，而漏掉的后果**不是崩溃，是"若干次操作之后系统悄悄不能用"** ——
这比崩溃难查得多。

### K2. 绕开一个报错，制造了一个更难查的问题 ⭐

worker 启动时注入 `RestClient.Builder` 失败：

```
Parameter 0 of constructor in SchedulingClient required a bean of type
'org.springframework.web.client.RestClient$Builder' that could not be found
```

我改成静态工厂 `RestClient.builder()` —— 服务起来了 ✓ 但**它造出来的是裸 Builder**，
**不带 `spring.jackson.*` 配的 ObjectMapper** ✗ 于是：

```
snake_case 的响应  vs  camelCase 的 record 字段  → 匹配不上
  → 传给 primitive 参数的是 null
  → Cannot map 'null' into type 'long'
```

**服务能启动、能连上、能领到任务，只是读不懂响应** —— 比原来的启动失败难查一个量级。

**根因**：`spring-boot-starter-web` **不包含** `spring-boot-restclient`
（Boot 4 把自动配置按模块拆开了，和之前 Flyway/JDBC 是同一回事）。
**永久修复**是补依赖 + 改回注入。

> **教训：绕开一个报错之前，先问"这个报错在告诉我什么"。**
> "换个写法让它能启动"往往只是把问题推迟到一个更隐蔽的地方。

### K3. `catch` 只打 `e.getMessage()` 会把根因丢掉

领单失败时我这样记日志：

```java
log.warn("领单出错，本轮放弃: {}", e.getMessage());
```

日志里只有一句 `Error while extracting response for type [ClaimedJob]` ——
**根因（哪个字段反序列化失败）完全看不到**，而那种错误**只存在于 cause 链里**。
白白多跑了一轮排查。

改成 `log.warn("领单出错，本轮放弃", e)`（打整个异常）之后，一眼就看到
`Caused by: MismatchedInputException: Cannot map 'null' into type 'long'`。

**教训**：兜底的 `catch` 里**不要只打消息**。消息是给人看的摘要，**cause 链才是证据**。

### K4. yml 的键名和属性字段对不上时，Spring **静默忽略**

`orbit-solver-worker` 的占位 `application.yml` 里写的是：

```yaml
orbit.worker:
  poll-interval-seconds: 2
  heartbeat-seconds: 15
  max-concurrent-solves: 2
```

而 `WorkerProperties` 的字段是 `pollIntervalMs` / `concurrency` ✗ —— **一个都没绑上** ✗
不报错、不警告，只是**悄悄用默认值**。配置看起来写了，其实没生效。

**教训**：改 yml 时要与属性类**逐一核对键名**。这类错误没有运行时信号，只能靠读。

### K5. Spring Boot 4 **用的是 Jackson 3**（包名 `tools.jackson`），与 Jackson 2 是两套

```java
import com.fasterxml.jackson.databind.ObjectMapper;   // Jackson 2（Boot 3 及以前）
import tools.jackson.databind.ObjectMapper;           // Jackson 3（Boot 4）
```

而 `MyBatis-Plus` 的 `JacksonTypeHandler` 用的是 **Jackson 2** ✗ 于是同一个项目里
**两套 Jackson 并存**，默认行为还不一样（Jackson 3 默认
`FAIL_ON_NULL_FOR_PRIMITIVES = true`，Jackson 2 是容忍的）。

**在跨服务的 JSON 契约上，这个差异会变成"一边发得出去、一边收不进来"。**
现在靠"补依赖 + 全局 SNAKE_CASE"对齐；更稳的做法是把跨服务 DTO 的 JSON 契约**显式化**
（`@JsonProperty` 或独立 schema），不要依赖全局配置的默认值。

### K6. 容量槽位该在**领单时**抢，不是在入队时

P1/P2 是"抢到槽位 → 立即求解"，槽位与任务同生共死。
P3 有了队列之后，任务可能在队列里**躺几分钟** —— 此时占着槽位等于
**空占产能**、把别的学校挡在门外。所以槽位挪到领单时抢。

⚠ 连带一个顺序细节：领单时**先试槽位、抢不到就什么都不写地返回 null**
（事务提交时只有 `FOR UPDATE` 的行锁被释放，任务仍是 `pending`）——
否则会把一个没产能做的任务误标成 `running`。

### K7. `mysqldump` 是**位置化** INSERT —— 给表加过列之后恢复不了 ⭐

P3 给 `schedule_versions` 加了两个列，然后用之前的快照恢复数据：

```sql
INSERT INTO `schedule_versions` VALUES (1, 1, ...);   -- 没有列名列表！
```

→ `Column count doesn't match value count` ✗ 恢复失败 ✗
而我把 stderr 丢掉了（`2>nul` ✗）→ **数据库被清空了我还以为恢复成功了** ✗✗

**两个修法（都要）**：
1. 恢复时用带列名的 INSERT：把快照里的 `INSERT INTO \`t\` VALUES`
   改写成 `INSERT INTO \`t\` (col1, col2, …) VALUES`；
2. **不要 `2>nul`** —— 那是给自己上眼罩。这与 G4（`2>&1` 把 stderr 混进 stdout）
   是同一族的两个方向：**对 stderr 的处理永远要显式且可见**。

### K8. 真故障注入 ≠ 模拟故障 ⭐

决策门要验"求解中 `kill -9` → 任务被接管 → 只落一版课表"。
我先用"把 `lease_until` 改到过去"模拟 —— 机制验过了 ✓ 但**漏掉了 K1 的第 4 条**。

真做的时候还遇到一个具体麻烦：**求解只要 ~4 秒**，而我原来的检测间隔是 3 秒 →
第一次执行时，我"准备杀"的时候它**已经算完了** ✗。
改用**紧轮询**（每 200ms 查一次 `status=running`）→ 第 2 次就命中 → 强杀成功 ✓

**教训**：
- **模拟故障能验证机制，只有真故障注入能发现机制里的漏洞**；
- 做故障注入要先算清**故障窗口有多宽**（这里 4 秒），检测间隔必须明显小于它。

### K9. PowerShell 的两个具体坑（P3 又踩）

| 坑 | 现象 | 修法 |
|---|---|---|
| `$pid` 是**只读自动变量** | `$pid = $conn.OwningProcess` → `Cannot overwrite variable PID because it is read-only` | 换个名字（`$workerProcId`） |
| `Start-Process -RedirectStandardOutput` **会把 pwsh 打崩** | 整条命令无输出、`exit code 4294967295` | 这条**我早就记过**（见 G 节）✗ 还是踩了。**长驻进程一律用后台 job**，不要用 `Start-Process` |

## 附：一句话总纲
这个项目里最花时间的**从来不是写代码**，而是这几类事：

1. **编码与换行**（A1–A3）：Windows 上跨工具传文本，永远要显式指定编码
2. **「引了依赖」≠「功能生效」**（B1、B2、C2）：Spring Boot 4 时代尤其明显
3. **静默失效**（B2、D1、D3）：不报错的功能没生效，最危险
4. **假绿**（F1）：测试通过但测错了东西
5. **验证手段本身的坑**（A5、G1）：验证脚本自己出问题，把你带偏

所以这个项目反复用的两条纪律是：

> **① 构建通过是最弱的验证 —— 能跑起来、跑起来对、且能证明为什么对，是三件不同的事。**
>
> **② 每个「我改了 X 就好了」的结论，都要能回答「如果不改 X，它会怎样」。**
> 回答不了，就说明你还没定位到根因，只是碰巧让现象消失了。
