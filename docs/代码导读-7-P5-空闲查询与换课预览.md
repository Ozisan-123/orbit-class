# 代码导读 7：P5 空闲查询、换课预览与质量评分

> 评分的逐方法说明、取整顺序、当前主数据读取范围及持久化边界，见[第 9 册：后端补遗](代码导读-9-后端补遗.md)。本册保留功能流程概览。

## 0. 用户动作到数据库

```text
课表工作区
  ├─ AvailabilityPanel
  │    → /api/availability/**
  │    → AvailabilityService：指定版本中查占用
  │
  └─ Timetable 拖动
       → POST /swap/preview
       → SwapService 在真实事务中执行全部换课逻辑
       → 比较前后条目 → 强制回滚
       → SwapPreviewModal 展示影响
       → 用户确认
       → POST /swap 正式提交 + 审计

QualityScoreCard
  → GET /api/schedule/versions/{id}/score
  → ScoreService：硬约束闸门 + 四维评分
  → schedule_versions.score 保存带 hash/revision 的 JSON 快照
  → GET /score/diff?against={id} 做历史版本分项对比
```

两项能力都强制绑定版本：空闲不是全局事实，换课确认也必须携带预览时的 revision。

## 1. 空闲查询后端

### `AvailabilityController`

**源码**：[AvailabilityController.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/availability/AvailabilityController.java)

三个入口分别查询教师时段、班级时段、教师全天空闲。`version_id`、day、period 都是明确参数；租户 id 只从 JWT 主体取得。

### `AvailabilityService`

**源码**：[AvailabilityService.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/availability/AvailabilityService.java)

#### `teacher(...)`

依次校验版本归属、教师归属、星期、学校当天最大节数，然后在 `schedule_version_entries` 中按 version/teacher/day/period 查询。

#### `schoolClass(...)`

先取班级与年级，period 必须落在该年级当天作息内，再按 version/class/day/period 查询。

#### `teacherFreeSlots(...)`

取该教师当天全部条目，以全校年级当天最大节数为候选范围；已有条目按 period 建 Map，剩余编号就是空闲节次。占用明细按节次排序，响应稳定。

#### `occupiedBy(...)`

将课表条目补齐班级、科目、教师名称。引用已删除时使用空字符串，与既有课表查询契约一致。

#### 校验辅助

`requireTeacher`、`requireClass` 都同时带 organizationId，别的租户资源表现为不存在；`requireDay` 固定 0..4；`requirePeriod` 使用实际作息上限。

### 响应 DTO

**源码**：[AvailabilityResponse.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/availability/AvailabilityResponse.java)、[FreeSlotsResponse.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/availability/FreeSlotsResponse.java)

单点查询返回 `available` 与可空的 `occupied_by`；全天查询返回 `free_periods` 和可核对的占用列表。两者都回显 version/day/resource，防止界面把旧结果误认为当前版本。

## 2. 换课预览后端

### `SwapController.preview(...)`

**源码**：[SwapController.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/swap/SwapController.java)

路径是 `POST /api/schedule/versions/{id}/swap/preview`，请求体与正式 swap 完全相同，因此预览得到的 `expected_revision` 可原样用于确认。

### `SwapService.preview(...)`

**源码**：[SwapService.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/swap/SwapService.java)

1. 读取版本的全部条目，冻结 before 位置。
2. 调 `swapInternal(..., recordAudit=false)`，真正执行版本锁、固定课保护、负值腾挪、跨班镜像和整体校验。
3. 再读条目并按 id 比较 before/after。
4. 无论成功还是业务冲突，都把当前事务标记 rollback-only。
5. 成功返回所有发生位置变化的条目；业务异常转换为 `conflicts`。

这不是复制一套“近似校验”。正式换课未来增加新校验后，preview 自动获得同样行为。

⚠ 预览不写审计。若先插审计再回滚，MySQL 数据行虽会回滚，但 AUTO_INCREMENT 可能留下编号间隙；所以内部方法用 `recordAudit` 明确关闭预览审计。

### `swapInternal(..., recordAudit)`

正式入口传 true，预览传 false。除最后的审计插入外，两条路径完全相同；版本 revision 和所有条目更新在预览事务结束时回滚。

### `SwapPreviewResponse`

**源码**：[SwapPreviewResponse.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/swap/SwapPreviewResponse.java)

- `can_swap`：能否确认。
- `affected_entries`：每个 entry 的 before/after 班级、科目、教师和坐标。
- `conflicts`：稳定类型加人话消息。
- `expected_revision`：确认时的乐观锁基线。

## 3. 前端组件

### `AvailabilityPanel`

**源码**：[AvailabilityPanel.tsx](../frontend/src/components/AvailabilityPanel.tsx)

选择教师/班级、当前版本、星期和节次后查询。教师额外支持“查看全天空闲”。切换资源、日期或版本相关选择时清旧结果，避免展示过期结论。

### `SwapPreviewModal`

**源码**：[SwapPreviewModal.tsx](../frontend/src/components/SwapPreviewModal.tsx)

冲突时禁用确认按钮并逐条显示消息；可执行时以表格展示所有受影响条目的前后位置，并显示预览 revision。班级 id 通过页面回调翻译为名称。

### `ScheduleView` 与 `ScheduleGenerate`

拖动后的流程改为：构造 `SwapRequest` → 请求 preview → 保存 pending request → 弹确认框。只有用户确认且 `can_swap=true` 才调用正式 swap。正式请求仍可能因别人中途修改而 409，此时关闭预览并重拉版本。

## 4. 质量评分

### 两条接口

- `GET /api/schedule/versions/{id}/score`：返回总分、硬约束问题、四个维度和逐条规则统计。
- `GET /api/schedule/versions/{id}/score/diff?against={id}`：两版分别按各自冻结的规则集评分，再返回总分及各维度差值。

入口在 [ScoreController.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/score/ScoreController.java)，计算在 [ScoreService.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/score/ScoreService.java)。

### 100 分口径

| 维度 | 分值 | 原始量 |
|---|---:|---|
| 软规则满足度 | 50 | 对版本 `rule_set_hash` 对应的每条软规则独立统计违规/机会，再按规则 weight 加权 |
| 教师空档 | 20 | 每位教师每天首节与末节之间没有课的节次 |
| 课程分布均衡 | 15 | 同班同科同一天第 2 节起视为集中课时 |
| 主科上午占比 | 15 | `category=major` 且落在前 4 节之外的课时 |

单项满足度统一为 `max(0, 机会数 - 违规数) / 机会数`，最后按维度分值四舍五入；没有可评机会不凭空扣分。取整函数集中在 [ScoreMath.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/score/ScoreMath.java)，边界由 `ScoreMathTest` 固定。

### 硬约束闸门

评分前独立检查：课程是否落在班级作息内、教师是否撞课、每班每科周课时是否准确、教师周课时是否超限，以及规则集里的硬规则；未知规则类型按违规处理。任一失败时 `valid=false` 且 `total_score=0`，四维原始统计仍返回。基础校验器只返回首个越界或撞课错误；周课时检查则会遍历当前组织全部班级，具体范围见第 9 册。

### 为什么保存 hash 和 revision

[V4__schedule_quality_score.sql](../backend-java/orbit-scheduling/src/main/resources/db/migration/scheduling/V4__schedule_quality_score.sql) 给 `schedule_versions` 增加 `score JSON`。每次读取都按当前课表重算并尝试覆盖快照，正文同时保存 `rule_set_hash`、`revision` 和 `computed_at`，便于核对评分依据。持久化更新没有显式 revision 比较，不能保证并发换课时保存的就是最新修订评分；规则按 hash 读取，作息、课程方案等主数据仍读取当前值。

复制课表时 [VersionService.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/version/VersionService.java) 会继承规则集、输入快照和模型指纹；否则复制出来的同一张课表会丢掉评分依据。

### 前端评分卡

[QualityScoreCard.tsx](../frontend/src/components/QualityScoreCard.tsx) 展示总分仪表、四维扣分解释、硬约束错误和逐条规则明细。选择历史版本后显示总分/分项升降；若两版 `rule_set_hash` 不同，会明确提示“分差仅供参考”。课表 revision 变化会自动重新拉分。

## 6. 修改检查表

- 空闲查询是否始终要求 version_id？
- 班级 period 是否按该年级当天作息校验？
- 预览是否复用正式 swap，而不是另写一套判断？
- 预览事务是否始终 rollback-only，且不插审计？
- 确认是否原样携带预览 revision？
- 409 后是否重拉版本与课表？
- 评分是否同时携带 rule_set_hash 与 revision？
- 新增规则类型是否在 ScoreService 中补了独立违规统计？
- 任一硬约束失败是否保持 total_score=0？
- 两版规则集不同时，前端是否提示分差口径不同？
