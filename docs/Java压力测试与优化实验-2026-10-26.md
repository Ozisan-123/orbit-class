# Java 排课内核压力测试与优化实验（2026-10-26）

> 后续已完成与 Python 同输入的复核：Java 单校 196 班在 12 秒时限下连续 3 次成功、两校各 160 班并发成功；200 班在 30 秒时限下成功。见 `docs/同输入Python-Java容量对照-2026-10-26.md`。下文 32/48 班仅是另一份真实学校拓扑在指定时限下的观测值，不能作为 Java 通用上限。

## 结论先行

这次**实际运行的是 Java `orbit-solver-core`**，不是历史 Python 压测，也不是微服务接口吞吐测试。在 8、16、32 班及本地真实学校拓扑上，现行 `RuleCompiler` 相比测试用的 `FaithfulModelBuilder`，变量数减少约 28%；但建模耗时中位数更长。真实学校拓扑的 10 秒限时求解做了 3 轮：现行实现 3/3 次得到 577 节可行课表，旧基线 0/3 次得到可行解。这个结果支持“模型去重改善限时求解的可行解产出”，**不支持“建模阶段提速”或“整个微服务系统提速”**。

## 实验对象和数据边界

- 现行实现：`backend-java/orbit-solver-core/src/main/java/com/orbit/solver/core/compile/RuleCompiler.java`，其变量索引和缓存位于 `engine/SlotVariableIndex.java`。
- 对照基线：`backend-java/orbit-solver-core/src/test/java/com/orbit/solver/core/legacy/FaithfulModelBuilder.java`。它是旧 Python 建模方式的 Java 忠实移植，保留重复的教师成员变量；**不是另一套线上 Java 服务**。
- 标准夹具：`backend-java/orbit-solver-core/src/test/resources/fixtures/school-8.json`，8 班、36 教师、64 任教关系。16/32 班是对该夹具复制 2/4 份，教师 ID 互不重叠，属于合成扩容，只测建模规模。
- 真实拓扑来源：仓库根目录 `schedule.db`，SHA-256 `72fd36b4bf048ee0f6a81ad217cc5e6474fd720433c4aedc45adb8363d83750f`。原库有 21 班、61 教师、167 任教关系、577 节已排课程、236 条按班级固定课。导出器只读数据库并把姓名替换为编号。
- **重要限制**：当前 Java `ScheduleInput` 只有 `gradeFixedSlots`，不能表达原库的 236 条按班级固定课。实际送给 Java 的是“真实班级、教师、课时与任教拓扑，移除按班级固定课”的数据，文件名也注明 `no_class_fixed`。因此这是基于真实拓扑的实验，**不是原业务数据的完整复现**。不能拿它与历史 Python 5.58 秒成绩直接比较。
- 本机没有检测到 8080/8081/8083/8085、3306、6379 端口上的服务，本次未获得网关、MySQL、Redis、任务队列或多租户并发的实测值。

## 实验方法

1. 同一 JDK、同一 OR-Tools 依赖、同一输入与软规则，比较旧基线和现行实现。两者均使用单个求解 worker。
2. 建模先预热一轮，再测 8 班 5 次、16/32 班和真实拓扑各 3 次；新旧交替执行，报告中位数。耗时包括建模与模型统计，不包括读 JSON、求解和数据库写入。
3. 8 班求解限时 5 秒，真实拓扑限时 10 秒，各测 3 次并交替先后顺序。求解计时不含建模；现行实现的结果用独立校验器检查教师时段冲突、班级时段冲突、各班各科周课时和任教关系。
4. 原始逐轮数据在 `output/bench/java-solver-benchmark.csv`。`UNKNOWN` 表示到时未得到可行解，不能把它的目标函数数值当作有效成绩。

## 找到的优化与代价

1. **已实现、得到模型统计支持的优化**：`SlotVariableIndex.subjectAt()` / `teacherAt()` 对成员布尔变量按键缓存复用；旧基线在教师冲突与周上限约束中重复构造教师变量。其结果是模型变量和约束都约少 28%，真实拓扑限时求解从 0/3 可行提升到 3/3 可行。
2. **已发现的建模代价**：同样的 21 班拓扑，现行建模中位数 71.804 ms，旧基线 39.992 ms。后续应对 `SlotVariableIndex` 的键对象创建、Map 查找、`String.format` 变量命名做 profiler 采样，再逐项 A/B；不能用“模型更小”掩盖建模回退。
3. **优先补的正确性缺口**：为 Java 输入和编译器加入按班级固定课，并把原库 236 条规则纳入测试；随后重新生成真实数据实验。当前移除固定课会改变搜索空间。
4. **待测的持久化热点**：`backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/job/JobResultWriter.java` 对每节课逐条 `entryMapper.insert()`。577 节至少触发 577 次插入调用。应在隔离的 MySQL 库里比较现状与分批插入（例如每批 100/500 条），测事务耗时、SQL 往返次数、回滚正确性；目前没有 MySQL 实测值，不能宣称批量写入收益。

## 补充：班级容量扫描（2026-10-26）

### 与 2026-09-21 的 160/320 班报告为什么不同

`BENCHMARK_REPORT.md` 测的是**Python 后端**的另一个合成场景：单校 160 班、每班 30 节、每班 1 条固定课；求解器每任务 2 个搜索线程、内部时限 12 秒。所谓 320 班是**两所各 160 班的学校同时跑两个独立任务**，不是在一个模型里排 320 班。单校 160 班的总耗时 15.86 秒，两任务并发总耗时 20.24 秒。

下面的 32/48 班测的是**Java 内核**，从本地 21 班真实拓扑复制为**一个模型**，每个模型只给 1 个搜索线程，时限分别为 10/30 秒。该拓扑的教师任教组合、年级每日节数、周课时与上次的规则化合成学校不同；而且 Java 当前无法导入原库的 236 条按班级固定课。**两份报告没有同输入、同规则、同线程与同时间限制的 A/B 实验，不能据此推断 Java 比 Python 容量下降。**先前把本次最大成功档位口语化称作“班级上限”，容易造成这种误解；准确名称是“本次输入和时限下最大已验证成功档位”。

若要判断 Java 相对 Python 的真实容量变化，下一步必须把旧合成数据生成器的同一份输出同时喂给两套求解器，统一固定课表示、OR-Tools 版本、搜索线程数、时间限制和成功校验，再分别跑 20/40/80/120/160 班以及 2×160 并发，并保留原始记录。

用户关心“班级上限”后，追加了**固定时限下的容量实验**。输入从上述 21 班真实拓扑复制，每份使用互不相同的班级、教师、科目与年级 ID；非 21 的整数倍时取下一份的前若干班。每档运行一个全新 JVM、单个 OR-Tools worker、Java 最大堆 2 GiB；本机 `JAVA_HOME` 为 JDK 21.0.12.1+1，系统报告 24 个逻辑处理器。计数 `valid=true` 要求输出节数与输入课时总和相同，并通过独立的班级/教师冲突和任教关系校验。

**扩容数据保留了原库的任教与课时分布，但教师组之间互不共享，且原库 236 条班级固定课仍未进入 Java 输入。**这不是一个跨学校都成立的“最大班级数”。`UNKNOWN` 表示时限内未找到可行解，不代表数学上无解；`FEASIBLE` 表示有有效课表，不代表最优。

| 求解时限 | 班级数 | 应排节数 | 有效课表 / 运行次数 | 结果 |
|---|---:|---:|---:|---|
| 10 秒 | 30 | 806 | 3/3 | 本次均得到可行解 |
| 10 秒 | 31 | 835 | 0/3 | 均超时 |
| 10 秒 | 32 | 864 | 3/3 | 本次均得到可行解 |
| 10 秒 | 33 | 893 | 0/3 | 均超时 |
| 10 秒 | 36、42 | 980、1,154 | 各 0/1 | 超时 |
| 30 秒 | 42、45 | 1,154、1,229 | 各 1/1 | 得到可行解 |
| 30 秒 | 46、47 | 1,254、1,279 | 各 0/1 | 超时 |
| 30 秒 | 48 | 1,304 | 3/3 | 本次均得到可行解 |
| 30 秒 | 49、50、63 | 1,329、1,354、1,731 | 各 0/1 | 超时 |

**容量结论：**在已测试的档位中，10 秒时限下最大的连续 3 次成功规模是 **32 班**；30 秒时限下是 **48 班**。但 31 班失败而 32 班成功、47 班失败而 48 班成功，说明求解难度并不随班级数单调变化。因此 32/48 是“当前输入和时限下最大已验证成功档位”，**不能当作稳定的生产上限**。若要给部署容量承诺，应先加入完整固定课、多种学校数据以及并发任务/数据库链路，并用更多随机种子与重复次数估计成功率。

CSV 中的 `heap_after_*_mb` 是两个时点的 Java 堆占用，**不是进程内存峰值**，也不含 OR-Tools 原生内存；不能据此断言系统只需这些内存。本轮压测的失败是时间限制内没有可行解，没有观测到 Java 堆耗尽。
