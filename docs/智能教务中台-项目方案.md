## 1. 项目定位与价值

### 1.1 从「排课工具」到「教务中台」

原项目只解决「算出一张课表」。真实教务场景的完整链路是：

```
维护教务数据 → 表达排课诉求 → 排课 → 看结果 → 人工调整/调课 → 发布 → 通知
                        ↑                                              ↓
                   教务老师不懂约束求解 ←──────── 反馈 ────────────────┘
```

中台要把整条链路覆盖，并解决三类真实痛点：

| 痛点 | 今天的状态 | 中台的做法 |
|---|---|---|
| 教务老师不会表达约束 | 约束写死在 `engine.py` 里，加一条要改代码重发版 | **规则系统**：约束变成可配置数据 |
| 无解时只报一句笼统错误 | 「排课无解，请检查任教关系、周课时、固定时段和教师课时上限」；超时也被当成无解 | **不可行性诊断**：结构化原因 + 人话解释 |
| 不会用界面、不会查课表 | 需要在多个页面间跳转自己拼 | **排课助手**：自然语言查询、调课、规则录入 |

### 1.2 技术价值（为什么值得作为一号项目）

| 能力 | 说明 |
|---|---|
| 真实 NP-hard | CP-SAT 建模，不是调 API |
| 真实分布式难题 | 跨进程互斥、fencing token 防旧写、租约自动回收 |
| 真实算法设计 | 规则编译、增量重排、不可行性诊断 |
| 受约束的 LLM 应用 | 知道 AI 该放在哪一层、怎么让不可信输出变可信 |

### 2.2 服务清单

| 服务 | 职责 | 拥有的表 | 伸缩特征 | 失败影响面 | 拆分理由强度 |
|---|---|---|---|---|---|
| **gateway** | 路由、JWT 校验、限流、SSE | 无 | 跟连接数 | 全站不可用 | 中（≥2 服务后才值） |
| **academic** | 教务主数据、认证、用户、组织 | 10 张（见 §5） | 跟用户数 | 数据维护不可用，**不影响正在跑的排课** | 强（与 computing 特征相反） |
| **scheduling** | 规则、快照、编排、版本、调课、审计 | 9 张 | 跟事务量 | 排课与调课不可用 | 强 |
| **solver-worker** | CP-SAT 建模与求解 | 无 | **跟 CPU 核数** | 当前任务失败，租约到期后重排 | **最强**（CPU 密集 + 长任务） |
| **assistant** | 工具注册表、会话、LLM 编排、审计 | 3-4 张 | 跟 I/O 与 LLM 配额 | 助手不可用，**不影响任何核心功能** | 中（有外部依赖与成本） |
| **analytics**（可选） | 大课表聚合、Excel 导出、报表 | 只读 | 跟导出量 | 导出失败 | 弱（先并入 scheduling） |

### 2.3 拆分理由的诚实评估

> 这一节刻意保留，用于答辩时回答「你为什么要拆」。

| 拆分 | 强度 | 理由 |
|---|---|---|
| academic ↔ scheduling | 强 | 资源画像相反：CRUD 短事务 vs 长任务 + 租约 + 心跳 |
| scheduling ↔ solver-worker | **最强** | 求解吃满 CPU 12-60 秒、峰值 1.8 GB（160 班实测）；Web 服务不该被它拖累 |
| assistant 独立 | 中 | 依赖外部 LLM：延迟不可控、会超时、有成本、有配额；**它的故障绝不能影响排课** |
| gateway 独立 | 中 | 统一鉴权 + Redis 限流；服务数 ≥2 后才有意义 |
| analytics 独立 | 弱 | 只是为了隔离导出内存；**建议先并入 scheduling，成为瓶颈再拆** |

**实施纪律**：不要一次性上 5 个服务。见 §10 路线图——**先模块化单体，验证契约，再逐个拆进程**。

## 3. 关键架构约束（五条铁律）

| # | 铁律 | 后果 |
|---|---|---|
| 1 | **排课的原子性不跨服务**：`job_token` 栅栏、租约续期、版本落库全部在 scheduling 内完成 | 保证不需要分布式事务 |
| 2 | **禁止跨服务写库**：每个表只有一个属主服务；跨服务只读走 API | 避免隐式耦合 |
| 3 | **排课输入用快照**：scheduling 一次性拉取并冻结输入数据 | 保证一致性与可审计 |
| 4 | **助手只提议不执行**：写操作一律「草案 → 差异预览 → 人工确认 → 执行」 | 把 LLM 不可信输出关在闸门后 |
| 5 | **禁止编造**：助手回答中的每个实体必须来自工具返回 | 可自动检测（事实可追溯率） |

### 4.1 基础与构建

| 技术 | 版本/选择 | 为什么 |
|---|---|---|

> **两处「不写就会静默失效」的构建配置**（P0 实测踩到，见 §15）：
> ① 用 BOM 导入而**不是**继承 `spring-boot-starter-parent` 时，`spring-boot-maven-plugin` 的
> `repackage` **不会**被继承 —— 必须显式绑定 execution，否则 `mvn package` 产出普通 jar，
> `java -jar` 报「没有主清单属性」。
> ② **Spring Boot 4 把自动配置拆成了独立模块**（`spring-boot-jdbc` / `spring-boot-flyway` /
> `spring-boot-webmvc` …）。只把 `flyway-core` 放进依赖里，自动配置不会生效 ——
> 不报错、不建表，启动看起来一切正常。必须用对应的 starter。

### 5.3 规则表结构（核心）

```sql
CREATE TABLE constraint_rules (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  organization_id BIGINT NOT NULL,
  rule_type       VARCHAR(64) NOT NULL,   -- 派发给对应 RuleHandler
  params          JSON NOT NULL,
  hardness        VARCHAR(8) NOT NULL,    -- 'hard' | 'soft'
  weight          INT NOT NULL DEFAULT 1, -- 仅 soft 有效
  scope           VARCHAR(16) NOT NULL,   -- org|grade|class|teacher|subject
  scope_id        BIGINT NULL,
  enabled         TINYINT(1) NOT NULL DEFAULT 1,
  description     VARCHAR(255),           -- 面向用户的人话描述
  source          VARCHAR(16) NOT NULL,   -- 'manual' | 'assistant'
  version         INT NOT NULL DEFAULT 1, -- 乐观锁
  INDEX (organization_id, enabled)
);
```

## 6. 核心模块设计

### 6.1 规则系统（约束数据化）

**两级模型**：规则 = 数据（用户可编辑）+ 实现（开发者写一次的 handler）。

**三层语义**（这个划分很重要，决定了哪些东西用户碰不到）：

| 层 | 含义 | 能否被用户关闭 |
|---|---|---|
| **不变量** | 课表违反了就是错的（同一教师同一时段上两个班） | ❌ 不可配置、不可关闭 |
| **数据驱动** | 约束内容来自教务数据本身（周课时、教师上限） | ❌ 不放进规则表，避免出现两个真相 |
| **可配置规则** | 学校的偏好与诉求 | ✅ 规则表里可增删改、可设硬/软与权重 |

#### 规则类型清单（实现状态：已全部落地）

| rule_type | params | 层 | 来源 |
|---|---|---|---|
| `teacher_no_conflict` | — | 不变量 | 现有硬约束 2 |
| `subject_weekly_hours` | — | 数据驱动（`grade_subjects.weekly_hours`） | 现有硬约束 1 |
| `teacher_max_weekly_hours` | — | 数据驱动（`teachers.max_weekly_hours`） | 现有硬约束 3 |
| `subject_max_per_day` | `subject_id?`, `max` | 可配置，硬软两用 | 现有软约束 1 |
| `subject_no_consecutive` | `subject_id?` | 可配置，软 | 现有软约束 2 |
| `teacher_max_daily_periods` | `teacher_id?`, `max` | 可配置，硬软两用 | 新增 |
| `teacher_unavailable` | `teacher_id`, `day`, `period` | 可配置 | 新增 |
| `subject_avoid_last_period` | `subject_id?` | 可配置，硬软两用 | 新增 |
| `main_subject_morning` | `subject_id?`, `morning_periods` | 可配置，硬软两用 | 新增 |
| `teacher_minimize_gaps` | `teacher_id?` | 可配置，软 | 新增 |

**三个约定（实现时确定，前端与助手都依赖它们）**：

1. **`?` 表示可省略，省略 = 适用于全体**。`subject_id?` 省略即「所有科目」，`teacher_id?` 省略即「所有教师」。
   这样一条规则既能表达「语文一天最多两节」，也能表达「任何科目都别连排」——后者正好等价于原 Python 的全局软约束。
2. **`weight` 不在 params 里**，而在 `constraint_rules.weight` 列（对应 §5.3 表结构），`hardness` 同理。
   params 只放「这条规则自己的业务参数」。写进 params 会和表结构重复，产生两个真相。
3. **`teacher_unavailable` 的 `day` / `period` 是 1 开始的自然语言编号**（「周 3 第 5 节」），
   与前端表单一致，内部减 1 使用。

#### Handler 接口（实际实现）

```java
public interface RuleHandler {
    String type();
    String displayName();
    List<RuleParamSpec> params();                   // 一份 schema 同时驱动前端表单 + 后端校验 + 助手工具定义
    boolean mandatory();                            // true = 不变量，自动施加且不可被规则集关闭
    String describe(RuleParams p);                  // 人话描述
    void apply(RuleContext ctx, RuleParams p, boolean hard, PenaltyCollector penalties);
}
```

`RuleParamSpec` 是 `(name, type, required, min, max, enumValues, label)`，
`type ∈ {INT, LONG, BOOL, STRING, ENUM}`，可**投影成 JSON Schema** 供前端渲染。

> **为什么 `hard` 是 `apply` 的参数而不是 handler 的属性**：硬/软属于**规则实例**（表里的 `hardness` 列），
> 不属于规则类型。同一条 `subject_max_per_day` 既可以是硬约束也可以是软偏好，由用户决定。
> 这也是它同时出现在「现有硬约束 1」与「现有软约束 1」两处的原因。

#### 技术核心 `RuleContext`（已实现）

现有 `engine.py` 里 `fixed`（固定课）处理散落 **39 处**，每条约束都要手工数 `fixed_count`。已经收敛：

```java
public final class RuleContext {
    // 固定课计数（固定课已算在内，handler 不再需要自己遍历 fixed 表）
    int fixedCountForSubject(long classId, long subjectId);
    int fixedCountForSubjectOnDay(long classId, long subjectId, int day);
    int fixedCountForTeacher(long teacherId);
    int fixedCountForTeacherOnDay(long teacherId, int day);
    int fixedCountForTeacher(long teacherId, int day, int period);
    boolean isFixed(long classId, int day, int period);
    long fixedSubjectAt(long classId, int day, int period);   // 非固定课返回 -1
    long fixedTeacherAt(long classId, int day, int period);

    // 变量访问（懒创建 + 缓存）
    BoolVar subjectAt(long classId, int day, int period, long subjectId);
    BoolVar teacherAt(long teacherId, long classId, int day, int period);

    // 时段集合（只含非固定时段）
    List<BoolVar> freeSubjectSlots(long classId, long subjectId);
    List<BoolVar> freeSubjectSlotsOnDay(long classId, long subjectId, int day);
    List<BoolVar> freeTeacherSlots(long teacherId);
    List<BoolVar> freeTeacherSlotsOnDay(long teacherId, int day);
    List<BoolVar> freeTeacherSlots(long teacherId, int day, int period);

    int periodsOn(long classId, int day);       // 各班各天节数可不同
    int maxPeriodsOn(int day);
}
```

**`freeTeacherSlots` 的缓存在这里很关键**：它同时被「教师不冲突」与「教师周上限」两条规则使用，
返回的是**同一批变量**。原 Python 实现各建一套，重复了约 **28%** 的变量（实测 13,452 → 9,676）。

**规则注册表 = 助手的工具箱**：新增一个 handler，助手立刻会用，无需改 prompt。
装配点在 `compile/BuiltinRules.registry()`——「有哪些内置规则」是装配知识，不属于注册表这个数据结构
（否则 `rule` 包与 `rule.handler` 会形成双向依赖）。


### 6.2 求解与任务编排

```
POST /api/schedule/generate
  → 取 enabled 规则集 → 冻结 rule_set_version(hash)
  → 取 academic 的 snapshot（一次调用，保证一致性）→ 存 scheduling_snapshots
  → 在 schedule_jobs 插入 pending 任务（带 job_token）
  → 立即返回 202 + 任务状态

solver-worker 循环：
  SELECT ... WHERE status='pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
  → 置 running + lease_until
  → 拿 snapshot → 编译模型（记录 model_fingerprint）→ CP-SAT 求解
  → 每 15s: POST /internal/jobs/{id}/heartbeat（带 job_token）
  → 完成: POST /internal/jobs/{id}/result（带 job_token + 结果）
        ↓ scheduling 侧校验 job_token → 写版本 + 审计（同一事务）→ 释放槽位
  → worker 崩溃: 租约到期 → 其他 worker 接手（幂等：先校验 token）
```

**为什么用 DB 队列而不是 MQ**：任务状态必须与 `job_token` 栅栏**在同一事务域**（铁律 1）。MQ 只用于真正解耦的场景（通知、文档解析）。

### 6.3 调课与空闲查询

**现有能力（复用，不重写）**：`POST /api/schedule/versions/{id}/swap` 已实现
乐观锁 `expected_revision`、仅草稿可改、固定课保护、跨班协同换（一次 4 条）、事后全量重校验 `_validate_version`、审计日志。

**新增只读接口**：

| 接口 | 返回 |
|---|---|
| `GET /api/availability/teacher/{tid}?day=&period=` | 是否空闲；占用则返回班级与科目 |
| `GET /api/availability/class/{cid}?day=&period=` | 同上 |
| `GET /api/availability/teacher/{tid}/free-slots?day=` | 全部空闲时段 |
| `POST /api/schedule/versions/{id}/swap/preview` | **干跑**：能否交换、影响哪几条、有无冲突 |

**四种交换语义**（助手必须正确区分）：

| 意图 | 接口表达 | 陷阱 |
|---|---|---|
| 同班两个时段对调 | 同班 + `target` 存在 | — |
| **跨班协同换** | `cross_class=true`，`target` **必须存在** | 否则 400「跨班拖动需要放到另一个班级已有课程上进行协同换时」 |
| **两个老师的课互换** | 通常是协同换的特例 | 识别错就撞上面的 400 |
| 单方移动（目标空） | `target` 为空 | 仅限同班 |

**失败信息翻译表**（助手直接用）：

| 接口返回 | 说给用户 |
|---|---|
| 400 目标节次不在两个班级的共同上课时间内 | 这两个班那天节数不同，该时段有一方没课 |
| 400 跨班协同换仅支持同一年级 | 跨年级不能换，只能同年级内互换 |
| 409 协同换时涉及固定课程 | 该时段是固定课，不能动 |
| 409 已发布课表不可拖动 | 已发布，我帮你复制一个新草稿再改 |
| 409 该草稿刚被其他用户修改 | 有人刚改过，我重新拉最新版给你 |

### 6.4 不可行性诊断

```
求解器输出（确定性、可验证）
  {type:"TEACHER_OVERLOAD", teacher_id:7, actual:24, limit:18, excess:6}
  {type:"FIXED_SLOT_CONFLICT", class_id:12, day:2, period:1, subjects:[3,5]}

### 6.5 智能助手

**工具清单**（三层，安全边界就在分层上）：

| 层 | 工具 | 执行方式 |
|---|---|---|
| **只读**（直接执行） | `check_teacher_availability`、`check_class_availability`、`find_free_slots`、`get_timetable`、`get_job_status`、`explain_diagnosis`、`score_timetable`、`check_config` | 直接调用 |
| **提议**（返回草案） | `propose_rule`、`propose_swap`、`propose_reschedule` | 返回草案 + 差异预览，**不落库** |
| **写**（需人工确认） | `apply_rule`、`apply_swap` | 用户确认后调用既有接口 |
| **禁止** | 直接发布课表、直接改课表内容 | 助手不做 |

**必须处理的四个问题**：

1. **歧义消解**：匹配到多条就反问（「张老师周三第二节有 3 个班的课，您指哪个？」），匹配到 0 条就说没找到，**绝不猜**
2. **乐观锁时序**：助手读课表 → 用户思考 → 点确认，中间 `revision` 可能已变。必须记录读取时的 revision，失败时提示并重拉
3. **禁止编造**：回答中每个班级/教师/节次必须来自工具返回
4. **成本控制**：小模型做意图路由、按 org 每日 token 预算、超预算降级为只读、结果落库复用

**Redis 在助手中的用途**：会话上下文（TTL）、LLM 调用限流、工具结果短缓存、SSE 并发限制。

**评测指标**：

| 指标 | 说明 |
|---|---|
| 意图路由准确率 | 100 条真实问法 |
| 工具参数正确率 | 生成的查询/规则参数 |
| **事实可追溯率** ★ | 回答中每个实体都能在工具返回里找到——**自动检测，专治编造** |
| 规则草案采纳率 | 用户点确认的比例 |
| P95 延迟 / 单次会话成本 | 性能与成本 |

### 7.5 五个关键技术点

**① SSE 不能用 `EventSource`**
`EventSource` 不支持自定义 header，**带不了 Bearer token**。必须用 `fetch` + `ReadableStream` 手动解析 SSE（或用 `@microsoft/fetch-event-source`）。这是实打实会卡住的地方。

**② JSON Schema → 动态表单：自己写，别引库**
只有 10 种规则、参数类型就 `integer / string / enum / boolean` 几种，自己写约 150 行的渲染器足够，引 Formily 是过度设计。
**关键收益**：一份参数 schema（`RuleHandler.params()` 返回的 `RuleParamSpec` 列表，可投影成 JSON Schema）同时驱动 **前端表单 + 后端校验 + 助手工具定义**——一处定义、三处使用，新增规则类型时前端零改动。

**③ 乐观锁的 UX 必须做完整**
`swap` 和规则编辑都带 `expected_revision`。收到 **409 不能只弹一个错误**，要给出明确操作：「这版课表刚被修改 → ［查看差异］［刷新并重试］」。这对应助手那边的同一个问题（§6.5 第 2 条）。

**④ 工具调用轨迹必须可视化**
助手不能只显示最终答案，要展示「我查了什么」：调用了哪个工具、参数是什么、结果摘要。
这既是**可解释性**，也是「禁止编造」在 UI 层的保障——**用户能自己核对**，而不是盲信。

**⑤ 确认卡片三栏布局**
草案确认必须同时展示：**用户原话** | **人话回述 + 展开的技术参数** | **影响预览**。评审成本降到几秒，人工确认这道闸门才不会被绕过。

## 9. 契约保持（迁移期前端只做分页适配）

> 本节标题原为「迁移期前端零改动的前提」，**已修正** —— 因为决定在 P1 引入分页契约，
> 而分页会改变列表接口的响应结构。详见 §7.1 的修正记录。

| 契约 | 现状 | 要求 |
|---|---|---|
| 前端 `baseURL` | `/api` 相对路径 | 生产由 gateway 同源提供，开发用 Vite proxy 指向 gateway |
| 未认证响应 | 前端拦截器**只认 401** 触发登出 | Spring Security 的 `AuthenticationEntryPoint` 必须返回 **401，不是 403**（P0 已落地） |
| 错误体 | `{"detail": "..."}` | `@ControllerAdvice` 保持该结构，不用 Spring 默认 `ProblemDetail` |
| 50 个接口路径与状态码 | 已固定 | 逐一保持，契约测试守护 |
| 按父级过滤 | `grade_id` / `teacher_id` / `class_id` / `version_id` **已有** | **保持不变**，不要动 |
| **列表响应结构** | **裸数组** `[...]`，无分页参数 | **统一改成** `{items: [...], total: N}` |
| **分页/搜索/排序参数** | 无 | 统一接受 `?page=&size=&keyword=&order_by=&order=` |

**明确不做的事**：不做「有分页参数时返回 `{items,total}`、无参数时还返回裸数组」的混合形态。
同一接口两种返回结构会让前端必须写两个分支、契约测试也无法覆盖 —— 省下的那点前端改动不值这个代价。

### 9.1 为什么分页必须放在 P1，不能等到 P2

```
如果 P1 只平移现有 50 个接口（不带分页）
    ↓
P1 的契约测试把「裸数组响应」冻结成基线
    ↓
P2 前端开工，发现表格在 160 班规模下必须分页
    ↓
要么改契约（P1 的契约测试全部失效，要重跑）
要么打补丁（同一接口两种响应结构）
```

**P1 本来就在逐字核对这些接口，此时引入分页的边际成本最低。**
代价是前端那 ~12 个列表函数要各加一层解包（1-2 天），这个代价换来了「契约一次做对」。

### 9.2 分页参数与响应（统一约定）

```
GET /api/teachers?page=1&size=20&keyword=张&order_by=name&order=asc

200 OK
{ "items": [ {...}, {...} ], "total": 123 }
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `page` | 1 | 从 1 开始 |
| `size` | 20 | **上限 200** —— 防止 `size=999999` 把库和内存打垮 |
| `keyword` | 空 | 各接口搜哪些字段见下表 |
| `order_by` | 各接口给合理默认 | **只允许白名单字段**，禁止把用户输入直接拼进 `ORDER BY`（SQL 注入） |
| `order` | `asc` | 只接受 `asc` / `desc` |

**搜索字段约定**（避免每个接口各写一套）：

| 资源 | 搜哪些字段 |
|---|---|
| 教师 / 用户 | `name` / `display_name` / `username` |
| 班级 / 年级 / 科目 | `name` |
| 课表版本 | `name` / `description` |
| 规则 | `description`（人话描述） |
| 审计日志 | `user_name` / `action` |

**大课表接口例外**：`/schedule/class|teacher|grade/{id}` 返回的是「一张课表」，
天然有上限（一个班一周最多几十行），**不需要分页**，但**保持裸数组**不变
（前端 `Timetable` 组件直接吃数组）。这一点要在契约清单里显式标注，否则实现者会顺手改掉。

## 11. 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| 1 | ~~OR-Tools Java JNI 在 Windows 加载失败~~ **已定位并解决** | 根因**不是**缺 MSVC 可再发行组件，而是 **JDK 23 与 OR-Tools 9.15 的 JNI 不兼容**：建模与指纹都正常，`CpSolver.solve()` 段错误（`EXCEPTION_ACCESS_VIOLATION` in `msvcp140.dll`，连 30s 超时都不触发）。**换 JDK 21 LTS 后完全正常**。项目统一 JDK 21（§4.1） |
| 2 | 跨语言建模不等价 | **判据已修正**：`model_fingerprint` **不能**当跨语言判据 —— 实测两边 `model_stats()` 统计行一字不差、变量数与约束数全同，指纹却不同（差异藏在 `objective.scaling_factor`：Python 的 `minimize()` 写 1.0，Java 留空 0.0，语义相同）。正确做法是**逐字段比对 `CpModelProto`**（变量名/定义域/约束逐条序列化）。指纹只当**同语言内的回归护栏**——它敏感于创建顺序与记账字段，这对回归是优点，对跨语言比对是噪音 |
| 3 | `@Transactional` 传播行为改变现有事务边界 | 显式用 `TransactionTemplate`；`_finish` 类独立事务单独确认 |
| 4 | 助手引入的两层非确定性 | 助手只做工具调用与翻译；求解保持确定性 |
| 5 | LLM 成本失控 | 按 org 预算 + 限流 + 小模型路由 + 结果复用 + WireMock 测试 |
| 6 | 微服务调试成本 | P1 先单体；每拆一步先补契约测试与追踪 |
| 7 | RAG 沦为主观演示 | 只在有真实语料且有评测集时做 |
| 8 | 范围蔓延 | 每个阶段设决策门，不达标不推进 |
| 9 | **Spring Cloud 与 Spring Boot 版本不兼容** | 这对版本**只在运行时校验**：Maven 能解析 BOM ≠ 兼容。实测 2025.1.1 + Boot 4.1.1 被 compatibility verifier 拒绝（要求 Boot 4.0.x），升到 2025.1.3 解决。**对策：升级任何一个都必须启动一次服务，不能只看构建通过** |
| 10 | **依赖「在 classpath 上」但功能静默失效** | Spring Boot 4 把自动配置拆成独立模块。只引 `flyway-core` 而不引 starter，Flyway 不会运行、不报错、不建表。**对策：每个「按文档引入了却没动静」的功能，都要有一次「它真的工作了吗」的验证**（本次靠 `/api/health` 里暴露 flyway 版本才抓到） |
| 11 | **共享库 + 按属主拆表 = DDL 层面的耦合** | scheduling 的 6 张表有 **16 个外键**指向 academic 的 5 张表，于是启动顺序被数据模型绑死（academic 必须先）。这是共享库方案的固有代价，也是将来「每服务独立库」时第一个要处理的障碍。当前选择：让它响亮失败，而不是关掉外键检查 |

### 2026-09 · 决定：P1 一并引入分页契约，并修正「迁移期前端零改动」

**背景**：P1 动工前做了一次「**从前端组件反推接口**」的评估

2. **12 个列表接口全部没有分页**，而前端表格现在是「**一次拉全量 + antd 前端分页**」的假分页

**决定**：**分页放在 P1 一起做**，统一改成 `{items, total}`（约定见 §9.2）。
理由是「平移时顺手做」边际成本最低；若等 P2 前端开工才发现，

#### 连带修正（这条比决定本身更重要）

原方案承诺「**迁移期前端零改动**」（§7.1 与 §9 标题）。**这个承诺作废了** ——
分页会改变响应结构，前端 `api/index.ts` 里约 12 个列表函数都要加一层解包：

现在：GET /api/teachers          → [{...}, {...}]              ← 裸数组
之后：GET /api/teachers?page=1   → {items: [...], total: 123}
```

于是下面几处一起改了：

| 位置 | 原文 | 修正为 |
|---|---|---|
| §7.1 | 迁移期前端「**不用改**」 | 迁移期前端「**只需适配分页**」（约 1-2 天） |
| §9 标题 | 「迁移期前端**零改动**的前提」 | 「迁移期前端**只做分页适配**」 |
| §7.8 | P1 前端工作「不动 / 0 天」 | 「适配分页 / 1-2 天」 |
| §10 P1 行 | 工期 2-3 周、决策门 2 条 | 工期 2.5-3.5 周、决策门加第 3 条 |
| §10 顺序纪律 5 | 「P1 迁移期前端不动」 | 「只需适配分页」 |
| §0 概览 | 前端「迁移期**不改**」 | 同 §7.1 |

**教训（值得记进方法论）**：

> **「前端零改动」是一个会被后续决策推翻的承诺。**
> 它当时是对的（逐字保持 50 个接口，前端确实不用改），
> 但它隐含了一个前提：**契约完全冻结、不做任何改进**。
> 一旦决定改进契约（比如加分页），承诺立刻失效。

所以这类承诺在方案里要**把前提条件写出来**，否则后来改的时候会漏掉连带影响 ——
这次是靠回头核对 §7.1/§7.8/§9/§10/§0 五处才找全的。

### 2026-09 · P1 边界澄清（动工前）

动工前把 P1 的边界逐条钉死。背景是发现**方案对 P1 的描述太粗**——

#### 边界 ①：P1 接 solver-core 时，用**规则系统 + 等价规则集**，不用 `FaithfulModelBuilder`

现状是一个矛盾：

| | 现状 |
|---|---|

| Java 侧 | `orbit-solver-core` 已经是**规则系统**形态（10 条规则 + 编译器） |

| 方案 | 做法 | 结论 |
|---|---|---|
| **A** | 规则系统 + 一套「等价于 Python 的规则集」（`legacyEquivalentRules`） | ✅ **采用**。它已是最终形态；`GoldenModelTest` 已验证「规则系统 + 等价规则集」的模型结构与 Python 一致 |
| B | `FaithfulModelBuilder`（忠实移植基线，逐行对应 `engine.py`） | ❌ **只在测试里用**。它是等价性的**基线**，P2 之后就该删；拿它当生产路径 = 把死代码上线 |

#### 边界 ②：P1 决策门原来只验证了一半 —— **补「结果等价」**

原决策门写的是「`CpModelProto` 逐字段一致」——那验证的是**建模等价**。
但「**求解结果等价**」（同一实例两边**最优目标值相同**）**从未验证过** ——
因为之前 Windows 上 `CpSolver.solve()` 会段错误，做不了（见 §11 风险 1）。

**现在 JDK 21 能跑了，这件事必须补进 P1。** 理由：

> 建模等价 ≠ 结果等价。
> 模型完全一样、求解器同一份 C++ 内核，理论上结果应该一样；
> 但 CP-SAT 有 `num_search_workers`、随机种子、并行 LNS ——
> **最优值应当相同，而具体解可能不同**。
> 不验证「最优目标值相同」，那「Java 与 Python 行为等价」这个结论有一半是悬空的。

**验证方式**：对现有 fixture（`school-8.json`）与后续的真实快照，
分别在 Python 与 Java 上求解，断言 `objectiveValue` 相同（并记录 `wallTime` 供参考）。

#### 边界 ③：拆进程后靠 **Vite 按路径分流**，真网关留到 P3

§10 P1 写的是「先做同进程模块，**再拆进程**」，但 gateway 被排在 P3。
那拆进程后前端怎么找到两个服务？—— 现在 `vite.config.ts` 是**单一 target**：

```ts
proxy: { '/api': { target: 'http://localhost:8000' } }
```

| 方案 | 做法 | 结论 |
|---|---|---|
| **A** | Vite proxy **按路径分流**：`/api/schedule/**` → 8083，其余 `/api/**` → 8081 | ✅ **采用**。开发期够用，把真网关留给 P3 |
| B | 提前把 gateway 做出来（等于把 P3 的 gateway 挪到 P1） | ❌ 增加 P1 工作量，且那时只有 2 个服务，网关价值未兑现 |

**分流规则**（拆进程后）：`/api/schedule/**`、`/api/rules/**`、`/api/availability/**` → scheduling；其余 → academic。
等 P3 上真网关时，Vite 配置改回单一 target 即可。

#### 有意的差异（不是 bug）

- **token 格式**：Java 用标准 JWT（3 段），Python 是自定义 HMAC（2 段），**互不通用**——
  实测交叉使用都被拒（各返回 401）。token 对前端不透明（只存 localStorage、原样回传），
  格式**不参与契约**。代价是灰度切换时用户需重新登录一次。
- **`ValidationErrorItem` 没有 `input`/`ctx`**：Spring 在参数校验失败时拿不到原始 body，
  且 Pydantic 的文案（`"Field required"`）无法在 Spring 里复刻。
  契约测试比对**状态码 + 结构**，不比对文案。

#### 本轮新踩的坑（详见 [踩坑总结](踩坑总结.md)）

| 坑 | 说明 |
|---|---|
| **B5 🔴 MyBatis-Plus 3.5.9 在 Boot 4 下完全不生效** | Boot 4 把 `DataSourceAutoConfiguration` 挪到 `spring-boot-jdbc` 模块并**改了包名**，3.5.9 的 `@AutoConfigureAfter` 变成悬空引用 → 排序**静默失效** → starter 不激活，而报错说的是 `sqlSessionFactory are required`（**指向完全错误的方向**）。靠 `--debug` 的条件评估报告才看出来。已升到 **3.5.17 + `mybatis-plus-spring-boot4-starter`** |
| Mapper 扫描与框架约定不匹配 | `@MapperScan("...**.mapper")` 期望 `mapper` 子包，但框架约定是「实体/Mapper/Controller/Service 同放领域包」→ 一个都没注册。改用 `@MapperScan(basePackages = "...", annotationClass = Mapper.class)`（精确扫描，且将来加服务接口不会被误注册） |
| Jackson 配了 `non_null`，与 Python 不符 | 骨架里写的 `default-property-inclusion: non_null`，但**实测 Python 是包含 null 的**（`"published_by":null`）→ 改成 `always`。**这是契约 bug**，P0 时没发现 |

#### 决策门：真实 kill -9 故障注入 ✅

求解只要 ~4 秒，所以用**紧轮询**盯住 `status=running` 就立刻强杀：

```
第 2 次轮询命中 running → 强杀 PID 40496（job=12 worker_id=worker-40496）
杀后：任务仍 running / worker=worker-40496（已死）/ attempt=1
      版本数仍是 3   ← 被杀的任务什么都没写，没有半成品
重启 worker（进程 B）后：
  任务  12/done/worker=worker-54352/attempt=2/version=13   ← attempt 1→2，worker 换新
  版本数 4（= 3 + 1）                                      ← 只落一版 ✓ 幂等
  事件  enqueued → claimed(40496,1) → takeover(54352,2)     ← 接管留痕
```

#### 这一路抓到的 4 个 bug —— 全是同一类

**「迁移一段清理逻辑时按功能点搬，于是漏了其中一部分」**。P1 的旧 runner 在一个 `finally`
里统一做"释放资源 + 收尾状态"，拆到任务路径后：

| # | 漏了什么 | 症状 |
|---|---|---|
| 1 | Redis 锁没人释放 | **第一次排课之后这所学校被永久锁死**（P3 改变了锁的职责：它现在只保护"检查+CAS+入队"这个短临界区） |
| 2 | 槽位不交还、对外状态不更新 | 任务显示 done 但**产能被一点点吃掉**、前端一直显示"正在排课" |
| 3 | 失败/取消后状态不收尾 | 任务已 failed，而状态仍是 running → **再也发不起新排课** |
| 4 | **接管时没释放死掉 worker 的槽位** | 槽位按 token 记，接管换了 token → 旧槽位**永久泄漏**。**只有真 kill -9 才暴露得出来**（纯模拟租约过期看不到） |

> 教训：迁移一段"清理逻辑"时，要**先列出它原本做的所有事**，再逐项确认新路径是否都做了。
> 这类漏掉的后果不是崩溃，而是"若干次操作之后系统悄悄不能用"——比崩溃难查得多。

#### ⑦ 不可行性诊断 ✅（本轮新增）

**两段式**：先静态（毫秒级，默认），后深诊断（`?deep=true`，最小冲突集）。

| 静态检查（不求解） | 抓什么 |
|---|---|
| `MISSING_ASSIGNMENT` | 某班某科有周课时要求却**没配老师** → 「周课时必须排满」这条不变量永远无法满足 |
| `CLASS_CAPACITY_SHORTFALL` | 一个班的周课时总量 > 一周座位数 |
| `TEACHER_OVERLOAD` | 教师被分配课时 > 自己的周上限（**方案 §6.4 举的就是这个例子**） |
| `FIXED_SLOT_CONFLICT` / `_OUT_OF_RANGE` / `_SHARED_SLOT` | 固定课自相矛盾 / 越界 / 多年级共用同一节 |

**先静态后求解的理由**：真实世界"排不出来"绝大多数是**数据问题**，
这四类都在毫秒级可判、而且结论是**确定的**。最小冲突集要对模型松弛再求解，贵得多，
应该只在静态一无所获时才用。

**深诊断的最小冲突集，用了一个不改内核的等价做法**：
方案 §6.4 原稿写的是「硬约束改为 `onlyEnforceIf(flag)`，最小化违反加权和」——
那要改动 solver-core 里**每一条 handler 的建模方式**。这里改成
**逐条去掉硬规则再求解**：去掉哪条之后能排出来，那条就在冲突集里。
代价是解 K 次（K = 硬规则条数，上限 5，每次只用 8 秒而非排课的 60 秒）。

**实测**（造了一个真的不可行场景：加一条硬规则「语文一天最多 1 节」，而语文每周 8 节）：

```
排课 → failed（对外文案仍是原句，没改）
GET /diagnosis          → kind=INFEASIBLE，note 提示可以深诊断
GET /diagnosis?deep=true → conflict_rules=[{rule_id:4, rule_type:subject_max_per_day,
                                            description:"语文一天最多 1 节（故意造不可行）"}]
                           耗时 0.6 秒 ✓
```

再测静态：把王老师的周上限从 18 改成 10（他实际 16）→
`TEACHER_OVERLOAD` + `{teacher_id:1, actual:16, limit:10, excess:6}` ✓
（**与 §6.4 的示例结构一致**）。

**三处实现上的取舍**：
1. **`INFEASIBLE` 与 `UNKNOWN` 分开报**。CP-SAT 能区分「证明了无解」与「到时限还没证明」，
   而后者**不该让用户去改数据**（延长时间就行）。Python 侧把两者压成同一句"排课无解"，
   这是 P2 新增的能力。对外文案仍然不动（P1 的契约）。
2. **排课失败时只做浅诊断**。深诊断要几十秒，而此刻任务还占着容量槽位与 Redis 锁 ——
   在里面跑它会让"排不出来"这种常见情况白白压住排课能力。贵的那部分留给按需触发。
3. **落库策略**：深诊断（贵）或确实有问题（需留痕）才落库；
   "一切正常"的浅诊断不落库（毫秒级能重算，落库只会把表撑大）。
