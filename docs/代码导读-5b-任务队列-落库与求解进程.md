# 代码导读 · 5b. 任务队列（落库与求解进程）

> 本册范围：
> * `com.orbit.scheduling.job` 中的**结果落库 / 内部协议 / 任务对外接口**部分，9 个类：
>   `JobResultWriter`、`InternalJobController`、`JobController`、`DiagnosisHook`、
>   `JobResultRequest`、`JobClaimResponse`、`JobResponse`、`JobEventResponse`、`HeartbeatRequest`
> * **整个** `orbit-solver-worker` 模块，6 个类：
>   `SolverWorkerApplication`、`WorkerProperties`、`SchedulingClient`、`JobRunner`、`WorkerLoop`、`ClaimedJob`
>
> 共 **15 个类**。上游：[代码导读.md](代码导读.md)（第 1 册）、[代码导读-4a-scheduling-排课编排.md](代码导读-4a-scheduling-排课编排.md)（入队与领单所在的 `JobQueueService` / `ScheduleJobMapper` 在 4a 册）。
> 骨架：[架构说明.md](架构说明.md) §5.8、§3.5。

## 本模块在系统里的位置

它解决的是「**一次排课请求的完整生命周期**」：请求方（前端）入队一个任务 →
独立进程 `orbit-solver-worker` 通过**内部 HTTP 接口**领走 → 求解 12~60 秒 →
把结果交回 → scheduling **确认它还是任务的持有者**后写入课表版本。

一句话概括服务边界：**worker 不碰数据库**（方案 §2.2 的服务清单写明它「拥有的表：无」），
所以它需要的一切（任务身份 `jobId`/`jobToken`、冻结的输入快照、当时那套规则）
都由 `POST /internal/jobs/claim` 一次性下发；它想说的每一句话
（续租、进度、取消、成功、失败）也都只能通过 HTTP 回传。

```
前端 ──► JobController(/api/schedule/jobs)  ──► JobQueueService（4a 册）
                                                     │
                        InternalJobController ◄──────┘   （同一张 schedule_jobs 表）
                        (/internal/jobs)
                              ▲
                              │ HTTP + X-Worker-Secret
                              │
              WorkerLoop(@Scheduled) ─► JobRunner ─► OrbitSolver.solve
                    ▲                        │
                    └── SchedulingClient ────┘
```

## 阅读顺序建议

1. **`JobResultWriter.persistIfStillOwner`** —— 先读它。整个 P3 的**幂等性**只落在
   这一个方法里（"还是我的任务吗？是就写版本 + 标记完成，不是就丢弃结果"）。
   读懂它，`job_token` 栅栏、`FOR UPDATE`、三处收尾的用意就都清楚了。
2. **`SchedulingClient` + `JobRunner`** —— worker 侧的两个主干。前者是协议的所有细节
   （含一个"服务能启动、能连上、能领到任务，只是读不懂响应"的实测坑），
   后者是"起心跳 → 求解 → 交回"的执行体。
3. 再看 **`InternalJobController`**（三个内部接口的语义）与 **`JobController`**（对外 5 个接口）。
4. 最后看 `WorkerLoop`（轮询与两处并发上限）与 6 个纯 DTO（本册用表格批量说明）。

## A 组 · `orbit-scheduling`：结果落库与协议层

### 5b.1 `JobResultWriter` —— P3 的结果闸门（"还是我的任务吗"）

**谁调它**：只有 `InternalJobController.result()` 调它，两个方法各一次：
先 `persistIfStillOwner(...)`，返回非 null 才调 `settle(jobId, persisted)`。
**它调谁**：`ScheduleJobMapper`（锁 + 标记完成）、`ScheduleVersionMapper`、
`ScheduleVersionEntryMapper`、`ScheduleAuditLogMapper`、`SchedulingSnapshotMapper`、
`ScheduleWorkerSlotMapper`、`ScheduleStateService`。

**它在 P3 中替换掉了什么**：P1 有一个 `ScheduleResultWriter` 做同一件事
（"确认还是我的任务，再写版本"），但判据是**组织级状态行 + 组织锁**；
P3 换成了**任务行 + `job_token`**。粒度更细（多个任务可以并存），
而且不再需要"一个组织只能有一个排课任务"这条约束。

#### 7 个字段 + 构造器（第 40-62 行）

全是 `final` 字段 + 构造器注入的 Mapper / Service，没有 `@Autowired` 字段注入。
**为什么值得注意**：`slotMapper` 与 `stateService` 这两个依赖**只被 `settle` 用**，
`persistIfStillOwner` 一次都不碰它们 —— 这个依赖分布本身就是"两件事属于两个事务域"
的第一个信号。

> ⚠ 这两个依赖在源码里写的是**全限定名**（`com.orbit.scheduling.capacity.ScheduleWorkerSlotMapper`、
> `com.orbit.scheduling.schedule.ScheduleStateService`）而不是 import ——
> 与文件顶部整齐的 import 风格不一致。**不影响行为**，但读的时候不要以为是别的类。

#### `record Persisted(Long versionId, int versionNo, int entryCount)`（第 65 行）

落库成功的**回执**，三个字段刚好是 `InternalJobController` 要拼进响应体的那三个
（`version_id` / `version_no` / `entry_count`），也是 `settle` 拼提示文案要用的两个。

⚠ **方法返回 `null` 不是"没有版本"，而是"结果被丢弃"** —— 这是本类最容易读错的地方。
javadoc 里写得很直白：`{@code null} 表示**结果被丢弃**（任务已被接管）`。
所以调用方必须写 `if (persisted == null)`，而不是判空"顺手当异常处理"。

#### `@Transactional Persisted persistIfStillOwner(...)`（第 68-128 行）

签名：

```java
public Persisted persistIfStillOwner(long jobId, String jobToken, List<TimetableEntry> entries,
                                     String solverStatus, String modelFingerprint,
                                     Long objectiveValue)
```

**整个方法就是一个事务**（`@Transactional`，无参数 → 默认传播 `REQUIRED`、运行时异常回滚）。
按代码顺序逐段：

| 行 | 做什么 | 为什么 / 不这么写会怎样 |
|---|---|---|
| 72 | `ScheduleJobEntity locked = jobMapper.lockForRunning(jobId, jobToken)` | 一条 `SELECT ... WHERE id=? AND job_token=? AND status='running' FOR UPDATE`。**三件事一次做完**：拿到任务行、确认 token 还是自己的、锁住这一行 |
| 73-76 | `locked == null` → `log.warn` + `return null` | 返回 null 表示**结果被丢弃**。**这是正常的**（接管发生后旧 worker 复活就会走到这里），所以只 `warn` 不抛异常 |
| 78 | `int versionNo = nextVersionNo(locked.getOrganizationId())` | 取本组织下一个版本号（见下面的独立小节） |
| 79-88 | `new ScheduleVersion()` 并逐个 set | `versionNo`、名称 `"智能排课方案 V" + versionNo`、描述、`status="draft"`、`revision=1`、`createdBy` 取**任务创建者**（不是 worker）、时间戳一律走 `UtcTimes.now()` |
| 90 | `version.setRuleSetHash(locked.getRuleSetHash())` | **溯源指纹①**：这版课表用的哪套规则（P2 的概念）。任务行上直接有，照抄 |
| 91 | `version.setSnapshotFingerprint(snapshotFingerprintOf(locked))` | **溯源指纹②**：用的哪份输入（P3）。任务表只存 `snapshot_id`，所以要走一次补查 |
| 92 | `version.setModelFingerprint(modelFingerprint)` | **溯源指纹③**：编译出的 CP-SAT 模型。由 **worker 传回来**（只有它知道） |
| 93 | `versionMapper.insert(version)` | 插入后 MyBatis-Plus 回填 `version.getId()`，下面明细与审计都要用 |
| 95-105 | `for (entry : entries)` 逐条插入 `ScheduleVersionEntry` | 一条明细 = 一个 (班级, 科目, 教师, 星期, 第几节)。`organizationId` 与 `versionId` 用**上面锁住的那行**的值，**不用请求里的值**（请求里根本没有这个字段） |
| 107-118 | 插一条 `ScheduleAuditLog` | `action="generated"`；`userId` = 任务创建者；`userName` = `"排课任务 #" + id`；`details` 是一个 `Map.of(entry_count, job_id, attempt)` |
| 121-122 | `int affected = jobMapper.complete(...)` | **同一个事务里**标记完成：`status='done'`、`progress=100`、回写 `solver_status`/`model_fingerprint`/`objective_value`/`version_id`/`entry_count`/`finished_at`，并 `lease_until = NULL` |
| 123-126 | `affected != 1` → 抛 `IllegalStateException` | 见下面「为什么这里敢抛异常」 |
| 127 | `return new Persisted(version.getId(), versionNo, entries.size())` | 返回回执，方法返回后事务才提交 |

**`@Transactional` 里的三件事**（javadoc 的 `① ② ③`，也是本册最该记住的三行）：

```
① SELECT * FROM schedule_jobs
     WHERE id=? AND job_token=? AND status='running' FOR UPDATE
        → null ⇒ 已被接管 ⇒ 丢弃结果（静默，不报错）
② 写 schedule_versions（带三个溯源指纹）+ 明细 + 审计
③ 置 job = done（同事务）
```

> ⚠⚠ **为什么"标记 done"必须和"写版本"在同一事务**
> —— 否则会出现"版本有了但任务还在跑"。
> 具体走法：版本已提交、进程在"标记完成"之前崩掉 →
> 任务行仍是 `running`、租约照旧会到期 → 另一个 worker 领走（`takeOver`，`attempt+1`）
> 重新求解 → 又写一版。结果是**同一个任务落了两份课表版本**，
> 而两份都是"合法"的，事后再也分不清哪份是最终答案。
> 这正是决策门要验的幂等性。

**为什么 `affected != 1` 时敢抛异常**（第 123-126 行）：注释写的是
"行还被我们锁着，理论上不可能；真发生了就整体回滚，宁可让 worker 重来"。
`complete` 的 `WHERE` 条件与第 72 行 `lockForRunning` **完全一致**
（`id` + `job_token` + `status='running'`），而这一行在本事务里已经被
`FOR UPDATE` 锁住、期间别人改不了它，所以正常路径下必然是 1。
抛异常 → 事务回滚 → 版本、明细、审计全部撤销 → worker 收到 5xx →
它自己会 `reportFailure`，租约到期后任务被接管重做。**宁可重做，不可半落**。

**为什么插入明细用 `locked` 而不是入参**：入参里只有 `entries`（`TimetableEntry`，
求解内核的领域类型），没有组织信息。把组织来源统一到"数据库里那一行"，
就不存在"请求里的 organizationId 与任务行不一致"这种可被伪造的状态。

#### `private String snapshotFingerprintOf(ScheduleJobEntity job)`（第 158-164 行）

任务表只有 `snapshot_id`（指纹存在快照表上），所以这里是**唯一的补查点**：
`snapshot_id == null` → 返回 `null`；`selectById` 查不到 → 也返回 `null`。

⚠ 两处都返回 null 而不是抛异常，意味着**这个溯源指纹可能是空的**。
这是刻意的宽容（P1 时代的任务没有 `snapshot_id`），代价是
"三个指纹缺一不可"这句话在**数据层面**没有强制约束 —— 只有代码在这里尽量填上。

#### `private static String ownerNameOf(ScheduleJobEntity job)`（第 166-168 行）

就一行：`"排课任务 #" + job.getId()`。
**为什么不用 `createdBy` 的用户名**：worker 交回的结果里没有"谁点的排课"这个信息，
而任务表只存了 `created_by` 的用户 id。为了审计日志里有一列人能看的名字，
这里用**任务编号**代替用户名（而不是再查一次用户表 —— 那会给结果落库路径
再加一个跨模块依赖，不值得）。

#### `private int nextVersionNo(long organizationId)`（第 170-178 行）

一条 MyBatis-Plus 的 `lambdaQuery()`：只 select `version_no` 列、按 organization 过滤、
`version_no` 倒序、`last("LIMIT 1")`；然后
`(latest == null || latest.getVersionNo() == null ? 0 : latest.getVersionNo()) + 1`。

⚠ **这是一个"读最大值 + 1"的版本号分配，不是数据库自增，也没有唯一约束兜底。**
它在"同一组织同时只能有一个排课任务"的前提下是安全的 ——
而这个前提正是由 scheduling 侧的**容量槽位**（每个组织最多一个在跑的任务）保证的。
换句话说：版本号的正确性**不靠这里，靠槽位**。读这个方法的时侯不要误以为它有并发保护。

#### `public void settle(long jobId, Persisted persisted)`（第 146-155 行）

**注意：它没有 `@Transactional`。** 这一点是本方法存在的全部意义。

```java
ScheduleJobEntity job = jobMapper.selectById(jobId);   // 147
if (job == null) return;                                // 148-150
slotMapper.releaseByToken(job.getJobToken());           // 151
stateService.finishByOrganization(job.getOrganizationId(), "done",
        "排课完成，已生成草稿 V" + persisted.versionNo() + "，共 "
                + persisted.entryCount() + " 节课");     // 152-154
```

| 行 | 做什么 |
|---|---|
| 147 | 按 id 重新读一次任务行。**不重用 `persistIfStillOwner` 里的 `locked`** —— 那个对象是另一个事务里的实体，早已脱离 |
| 148-150 | 查不到就直接返回。此时**什么都不做**（任务被物理删掉了，没有槽位也没有状态要收） |
| 151 | `releaseByToken(job.getJobToken())` 把槽位三个字段清空（`organization_id`/`job_token`/`lease_until` 置 NULL） |
| 152-154 | 把**组织级对外状态**收尾：`status="done"` + 一句给人看的中文消息 |

> ⚠⚠ **为什么 `settle` 必须在事务之外**（javadoc 第 133-139 行给了两条理由，这里逐条展开）：
>
> **① 槽位是"产能"，交还得越早越好。** 放在事务里，SQL 虽然执行了，
> 但真正的效果要等**提交后**才对别的连接可见 —— 而 `persistIfStillOwner`
> 里还有"插 N 条明细"（160 个班就是一二百条 INSERT）。把释放槽位写在那个事务里，
> 等于让产能多被占住"整个版本落库的时间"。P3 的槽位是**全局并发上限**，
> 每多占一秒都会把别人的任务挡在门外。
>
> **② 状态更新是给前端轮询看的，它不该因为版本落库回滚而跟着回滚。**
> 如果 `settle` 在同一个事务里，那么"标记 done 失败 → 整体回滚"时
> 连槽位释放和状态收尾也一起撤销 —— 结果是一个已经写好的版本被回滚了，
> 前端却什么都没看到（甚至可能已经看到过一帧"完成"）。
> javadoc 特别注明 P1 的 `_finish` 也是用**独立 session** 做的，
> 就是为了达到同样效果。
>
> **③ 顺序也有约束：必须在 `persistIfStillOwner` 返回非 null 之后调用。**
> 它用到 `persisted.versionNo()` 与 `persisted.entryCount()` 拼文案；
> 更关键的是 —— 结果被丢弃（null）时**绝不能**调它，
> 因为那会把一个**已经被别人接管、正在被别人求解**的任务，
> 从旧 worker 手里"顺手"标成完成并释放掉**新持有者**的槽位。

> ⚠⚠ **实测踩坑（javadoc 第 141-144 行原文）**：
> "最初我把这两件事漏了 —— 因为 P1 的旧 runner 里它们写在别处，
> 搬到任务路径时只搬了'落库'。症状很具体：任务显示 `done`，但
> **槽位永远不释放**（排课能力被一点点吃掉）、**前端一直显示"正在排课"**。
> 实测跑一遍才看出来。"
> 这两句话是本类最值钱的部分：**漏掉 `settle` 不会崩，只会慢慢把系统憋死**。

**关于 `releaseByToken` 的幂等性**：它在 `schedule_worker_slots` 上
`WHERE job_token = ?` 更新（源码注释：任务被接管后旧 worker 再来释放会更新 0 行，无害）。
所以在"结果被丢弃"的路径上即使误调也不会破坏别人的槽位 ——
但**不能靠这个幂等性来省掉 `persisted == null` 的判断**，因为第 152 行的状态收尾
用的是 `job.getOrganizationId()`，会把这个组织正在跑的任务对外显示成"已完成"。

### 5b.2 `InternalJobController` —— 三个内部接口与共享密钥

**谁调它**：只有 `orbit-solver-worker` 的 `SchedulingClient`（三个方法一一对应）。
**它调谁**：`JobQueueService`（领单/心跳/取消/失败）、`JobResultWriter`（落库 + 收尾）、
`DiagnosisHook`（失败后补浅诊断）、`ScheduleStateService`（取消后收尾对外状态）。

**类注释第 22-29 行回答了"为什么不让 worker 直连数据库"**：
`SKIP LOCKED` 领单本质是**写** `schedule_jobs`，让 worker 直接写就违反了铁律 2
（禁止跨服务写库）。代价是每次领单多一次 HTTP，换来的是**表属主始终清晰**，
P3 之后拆独立库时不用回头改。

#### 共享密钥怎么校验

| 位置 | 内容 |
|---|---|
| 第 42 行 | `public static final String WORKER_SECRET_HEADER = "X-Worker-Secret"` —— 头名是**公开常量**，worker 侧 `SchedulingClient` 是**照抄字面量** `"X-Worker-Secret"`（不是引用这个常量：两个模块之间没有编译期依赖） |
| 第 54 行 | 构造器注入 `@Value("${orbit.worker.secret:orbit-dev-worker}") String expectedSecret` —— 期望值来自配置，**带默认值** |
| 第 171-175 行 | `requireWorker(secret)`：`secret == null \|\| !secret.equals(expectedSecret)` → `throw BusinessException.unauthorized("内部接口需要合法的 worker 密钥")` |
| 三个接口 | 每个的第一行都是 `requireWorker(secret)`，一个不漏 |

三点值得注意：

1. **`@RequestHeader(required = false)`**：没带这个头**不会**被 Spring 拦成 400，
   而是让 `secret` 为 null 落到 `requireWorker` 里 → 返回 401 + 中文文案。
   这样"缺密钥"和"密钥错"是同一个响应，不泄漏"哪个头是对的"。
2. **`equals` 的方向是 `secret.equals(expectedSecret)`** —— 入参在前。
   两边都不会是 null 时方向无所谓；这里先判了 `secret == null`，所以安全。
   （⚠ 但要注意它**不是**常量时间比较，理论上可被时序侧信道攻击。
   内部接口 + 网络层限制的前提下属可接受，生产环境靠网关兜底。）
3. **配置现状（读代码时容易误会）**：`orbit-scheduling/src/main/resources/application.yml`
   里**没有** `orbit.worker.secret` 这一项（`orbit` 下只有 `jwt`/`scheduling`/`academic`），
   所以实际生效的是 `@Value` 的默认值 `orbit-dev-worker`；
   而 worker 侧 `application.yml` 的 `secret: ${WORKER_SHARED_SECRET:orbit-dev-worker}`
   默认值**恰好相同**，所以开发环境开箱能通。
   ⚠ 但 javadoc 第 170 行写的「空密钥配置会在启动日志里被警告（见 `scheduling.yml`）」
   **在代码里找不到对应实现**（没有 `scheduling.yml`，也没有任何启动检查），
   本册按"注释描述的是意图、代码未实现"记录，**不编造一个不存在的警告**。

#### 为什么 `/internal/**` 在 Spring Security 里是 `permitAll`

配置在 [SchedulingSecurityConfig.java](../../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/config/SchedulingSecurityConfig.java) 第 64-68 行：

```java
// P3：worker 的内部接口。它们**不能**要求用户 JWT（worker 没有用户身份），
// 所以在这里放行、由 InternalJobController 自己校验共享密钥
// X-Worker-Secret。生产环境还应该在网络层限制（只有 worker 能访问），
// 那是 P3 网关的职责。
.requestMatchers("/internal/**").permitAll()
```

**为什么是"放行 + 控制器自己验"，而不是"给 worker 发一个 JWT"**：

* worker **没有用户身份** —— 它不代表任何一个用户，而是代表"系统自己"。
  给它签一个用户 JWT 会污染 `SchedulePrincipal` 的语义（它会带 `organizationId`，
  而 worker 要处理**任何**组织的任务）。
* 但是**不能真的不验**：`permitAll` 只表示"安全链不做认证"，
  控制器里的 `requireWorker` 是这次请求唯一的门。两者合起来才是完整设计 ——
  少写 `requireWorker` 就等于对全网开放"写课表"的接口。
* ⚠ 这里有一个**结构性风险**值得记住：往这个包新增一个 `@PostMapping` 而忘了
  `requireWorker(secret)`，**不会报错、不会被测试发现**（因为功能是通的），
  只会静默地多一个无鉴权的写接口。三个方法目前都写了，改这个类时先数一遍 `requireWorker` 的个数。

#### `private long organizationIdOf(long jobId)`（第 63-65 行）

一行：`queueService.requireJobById(jobId).getOrganizationId()`。
注释写明"只用于更新对外状态"。它是 `requireJobById`（**只按 id 查，不做租户校验**）
的唯一调用点 —— 因为 worker 没有租户上下文，只有 `jobId`。
⚠ 注意它查不到时会**抛异常**（`requireJobById` 的语义），而在 `result` 的取消分支里
这个调用发生在"已经成功标记取消"之后 —— 若此时任务恰好被删，会得到一个 500，
但取消其实已经生效了。这是可接受的边角（任务不会被删），但读的时候要知道它不幂等。

#### `@PostMapping("/claim")`（第 71-78 行）

```java

        @RequestParam(name = "worker_id") String workerId,
        @RequestHeader(name = WORKER_SECRET_HEADER, required = false) String secret) {
    requireWorker(secret);

```

* `worker_id` 是**查询参数**（`POST /internal/jobs/claim?worker_id=worker-1234`），
  而不是请求体 —— 因为这是 POST 但没有 body，`SchedulingClient` 也是这么发的。
* **为什么"没活干"用 204 而不是 404**（类注释与 §5.8 都强调了）：
  它是**正常状态不是错误**，worker 隔 2 秒再来问。
  用 404 的话，worker 侧就必须把 404 从"错误"里特判出来，
  而 404 在 HTTP 语义里意味着"这个资源不存在"，会误导日志与监控。
* ⚠ `worker_id` **没有做非空/格式校验**：传空串也会被写进
  `schedule_jobs.worker_id`。这是内部接口，靠网络层与共享密钥兜底。

#### `@PostMapping("/{jobId}/heartbeat")`（第 86-98 行）

```java
boolean ok = queueService.heartbeat(jobId, request.jobToken(),
        request.progress() == null ? 0 : request.progress());
Map<String, Object> out = new LinkedHashMap<>();
out.put("ok", ok);
out.put("cancel_requested", ok && queueService.isCancelRequested(jobId, request.jobToken()));
```

返回的是一个手写的 `LinkedHashMap`（不是 DTO record）。用 `LinkedHashMap` 而不是
`Map.of` 是为了**稳定字段顺序**（响应 JSON 里 `ok` 永远在前），小事，但读日志时省心。

> ⚠ **`ok=false` 的语义是"token 已失效"（任务被接管或已终结），worker 应当立即停止求解**
> —— 继续算下去的结果也不会被接受。这一句在 `InternalJobController`、
> `SchedulingClient`、`JobRunner` 三处各写了一遍，不是冗余：它是跨进程的**协议约定**。

`cancel_requested` 里那个 `ok &&` 很关键：**token 都失效了就不再报"取消"**，
避免 worker 收到一个自相矛盾的信号（既"你不是持有者"又"用户要取消"），
进而走错分支去 `submitCancellation`（那对已经被接管的任务是无意义的写入）。
另外 `isCancelRequested` 在 `HeartbeatRequest.progress() == null` 时会传 0，
所以进度不会是 null（心跳 SQL 里 `progress = #{progress}` 需要非 null）。

**`cancel_requested` 是取消请求到达 worker 的唯一通道**：worker 不碰数据库，
它只能在心跳响应里知道"用户点了取消"（`HeartbeatRequest` 的类注释原话）。

#### `@PostMapping("/{jobId}/result")`（第 112-168 行）

**一个请求同时表达"成功"与"失败"**（`JobResultRequest` 的类注释：这样 worker 侧只有一条
回写路径，不会出现"失败了但忘了调失败接口"）。控制器里按**优先级**分三支：

**① 取消分支（第 119-128 行）—— 优先级最高**

```java
if (Boolean.TRUE.equals(request.cancelled())) {
    boolean recorded = queueService.markCancelled(jobId, request.jobToken());
    out.put("accepted", recorded);
    out.put("cancelled", true);
    if (recorded) {
        stateService.finishByOrganization(organizationIdOf(jobId), "idle", "排课任务已取消");
    }
    return out;
}
```

* 注释点明优先级的原因：**"它和'失败'是两回事，失败可能被重试、取消绝不该"**。
  放在最前面判断，是为了让"cancelled=true 且顺手带了 error"这种重叠请求
  一定走取消路径 —— 否则任务会被退回队列重新拉起来跑。
* `recorded == false` 表示 token 已失效（被接管）—— 那么**不收尾对外状态**：
  这个组织现在的状态属于**新持有者**，旧 worker 无权把它改成 idle。
  这个 `if (recorded)` 和 `settle` 里"只在 persisted 非 null 时调用"是同一个原则。
* ⚠ 取消的收尾状态是 `"idle"`（不是 `"done"`）—— 因为"取消"意味着
  **这所学校现在没有在排课**，可以让用户再发起。可以与 `JobResultWriter.settle`
  的 `"done"` 对照读。
* ⚠ 这里也**没有**把 `DiagnosisHook` 或槽位释放串进来：槽位在
  `queueService.markCancelled` 内部处理；取消不需要诊断（用户主动取消，不是失败）。
* ⚠ 对比 `JobQueueService.cancel`（用户点取消、任务还没被领走的路径）：
  那条路径的收尾文案是 `"排课任务已取消"`、状态也是 `"idle"` —— **两处文案逐字相同**，
  这是刻意的对外契约一致。

**② 失败分支（第 130-144 行）**

```java
if (request.error() != null && !request.error().isBlank()) {
    boolean retryable = Boolean.TRUE.equals(request.retryable());
    boolean recorded = queueService.fail(jobId, request.jobToken(), request.error(),
            request.solverStatus(), retryable);
    out.put("accepted", false);
    out.put("failed", recorded);
    out.put("requeued", recorded && retryable);
    if (recorded) { diagnosisHook.onJobFailed(jobId); }
    return out;
}
```

* **判据是 `error` 非空**，不是 `cancelled`（已先判）也不是 `!retryable`。
  与 `JobResultRequest.error` 的 javadoc「非空表示失败」严格对应。
* `accepted` 在失败分支里**恒为 false** —— 失败不是"被采纳的结果"。
  这个字段的语义是"有没有落一版课表"，不是"请求处理成功没有"。
* `requeued` 是**派生字段**：`recorded && retryable`。它告诉 worker
  "这一单会不会被别人再做一遍"，但**真实结果还取决于 `attempt < max_attempts`**
  （见 `ScheduleJobMapper.fail` 的 `CASE WHEN`）—— 所以 `requeued=true`
  只是一个"意图"，不是承诺。⚠ 读的时候不要把它当成"一定回到队列了"。
* **失败后顺手做浅诊断**（`DiagnosisHook.onJobFailed`）：注释写明
  "这样用户在任务列表里点开就能看到'为什么失败'"。
* ⚠ `if (recorded)` 同样重要：token 失效（被接管）时不诊断 ——
  否则会给一个**正在被新 worker 求解**的任务落一份"失败诊断"。

**③ 成功分支（第 146-167 行）**

```java
if (request.entries() == null || request.entries().isEmpty()) {
    throw BusinessException.badRequest("结果里既没有 entries 也没有 error —— worker 应当二选一");
}
JobResultWriter.Persisted persisted = resultWriter.persistIfStillOwner(...);
if (persisted == null) {
    log.warn("结果被丢弃（任务已被接管）job={}", jobId);
    out.put("accepted", false);
    out.put("reason", "任务已被接管，结果已丢弃");
    return out;
}
out.put("accepted", true);
out.put("version_id", persisted.versionId());
out.put("version_no", persisted.versionNo());
out.put("entry_count", persisted.entryCount());
resultWriter.settle(jobId, persisted);   // 事务之外
return out;
```

* 第 146-150 行是**唯一一个会抛 400 的地方**：既没有明细也没有错误。
  注释写明"这是 worker 的 bug，但别让它污染任务状态" ——
  ⚠ 注意抛异常意味着**事务上下文什么都不做**：任务保持 `running`，
  租约到期后被接管。这是刻意的（"worker 的 bug 不该由 scheduling 猜一个状态"）。
* 第 155-160 行：**`accepted=false` 不是错误**。响应仍是 HTTP 200，
  只多一个 `reason` 字段给人看。worker 侧据此只记一条日志（见 `JobRunner` 第 102-104 行）。
  ⚠ **为什么它不是错误**：被接管是**设计内的正常路径**（worker 崩溃后旧 worker 复活、
  网络分区后两个 worker 都以为自己该交结果），如果把它当错误，
  worker 就会重试提交、刷错误日志、甚至告警 —— 而正确的动作是"什么都不做"。
* 第 161-164 行的三个字段与 `JobResultWriter.Persisted` 一一对应。
* 第 166 行 `settle` 在 `persistIfStillOwner` **之后、且只有成功才调** —— 见 5b.1 的三条理由。

#### 三个返回语义（worker 侧必须区分的，javadoc 第 103-110 行）

| 响应 | 含义 | worker 该怎么做 |
|---|---|---|
| `accepted=true` | 结果已被采纳（版本已落库） | 记一条 info |
| `accepted=false` | **结果被丢弃**（任务已被接管）—— **不是错误** | 不重试、不报错，记日志即可 |
| `failed=true` | 失败已记录；`requeued=true` 表示已退回队列 | 不做任何事，等下一次领单（可能是别的 worker） |

### 5b.3 `JobController` —— 对外的 5 个任务接口

**谁调它**：前端 `ScheduleGenerate.tsx` 的**任务列表与进度**（P3 新增）。
**它调谁**：只调 `JobQueueService` 与两个静态工厂（`JobResponse.of` / `JobEventResponse.of`）。
URL 前缀 `/api/schedule/jobs`（Vite 分流到 8083）。

**类注释第 21-29 行说明了"为什么需要它"**：P1/P2 的排课状态只有一行组织级状态
（`scheduling_state`），它能回答"现在在跑吗/完成了吗"，但回答不了
「我排第几」「上次为什么失败」「能重试吗/能取消吗」。有了任务队列，这些都有据可查。

| 接口 | 方法 | 做什么 |
|---|---|---|
| `GET /api/schedule/jobs` | `list` | 按 `status`（可选）筛选 + 分页；每项都带 `queue_position` 与 `lease_expired` |
| `GET /api/schedule/jobs/{jobId}` | `detail` | 单项详情（同一个 `toResponse`） |
| `POST /api/schedule/jobs/{jobId}/retry` | `retry` | 人工重试（只对失败/已取消有效） |
| `POST /api/schedule/jobs/{jobId}/cancel` | `cancel` | 取消（pending 立刻终结 / running 打标记） |
| `GET /api/schedule/jobs/{jobId}/events` | `events` | 事件时间线 |

#### `list`（第 54-63 行）：分页 + 排队位置

```java
long organizationId = requirePrincipal(principal).organizationId();
PageResponse<ScheduleJobEntity> page = queueService.listByPage(organizationId, status, query);
List<JobResponse> items = page.items().stream().map(job -> toResponse(organizationId, job)).toList();
return PageResponse.of(items, page.total());
```

* `PageQuery query` 是**直接作为方法参数**的（record 构造器绑定，见第 1 册 `PageQuery`），
  所以页码/条数/关键字/排序的归一化都自动做了。
* **先查 Entity 页、再逐条转 Response**：不是 N+1 查询吗？不是 ——
  每条只多做两件**纯内存 + 一次 count 查询**的事（`queuePosition` 与 `isLeaseExpired`）。
  ⚠ 但严格说 `queuePosition` 确实是**每行一次 count 查询**（见下），
  一页 20 条就是 20 次 count。任务表不长、页大小有限，这里选择了"代码简单"。
  改成分页时批量算会更快 —— 但那是优化，不是 bug。
* `PageResponse.of(items, page.total())` 保留**过滤后的总数**（`total` 来自
  `listByPage`，不受当前页影响），这是第 1 册里 `PageResponse` 的既定语义。

#### `toResponse`（第 113-117 行）：两个派生字段的装配点

```java
long position = "pending".equals(job.getStatus())
        ? queueService.queuePosition(organizationId, job.getId()) : 0;
return JobResponse.of(job, position, queueService.isLeaseExpired(job, UtcTimes.now()));
```

* **不是 pending 的任务不查排队位置**（短路成 0）：它要么在跑、要么已结束，
  "前面还有几个"没有意义。这省掉了一次 count 查询。
* `UtcTimes.now()` 是**服务端时间基准**（UTC、截断到秒），
  传给 `isLeaseExpired` 而不是让前端自己比 —— 见下面的 ⚠。

> ⚠ **`queue_position` 与 `lease_expired` 为什么是派生字段、不落库**（`JobResponse` 的
> javadoc 第 8-21 行给了三条，逐条展开）：
>
> **① `queuePosition`** —— "我前面还有几个"。它的口径**必须与领单完全一致**
> （都是 `ORDER BY id`，见 `ScheduleJobMapper.lockNextClaimable` 的注释），
> 否则显示的名次会是错的。如果存成列，就得在每次领单/取消/重试时维护它，
> 任何一处漏改都会让名次长期错位 —— 而它本来就只是一个 count。
> ⚠ **实现上的一个边界**：`JobQueueService.queuePosition` 的 count 条件只有
> `status='pending'` 与 `id < jobId`，**没有按 `organization_id` 过滤**
> （尽管方法签名收了 `organizationId`）。在当前"任务表按组织天然隔离、
> id 全局递增"的前提下，结果与按组织过滤相同；但**多组织的待办交错时，
> 这个数字会包含别组织的任务**。这里按代码事实记录，不推测作者意图。
>
> **② `leaseExpired`** —— 租约是否已过期。它**每时每刻都在变**，所以不能存成列：
> 存了就会有一个"库里的值和真实情况不一致"的窗口
> （写入瞬间是对的，下一秒就过期了，但列里还是 false）。
> 实现是 `"running".equals(status) && (leaseUntil == null || leaseUntil.isBefore(now))`。
>
> **③ `stuck`**（javadoc 里叫这个名字，**record 里没有这个组件**）：
> "`running` 但租约过期 = 持有者可能已经死了"，界面据此提示"卡住了，等一下会被自动接管"。
> ⚠ 本册只按注释记录它的**意图**；字段本身在当前代码里不存在，
> 前端也拿不到它。不要以为响应里有 `stuck`。
>
> ⚠ **为什么要有服务端算的 `leaseExpired`、而不让前端自己比 `lease_until` 与 `new Date()`**：
> 这个判断需要**服务端的时间基准**，而客户端的时钟可能差几分钟，
> 用它算会得出**相反**的结论（客户端快 5 分钟 → 一个健康的任务被渲染成"卡住了"）。
> 这也解释了为什么 `leaseUntil` 仍然返回 —— 它是给人看的原始值，
> 而"是不是过期"这个**结论**必须由服务端给。

#### `detail`（第 65-70 行）

一行：`toResponse(organizationId, queueService.requireJob(organizationId, jobId))`。
租户校验在 `requireJob` 里（查不到/不属于本组织 → 抛异常）。

#### `retry`（第 78-83 行）

```java
return toResponse(organizationId, queueService.retry(organizationId, jobId));
```

**它自己没有任何逻辑**，全部判据在 `JobQueueService.retry` →
`ScheduleJobMapper.requeue` 的 `WHERE ... AND status IN ('failed','cancelled')`：
`requeue != 1` 就抛 `BusinessException.badRequest("只有失败或已取消的任务可以重试")`。

> ⚠ **为什么只对失败/取消有效**（javadoc 第 72-77 行）：
> * **成功完成的任务不能重试 → 那会凭空多出一版课表。**
>   完成的任务已经有 `version_id` 了；把它重置为 pending 会**再跑一遍求解、
>   再落一版** —— 而且新版本与旧版本没有任何区别（同样的快照、同样的规则），
>   纯粹是数据垃圾，还会把版本号往上顶。
> * **正在跑 / 排队的也不能重试** —— 它本来就会跑。
>   重置它只会把 `attempt` 清零、把已经投入的求解工作丢掉。
>
> `requeue` 的 SQL 还会顺手重置一串字段（`attempt=0`、`progress=0`、
> `cancel_requested=FALSE`、`last_error=NULL`、`worker_id=NULL`、
> `lease_until=NULL`、`started_at/finished_at=NULL`）—— 语义是"当成一个全新的任务重新入队"。

#### `cancel`（第 96-101 行）

同样是薄封装，逻辑在 `JobQueueService.cancel`。**两条路径**（javadoc 第 88-94 行）：

| 情形 | 行为 |
|---|---|
| 还没被领走（`pending`） | **立刻终结**为 `cancelled`（`cancelPending`），并收尾对外状态为 `"idle"` —— worker 根本不会看到它 |
| 正在跑（`running`） | 只打 `cancel_requested = TRUE` 标记；worker 在**下次心跳**时看到并收手 |

已结束（`done`/`failed`/`cancelled`）的任务取消会 400：`"该任务已经结束，无法取消"`。

> ⚠ **正在跑的最坏情况要等一次求解跑完**（javadoc 第 93-94 行，并与 `JobRunner` 互指）：
> 求解调用本身**无法中断**，所以取消只能做到"求解前检查 + 求解后丢弃"。
> 前端不能承诺"点取消立刻停"。
>
> ⚠ `JobQueueService.cancel` 里还有一段与本节主线相关的实测坑（原文）：
> "**取消一个还没开始的任务同样是'终态'，必须收尾对外状态 ——
> 否则这所学校会一直显示'正在排课'，发不起新任务。**
> （与失败路径是同一类问题，只是更容易被忽略：取消看起来'什么都没发生'。）"
> 这是"三处终态都必须收尾对外状态（失败/取消/完成）"这条规矩的第二个落点。

#### `events`（第 104-111 行）

```java
queueService.requireJob(organizationId, jobId);          // 先确认任务属于本组织
return queueService.events(jobId).stream().map(JobEventResponse::of).toList();
```

**先 `requireJob` 再取事件**，注释写明原因：**否则任何人都能看别人的事件流**。
⚠ 注意 `queueService.events(jobId)` 本身**只按 jobId 查**，不做租户过滤 ——
所以第 109 行那个"看起来什么都没做"的调用**就是这里的鉴权**，
删掉它就是一个越权读取漏洞。这种"用一次查询做鉴权"的写法很容易在重构时被当成死代码删掉。

**返回的是裸数组**（`List<JobEventResponse>`）而不是 `PageResponse` —— 与第 1 册里
"Python 原版所有列表接口都是裸数组"的背景不冲突：这是 P3 新增接口，没有影子对比对象，
事件条数天然有限（一个任务几条到几十条），前端一次性拉完画时间线。

#### `requirePrincipal`（第 119-124 行）

`principal == null` → 抛 `BusinessException.unauthorized("请先登录")`。
理论上安全链已经拦住了未认证请求，这里是**第二道网**（对应 `SchedulingSecurityConfig`
里那句"已认证但权限不够时的安全网**真实检查写在代码里**"）。

**关于 SSE**（类注释第 31-36 行）：方案 §13.2 给 `/events` 标注的是「（SSE）实时进度，
替代现在的 1 秒轮询」并注明**可选**。本期先返回**普通 JSON 事件列表**。
理由：SSE 的价值在于"长时间盯着看"，而排课任务通常几十秒就结束，
为它引入长连接 + 断线重连 + 代理超时的复杂度不划算。

### 5b.4 `DiagnosisHook` —— 失败后顺手补一份浅诊断

**谁调它**：`InternalJobController.result()` 的失败分支（**唯一**调用点）。
**它调谁**：`DiagnosisService.diagnoseWithStatus(...)`、`ScheduleJobMapper.selectById`。

#### `onJobFailed(long jobId)`（第 33-46 行）

```java
try {
    ScheduleJobEntity job = jobMapper.selectById(jobId);
    if (job == null) { return; }
    diagnosisService.diagnoseWithStatus(job.getOrganizationId(), job.getJobToken(), null,
            false, job.getSolverStatus());
} catch (Exception e) {
    log.warn("任务失败后的诊断出错（不影响任务状态）: job={} {}", jobId, e.getMessage());
}
```

逐点：

* **整个方法体包在 `try/catch(Exception)` 里，只 warn 不上抛** ——
  注释写明"诊断出错不影响任务本身的状态"。这是刻意的：
  此时任务**已经**被标记为失败/退回队列（`queueService.fail` 已提交），
  让诊断的异常冒出去会让 worker 收到 500、以为回写失败而重试 —— 那会重复诊断。
* 第三个参数传 `null`（`jobToken` 之外的参数，含义见 `DiagnosisService` 的签名），
  第四个参数传 `false` —— ⚠ **这里按代码事实记录，不推测这俩参数的业务含义**：
  本册只负责"它们被固定传成 `null` / `false`"这个事实。
* **`job.getSolverStatus()` 必须带上**（⚠ 注释原文）：
  "不然'因为规则太紧而失败、静态检查又没发现问题'的任务会被诊断成 `kind=OK`
  —— **一个失败的任务，诊断却说一切正常。**"
* **只做浅诊断**（静态检查，毫秒级）：深诊断要解好几次、几十秒，
  而此刻任务刚失败、用户可能正盯着列表，不该让它再等 ——
  贵的那部分留给用户按需触发（`GET /api/schedule/diagnosis?deep=true`）。

**为什么它是独立的一个类、而不是把这三行写进 `InternalJobController`**（类注释第 11-13 行）：
控制器只该管"协议"，"失败之后要做什么"属于**业务编排**；
而且这一点将来会变（比如 P4 要在失败后通知助手），变的时候不该动协议。

> ⚠ 与 `JobResultWriter.settle` 对照：`DiagnosisHook` 也在**事务之外**被调用
> （它由 `InternalJobController` 在 `queueService.fail` 返回后调用），
> 但它的理由不是"产能"或"对外状态"，而是"诊断很慢，不该拖住回写路径"。

### 5b.5 四个 DTO / 请求体（表格批量说明）

> 本节按规范第 3 节第 2 条**降级为表格说明**（纯 record，无逻辑分支，逐行展开价值低）。
> 其中 `JobResultRequest` 的"失败 vs 取消"与 `JobClaimResponse` 的"一次带齐"是协议核心，
> 已在 5b.2 / 5b.6 展开讲。

#### `JobResultRequest`（50 行，`POST /internal/jobs/{id}/result` 的请求体）

| 字段 | 类型 | 说明 |
|---|---|---|
| `jobToken` | `String`，`@NotBlank(message="Field required")` | **必填**。校验不过 → 400（文案与 Python 的 Pydantic 对齐，见第 1 册第 0.3 节） |
| `solverStatus` | `String` | `OPTIMAL` / `FEASIBLE` / `INFEASIBLE` / `UNKNOWN` |
| `modelFingerprint` | `String` | 溯源指纹③，由 worker 交回 |
| `objectiveValue` | `Long` | 目标值（软约束罚分），判定"行为等价"用的（§6 ②） |
| `entries` | `List<TimetableEntry>` | 成功时的明细；失败时为 null |
| `error` | `String` | **非空表示失败**（求解异常、无解等） |
| `cancelled` | `Boolean` | worker 察觉用户取消 → 交回取消 |
| `retryable` | `Boolean` | 失败是否值得重试 |

三条关键约定：

1. **一个请求同时表达成功与失败**（`error` 非空即失败）——
   worker 侧只有一条回写路径，不会出现"失败了但忘了调失败接口"。
2. ⚠ **`entries` 直接复用 solver-core 的 `TimetableEntry` record**，不在这里另建一个
   形状相同的 DTO —— 那会出现两个"看起来一样"的类型，改一个忘一个。
   这与 worker 侧 `ClaimedJob` "刻意重复"的取舍**方向相反**，原因也写得很清楚：
   `TimetableEntry` 属于**求解内核的领域类型**（与 `ScheduleInput`/`ConstraintRule` 同类），
   两边共享是正确的；而"信封"（谁领的、租约多长）属于各自服务的协议。
3. ⚠ **`cancelled` 与 `error` 是两个字段**（javadoc 第 37-39 行）：
   "失败是'这次没排出来'（可能该重试），取消是'用户不想排了'（**绝不该重试**）。
   混成一个会把用户主动取消的任务重新拉起来跑。"
   **为什么不能合成一个 `error` 字符串**：`fail` 的 SQL 里有一条
   `CASE WHEN retryable AND attempt < max_attempts THEN 'pending' ELSE 'failed'` ——
   也就是说**失败可以被退回队列重做**。取消若走这条路，用户点一次取消、
   任务反而又被拉起来跑一遍（可能反复）。这是"两个字段"的全部理由，
   也是 §5.8 "三个刻意的设计决定"里的第 3 条。
4. ⚠ **`retryable` 由 worker 判断**，不是 scheduling 猜的：
   只有 worker 才知道失败的性质 —— 进程被杀/网络抖动 → 该重试；
   `INFEASIBLE`（**证明**无解）→ 重试多少次都一样。

#### `JobClaimResponse`（40 行，`POST /internal/jobs/claim` 的响应体）

| 字段 | 说明 |
|---|---|
| `jobId` / `jobToken` | 任务身份。**token 是每次领单新生成的**（48 位十六进制，对应 Python 的 `secrets.token_hex(24)`），是所有回写的通行证 |
| `organizationId` / `snapshotId` | 租户与快照 id（worker 只用它们做日志与溯源，不用来查库） |
| `snapshotFingerprint` / `ruleSetHash` | 两个溯源指纹（③ model_fingerprint 由 worker 自己产生） |
| `rules` | `List<ConstraintRule>` —— **当时那套规则**（按 `ruleSetHash` 取出的快照） |
| `input` | `ScheduleInput` —— **冻结的输入快照**（快照表 payload 转换而来） |
| `attempt` / `maxAttempts` | 本次是第几次尝试 / 上限 |
| `leaseSeconds` / `heartbeatSeconds` | 租约时长（默认 300）与心跳间隔（15）—— **由服务端下发**，worker 不自己配 |
| `takeOver` | 这一单是不是**接管**来的（原持有者的租约过期了）。为 true 时值得在 worker 侧打一条日志 |

> ⚠ **"一次带齐"的两个好处（类注释第 14-21 行，都是刻意的）**：
> **① worker 不需要碰数据库** —— 与方案 §2.2 的「拥有的表：无」一致，铁律 2 在 P3 仍然成立。
> 代价是每次领单多传一份快照，而那是**几 KB 的 JSON**，可以接受。
> **② worker 拿到的是"当时"的输入与规则** —— 任务排队期间教务数据或规则被改了
> 也不影响这次求解，而且**事后可复现**。
> 第 ② 条是"任务队列"这个设计真正的价值：求解结果永远能追溯到它当时看到的世界，
> 这也是三个溯源指纹存在的意义。

#### `JobResponse`（58 行，任务列表/详情的一项）

| 字段 | 来源 | 说明 |
|---|---|---|
| `id` / `status` | 实体列 | `pending`/`running`/`done`/`failed`/`cancelled` |
| `ruleSetHash` / `snapshotId` | 实体列 | 这版课表的输入溯源 |
| `attempt` / `maxAttempts` | 实体列 | 第几次 / 上限 |
| `progress` | 实体列 | 0-100，由**心跳**写入 |
| `cancelRequested` | 实体列 | 用户点了取消、等 worker 收手 |
| `workerId` | 实体列 | 谁在做（多副本时靠它区分） |
| `lastError` / `solverStatus` | 实体列 | 上次为什么失败 |
| `objectiveValue` / `versionId` / `entryCount` | 实体列 | 结果摘要 |
| `queuePosition` | **派生**（`JobController.toResponse` 算） | 仅 `pending` 有意义；`of` 里对非 pending **返回 null** |
| `leaseExpired` | **派生**（`isLeaseExpired` 算） | running 且租约已过 → 持有者大概率已死 |
| `leaseUntil` / `createdAt` / `startedAt` / `finishedAt` | 实体列 | 时间轴 |

⚠ **`queuePosition` 在 `of` 里被判成 null，而 `JobController` 传的是 0**：
`of(..., "pending".equals(job.getStatus()) ? queuePosition : null, ...)` ——
所以直接调 `of` 拿到的非 pending 项是 `null`，走 `toResponse` 则是 `0`。
两条路各写了一遍同样的判断，**结果一致但没有共用**。
读的时候不要以为 `JobResponse.of` 单独用时会给出 `0`。

#### `HeartbeatRequest`（17 行，`POST /internal/jobs/{id}/heartbeat` 的请求体）

| 字段 | 类型 | 说明 |
|---|---|---|
| `jobToken` | `String`，`@NotBlank(message="Field required")` | 必填；不匹配 → `ok=false` |
| `progress` | `Integer` | 0-100。注释：**OR-Tools 不直接给百分比，worker 会用"已耗时 / 时限"估算** |

⚠ **`progress` 是包装类型 `Integer` 而不是 `int`**：请求里没带它时会是 null，
`InternalJobController` 用 `request.progress() == null ? 0 : ...` 兜住。
如果声明成 `int`，遇到 JSON 里的 null 会在**反序列化阶段**抛异常
（见第 1 册 `PageQuery` 坑 1 —— 同类问题在这个项目里出现过两次）。

#### `JobEventResponse`（28 行，`GET /api/schedule/jobs/{id}/events` 的每一项）

| 字段 | 说明 |
|---|---|
| `id` / `event` | 事件类型（`claimed`/`takeover`/`completed`/`failed`/`cancelled`/`retried` 等，常量在 `ScheduleJobEventEntity`） |
| `workerId` / `attempt` | 谁、第几次 |
| `detail` | 人看的一句中文（如 `"接管：上一个持有者的租约已过期（attempt 2）"`） |
| `createdAt` | 事件时间 |

它是**结构化的状态迁移记录，不是日志**（javadoc 第 8-14 行）。前端把它画成时间线，
用户就能回答三个问题：

* 「这个任务为什么跑了 3 次」→ 看 `takeover` 事件
* 「求解到底卡在哪」→ 看 `heartbeat` 事件的**间隔**（断了就是卡了）
* 「谁做的」→ 看 `worker_id`

`of(ScheduleJobEventEntity)` 是纯字段搬运，没有任何转换逻辑。

## B 组 · `orbit-solver-worker`：独立求解进程

### 5b.6 `SolverWorkerApplication` —— 独立进程的入口

**它是一个 Spring Boot 应用**（`@SpringBootApplication`），但**没有数据库连接**：
`pom.xml` 刻意不依赖 `orbit-common` / `orbit-academic` / `orbit-scheduling` / MySQL /
MyBatis / Flyway（pom 第 25-33 行的注释：*"用依赖隔离强制'求解进程不碰数据库'这条架构约束"*）。
它只通过 HTTP 与 scheduling 通信。

**三个注解，各有作用**：

| 注解 | 作用 | 不写会怎样 |
|---|---|---|
| `@SpringBootApplication` | 组件扫描 + 自动配置 | —— |
| `@EnableScheduling` | 让 `@Scheduled` 生效 | ⚠ 类注释：**"轮询循环靠 `@Scheduled` 驱动"** —— 没有它 `WorkerLoop.poll()` 一次都不会被调用，进程**静默地什么都不做**（照样能启动、不报错） |
| `@EnableConfigurationProperties(WorkerProperties.class)` | 把 `orbit.worker.*` 绑到 `WorkerProperties` | ⚠ 类注释：**"不写它的话 `orbit.worker.*` 一个字段都不会生效（而且不报错）"** |

`main` 就是一行 `SpringApplication.run(SolverWorkerApplication.class, args)`。
端口是 8084（`application.yml`），**不对外提供业务接口**，只暴露 actuator
供 Prometheus 抓取（`health,info,metrics,prometheus`）。

**为什么值得单独一个进程**（类注释引 §2.3，说这是"拆分理由最强"的一条）：
求解是 CPU 密集的长任务（**160 班实测吃满 CPU 12-60 秒、峰值 1.8 GB**）。
与 Web 请求放在一起时，一次排课就能把接口响应拖慢，而且进程重启会
**凭空丢掉正在跑的任务**。拆开之后：

* Web 服务不受求解影响（可以用很小的堆）
* worker 崩了，租约到期后任务被接管，**不会有任务凭空消失**
* worker 可以按 CPU 核数独立扩容（它不持有任何状态）

### 5b.7 `WorkerProperties` —— 只有"怎么找到 scheduling"与"我是谁"

**谁用它**：`SchedulingClient`（baseUrl + secret + id）、`JobRunner`（timeLimit + numSearchWorkers）、
`WorkerLoop`（concurrency + pollInterval + timeLimit）。
`@ConfigurationProperties(prefix = "orbit.worker")`，是一堆 getter/setter 的**可变类**
（不是 record —— `@ConfigurationProperties` 的绑定需要 setter 或构造器绑定）。

| 属性 | 默认值 | 说明 |
|---|---|---|
| `schedulingBaseUrl` | `http://127.0.0.1:8083` | ⚠ P3 还没有网关，直连 scheduling；上网关后应改成网关地址 |
| `secret` | `orbit-dev-worker` | 与 `InternalJobController` 的 `expectedSecret` 对应（**两边默认值相同才能开箱通**） |
| `id` | `"worker-" + ProcessHandle.current().pid()` | ⚠ 见下面 |
| `concurrency` | `1` | 本进程最多同时求解几个（真正的全局上限在 scheduling 侧的容量槽位） |
| `pollIntervalMs` | `2000` | 没活干时多久轮询一次 |
| `timeLimitSeconds` | `60` | 单次求解时间上限，**对应 Python 的 `time_limit=60`** |
| `numSearchWorkers` | `2` | CP-SAT 的搜索线程数 |

> ⚠ **`id` 的默认值带进程号，注释写明"不能是固定字符串"**：
> 它会写进 `schedule_jobs.worker_id` 与事件流，多副本部署时
> 「这一单是谁做的 / 谁被接管了」全靠它区分 —— 两个副本用同一个 id
> 就会互相冒充，接管排查彻底失效。
> ⚠ 注意默认值的求值发生在**字段初始化**时（`ProcessHandle.current().pid()`），
> 配置里 `id` 留空（`orbit.worker.id:` 空值）会绑定成空串而**不是**走这个默认值 ——
> `application.yml` 里干脆没有 `id` 这一项，就是为了让它走代码默认值（注释也这么写了）。

> ⚠⚠ **`application.yml` 里有一段"静默失败"的实测记录**（第 30-34 行原文）：
> "**键名必须与 `WorkerProperties` 的字段一一对应。** Spring 默认**静默忽略**
> 认不出来的键 —— 写错了不报错，只是悄悄用默认值。这个文件原来的占位版本就踩了这个坑：
> 里面写的是 `poll-interval-seconds` / `max-concurrent-solves`，
> 而实际的属性名是 `poll-interval-ms` / `concurrency`，**一个都没绑上**。"
> 这条与 `@EnableConfigurationProperties` 那条是**同一类问题的两个面**：
> 配置绑定错误在这个项目里从来不报错，只会静默用默认值。

配置里**没有任何数据源相关项**（无 `spring.datasource.*`）—— 类注释：
"所以它的配置里只有'怎么找到 scheduling'与'我自己是谁'，没有数据源。"

### 5b.8 `SchedulingClient` —— 三个内部接口的客户端

**谁调它**：`WorkerLoop`（`claim`）与 `JobRunner`（`heartbeat`/`submitResult`/`submitFailure`/`submitCancellation`）。
**它调谁**：HTTP。**它不认识数据库**。

#### 构造器与 `RestClient`（第 53-59 行）—— 本册最重的一个 ⚠

```java
public SchedulingClient(RestClient.Builder builder, WorkerProperties properties) {
    this.properties = properties;
    this.http = builder
            .baseUrl(properties.getSchedulingBaseUrl())
            .defaultHeader("X-Worker-Secret", properties.getSecret())
            .build();
}
```

* **注入的是 `RestClient.Builder`（Boot 自动配置提供的 bean），不是自己 new 一个**。
  `defaultHeader` 把共享密钥**装在客户端上**，所以后面每个请求都不用再传
  —— 三点好处：不会漏（新增方法不可能忘）、不会写错头名、密钥不出现在业务代码里。
* `.baseUrl(...)` 来自配置，上网关后改一行配置即可。

> ⚠⚠ **为什么必须注入 Boot 配置好的 `RestClient.Builder`，不能用静态工厂 `RestClient.builder()`**
> （javadoc 第 39-52 行 + pom 第 38-54 行的注释，两处说的是同一件事）：
>
> **差别不在"能不能发请求"，而在消息转换器里的 `ObjectMapper`。**
> 静态工厂造出来的是**裸的**，不带 `spring.jackson.*` 的配置；
> 而 `application.yml` 里配的是 `property-naming-strategy: SNAKE_CASE`。
> 于是：scheduling 发的是 snake_case（`job_token`、`heartbeat_seconds`），
> worker 的 record 字段是 camelCase（`jobToken`、`heartbeatSeconds`）→ **匹配不上** →
> 字段全是 null → 而 `ClaimedJob` 里有 `int leaseSeconds` / `int heartbeatSeconds` /
> `int attempt` 这些 **primitive** 字段 → 传 null 进去直接抛
> **`Cannot map 'null' into type 'long'`**。
>
> **为什么这个坑特别难查**（原文）："服务能启动、能连上、能领到任务，
> **只是读不懂响应**"。日志里只会看到
> `Error while extracting response for type [ClaimedJob]`（这正是 `WorkerLoop` 第 78 行
> 那段"必须打整个异常而不是 getMessage()"注释的来历）。
>
> **另一半原因在依赖上**（pom 第 38-58 行）：`RestClient.Builder` 这个 bean 由
> **`spring-boot-restclient`** 提供，而 **`spring-boot-starter-web` 不包含它**
> （注释：Boot 4 把自动配置按模块拆开了）。少了那个依赖的后果是两级：
> ① 构造注入 `RestClient.Builder` → **启动直接失败**
> `"required a bean of type 'RestClient$Builder' that could not be found"`；
> ② 于是改成静态工厂 → 能启动了，然后掉进上面的反序列化坑。
> **所以 `spring-boot-restclient` 这个依赖"不能省"。**
>
> ⚠ 还有第三层原因写在 `application.yml` 第 15-26 行：Spring Boot 4 用的是 **Jackson 3**
> （包名 `tools.jackson`），它**默认对"primitive 字段收到 null"直接抛异常**，
> 而 scheduling 侧用 Jackson 2。所以配置里显式写了
> `fail-on-null-for-primitives: false` 来"按宽容对齐 Jackson 2 的行为"。
> 换句话说：**注入正确的 Builder** 解决的是"snake_case 能不能匹配上"，
> **这条配置**解决的是"匹配上之后 null 能不能进 primitive" ——
> 两个不同的问题，两个都要有。

#### `public ClaimedJob claim()`（第 62-78 行）

```java
try {
    return http.post()
            .uri(uri -> uri.path("/internal/jobs/claim")
                    .queryParam("worker_id", properties.getId()).build())
            .retrieve()
            .body(ClaimedJob.class);
} catch (RestClientResponseException e) {
    log.warn("领单失败: {} {}", e.getStatusCode(), e.getStatusText());
    return null;
} catch (ResourceAccessException e) {
    log.debug("scheduling 暂不可达: {}", e.getMessage());
    return null;
}
```

* `worker_id` 走 `queryParam`（对应服务端 `@RequestParam`）；POST **没有 body**。
* ⚠ **注释："204 No Content → RestClient 返回 null，不需要额外的 onStatus 处理"** ——
  这是 `.retrieve()` 的默认行为：2xx 且无 body → 返回 null。所以
  **"没活干"和"出错了"在返回值上是同一个 null**，调用方（`WorkerLoop`）不必区分
  —— 两者的正确反应都是"等下一轮"。
* **两类异常分开记，级别也不同**：
  * `RestClientResponseException`（4xx/5xx）→ `log.warn`（**对方说话了，但说得不对**，
    比如密钥错了返回 401 —— 这是必须有人看到的信号）。
  * `ResourceAccessException`（连不上/超时）→ `log.debug`（**注释原文：
    "scheduling 暂时不可达（重启中 / 网络抖动）—— 静默等下一轮，别刷屏"**）。
    每 2 秒轮询一次，如果这里用 `warn`，scheduling 重启 30 秒就会刷出 15 行噪音。
  * ⚠ 两者都 return null，**不做重试、不做退避** —— 因为 `@Scheduled` 的下一轮
    2 秒后就到，重试逻辑放在这里纯属重复。
* ⚠ **5xx 与"没活干"在 worker 侧无法区分**（都是 null）：
  如果 scheduling 一直 500，worker 会一直安静地"没活干"。
  这是刻意的取舍（不想为内部接口造一套错误分类），代价是
  **scheduling 挂了但状态良好（能连上、返回 500）时，worker 看起来完全正常**。

#### `record HeartbeatResult(boolean ok, boolean cancelRequested)`（第 81-82 行）

一个只有两个 boolean 的小 record，把"响应是一个 Map"收成类型安全的两个字段。
**为什么服务端用 `Map`、客户端用 record**：服务端返回的是手写 `LinkedHashMap`，
客户端解析成 `Map` 再抽字段（`Boolean.TRUE.equals(body.get("ok"))`）——
这样**对端多返回一个字段不会导致解析失败**（对内部协议来说这是好事）。

#### `public HeartbeatResult heartbeat(long jobId, String jobToken, int progress)`（第 84-104 行）

```java
Map<?, ?> body = http.post()
        .uri("/internal/jobs/{id}/heartbeat", jobId)
        .body(Map.of("job_token", jobToken, "progress", progress))
        .retrieve().body(Map.class);
if (body == null) { return new HeartbeatResult(true, false); }
return new HeartbeatResult(
        Boolean.TRUE.equals(body.get("ok")),
        Boolean.TRUE.equals(body.get("cancel_requested")));
} catch (RuntimeException e) {
    log.warn("心跳失败（按仍然有效处理）: job={} {}", jobId, e.getMessage());
    return new HeartbeatResult(true, false);
}
```

> ⚠⚠ **心跳失败为什么不能当成"被接管"**（注释第 98-100 行原文）：
> "网络抖一下就把任务丢掉太草率了。返回 `ok=true` 让它继续跑；
> **真正的接管会在交回结果时被 token 挡住**。
> （只有 scheduling 明确说 `ok=false` 才是真的失效。）"
>
> 逐条展开这个设计：
> * **误判的代价不对称。** 把"网络抖动"误判为"被接管" → 一个正在正常求解的任务被
>   本进程主动放弃 → 结果不交回 → 租约到期 → 被接管重做 → **白烧一次 12-60 秒的 CPU**。
>   反过来（把"真被接管"当成"还活着"）→ 求解继续跑完 → 交回结果 →
>   `job_token` 对不上 → `accepted=false` → **结果被丢弃，后端没有任何损伤**。
>   两边的代价差一个数量级，所以选择**偏向"继续跑"**。
> * **为什么"结果会被 token 挡住"这句话是可信的**：所有回写 SQL 都带
>   `AND job_token = ?`（`complete` / `fail` / `markCancelled` / `heartbeat`），
>   而接管时 `markRunning` 会**换一个新 token**。所以旧持有的提交**必然写不进去**。
>   这就是 §5.8 说的"`job_token` 栅栏"。
> * `catch (RuntimeException)` 捕得很宽（含网络异常、解析异常）—— 同样是为了
>   "宁可继续跑"。⚠ 代价：**连"401 密钥配错了"也会被当成"心跳正常"**，
>   此时 worker 会跑到求解结束、交回结果时才发现问题。这是可接受的
>   （`submitResult` 不受这个 catch 影响，会真的报错）。
> * `body == null` 也返回 `(true, false)` —— 与"没活干"同一个理由：
>   2xx 无 body 是正常状态。⚠ 但心跳按理总该有 body，所以这个分支实际上
>   覆盖的是"服务端返回了 200 但体为空"这种异常情况，选择宽容。

#### 四个交回方法（第 107-150 行）

| 方法 | 请求体 | 说明 |
|---|---|---|
| `submitResult(jobId, jobToken, solverStatus, modelFingerprint, objectiveValue, entries)` | `Map.of("job_token", …, "solver_status", …, "model_fingerprint", …, "objective_value", …, "entries", entries)` | 成功交回。**返回原始响应 Map**，由调用方判 `accepted` |
| `submitFailure(jobId, jobToken, error, solverStatus, retryable)` | 一个 `HashMap`（**不是 `Map.of`**） | 失败交回 |
| `submitCancellation(jobId, jobToken)` | `Map.of("job_token", jobToken, "cancelled", true)` | 取消交回（⚠ 见下） |

两个细节值得注意：

* **`model_fingerprint == null ? "" : modelFingerprint`** 与
  **`objective_value == null ? 0 : objectiveValue`**（第 115-116 行）：
  用空串和 0 取代 null。⚠ 这看起来像"随手写"，实际是在**绕开 Jackson 3 的
  primitive-null 严格性**（服务端 `JobResultRequest` 里 `objectiveValue` 是包装类型 `Long`，
  其实能收 null；但 `solverStatus` 等其它字段不能）。**这里按代码事实记录这个三元表达式的行为，
  不推测作者的确切动机** —— 但要知道：**成功路径永远会带上一个 `objective_value`（哪怕是 0）**，
  所以服务端拿到的 0 无法区分"目标值真的是 0"与"worker 没算出来"。
* **`submitFailure` 用手写 `HashMap` 而不是 `Map.of`**：因为 `error` 可能是 null，
  而 `Map.of` **不接受 null 值**（会抛 NPE）。这是 `Map.of` 的一个常见陷阱 ——
  同类写法在本文件里只此一处，改动时不要"顺手统一成 `Map.of`"。
* **`submitCancellation` 只发两个字段**：`job_token` + `cancelled: true`。
  服务端 `InternalJobController.result` 按优先级先判 `cancelled`，所以这两个字段就够了 ——
  它也**不该**带 `error`（带了也会被取消分支先截住）。
* ⚠ **这三个方法都不 catch 异常**（注释第 152 行说得不对——见下）：
  异常会冒到 `JobRunner`。`submitResult` 的异常被 `JobRunner.run` 的
  `catch (RuntimeException)` 兜住；`submitFailure`/`submitCancellation` 由
  `JobRunner.reportFailure` 自己的 try/catch 兜住。
  ⚠ 第 152 行那句 `/** 4xx 时不要抛异常堆栈里塞满 HTTP 细节，留给调用方判断。 */`
  是 `workerId()` 的 javadoc，**与 `workerId()` 的行为对不上**（它只是
  `return properties.getId()`，没有 HTTP 也没有异常）。这是**注释与代码错位**，
  本册按代码事实记录，不编造一个"4xx 处理"。

#### `public String workerId()`（第 153-155 行）

一行：`return properties.getId()`。⚠ 注释与实现错位（见上）。
它在当前代码里**没有任何调用点**（`WorkerLoop` 直接用 `client.claim()`，

### 5b.9 `JobRunner` —— 求解一个任务：起心跳 → 求解 → 交回

**谁调它**：`WorkerLoop` 的线程池（`runner.run(job)`）。
**它调谁**：`OrbitSolver.solve(...)`（求解内核）+ `SchedulingClient` 的四个交回方法。

#### `public void run(ClaimedJob job)`（第 60-113 行）

**三个 `Atomic*` 状态位**（第 62-64 行）：

```java
long startedAt = System.nanoTime();
AtomicBoolean tokenLost = new AtomicBoolean(false);
AtomicBoolean cancelRequested = new AtomicBoolean(false);
AtomicInteger progress = new AtomicInteger(0);
```

* `tokenLost` / `cancelRequested`：由**心跳线程写、主线程读**，所以必须是
  `Atomic*`（或 `volatile`）。⚠ 这里用的是 `AtomicBoolean` 而非 `volatile boolean`，
  但**只用到了单次读写**，没有 `compareAndSet` —— 功能上等价，写法更重一点。
* `progress`：心跳线程**读**它（上报），主线程**写**它（求解结束时置 100）。
  在 60 秒的求解过程中它一直是 0 —— ⚠ **这一点很重要**：类注释说的
  "OR-Tools 不直接给百分比，worker 会用'已耗时 / 时限'估算"（见 `HeartbeatRequest`
  的 javadoc）在当前代码里**没有实现**：`progress.set(100)` 是唯一的写入点。
  所以任务列表里的进度条在求解期间恒为 0、结束时跳到 100。
  **这里按代码事实记录**，不按注释推测一个不存在的估算逻辑。
* `System.nanoTime()` 而不是 `currentTimeMillis()`：只用于**测耗时**
  （单调时钟，不受系统时间调整影响），日志里输出 `elapsedMs`。

**主流程（第 66-113 行）**：

| 阶段 | 行 | 做什么 |
|---|---|---|
| 起心跳 | 66 | `Thread heartbeat = startHeartbeat(job, tokenLost, cancelRequested, progress)` |
| **求解前检查取消** | 68-71 | `if (cancelRequested.get()) { reportCancelled(job); return; }` —— 心跳可能在我们还没开始算时就已经读到了取消 |
| 求解 | 73-75 | `OrbitSolver.solve(job.input(), job.rules(), new SolverSettings(timeLimitSeconds, numSearchWorkers, false))` |
| 收尾状态 | 76-77 | `progress.set(100)`；算 `elapsedMs` |
| **检查 token** | 79-83 | `if (tokenLost.get())` → `log.warn("求解完成但已被接管，丢弃结果")` + return（**不交回**） |
| **求解后检查取消** | 84-87 | `if (cancelRequested.get()) { reportCancelled(job); return; }` |
| 无解分支 | 89-97 | `entries` 空 → `reportFailure(..., retryable = outcome.timedOut())` |
| 交回成功 | 99-104 | `client.submitResult(...)`，然后判 `accepted` 并打一条 info 日志 |
| 异常兜底 | 105-109 | `catch (RuntimeException)` → `reportFailure(job, "求解出错：" + e, null, true)` |
| finally | 110-112 | `heartbeat.interrupt()` |

**四处刻意的细节**：

* **`SolverSettings(..., false)` 第三个参数**：⚠ 按代码事实记录它是 `false`
  （本册不推测这个开关的语义，见 `orbit-solver-core` 的 `SolverSettings`，属第 2 册范围）。
* **`tokenLost` 检查在 `cancelRequested` 之前**（79 行 vs 84 行）：如果两者都为 true，
  优先按"被接管"处理（**什么都不交回**）。理由：此时交回取消也会被 token 挡住
  （`markCancelled` 带 `AND job_token = ?`），不如省一次网络往返 ——
  注释写的就是"结果不会被接受，不必白跑一次网络"。
* **无解的 `retryable = outcome.timedOut()`**（第 92 行）：一行决定重试策略。
  > ⚠ **为什么 `INFEASIBLE` 要标成不可重试**（注释第 91 行 + 类注释第 31-32 行）：
  > `INFEASIBLE` 是求解器**证明**了"在这套输入 + 这套规则下不存在任何可行课表"。
  > 既然如此，**重试多少次结果都一样** —— 输入和规则都是冻结的快照，
  > 没有任何随机性会让第二次变得可行。
  > 标成可重试只会**白烧两轮 12-60 秒的 CPU**（`maxAttempts` 内会被反复领走），
  > 而且会把用户的注意力从"该去改规则/补教师"引开。
  > 反过来，**超时（`timedOut()`）是可重试的** —— 超时只说明"这次时限内没证明出来"，
  > 换个时间、换个搜索路径（CP-SAT 的多线程搜索有随机性）可能就出来了。
  > 这条分支把"证明无解"和"没证明出来"分开了，这正是 `retryable` 这个字段
  > 由 **worker**（而不是 scheduling）决定的理由。
* **异常一律可重试**（第 107-109 行）：注释原文"进程/环境问题居多"，
  而"证明无解那类我们已经在上面的分支里标成不可重试了" ——
  两条路径互斥，不会互相覆盖。
* **`finally { heartbeat.interrupt(); }`**：不 `interrupt` 的话，心跳线程会继续
  每 15 秒续租一次 —— 对一个已经交回、甚至已经被接管的任务续租，
  会**让租约永远不到期**。⚠ 而且它是 `while (!interrupted())` 循环 +
  `Thread.sleep`，`interrupt()` 能让它立刻从 sleep 里出来并 return。
  两个 `return` 分支（tokenLost / cancel）也在 `try` 里，所以同样会走到 finally。

#### `private Thread startHeartbeat(...)`（第 116-144 行）

```java
Thread thread = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            Thread.sleep(Math.max(1, job.heartbeatSeconds()) * 1000L);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return;
        }
        SchedulingClient.HeartbeatResult result =
                client.heartbeat(job.jobId(), job.jobToken(), progress.get());
        if (!result.ok()) {
            log.warn("心跳被拒（任务已被接管）: job={}", job.jobId());
            tokenLost.set(true);
            return;
        }
        if (result.cancelRequested()) {
            cancelRequested.set(true);
            return;
        }
    }
}, "orbit-hb-" + job.jobId());
thread.setDaemon(true);
thread.start();
return thread;
```

逐点：

* `Thread.sleep(Math.max(1, job.heartbeatSeconds()) * 1000L)` ——
  **间隔由服务端下发**（`ClaimedJob.heartbeatSeconds`，默认 15 秒），
  worker 不自己配。`Math.max(1, ...)` 防的是"服务端给了 0"导致忙循环 ——
  小防御，但省掉一整类难以复现的 CPU 打满问题。
* 线程名 `"orbit-hb-" + jobId` —— 排查时能在 jstack 里直接认出哪个任务的心跳。
* `setDaemon(true)` —— 心跳是**附属**线程，进程退出时不该被它拖住。
  ⚠ 与 `WorkerLoop` 里求解线程的 `setDaemon(false)` **正好相反**，
  这是刻意的对照组：**求解线程跑着的时候进程不该退出**，心跳则相反。
* **`!result.ok()` → `tokenLost.set(true)` 后立刻 `return`**（停止心跳）：
  注释原文"被接管了：继续算下去也不会被接受，但**求解调用无法中断**，
  所以只能打标记，外层算完后丢弃结果"。
  注意它**只打标记、不打断主线程** —— 因为打断不了（见下面的局限）。
* **`cancelRequested` 分支同样 `return`**（停止心跳）：已经知道要取消了，
  继续续租没有意义 —— 但 ⚠ 注意**租约还得撑到求解结束**，
  否则这个任务会在我们还在算的时候被别人领走（`lease_until` 不再续期 → 到期 → 接管）。
  这是个**微妙的取舍**：worker 停止心跳后，一个 60 秒的求解如果超过了剩余租约
  （默认 300 秒，通常不会），任务就可能被接管重做。
  按默认参数（租约 300s、时限 60s）是安全的。
* ⚠ **返回 `HeartbeatResult` 的 `ok()` 与 `cancelRequested()` 是同一个响应的两个字段**，
  而 `SchedulingClient` 在**网络失败**时返回 `(true, false)` ——
  所以"心跳失败"在这里表现为"什么都没发生"，循环继续等下一个 15 秒。这就是
  5b.8 那条 ⚠ 在调用侧的体现。

#### 三种收场（类注释第 27-34 行）

| 收场 | 动作 | 服务端结果 |
|---|---|---|
| **成功** | `submitResult` | `accepted=true` → 落版本；`false` → 结果被丢弃（被接管），**不是错误**，只记日志 |
| **无解/超时** | `reportFailure`，`retryable = timedOut()` | 可重试 → 回 `pending`；不可重试 → `failed` |
| **被取消** | `submitCancellation`（`reportCancelled`） | `markCancelled` → `cancelled` |

#### `private void reportCancelled(ClaimedJob job)`（第 146-149 行）

```java
Map<?, ?> response = client.submitCancellation(job.jobId(), job.jobToken());
log.info("任务已响应取消: job={} {}", job.jobId(), response);
```

⚠ **它没有 try/catch** —— 与 `reportFailure` 不同。它被两个地方调用
（第 69、85 行），两处都在 `run` 的 `try` 块里，所以异常会被
第 105 行的 `catch (RuntimeException)` 兜住 → 走到 `reportFailure(..., true)`。
**后果**：一个"取消交回失败"的任务会被**当成求解出错、且标成可重试** →
退回队列 → **重新被领走跑一遍**。
⚠ 这是"取消绝不该重试"原则在实现上的一个**漏点**：它只在"取消交回成功"时成立。
本册按代码事实记录，不判断这是否是有意为之。

#### `private void reportFailure(...)`（第 151-160 行）

```java
try {
    Map<?, ?> response = client.submitFailure(job.jobId(), job.jobToken(), error, solverStatus, retryable);
    log.info("已交回失败: job={} retryable={} {}", job.jobId(), retryable, response);
} catch (RuntimeException e) {
    // 交回失败也没别的办法：租约到期后任务会被接管重做
    log.error("交回失败结果时出错: job={}", job.jobId(), e);
}
```

**为什么这里必须吞异常**（注释原文）："交回失败也没别的办法：**租约到期后任务会被接管重做**"。
这是整个容错设计的兜底：worker 侧的**任何一种收场失败**（进程被杀、网络断、
服务端 500）最终都由**租约到期 + 接管**收住 —— 前提是心跳也停了。
⚠ 反过来说：如果心跳线程还在续租而交回一直失败，任务会被**永远**续租下去
（`lease_until` 一直往后推）→ 没有人能接管它。当前代码里
`reportFailure` 失败后仍会走到 `finally { heartbeat.interrupt(); }`（第 111 行），
所以这个洞被堵住了。**读这段代码时要把 `finally` 那行和这里连起来看。**

#### ⚠⚠ 一处已知的局限：**求解中途无法真正中断**（类注释第 36-45 行）

```
OR-Tools 的 solver.solve() 是**阻塞调用**，没有提供中断接口。
所以取消请求只能做到：
  * **求解前**检查 → 根本没开始就直接交回取消
  * **求解后**检查 → 算出结果但发现取消了，丢弃结果并交回取消
也就是说一次 60 秒的求解**最坏要跑完**才会响应取消。
要真正做到"中途停"得靠 `CpSolver.stopSearch()`
（需要在求解线程外调用，且语义是"停止搜索并返回当前最好解"）
—— 那是 P5 的可观测/压测阶段一起做的事。
```

**为什么"只能做到这两步"值得单列一条**：
* 用户感知上，"点取消"→"任务还在跑 60 秒"是**必须向用户解释**的行为
  （`JobController.cancel` 的 javadoc 也写了"最坏要等这次求解跑完"）。
* 架构上，这正是 `tokenLost` / `cancelRequested` 两个标记"只打标记不打断"的原因 ——
  **不是懒，是打断不了**。理解这一点，`JobRunner` 里所有"算完了才检查"的写法就不再像是疏漏。
* ⚠ `stopSearch()` 的调用约束（必须在求解线程外、语义是"返回当前最好解"）
  在注释里写明了，属于**未实现**的设计；本册只记录，不展开。

### 5b.10 `WorkerLoop` —— 轮询领单、两处并发上限、优雅停机

**谁调它**：Spring 的 `@Scheduled`（只调 `poll()`）+ 容器关闭时调 `shutdown()`。
**它调谁**：`SchedulingClient.claim()` → `JobRunner.run(job)`（丢进线程池）。

#### 构造器（第 44-57 行）

```java
int concurrency = Math.max(1, properties.getConcurrency());
this.pool = Executors.newFixedThreadPool(concurrency, r -> {
    Thread t = new Thread(r, "orbit-solve");
    t.setDaemon(false);   // 求解线程**不能是守护线程**：它跑着的时候进程不该退出
    return t;
});
log.info("solver-worker 启动: id={} scheduling={} 本进程并发={} 求解时限={}s", ...);
```

* `Math.max(1, ...)`：配置成 0 或负数也不会造出一个"永远领不到活"的循环
  （`newFixedThreadPool(0)` 会抛 `IllegalArgumentException`）。
* ⚠ **`setDaemon(false)` 是这里最值得注意的一行**（注释原文：
  "求解线程**不能是守护线程**：它跑着的时候进程不该退出"）。
  如果它是守护线程，JVM 在"只剩守护线程"时会直接退出 —— 一次 60 秒的求解
  会在主线程结束的瞬间**被无声掐死**，而这正是 P3 要消灭的
  "任务凭空消失"（§5.8 的①）。**非守护 + `@PreDestroy` 的 `awaitTermination`**
  一起构成优雅停机。
* 启动日志打了四样东西（id / scheduling 地址 / 本进程并发 / 求解时限）——
  这四个是排查"worker 为什么没干活"必看的，放在一行里省得再去翻配置。

#### `@Scheduled(fixedDelayString = "${orbit.worker.poll-interval-ms:2000}") public void poll()`（第 65-101 行）

```java
int concurrency = Math.max(1, properties.getConcurrency());
while (inFlight.get() < concurrency) {
    ClaimedJob job;
    try {
        job = client.claim();
    } catch (RuntimeException e) {
        log.warn("领单出错，本轮放弃", e);
        return;
    }
    if (job == null) {
        return;   // 没活干（或没有全局槽位），等下一轮
    }
    if (job.takeOver()) {
        log.warn("接管任务: job={} attempt={}/{} 上一个持有者没能收尾", ...);
    }
    inFlight.incrementAndGet();
    pool.submit(() -> {
        try {
            runner.run(job);
        } catch (Throwable t) {
            log.error("求解任务时未捕获的错误: job={}", job.jobId(), t);
        } finally {
            inFlight.decrementAndGet();
        }
    });
}
```

* **`fixedDelayString` 而不是 `fixedRateString`**：`fixedDelay` 是"上一次执行**结束后**
  再等 2 秒"，`fixedRate` 是"每 2 秒开始一次"。这里必须是 `fixedDelay` ——
  否则一次长时间领单（网络慢）会和下一轮重叠，出现两个并发领单循环。
  `${...:2000}` 让间隔可由配置覆盖，默认值与 `WorkerProperties.pollIntervalMs` 一致
  （⚠ 注意 `@Scheduled` 是**直接读配置**、不经过 `WorkerProperties`，
  所以 `WorkerProperties.pollIntervalMs` 实际上**在轮询里没被用到** ——
  它只作为一个"配置项文档"存在。这是代码事实。）
* ⚠⚠ **一次 poll 会连着领多个（`while` 循环），而不是每轮只领一个**（注释原文）：
  "否则**并发度设成 4 却要 8 秒才能填满**"。
  因为 `@Scheduled` 的下一轮要等 2 秒，如果每轮只领一个，
  填满 4 个槽位需要 4 轮 = 8 秒 —— 而 scheduling 那边明明有 4 个任务在排队。
  这个 `while` 让"领单"变成"把本地并发填满为止"。
* 循环的**两个出口**：`job == null`（服务端 204，没活干 / 没有全局槽位）
  或 `inFlight >= concurrency`（本地已满）。**没有 `inFlight` 之外的上限** ——
  因为全局上限在 scheduling 的容量槽位上（见下）。
* **`inFlight` 的增减位置很关键**：`incrementAndGet()` 在 `pool.submit` **之前**
  （否则 while 判断会看到旧值，可能超领），`decrementAndGet()` 在
  `finally` 里（**保证任何异常路径都会还回去**）。
  ⚠ 如果 decrement 漏了，`inFlight` 只增不减 → 几分钟后这个进程**永远不再领单**，
  而且不报错 —— 与 `JobResultWriter.settle` 漏掉是同一类"静默憋死"的故障。
* **`catch (Throwable t)`**（不是 `RuntimeException`）：
  注释"兜底：绝不能让一个任务把线程池里的线程吃掉"。
  `Throwable` 连 `Error`（如 `OutOfMemoryError`）都兜 ——
  理由是**线程池的线程是与任务绑定的**：如果异常逃出去，
  `decrementAndGet()` 因为写在 `finally` 里仍然会执行，但线程会被替换掉。
  更重要的是保证 `inFlight` 一定被减。
* ⚠ **`client.claim()` 的异常被 `catch` 后 `return`**（不是 `continue`）：
  注释"领单出错，本轮放弃"。这个 `catch` 其实**永远不会触发** ——
  因为 `SchedulingClient.claim()` 自己已经把两类异常都吞成 null 了。
  它是"以防万一"的冗余保护（比如 `ClaimedJob` 反序列化抛出的
  `RestClientException` 之外的异常）。
  > ⚠⚠ **这里有一段本册最实用的实测记录**（注释第 73-77 行原文）：
  > "必须打**整个异常**而不是 `getMessage()`。这里最初只打了消息，于是日志里只有
  > `Error while extracting response for type [ClaimedJob]`
  > ——**根因（哪个字段反序列化失败）完全看不到**，而那种错误恰恰只存在于 cause 链里。"
  > 这条与 5b.8 的 `RestClient.Builder` 坑是**同一场事故的两半**：
  > 前一版代码因为只打 message，导致"`Cannot map 'null' into type 'long'`"
  > 这个真正的根因**没有出现在日志里**。
  > 修法是 `log.warn("领单出错，本轮放弃", e)` —— **把异常对象作为最后一个参数**
  > （而不是字符串拼接），SLF4J 才会打出完整堆栈与 cause 链。
* **接管的日志是 `warn`**（第 84-88 行）：注释"接管是**值得记一笔**的事件：
  说明上一个 worker 没能收尾"。接管是正常机制，但它**意味着有一次 12-60 秒的
  计算被白白浪费**，所以值得 warn 级别（而"正常领单"连日志都不打）。

#### 两处并发上限，各管一层（类注释第 24-31 行）

| 上限 | 在哪 | 管什么 |
|---|---|---|
| `orbit.worker.concurrency` | 本进程（线程池大小 + `while (inFlight < concurrency)`） | **本进程**最多同时算几个 |
| scheduling 侧的**容量槽位** | scheduling（跨所有 worker 副本） | **全局**最多几个；抢不到槽位时 `claim` 返回 204，本循环自然空转等下一轮 |

**为什么必须两层**（类注释原文）："只有本地上限时，起 4 个副本就变成 4 倍并发，
可能把机器打满；所以全局上限留在 scheduling 那边，worker 这边只是'别把自己压垮'。"
⚠ 换句话说：`concurrency` 是**自我保护**，不是产能控制 —— 想改"这个系统最多同时排几所学校的课"，
要改的是 scheduling 的 `orbit.scheduling.max-concurrent-schedules`（默认 2），
**不是** worker 的 `concurrency`。改错地方的效果是"改了不起作用"。

#### 为什么是"轮询"而不是长连接或消息推送（类注释第 16-22 行）

* **"领单本身就能表达'没活干'"**（scheduling 返回 204），不需要额外的通知机制。
  轮询间隔 2 秒，代价是每 2 秒一次 HTTP —— 对一个"求解要 60 秒"的场景完全可以忽略。
* **用 MQ 反而更麻烦**：任务状态必须与 `job_token` 栅栏在**同一事务域**（铁律 1），
  MQ 的"消息被消费"与"任务行被标记"是两件事，需要分布式事务或幂等补偿。
  （同一段论证也写在 `JobQueueService` 的类注释"为什么是数据库当队列"里。）

#### `@PreDestroy public void shutdown()`（第 104-116 行）

```java
pool.shutdown();
try {
    if (!pool.awaitTermination(properties.getTimeLimitSeconds() + 10L, TimeUnit.SECONDS)) {
        log.warn("停机超时，仍有 {} 个求解未完成 —— 它们的租约到期后会被接管", inFlight.get());
        pool.shutdownNow();
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    pool.shutdownNow();
}
```

* `pool.shutdown()`（**不是** `shutdownNow`）：**不再接新任务、但让已提交的跑完**。
  这正是"优雅停机"的定义 —— 已经在算的任务不该被掐死。
* 等待上限 = `timeLimitSeconds + 10`：一个正在跑的求解最长就是时限（默认 60），
  再加 10 秒余量。⚠ 注意这只覆盖**"已经在池里"**的任务；
  如果池满且还有排队任务，`shutdown()` 之后它们永远不会被执行
  （`awaitTermination` 会等到超时才发现）—— 但它们**没有**被领走以外的损失：
  ⚠ 事实上**它们已经被领走了**（`claim` 已把它们置成 `running` 且换了 token），
  所以只能靠租约到期（300 秒）被别人接管。这是能接受的（§5.8 的容错设计），
  但意味着"优雅停机"并不能避免所有重算。
* 超时后的日志**点明了后果**："它们的租约到期后会被接管"——
  ⚠ 但注意此时 `pool.shutdownNow()` 只是 `interrupt()` 求解线程，
  而 `JobRunner` 里的求解是**阻塞调用**（`solve()`），中断未必有效
  （`WorkerLoop` 没有对 `InterruptedException` 做任何处理，
  且 `JobRunner` 的线程不检查中断标志）。所以这行日志描述的
  "会被接管"**依赖的就是租约过期**，而不是 `shutdownNow()` 真的停下了什么。
* `catch (InterruptedException)` 里重新 `interrupt()` 当前线程 ——
  标准做法（不要吞掉中断状态），然后同样 `shutdownNow()`。
