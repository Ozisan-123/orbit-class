## 0. 一页速览

| 维度 | 现状 |
|---|---|
| 后端 | Maven 多模块，**7 个模块**（5 个有实质代码 + 2 个占位）；Spring Boot **4.1.1** + JDK **21** |
| 接口 | **72 个**：P1 平移的 **51 个**（与 Python 侧一一对应）+ P2 新增 **13 个**（规则 11 + 诊断 1 + …）+ P3 新增 **8 个**（任务 5 + 内部 3） |

| 求解 | OR-Tools CP-SAT **9.15.6755**（与 Python wheel 同一份 C++ 内核），包在自研**规则系统**里；**跑在独立进程** `orbit-solver-worker` |
| 前端 | React **19** + antd **6** + Vite **8**，7 个页面 |

| 迁移状态 | **P1 双服务平移** ✅ · **P2 规则系统** ✅ · **P3 求解隔离** ✅ |

每一步都有实测等价性证据** 的中台骨架。

## 1. 架构要解决的问题

老系统是 FastAPI + SQLAlchemy 的单体：50 个路由、16 张表、一个进程里既有教务 CRUD
又有求解器，约束**硬编码在 `scheduler/engine.py` 的 367 行里**。三个具体痛点决定了现在的架构：

| 痛点 | 现状 | 架构上的回答 |
|---|---|---|
| **加一条约束要改求解器代码并重新部署** | `engine.py` 里硬编码硬 1/2/3 + 软 1/2 | 拆出 **`orbit-solver-core`**：约束变成"规则"，有类型、参数 Schema、独立 Handler |
| **排课是"一个进程里跑一个后台线程"，多实例就乱** | `threading.Thread` + Redis 锁 + 容量槽位 | 把并发控制**收进一个服务**（`orbit-scheduling`），并明确"原子性不跨服务" |
| **教务数据与排课数据混在一张库、一次迁移，谁都能写** | 单库、跨模块直接改表 | 给每张表定**唯一属主**，跨服务只读走 API；**禁止跨服务写库** |

由此定下 **五条铁律**（原文见方案 §3）：

| # | 铁律 | 后果 |
|---|---|---|
| 1 | **排课的原子性不跨服务**：`job_token` 栅栏、租约续期、版本落库全部在 scheduling 内完成 | 保证不需要分布式事务 |
| 2 | **禁止跨服务写库**：每个表只有一个属主服务；跨服务只读走 API | 避免隐式耦合 |
| 3 | **排课输入用快照**：scheduling 一次性拉取并冻结输入数据 | 保证一致性与可审计 |
| 4 | **助手只提议不执行**：写操作一律「草案 → 差异预览 → 人工确认 → 执行」 | 把 LLM 不可信输出关在闸门后 |
| 5 | **禁止编造**：助手回答中的每个实体必须来自工具返回 | 可自动检测 |

> 铁律 4、5 是给 **P4 的 AI 助手**（`orbit-assistant`）定的，那个模块现在还是占位。
> 铁律 1、2、3 在 P1 已经**落到了代码里**，本文后面会逐条指出落点。

## 3. 七个模块各负责什么

### 3.1 `orbit-common` —— 契约层（10 个类）

不装业务，只装**"所有服务必须表现一致"的那些东西**。它是唯一被所有模块依赖的模块。

| 包 | 类 | 负责 |
|---|---|---|
| `dto` | `PageQuery` / `PageResponse` | 列表接口的统一分页契约（§9.2）。`PageQuery` 负责把缺省的 `page/size` 归一化，`PageResponse` 负责输出 `{items,total}` |
| `error` | `BusinessException` / `ErrorResponse` / `ApiExceptionHandler` / `ValidationError*` | **错误体的契约**：把 Spring 的异常翻译成 FastAPI 形状的 `{"detail": ...}` |
| `security` | `JwtService` / `AuthFailure` | 签发与校验 JWT（HS384）；`AuthFailure` 是 401 的三种文案与请求属性名 |
| `util` | `UtcTimes` | 统一时间：UTC + **截断到秒**（Python 的 `datetime` 没有纳秒） |

**为什么这些必须共享**：错误体、分页结构、时间精度是**契约的一部分**。
如果让每个服务自己实现，两个服务的 422 响应迟早长得不一样 —— 而前端只有一套解析逻辑。

### 3.2 `orbit-academic` —— 教务主数据（78 个类，37 个接口）

**它是"这所学校长什么样"的唯一权威**：组织、账号、年级、班级、科目、教师、周课时、
任教关系、固定课。**它不理解排课**，也不知道什么叫 `job_token`。

11 个领域包，每个包都是同一套五件套（实体 / Mapper / 请求 DTO / 响应 DTO / Service / Controller）：

| 包 | 对应接口 | 说明 |
|---|---|---|
| `auth` | `/api/auth/*`（3） | 登录、当前用户、改密码。含 `PythonPbkdf2PasswordEncoder`（**为了能读老库的密码哈希**）、`LoginAttemptGuard`（限流）、`JwtAuthenticationFilter` |
| `user` | `/api/users`（3） | 账号管理 |
| `organization` | `/api/organizations`（2） | 学校 |
| `grade` | `/api/grades`（4） | 年级，含 `periods_per_day`（每天几节，**按天存 JSON**） |
| `clazz` | `/api/classes`（4） | 班级（实体类名 `Clazz`，因为 `Class` 是 Java 关键字） |
| `subject` | `/api/subjects`（3）+ `/api/grade-subjects`（4） | 科目 + **年级周课时**（排课的核心需求输入） |
| `teacher` | `/api/teachers`（4） | 教师，含 `max_weekly_hours`（排课的硬约束输入） |
| `assignment` | `/api/assignments`（5） | 任教关系 + **自动分配算法** |
| `fixedslot` | `/api/fixed-slots/by-grade`（3） | 年级固定课（引擎会展开到该年级每个班） |
| `health` | `/api/health`（1） | 健康检查 |
| `config` | — | `SecurityConfig` / `JwtConfig` / `MybatisPlusConfig` |

**它不碰的表**（属于 scheduling）：`scheduling_state`、`schedules`、`schedule_versions`、
`schedule_version_entries`、`schedule_audit_logs`、`schedule_worker_slots`。

> ⚠ 有一处**已知的行为偏离**：Python 在新建组织时会顺手写一行 `scheduling_state`，
> Java 不写（铁律 2）。改为由 scheduling **懒初始化** —— 查不到就返回默认的 idle 状态。
> 对外可见行为一致（Python 返回的也是那行 idle），但少了一次跨服务写库。

### 3.3 `orbit-scheduling` —— 排课 · 课表 · 规则 · 任务队列（约 90 个类，32 个接口）

**整个系统最复杂的一块**，因为排课天然是"长时间运行的写操作 + 并发敏感"。
它同时也是铁律 1、2、3 的落点。

| 包 | 类 | 负责 |
|---|---|---|
| `security` | `AuthUser` / `AuthUserMapper` / `JwtAuthenticationFilter` / `SchedulePrincipal` | **只校验 token，不签发**（所以没有 `PasswordEncoder`、没有登录接口）。`AuthUser` 是 `users` 表的**只读**映射，**刻意不含 `password_hash` 字段** |
| `capacity` | `CapacityService` / `ScheduleWorkerSlot(+Mapper)` | **全局并发度**：2 个槽位，靠**条件 UPDATE + 看 rowcount** 抢。⚠ P3 起在**领单时**抢（不是入队时，否则排队的任务会空占产能） |
| `lock` | `ScheduleLockService` | **每校互斥**：Redis `SET NX EX` 抢锁，释放/续租用 **Lua 比对 token**。⚠ P3 起它的职责缩回"保护「检查 + CAS + 入队」这个短临界区"——见 §5.8 |
| `schedule` | `ScheduleRunService` / `ScheduleStateService` / `TimetableGenerationService` / `SchedulingState(+Mapper)` / `ScheduleEntity(+Mapper)` / `ScheduleStatusResponse` / `ScheduleController` | 状态机 + **generate 的入队关卡** + 对外状态查询。P3 删掉了进程内线程的 `ScheduleRunner` 与 `ScheduleResultWriter` |
| `job`（**P3 新增**，约 12 个类） | `JobQueueService` / `ScheduleJobMapper` / `ScheduleJobEntity` / `JobResultWriter` / `SnapshotService` / `InternalJobController` / `JobController` / `DiagnosisHook` + DTO | **持久任务队列**：入队、`SKIP LOCKED` 领单、心跳续租、租约过期接管、结果落库闸门、输入快照冻结、内部接口、5 个任务接口。见 §5.8 |
| `snapshot` | `ScheduleInputLoader` + 7 个 `*Ref` | 读 academic 的 7 张表（**只读**）→ 装配成 solver-core 的 `ScheduleInput`。P3 起由它喂给快照冻结 |
| `version` | `VersionService` / `VersionController` / `ScheduleVersion(+Mapper)` / `ScheduleVersionEntry(+Mapper)` / `VersionResponse` / `VersionUpdateRequest` | 草稿的列表/改名/复制/发布。版本上记着**三个溯源指纹** |
| `audit` | `ScheduleAuditLog(+Mapper)` / `AuditResponse` | 审计流水（谁在什么时候改了什么） |
| `validate` | `VersionValidator` | **独立的课表校验器**：发布前、每次换课后都要跑一遍 |
| `swap` | `SwapService` / `SwapRequest` / `SwapController` | 拖动换课（全项目最"绕"的一段，见 §5.3） |
| `query` | `ScheduleQueryService` / `ExportService` / `ScheduleQueryController` / `ScheduleResponse` | 按班/教师/年级看课表（**刻意不分页**）+ 导出 xlsx |
| `system` | `SystemService` / `SystemController` / `SystemStatsMapper` | `/api/system/*` 三个运维接口 |
| `rule`（**P2 新增**，14 个类） | `RuleTypeCatalog` / `RuleSetService` / `RuleService` / `RuleTrialService` + 实体/Mapper/DTO | **规则系统**：类型 Schema 投影、CRUD、规则集哈希与版本、试算。见 §5.6 |
| `diagnosis`（**P2 新增**，7 个类） | `StaticDiagnostics` / `DiagnosisService` / `ScheduleDiagnosisEntity` + Mapper/DTO | **不可行性诊断**：静态检查（4 类）+ 最小冲突集。见 §5.7 |
| `config` | `SchedulingSecurityConfig` / `SchedulingInfraConfig` | 含 `/internal/**` 的放行（由控制器自己校验共享密钥） |

**它读 academic 的表**（`users`/`grades`/`classes`/`subjects`/`teachers`/`grade_subjects`/
`teacher_assignments`/`grade_fixed_slots`），**但从不写**。

> 这是一处**已知耦合**：读不违反铁律 2，但 P3 拆独立库时会断。
> 届时的两条路：① 鉴权上移到网关（校验后在请求头注入 `userId`/`organizationId`/`role`）；
> ② 各服务维护只读投影。已记入 TODO。

### 3.4 `orbit-solver-core` —— 规则化求解引擎（33 个类）

**独立性最强**：它的整个 `pom.xml` 只有三个依赖 —— **`ortools-java`、`jackson-databind`、`junit-jupiter`**。
代码里 `org.springframework.*` / `com.baomidou.*` / `jakarta.*` 的 import **出现 0 次**。
它不知道 Spring、不知道数据库、不知道 HTTP 是什么。

输入是一个 `ScheduleInput` 记录，输出是一个 `SolveOutcome` 记录。
**这个边界是刻意的**：正因为它是纯库，P3 才能**原封不动**地把它搬进独立的
`orbit-solver-worker` 进程 —— 搬运时 solver-core **一行都没改**（只有 worker 侧新增了调度代码）。

```
model/      ScheduleInput（对标 Python 的那 7 条查询）
            ClassData（每班每天的节数 —— 是个数组，不是常数）
            TimetableEntry（一节课）

rule/       ConstraintRule（一条规则的声明：type + 参数 + 权重 + 硬软）
            RuleHandler（规则的实现接口）
            RuleParams / RuleParamSpec（参数与其 Schema —— 前端表单的单一来源）
            RuleRegistry（type → handler 的映射）
            PenaltyCollector / RuleContext

rule/handler/  10 个内置规则的具体实现

compile/    RuleCompiler（规则集 → CP-SAT 模型）
            CompiledModel（编译结果：模型 + 指纹）
            BuiltinRules（装配点：有哪些内置规则）
            RuleSets（预设规则集，含 legacyEquivalent）

engine/     OrbitSolver（对外唯一入口：compile / solve / fingerprintOf）
            SlotVariableIndex（时段索引）
            ModelFingerprints（模型指纹）
            TimetableExtractor（从解里取出课表）
            SolveOutcome（**带 status** —— 能区分"超时"与"真的无解"）
            SolverSettings / SolverNatives / ConstructionInfeasible
```

**10 条内置规则**，分两类：

| 类型 | 规则 | 何时生效 |
|---|---|---|
| **不变量 / 数据驱动**（3） | `teacher_no_conflict`、`subject_weekly_hours`、`teacher_max_weekly_hours` | **总是**生效（`mandatory`），顺序敏感 |
| **可配置**（7） | `subject_max_per_day`、`subject_no_consecutive`、`teacher_max_daily_periods`、`teacher_unavailable`、`subject_avoid_last_period`、`main_subject_morning`、`teacher_minimize_gaps` | 只有规则集**显式引用**时才生效 |

> **"有哪些内置规则"是装配知识**，所以放在 `compile/BuiltinRules` 而不是 `RuleRegistry` ——
> 注册表只管 `type → 实现` 的映射。这样"新增一种规则"只有一处要改：
> 写一个 Handler + 在 `BuiltinRules` 登记一行。

### 3.5 `orbit-solver-worker` —— 独立求解进程（P3，5 个类）

**一个不连数据库的进程**：方案 §2.2 的服务清单写明它「拥有的表：**无**」。
它需要的一切（任务身份、冻结的输入快照、当时那套规则）都由 scheduling 的
`POST /internal/jobs/claim` 一次性下发。

| 类 | 负责 |
|---|---|
| `WorkerProperties` | 配置：scheduling 地址、共享密钥、本进程并发、轮询间隔、求解时限 |
| `SchedulingClient` | 三个内部接口的客户端（claim / heartbeat / result） |
| `JobRunner` | 求解**一个**任务：起心跳线程 → 求解 → 交回结果 |
| `WorkerLoop` | `@Scheduled` 轮询领单，丢给线程池；优雅停机 |
| `ClaimedJob` | 领单响应的**镜像**（刻意与 scheduling 的 DTO 重复 —— 两个服务之间只有 JSON 契约，共享 Java 类会让改一边悄悄改变另一边） |

**为什么值得单独一个进程**（§2.3 说这是"拆分理由最强"的一条）：求解吃满 CPU 12-60 秒、
峰值 1.8 GB。与 Web 请求放一起时，一次排课就能把接口响应拖慢，而且
**进程重启会凭空丢掉正在跑的任务**。拆开之后 worker 可以按 CPU 核数独立扩容
（它不持有任何状态），崩了则由租约到期 + 接管兜住。

> ⚠ 两处已知局限（记在 TODO）：
> ① **求解中途无法真正中断** —— OR-Tools 的 `solve()` 是阻塞调用，取消只能做到
> "求解前检查 + 求解后丢弃"，一次 60 秒的求解最坏要跑完；
> ② worker 还没进 `docker-compose`，目前手工起进程。

### 4.1 调用关系（谁依赖谁）

                       └───────▲───────┘

### 4.3 三条横切关系

**① 契约关系**（`orbit-common` ↔ 所有服务 ↔ 前端）
`BusinessException` 决定状态码，`ApiExceptionHandler` 决定响应体形状，
前端 `api/index.ts` 用 `error?.response?.data?.detail ?? fallback` 解析。
**三者必须同时改**，否则前端会拿到 `undefined` 去渲染 —— 实测过：`detail` 是数组时会直接让 React 崩。

**② 快照关系**（academic 的表 → `snapshot` → `solver-core`）
```
academic 的 7 张表
      │  ScheduleInputLoader.load(organizationId)   ← 铁律 3 的边界就在这个方法的签名上
      ▼
ScheduleInput（一个不可变 record）
      │  TimetableGenerationService.solve()
      ▼
SolveOutcome → TimetableEntry 列表
```
**这个接口的收口是有意的**：现在实现是"现查一遍"（与 Python 一致，同一个库），
但 P3 拆库时只要把 `load()` 换成"调 academic 的接口一次性拉取并冻结"，
**调用方一行都不用改**。

**③ 验证关系**（`tools` ↔ 两个后端 + Python）
影子对比工具**同时依赖三样东西**：Python 应用、Java academic、Java scheduling。
它自己就是"拆进程后的路由表"——工具里的分流规则与 `vite.config.ts` **必须一致**，
不一致会出现"工具全绿但页面报错"。

### 4.4 一次排课的完整旅程

这是整个系统最值得看的一条链路，它同时穿过 §3.2、§3.3、§3.4、§3.5 和三条铁律。

> ⚠ **P3 把这条链路改了**：求解从"进程内线程"变成"持久任务队列 + 独立进程"。
> 下面画的是**现在**的样子。

```
① 前端 POST /api/schedule/generate
        │
        ▼  Vite 按路径分流 → :8083
② ScheduleRunService.trigger()  ── 四道关卡，顺序不能变：
        │
        ├─ 1. Redis 锁    抢不到 → 409 本校已有排课任务正在运行，请稍后再试
        │      ⚠ P3 起它**只保护下面这个短临界区**，不再握到求解结束
        │
        ├─ 2. 状态检查    有未过租约的 running → 409 <谁>正在排课，请稍后再试
        │
        ├─ 3. CAS 抢状态  UPDATE ... WHERE status<>'running'
        │                    OR started_at IS NULL
        │                    OR started_at < 租约线
        │      受影响行数必须 = 1
        │
        └─ 4. 冻结输入快照 + 入队
               ScheduleInputLoader 读 academic 的 7 张表（只读）
                 → 存 scheduling_snapshots（含指纹）      ← 铁律 3 的真正落地
               hashOf(规则集) → 记在任务上
               INSERT schedule_jobs(status='pending', job_token=…)
        │
        ▼  立刻释放 Redis 锁 → 返回 {"status":"running","message":"已入队，等待求解…"}
        │     （0.26 秒返回；前端每 1 秒轮询 /api/schedule/status 与 /api/schedule/jobs）
        │
   ═════╪═════════════════ 进程边界 ═══════════════════════════
        │
③ solver-worker（**独立进程，不连数据库**）轮询 POST /internal/jobs/claim
        │
        ▼  scheduling 侧在**一个事务**里：
        │     ① 抢容量槽位（抢不到 → 204，什么都没有写，任务仍是 pending）
        │     ② SELECT ... WHERE status='pending'
        │            OR (status='running' AND lease_until < now)
        │        ORDER BY id LIMIT 1 **FOR UPDATE SKIP LOCKED**   ← 队列的核心
        │     ③ 换新 job_token + 置 running + 续租 + attempt+1
        │        ⚠ 接管时先用**旧 token** 释放上一个持有者占着的槽位（否则永久泄漏）
        │     ④ 下发：冻结的输入快照 + **当时那套规则**（按 rule_set_hash 从
        │        constraint_rule_versions 的冻结快照里取回）
        │
        ▼
④ worker：起心跳线程（每 15 秒）
        │     ① 续租   ② 读回 cancel_requested（用户取消的唯一通道）
        │     续不上 → ok=false → 打标记，算完后**丢弃结果**
        │     ⚠ 求解调用本身无法中断，所以取消最坏要等这次求解跑完
        │
        ├─ OrbitSolver.solve(input, rules, timeLimit=60s, workers=2)
        │
        └─ POST /internal/jobs/{id}/result（成功 / 失败 / 取消，三者之一）
        │
   ═════╪═════════════════════════════════════════════════════
        │
⑤ JobResultWriter —— **一个事务**里：
        │  ① SELECT ... FOR UPDATE WHERE id=? AND job_token=? AND status='running'
        │        → null ⇒ **结果被丢弃**（已被接管）。不是错误，静默结束
        │  ② 写 schedule_versions（三个溯源指纹）+ 明细 + 审计
        │  ③ 标记 job=done（与①同事务 ⇒ 不会出现"版本有了但任务还在跑"）
        │
   事务外：交还槽位 + 收尾对外状态（done/failed/idle）
        │
        ▼
   对外状态 → done: 排课完成，已生成草稿 V{n}，共 {N} 节课
```

**四个设计要点**：

1. **Redis 锁的职责在 P3 变了**。P1 时它要握到求解结束（那时"谁在跑"只有锁知道）；
   P3 有了任务队列之后，跨实例互斥由 `SKIP LOCKED` 保证、同校互斥由状态 CAS 保证 ——
   锁**如果继续握着，第一次排课之后这所学校就被永久锁死**（worker 根本不知道锁的存在，
   没人会去释放它）。所以它缩回"检查 + CAS + 入队"这个短临界区。
   *（这个 bug 是实测跑第二遍 generate 时才暴露的：直接 409。）*

2. **求解与落库之间必须有一次 `FOR UPDATE` 重新确认**。求解可能跑 60 秒，
   期间租约可能超时、任务可能已被接管 —— 不再确认的话，
   一个**已作废的求解结果会覆盖新任务的成果**。

3. **`job_token` 在每次领单时都会换**。于是"被接管后旧 worker 又醒过来提交结果"
   这种情况**写不进去** —— 它的 token 已经失效。这是幂等的全部秘密。
   **"被接管"不是错误**：静默丢弃即可，新任务会自己收尾。

4. **快照与规则都在入队/领单时冻结，不是求解时现取**。任务可能在队列里躺几分钟，
   期间教务数据或规则完全可能被改 —— 不冻结的话，排出来的课表对应的是"另一份数据"，
   而且 `rule_set_hash` 会与实际用的规则自相矛盾。

## 5. 关键机制详解

### 5.1 并发控制：为什么是"锁 + 槽位 + 栅栏"三层

| 层 | 机制 | 挡什么 | 放在哪 |
|---|---|---|---|
| Redis 锁 | `SET NX EX` + Lua 比对 token | **跨实例**的重复提交（多副本部署时） | `lock/ScheduleLockService` |
| 容量槽位 | DB 行上的**条件 UPDATE + rowcount** | **全局并发度**（不同学校之间） | `capacity/CapacityService` |
| `job_token` 栅栏 | CAS 条件 UPDATE + `FOR UPDATE` | **同校内**的竞态 + **过期任务接管** | `schedule/ScheduleRunService` |

**为什么槽位用条件 UPDATE 而不是"先查再改"**：
```sql
UPDATE schedule_worker_slots
   SET organization_id=?, job_token=?, lease_until=?
 WHERE id=? AND (job_token IS NULL OR lease_until IS NULL OR lease_until < ?)
```
一条语句同时完成"判断可用"与"占用"，`rowcount=1` 就是抢到了。
**这正是方案选 MyBatis 而不是 JPA 的原因** —— 要看得到受影响行数。

> ⚠ 这个手法有个必须记住的配套：写操作**必须用 `@Update`/`@Insert`/`@Delete` 注解**。
> 用 `@Select` 标 UPDATE 时 MyBatis 会当查询执行，拿不到 rowcount →
> `BindingException: attempted to return null from a method with a primitive return type (int)`。
> **编译期完全看不出来**，只有真的点到"排课"才炸。（踩坑总结 B7）

### 5.2 规则系统的设计取向（**实现见 §5.6**）

**老的做法**（Python `engine.py`）：5 条约束直接写成 CP-SAT 的变量与约束，改一条要动求解器。

**新的做法**（solver-core）：一条规则 = `ConstraintRule`（声明）+ `RuleHandler`（实现）。

```java
// 声明：类型 + 参数 + 权重 + 硬软
ConstraintRule.soft(SubjectMaxPerDayHandler.TYPE,
                    RuleParams.of(Map.of("max", 1)), 1, "任何科目一天最多 1 节")
```

好处有三个，都是**可以在代码里指出来的**：

1. **参数有 Schema**（`RuleParamSpec`）→ 前端规则配置表单可以直接生成，不用后端加接口。
2. **可组合**：同一条规则既能当硬约束也能当软约束（`subject_max_per_day` 就是），
   靠 `ConstraintRule` 的硬软标记切换。
3. **可去重**：规则编译器知道两条规则共用同一个"教师成员布尔"，
   合并后变量数从 13,452 降到 **9,676（−28.1%）**。

**迁移期的关键预设**：`RuleSets.legacyEquivalent()` —— 一份语义上等价于
Python 那 5 条硬编码约束的规则集：

| Python | 规则 | 怎么生效 |
|---|---|---|
| 硬 1 教师不撞课 | `TeacherNoConflict` | `mandatory`，自动施加 |
| 硬 2 周课时必须排满 | `SubjectWeeklyHours` | `mandatory`，自动施加 |
| 硬 3 教师周课时上限 | `TeacherWeeklyLimit` | `mandatory`，自动施加 |
| 软 1 一科一天最多 1 节 | `SubjectMaxPerDay(max=1)` | 显式列出 |
| 软 2 一科不连排 | `SubjectNoConsecutive` | 显式列出 |

> 它**原先只存在于测试代码里**，P1 时提升为**生产预设**，测试改为引用它 ——
> 因为迁移期的 scheduling 服务求解时也必须用同一套。**只有一份定义，不可能漂移。**

### 5.3 负值腾挪：换课怎么绕过唯一约束

`schedule_version_entries` 上有唯一约束：
```
uq_version_class_slot (version_id, class_id, day_of_week, period_index)
```

想把 A 挪到 B 的位置、B 挪到 A 的位置时，**无论先改哪一个都会撞这个约束**。

解法是把要移动的记录**先改成负值坐标**，暂时移出冲突范围：

```java
first.dayOfWeek  = -1;              // 负数不会与任何真实时段冲突
first.periodIndex = -first.id;      // 用 -id 而不是固定 -1：跨班时会调两次，不能互相撞
// ... 让 second 占住旧位置 ...
// ... 再把 first 放到目标位置 ...
```

**这个设计直接依赖唯一约束的存在**（否则没必要绕），所以**改表结构时必须一起看这里**。

跨班协同换时还要处理两个"镜像"（对方班在我原时段那一节、我在对方目标时段那一节），
以及**固定课保护**（涉及到的 `(年级, 星期, 节次)` 里有年级固定课就拒绝）。

换完还会跑一次 `VersionValidator` **整体重校验** —— 不信任"这次换课本身没冲突"，
因为一次拖动可能间接造成别处的冲突。

> ⚠ 校验器里"报第一个冲突"必须用 `LinkedHashMap`。
> 用 `HashMap` 时**两边都正确地拒绝了换课，却报了不同的冲突**
> （Python 说"王老师在周1第2节"，Java 说"钱老师在周1第1节"）——
> 同一个输入给出不同答案。踩坑总结 H10。

### 5.4 模型指纹：怎么保证"模型没被悄悄改掉"

CP-SAT 的 `CpModel` 可以序列化成 `CpModelProto`，把它哈希一下就得到**模型指纹**。

- Python 侧同一份夹具的指纹：`0x874e810d17f32a8b`
- Java 的**忠实移植**（`legacy.FaithfulModelBuilder`）必须**逐字符相同** → `GoldenModelTest` 守着
- Java 的**规则系统**指纹：`0x3cbfb67312cda176`（变量 9,676 而不是 13,452）

**它守的是"模型漂移"**：任何 Handler、`SlotVariableIndex`、`RuleCompiler` 的改动，
只要改变了模型的变量/约束结构，测试就会红 —— **而这是好事**，
因为"模型变了"必须是有意的，并且要重新解释。

### 5.5 影子对比：怎么证明"两边行为一致"

**核心思路**：同一批请求，分别打 Python 和 Java，把两边响应**归一化后**逐字段比对。

几个不得不做的处理，每一个都对应一个真实的坑：

| 处理 | 为什么 |
|---|---|
| 两种 token 都在工具里**现签** | Python 用它的 `create_token`；Java 用**纯 Python 复刻的 HS384**。这样不需要口令、不写库、可重复 |
| `VOLATILE_KEYS`（删键） vs `VOLATILE_VALUE_KEYS`（只换值） | 前者如 `created_at`（每次不同），后者如 `used_memory`／`database_size_bytes`——这些**键本身必须存在**，只把值换成占位符 |
| 422 响应特殊归一化 | Pydantic 的 `loc`/`type`（`less_than_equal`）与 Spring 的校验注解不是一回事，需要映射 |
| 列表接口的三种基线 | `equal`（逐字段）、`superset`（Java 是 Python 的子集）、`first_page`（Java 返默认页，Python 返全量） |
| `unique_placeholder` + `cleanup` | 创建类用例会撞唯一约束（两个后端用同一个库）→ 每次运行用带 `RUN_ID` 的名字 |
| 登录用例按后端区分用户名 | 限流计数器在 Redis 里**是共享的**（这是刻意的），所以两边要用不同的用户名 |

### 5.6 规则系统：约束怎么从"代码"变成"数据"（P2）

**一份 schema，三处消费** —— 这是整个设计的枢纽：

```
RuleHandler.params()  →  RuleParamSpec  →  ┬─→ 前端"新建规则"表单（动态渲染，不为每条规则写页面）
                                            ├─→ 后端保存时的参数校验
                                            └─→ 助手的工具定义（P4/P5，新增规则类型自动可用）
```

`RuleTypeCatalog` 只是把 `BuiltinRules.registry()` **换个形状暴露出去**，
它没有任何类型白名单或 if/else —— **新增一个 handler，接口下次请求就自动多一条**。

**规则集指纹（`rule_set_hash`）** 是"这版课表用的哪套规则"的唯一凭据：

```
每行 → rule_type|hardness|weight|scope|scope_id|<params 的键排序 JSON>
全部行排序后换行拼接 → sha256 → 小写 hex
```

刻意**不含** `id`（删掉再建一条一样的规则应当算"没变"）、`description`（纯展示）、
`enabled`（哈希只覆盖 enabled 的行，所以启停会自然改变哈希）。

**版本是哈希去重的**，这带来一个反直觉但正确的后果（实测踩过）：
把规则改回原样会让规则集**回到一个编号更小的版本**，
所以"当前版本"必须**按哈希查**，而不是取 `version_no` 最大的那个。

**首次访问自动初始化**：新组织的规则是懒初始化的，写入的正是
`RuleSets.legacyEquivalent()`（P1 用来复现 Python 行为的那两条）。于是
**P2 上线不改变任何一所学校的排课结果**，只是那些约束从此看得见、改得动。
并发安全靠 InnoDB 在 REPEATABLE-READ 下对 `organization_id` 索引的 **gap lock**。

### 5.7 不可行性诊断：先静态（毫秒），后求解（几十秒）

**真实世界"排不出来"绝大多数是数据问题**，四类检查都能在毫秒级算出来、结论是确定的：

| 检查 | 抓什么 |
|---|---|
| `MISSING_ASSIGNMENT` | 某班某科有周课时要求却没配老师 →「周课时必须排满」这条不变量永远无法满足 |
| `CLASS_CAPACITY_SHORTFALL` | 一个班的周课时总量 > 一周座位数 |
| `TEACHER_OVERLOAD` | 教师被分配课时 > 自己的周上限 |
| `FIXED_SLOT_*` | 固定课自相矛盾 / 越界 / 多年级共用同一节 |

**最小冲突集用了一个不改内核的等价做法**：方案原稿是「硬约束改为 `onlyEnforceIf(flag)`，
最小化违反加权和」——那要改动 solver-core 里**每一条 handler 的建模方式**。
这里改成**逐条去掉硬规则再求解**：去掉哪条之后能排出来，那条就在冲突集里。
代价是解 K 次（K = 硬规则条数，上限 5，每次只用 8 秒而非排课的 60 秒）。

**`INFEASIBLE` 与 `UNKNOWN` 必须分开报**：CP-SAT 能区分「证明了无解」与「到时限还没证明」，
而后者**不该让用户去改数据**（延长时间就行）。Python 侧把两者压成同一句"排课无解"——
这是 P2 新增的能力。对外文案仍然不动（P1 的契约）。

**两个资源取舍**：
1. 排课失败时**只做浅诊断**（静态 + 记 kind，毫秒级）——此刻任务还占着容量槽位与 Redis 锁，
   在里面跑几十秒的深诊断会让"排不出来"这种常见情况白白压住排课能力。
2. **落库策略**：深诊断（贵）或确实有问题（需留痕）才落库；"一切正常"的浅诊断不落库。

**结论的可信度说明（`note`）是刻意写的**：诊断最危险的失败方式不是没结论，
而是给一个听起来确定、其实是猜的结论。所以静态一无所获 + 深诊断也一无所获时，
`note` 会明确说"冲突来自不变量的组合，这类情况需要最小冲突集算法"，
而不是编一个原因。

### 5.8 任务队列与求解隔离（P3）

**为什么不能再用线程** —— 线程版有三个治不好的问题：
① 进程重启 → 正在跑的任务**凭空消失**（没有任何记录说明它存在过）；
② 求解吃满 CPU 时会和 Web 请求抢核（§2.3 说这是"拆分理由最强"的一条）；
③ 无法回答"排队中吗 / 排第几 / 上次为什么失败"。

**三个必须一起看的机制**（它们全在 `schedule_jobs` 这一张表上）：

| 机制 | 做法 | 挡什么 |
|---|---|---|
| **`FOR UPDATE SKIP LOCKED`** | 领单时锁住一行并跳过已被锁的行 | 多个 worker 并发领单**不需要任何应用层锁** —— 这正是拿数据库当队列的价值 |
| **`job_token` 栅栏** | **每次领单都换一个新 token**，所有回写都带 `AND job_token = ?` | "被接管后又醒过来的旧 worker"提交的任何东西都**写不进去** |
| **`lease_until` 租约** | worker 每 15 秒续一次；没续上就允许别人领走 | worker 崩溃/被杀 → 任务**被接管**而不是失踪 |

**一次接管的完整过程**（这是决策门要验的东西）：

```
worker A 领单 → token=A，attempt=1，租约 300 秒
worker A 被 kill -9（或卡死）→ 心跳停了，租约到期
worker B 领单 → 同一行满足 status='running' AND lease_until < now
             → **换 token=B**，attempt=2
             → 先用**旧 token A** 释放 A 占着的容量槽位（否则永久泄漏）
worker A 若"复活"并交回结果 → token 不匹配 → accepted=false，结果被丢弃
worker B 交回结果 → 写版本 + 标记 done（同一事务）
→ **版本只落一版**（幂等）
```

**三个刻意的设计决定**：

1. **worker 不碰数据库**。方案 §2.2 写明它「拥有的表：无」，而 `SKIP LOCKED` 领单
   本质是**写** `schedule_jobs` —— 直连就违反铁律 2。所以领单走 scheduling 的内部接口，
   代价是每次多一次 HTTP，换来表属主始终清晰。
2. **"没活干"用 204 而不是 404**。它是正常状态不是错误；worker 隔 2 秒再来问。
3. **失败与取消分开**（`JobResultRequest` 里是两个字段）。失败是"这次没排出来"
   （可能该重试），取消是"用户不想排了"（**绝不该重试**）——
   混成一个会把用户主动取消的任务重新拉起来跑。

**容量槽位挪到领单时抢**：P1/P2 是"抢到槽位 → 立即求解"，槽位与任务同生共死；
P3 里任务可能在队列躺几分钟，此时占着槽位等于**空占产能**、把别人挡在门外。

**三处终态都必须收尾对外状态**（失败 / 取消 / 完成）——
漏掉任何一处的症状都是"这所学校再也发不起新排课"，而不是崩溃。
这一点 P3 实测漏了三次（见 §8 的"P3 遗留"与踩坑总结）。

## 6. 特色

按"别人一般怎么做 → 这里怎么做 → 为什么"来讲。

### ① 迁移靠"影子对比"，不靠人工核对

**一般做法**：写完对着 Postman 点一遍。
**这里**：860 行的对比工具，**100 项检查**覆盖 P1 平移的**全部 51 个接口**，
连**响应体文案**一起比。（P2 新增的 13 个规则/诊断接口在 Python 侧没有对应物，
没法用影子对比，判据换成了"用 DB 规则集排课 == 用 legacy 等价规则集"。）

**为什么值得**：这一套抓出了 **6 个手写脚本抓不到的 bug** ——
`loc` 用了 Java 属性名而不是 snake_case、嵌套校验路径与 Pydantic 不同、
"必填参数没传"应该是 422 而不是 400、"报第一个冲突"依赖遍历顺序、
空单元格 `None` vs `""`…… 而手写的 PowerShell 探测脚本**自己被转义问题误导了 3 次**。

### ② 用"最优目标值"而不是"解"判定等价

**一般做法**：比对两份课表是否逐行相同。
**这里**：比对**硬约束是否都满足 + 软约束罚分（目标值）是否相同**。

**为什么必须这样**：实测同一起点各排一次 —— **目标值都是 12，而解有 78% 不同**。
CP-SAT 在多个最优解之间选择是不确定的，**"解不同"不代表"行为不等价"**。

### ③ 每张表只有一个属主，跨服务只读

**一般做法**：单体一把梭，或者多服务共享一个库、谁都写。
**这里**：16 张表划成 10 + 6，**铁律 2 写进文档并落到代码**。

**代价是真实的**：新建组织时 academic 不能顺手写 `scheduling_state`，
所以那个状态改成了**懒初始化**。但收益是**拆库时不需要拆事务**。

### ④ 求解器里没有硬编码约束

**一般做法**：约束写在建模代码里。
**这里**：规则有类型、参数 Schema、独立 Handler、硬软两用、编译期去重。

**迁移期的谨慎**：为了不改行为，专门定义了 `RuleSets.legacyEquivalent()`，
并且**把它放在生产代码里、让测试引用它**（而不是反过来）。

### ⑤ 三层并发控制，且"被接管不是错误"

Redis 锁 / 容量槽位 / `job_token` 栅栏各管一件事；
求解与落库之间的 `FOR UPDATE` 重新确认保证了**过期结果不会覆盖新成果**；
而"被接管"走的是**静默丢弃**而不是报错 —— 因为新任务会自己收尾。

### ⑥ 模型指纹守漂移

把 `CpModelProto` 哈希成指纹，**忠实移植必须与 Python 逐字符相同**。
这让"模型变了"这件事**不可能悄悄发生**。

### ⑦ 包归属按"它是什么"，不按"它在哪一层"

几个刻意的例子：

| 类 | 放在 | 为什么 |
|---|---|---|
| `AuthUser` | `scheduling/security` | 它**不是** academic 的 User —— 是 scheduling 的一份**只读视图**（连 `password_hash` 字段都不映射） |
| 7 个 `*Ref` | `scheduling/snapshot` | 按框架，它们的职责是"**冻结并消费**排课输入快照" |
| `RuleSets` | `solver-core/compile` | 它是"装配知识"（有哪些预设），不是注册表（type→实现） |
| `ExportService` | `scheduling/query` | 导出是"课表查看"的另一种形式，不是独立领域 |

**而且 Mapper 就放在领域包里**（`UserMapper` 在 `user/` 而不在 `user/mapper/`）——
所以 `@MapperScan` 用的是 `annotationClass = Mapper.class` 而不是包通配。

### ⑧ 有意偏离都有记录

与 Python 的偏离**只有三处**，且都写进了文档：

1. **token 格式**：Java 用标准 JWT（3 段），Python 是自定义 HMAC（2 段），互不通用。
   理由：token 对前端不透明，格式不参与契约。
2. **列表响应**：`{items,total}` 取代裸数组。理由：Python 侧完全忽略分页参数，
   到 160 班规模会拉几千行。
3. **`scheduling_state` 懒初始化 + `/api/system/*` 归 scheduling**。理由：铁律 2。

**除此之外还有几处"已知不等价"被明确标注**（不是假装没有）：
422 响应缺 `input`/`ctx`；`json_invalid` 的 `loc` 没有数组下标；
`nextVersionNo` 的竞态（Python 也有）；`schedules` 表的清理归属。

### ⑨ 工具与配置共用一份"路由真相"

拆进程后的分流规则，**同时存在于三处并且要求一致**：
`tools/contract-diff/compare.py` 的 `SCHEDULING_PREFIXES`、
`frontend/vite.config.ts` 的 proxy 表、以及文档。
不一致会出现"工具全绿但页面报错"。

> P3 上真网关后，Vite 改回单一 `/api → 8080`，业务代码一行不用动。

### ⑩ 踩坑总结按"主题"分类，且给可操作的信号

`docs/踩坑总结.md`（699 行）不是流水账，而是按
**环境 / Maven / 运行时依赖 / 数据库 / 求解建模 / 验证方法论 / 操作失误 / Web 层契约**
分类，每条都带"现象 → 根因 → 修法 → 教训"。

几个可以直接用的信号：
- 运行时报 `java.lang.Error: Unresolved compilation problems` → 陈旧 class，直接 `mvn clean`
- `mvn package` 成功但源码编译不过 → IDE 写了 `target/classes`，Maven 增量跳过了重编译
- 日志说 401 但实际是 200 → `2>&1` 把 stderr 混进了 stdout

| **`datetime` 时区语义** | 靠 `serverTimezone=UTC` + `UtcTimes.now()`（截断到秒）对齐，逐字段核对还没做 | P1 |
| **鉴权在拆库时的归属** | scheduling 读 academic 的 `users` 表（不违反铁律 2，但是耦合） | P1 |
| **`schedules` 表的清理归属** | academic 删年级/班级时不写它（铁律 2），Python 会级联删。当前该表为空，无可观察差异 | P1 |
| **`nextVersionNo` 的竞态** | 两个管理员同时复制会算出同一个版本号 → 撞唯一约束 | P1 |
| **细粒度作用域（grade/class/…）** | 表已支持，接口**明确拒绝**非 `org` —— "同一条规则在多个 scope 上叠加、冲突时谁赢"的语义还没定 | P2 |
| **最小冲突集只覆盖可配置硬规则** | 不变量（教师不撞课 / 周课时 / 教师上限）去不掉，冲突若来自它们深诊断会一无所获（`note` 如实说明） | P2 |
| **SSE 事件流** | 现在返回普通 JSON 列表。排课几十秒就结束，不值得引入长连接 | P3 |
| **求解中途无法真正中断** | OR-Tools 的 `solve()` 是阻塞调用，取消最坏要等这次求解跑完 | P3 |
| **worker 没进 `docker-compose`** | 目前手工起进程 | P3 |
| **跨服务 Jackson 版本差异** | worker 是 Jackson 3、`JacksonTypeHandler` 是 Jackson 2，靠全局 SNAKE_CASE 对齐 | P3 |
| **`zustand` 是未使用的依赖** | 装了但 0 引用 | P1 |

### 环境怎么起

```powershell
# 1) 起 Docker + MySQL/Redis + academic + scheduling
#    ⚠ 顺序有讲究：academic 必须先起（scheduling 的迁移有 16 个外键指向它）
backend-java\start.cmd

# 2) Python 基准要单独起（它是比对基准，不是被替代品）
backend\venv\Scripts\python.exe -m uvicorn --app-dir backend main:app --port 8000

# 3) 求解进程（P3）—— 不连数据库，只需要知道 scheduling 在哪
java -jar backend-java\orbit-solver-worker\target\orbit-solver-worker-0.1.0-SNAPSHOT.jar

# 4) 确认还是全绿
python tools\contract-diff\compare.py
```

> ⚠ **scheduling 必须在 academic 之后启动** —— 它的建表脚本有 16 个外键指向 academic 的表。
> ⚠ **worker 不起也能跑**：排课会入队并停在 `pending`，前端任务列表会显示"排队中（前面还有 N 个）"。
> 这是有意的 —— 队列让"求解进程没起来"变成一个**可见的状态**，而不是静默失败。
