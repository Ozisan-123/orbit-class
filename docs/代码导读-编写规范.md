# 代码导读 · 编写规范

> 这份文件是给**写导读的人（或 agent）**看的，不是给读者看的。
> 动笔前**必须先读**这一份 + [代码导读.md](代码导读.md)（第 1 册，格式基准）。

## 1. 目标

写「**这个类/这个函数到底在干嘛、谁调它、不这么写会怎样**」。

**与已有文档的分工**（不要重复它们的内容）：
- [架构说明.md](架构说明.md) 讲「为什么这么分、各部分怎么协作」→ **不重复**
- 源码里的 javadoc 讲「为什么有这个类」→ **可以直接引用结论，但不要只抄它**
- **你要补的是：代码逐行在做什么** —— 这是现在唯一缺的东西

## 2. 详细程度

每个类：
1. **一句话定位**
2. **谁调它**（上游是谁、下游调谁）
3. **逐方法展开**

每个方法：
1. **方法签名**
2. **按代码顺序逐段/逐行讲**在做什么
3. **为什么这么写** / **换一种写法会怎样**
4. 有坑就标出来

**保留源码里所有的 `⚠` 陷阱和「实测……」标记** —— 那是这个项目最值钱的部分。
如果把 javadoc 里的 `⚠` 段落漏掉了，这篇导读就是失败的。

## 3. 🔴 四条红线

**① 不许编造。**
看不懂的地方写「（此处未完全理解，代码行为是 X）」，**不要编一个合理但错误的解释**。
项目本身有一条铁律就是「禁止编造」；**虚构的代码解释比没有解释害处大得多**。

**② 必须先读文件再写。**
用 `glob` 列出你负责的文件，**逐个读完**。不许凭类名猜内容。
读文件是必须的成本，不能省。

**③ 一篇不超过 900 行。**
⚠⚠ **这一条是硬性的** —— 上一轮 7 个 agent 全部因为「一次 `write` 输出两千行」
而**在写文档那一刻挂掉** ✗ 宁可少写几个类，也不能让整篇失败。

超了怎么办（按优先级）：
1. 优先保证**主干类**（Service / Controller / Mapper / 算法核心）的逐行深度；
2. 纯 DTO / Entity（record）**用表格批量说明字段与用途**，不必逐行；
3. 在文首写明「哪些类被降级为表格说明」。

**④ 只写你负责的那一个文件。**
不许改动项目里任何其他文件（包括不要"顺手修一下"源码注释）。

## 4. 格式

````markdown
# 代码导读 · N. <模块名>

> 本册范围：<包路径>，共 N 个类。
> 上游：[代码导读.md](代码导读.md)（第 1 册）

## 本模块在系统里的位置
（3-5 行：它解决什么问题、被谁调用、又调谁）

## 阅读顺序建议
（先看哪 2-3 个类能最快建立整体理解，为什么）

---

### N.1 `<ClassName>` —— <一句话定位>

**谁调它**：……

#### `方法签名`

| 行 | 做什么 |
|---|---|
| `xxx` | …… |

（或按代码顺序分点讲；算法密集的类用分点，CRUD 类用表格）

> ⚠ <源码里的坑，或你发现的坑>

---
````

**引用项目内其他文件**用相对路径 markdown 链接，例如：
`[RuleCompiler](../../backend-java/orbit-solver-core/src/main/java/com/orbit/solver/core/compile/RuleCompiler.java)`

## 5. 语言

中文。专业术语保留原文（CP-SAT、`addExactlyOne`、record、`@Transactional`、`FOR UPDATE SKIP LOCKED` 等）。
代码片段照抄原文，不要"顺手美化"。

## 6. 完成后回复什么

**一句话**：文件路径 + 总行数 + 覆盖类数 + （如果有）哪些类被降级为表格说明。
**不要复述内容**。
