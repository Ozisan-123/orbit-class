## 本模块在系统里的位置

P3 之前，"求解"是**进程内起一个线程**。线程版的三个问题治不好（架构说明 §5.8）：
① 进程重启 → 正在跑的任务**凭空消失**；② 求解吃满 CPU 时和 Web 请求抢核；
③ 答不出"排队中吗 / 排第几 / 上次为什么失败"。

P3 把它换成 **持久任务队列 + 独立求解进程**：`orbit-solver-worker`（:8084）不碰数据库，
隔 2 秒向 scheduling 的内部接口 `POST /internal/jobs/claim` 问一次"有没有活"。
`job/` 这个包就是**队列的全部实现**。

```
POST /api/schedule/generate
  → ScheduleRunService.trigger                  四道关卡（4a 册）
  → SnapshotService.freeze(org)                 ★ 入队时就冻结输入
  → JobQueueService.enqueue(...)                ★ 写 pending 一行 + enqueued 事件
--------------------------------------------------------------- 到这里 HTTP 就返回了
  worker: POST /internal/jobs/claim
  → JobQueueService.claim(workerId)             ★ 领单：SKIP LOCKED + 换 token + 抢槽位
  → InternalJobController 回 JobClaimResponse（快照 + 规则 + 租约参数）
  worker: 本地起 CP-SAT 求解，每 15 秒 POST /internal/jobs/{id}/heartbeat
  → JobQueueService.heartbeat → 顺带回传 cancel_requested
  worker: POST /internal/jobs/{id}/result
  → JobQueueService.complete / fail / markCancelled   ★ 全部带 AND job_token = ?
```

**三个必须一起理解的机制**（全在 `schedule_jobs` 这一张表上）：

| 机制 | 做法 | 挡什么 |
|---|---|---|
| **`FOR UPDATE SKIP LOCKED`** | 领单时锁住一行并跳过已被锁的行 | 多 worker 并发领单**不需要任何应用层锁** |
| **`job_token` 栅栏** | **每次领单都换一个新 token**，所有回写带 `AND job_token = ?` | "被接管后又醒过来的旧 worker"提交的东西写不进去 |
| **`lease_until` 租约** | worker 每 15 秒续一次；没续上就允许别人领走 | worker 崩溃/被杀 → 任务**被接管**而不是失踪 |

> ⚠ 这三个机制**任何一个单独拿掉都会静默出错**：去掉 `SKIP LOCKED` → 两 worker 领到同一单
> （表现为"同一份课表落了两版"）；去掉换 token → 旧 worker 复活后覆盖新 worker 的结果；
> 去掉租约 → 一次 `kill -9` 就永久吃掉一份产能。所以本篇把它们放在一起讲。

### 1.1 `ScheduleJobMapper` —— 并发控制的全部落点

**一句话定位**：`schedule_jobs` 表的 Mapper，**整个队列机制的落点** ——
10 条自定义 SQL 就是全部并发控制，**没有一行应用层锁**。

**谁调它**：只有 [`JobQueueService`](#12-jobqueueservice--任务队列业务逻辑)（以及
`JobResultWriter` 调其中的 `lockForRunning`）。它下游只有 MySQL，不调任何别的 Mapper。

**类注释里两条先记下来**：

1. 三个机制（`SKIP LOCKED` / `job_token` / `lease_until`）的 javadoc 就在类头，**逐字保留**：
   换 token 是"幂等的关键，不能省"。
2. > ⚠ 写操作一律用 `@Update`（用 `@Select` 标 UPDATE 拿不到 rowcount，见踩坑总结 B7）
   > ——而本类**全靠 rowcount 判断成败**。

   这条是本类的"读法总纲"：**每一个 `int` 返回值都不是"顺手返回"，而是调用方唯一的判据**。
   下面 8 个写方法里，`int` 的含义统一是「**这次回写是否被接受**」。

#### `lockNextClaimable(LocalDateTime now)` —— ★ 本篇第一重点

```java
@Select("""
        SELECT * FROM schedule_jobs
         WHERE status = 'pending'
            OR (status = 'running' AND lease_until < #{now})
         ORDER BY id
         LIMIT 1
         FOR UPDATE SKIP LOCKED
        """)
ScheduleJobEntity lockNextClaimable(@Param("now") LocalDateTime now);
```

**逐句讲**：

| 片段 | 在做什么 | 为什么必须这么写 |
|---|---|---|
| `SELECT *` | 把整行取回来 | 调用方 `claim` 要用到 `status`（判断是不是接管）、`jobToken`（旧 token，见下）、`organizationId`、`snapshotId`、`attempt`、`maxAttempts` —— 所以不能只 select id |
| `WHERE status = 'pending'`<br>`OR (status = 'running' AND lease_until < #{now})` | **两个分支 = 两种"可做"** | **分支一**：从没跑过的任务，正常排队。**分支二**：已经被领走、但租约过期的任务 —— 它的持有者可能已经崩了。**第二个分支就是"接管"的全部实现**：没有它，一次 `kill -9` 之后那一行会永远停在 `running`，谁也不碰它 |
| `lease_until < #{now}` 严格小于 | 租约到点即可被抢 | `now` 由 `JobQueueService.claim` 用 `UtcTimes.now()` 传入（秒级截断的 UTC），**不是** SQL 里的 `NOW()` —— 这样"过期"的口径由应用统一决定，与库里时间格式对齐（见第 1 册 `UtcTimes`） |
| `ORDER BY id` | **FIFO**（先入先出） | ① `id` 是自增主键，唯一的入队顺序；② 它**同时决定了"排队位置"的口径** —— `JobQueueService.queuePosition` 算名次用的也是 `id` 顺序（`WHERE status='pending' AND id < ?`）。**两处口径不一致，"你前面还有 3 个"就会显示成错的** |
| `LIMIT 1` | 一次只领一单 | worker 是"领一单 → 算完 → 再来领"的循环，不需要批量；而且 `FOR UPDATE SKIP LOCKED` 锁的粒度是行，批量领会让一整个事务持锁更久 |
| `FOR UPDATE SKIP LOCKED` | **对命中的那一行加排他行锁**；如果那行已经被别的未提交事务锁住，**不等待、直接跳过，去看下一行** | 见下面单独一节 |

##### 为什么 `FOR UPDATE SKIP LOCKED` 让并发领单不需要任何应用层锁

不用它的话，两个 worker 会这样撞车：

```
worker A: SELECT ... WHERE status='pending' ORDER BY id LIMIT 1  → 拿到 #7
worker B: SELECT ... WHERE status='pending' ORDER BY id LIMIT 1  → 也拿到 #7   ✗ 同一单给两个人
```

两个人都"先读后写"，读的时候都还是 `pending` —— 这是经典的检查-使用竞态。
常见的补法是加 Redis 锁或 `SELECT ... FOR UPDATE`：

- **加 `FOR UPDATE` 但不加 `SKIP LOCKED`**：A 锁住 #7，B 的 `SELECT ... FOR UPDATE` 会**阻塞等待**。
  结果不是重复领单，而是**所有 worker 串行化**成一条队伍，"并发领单"退化成"排队领单"。
  更糟的是 B 等到 A 提交后**会拿到刚刚变成 `running` 的那一行**吗？不会 —— 但 B 白等了一整个事务的时间，
  吞吐与 worker 数无关。
- **加 Redis 锁**：又引入一个新的失效点（锁没人释放 → 全系统停止领单），而且它和任务行**不在同一个事务域**，
  违背架构说明 §5.8 引用的方案 §6.2 原话：**任务状态必须与 `job_token` 栅栏在同一事务域**。

`SKIP LOCKED` 的做法是：**被锁的行直接当作"不存在"**。
于是 A 拿到 #7 并锁住它，B 的同一句 SQL **看都不看 #7**，直接命中 #8 ——
两个 worker 各拿一单、都不阻塞、**谁也不需要知道对方存在**。

而且关键在于：这一步是 **`SELECT ... FOR UPDATE`，它本身就在写事务里**。
`claim` 方法带 `@Transactional`，紧接着的 `markRunning`（把 `status` 改成 `running`）
在**同一个事务**里提交。所以"选中这一行"和"占住这一行"之间没有任何窗口 ——
**这就是"用数据库当队列"的全部价值**：拿数据库的行锁换掉一个分布式锁组件。

> ⚠ 类注释里那条警告是硬约束：**必须在事务里调用**，否则 `FOR UPDATE` 的锁在语句级事务结束
> 就释放了，两个 worker 会领到同一单。`JobQueueService.claim` 上的 `@Transactional` 不是装饰。

##### 拿不到行时 `null` 的含义

`lockNextClaimable` 返回 `null` **只有一种含义：当前没有"可做"的任务**。
它**不是错误** —— 队列空了、或者所有 `pending` 行正被别的 worker 锁着（还没提交），都会是 `null`。

调用方的处理是刻意设计的（详见 `claim`）：
`claim` 返回 `null` → `InternalJobController.claim` 回 **204 No Content**（不是 404），
worker 隔 2 秒再来问。架构说明 §5.8 的第二个设计决定就是这个：
**"没活干"是正常状态，不是错误。**

**还要注意 `null` 时锁的副作用**：这一句 `FOR UPDATE` 没有命中行 → 没有加锁（gap lock 的细节
依赖隔离级别与索引选择，此处以"没有命中行就没有行锁"为准）；
而 `claim` 在返回 `null` 前**什么都不写**，所以事务提交时没有任何状态变化 ——
**队列空不会有任何写入**。

> ⚠ **本类的索引与查询形状**：`V3__schedule_jobs.sql` 建了
> `KEY ix_schedule_jobs_queue (status, id)`，注释写的是
> `WHERE status='pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED`。
> 而实际的 SQL 是**两个分支的 `OR`**（`status='pending' OR (status='running' AND lease_until < ?)`）。
> MySQL 的优化器**对 `OR` 有专门的索引合并（index merge）策略**，
> 在何种形状下走哪一种计划、`SKIP LOCKED` 与 `ORDER BY` 的配合是否仍然高效，
> **本项目尚未实测**（此处未完全理解，代码行为是：SQL 正确地返回"最小编号的待办行"，
> 至于执行计划与锁范围，需要用 `EXPLAIN` 在真实数据上确认）。
> 如果将来出现"领单慢"或"领单互相阻塞"，**这里是第一个该看的地方**。

#### `lockForRunning(id, jobToken)` —— 结果落库前的"重新确认"

```java
@Select("""
        SELECT * FROM schedule_jobs
         WHERE id = #{id} AND job_token = #{jobToken} AND status = 'running'
         FOR UPDATE
        """)
ScheduleJobEntity lockForRunning(@Param("id") long id, @Param("jobToken") String jobToken);
```

**逐句讲**：

| 片段 | 做什么 |
|---|---|
| `WHERE id = ? AND job_token = ? AND status = 'running'` | 三个条件**缺一不可**：行存在、**还是我的**（token 没被换）、**还在跑**（没被取消/终结） |
| `FOR UPDATE` | 锁住这一行，**一直持到调用方的事务提交** —— 让它和"写课表版本"在同一个事务里原子；`SKIP LOCKED` 在这里**故意不加**：这里不是抢活，而是"确认归属"，抢不到就该丢弃结果，不需要去跳下一行 |

**返回 `null` 的含义**：已被接管 / 已终结 → 调用方应**丢弃结果**（不是报错）。
架构说明 §5.8 的第五个特色「被接管不是错误」说的就是它：
走**静默丢弃**而不是抛异常，因为新任务会自己收尾。

**为什么需要这一步（P1 就有同一套路）**：从"worker 交回结果"到"结果写进课表版本"之间，
任务可能已经被别人接管。如果不重新确认，旧 worker 的过期结果会**覆盖**新 worker 的成果。
类注释点明了它与 P1 的关系：

> ⚠ 这一步与 P1 的 `SchedulingStateMapper.lockForRunning` 是同一个套路，
> 只是判据从"组织级状态行"换成了"任务行 + token" —— 粒度更细，
> 而且多个任务可以并存（不同组织）。

**与 `AND job_token = ?` 的分工**：本方法（`SELECT ... FOR UPDATE`）负责**锁**，
`complete` / `fail` / `markCancelled` 里的 `AND job_token = ?` 负责**判**。
`JobResultWriter` 是两者一起用的地方。

#### `markRunning(...)` —— ★ 本篇第二重点

```java
@Update("""
        UPDATE schedule_jobs
           SET status = 'running',
               job_token = #{jobToken},
               worker_id = #{workerId},
               attempt = attempt + 1,
               lease_until = #{leaseUntil},
               heartbeat_at = #{now},
               started_at = COALESCE(started_at, #{now}),
               finished_at = NULL,
               last_error = NULL
         WHERE id = #{id}
           AND status IN ('pending', 'running')
        """)
int markRunning(@Param("id") long id, @Param("jobToken") String jobToken,
                @Param("workerId") String workerId,
                @Param("leaseUntil") LocalDateTime leaseUntil, @Param("now") LocalDateTime now);
```

**8 个 SET 逐个讲**：

| SET | 值 | 为什么 |
|---|---|---|
| `status = 'running'` | 常量 | 状态机 `pending → running`；接管时是 `running → running`（换了持有者） |
| `job_token = #{jobToken}` | **一个全新的随机 token** | ★ 见下面单独一节 |
| `worker_id = #{workerId}` | 领单的 worker | 只为**可观测性**（事件流、日志、"谁在跑"），**不参与任何判据** —— 判据一律是 token。⚠ 别看到 worker_id 就以为"同一 worker 会拿回自己的单"：它不会 |
| `attempt = attempt + 1` | **在 SQL 里加**，不是"读出来 +1 再写" | ★ 见下面 |
| `lease_until = #{leaseUntil}` | `now + leaseSeconds`（默认 300 秒） | 租约起点。`leaseSeconds` 来自 `@Value("${orbit.scheduling.lease-seconds:300}")`，且被 `Math.max(120, ...)` 兜底 —— 与容量槽位租约一致，**不允许短于 120 秒**（`JobQueueService` 构造器注释） |
| `heartbeat_at = #{now}` | 领单即算一次心跳 | 否则"刚领走、还没发第一次心跳"的任务在监控上看是"心跳时间是很久以前" |
| `started_at = COALESCE(started_at, #{now})` | **只在第一次领单时写** | `COALESCE` 保留最早的一次 —— 接管不该把"这个任务什么时候开始跑的"改晚。于是 `started_at→finished_at` 是**这个任务的总时长**（含所有 attempt），不是最后一次 attempt 的时长 |
| `finished_at = NULL` | 清空 | 接管一个曾经终结过的行不可能发生（`WHERE` 已排除），这里是**幂等防线**：万一状态被人手工改过，重领一次不会留下"已完成时间"这种自相矛盾的行 |
| `last_error = NULL` | 清空 | 上一次 attempt 的错误信息不该出现在这一次的记录里；新的错误会由 `fail` 写回。⚠ 反过来说：**`last_error` 只有"最近一次"**，历史错误要去 `schedule_job_events` 里看 |

**`WHERE id = ? AND status IN ('pending', 'running')`**：

类注释写明了理由 —— **防止把一个已经被取消/完成的任务重新拉起来**。
注意它**不**带 `job_token` 条件（这是唯一一个不带 token 的写方法）：

- 领单时我们还**没有**新 token 的写入权（token 正是这一步写进去的），所以判不了 token；
- 但此时我们**持有着 `lockNextClaimable` 拿到的行锁**，别的 worker 进不来；
- 真正可能改变状态的是**用户的取消**（`requestCancel` 是另一条独立事务）：
  它把 `cancel_requested` 置 true 但**不改 status**（`status IN ('pending','running')`），
  所以这里的 `IN ('pending','running')` 挡不住它 —— 这是**故意的**：
  取消是"请求"，worker 领到后通过心跳响应看到 `cancel_requested=true` 再自己收手
  （`isCancelRequested`）。见 `claim` 与 `markCancelled`。
- 它**挡得住**的是：`cancelPending`（pending → cancelled）、`requeue`、
  以及任何别的把行推进终态的路径。行数 0 = 别硬来。

##### 为什么每次领单都要换一个新 `job_token` —— 幂等的全部秘密

先说 token 是什么：`newJobToken()` = `SecureRandom` 取 24 字节 → `HexFormat` 成
**48 个十六进制字符**，对应 Python 的 `secrets.token_hex(24)`。
建表时 `UNIQUE KEY uq_schedule_jobs_token (job_token)` —— **全局唯一**，
所以一个 token 值能唯一确定"哪一行、哪一次持有"。

**不换 token 会怎样**（这是最容易漏的一条）：

```
job #7 第一次领单：token = T
worker A 被 kill -9 → 租约到期
worker B 接管 #7：如果 token 仍然是 T    ✗
worker A 复活（其实没死，只是长时间 GC 卡住），交回结果：
        UPDATE schedule_jobs SET status='done', ... WHERE id=7 AND job_token=T AND status='running'
        → 命中！A 的过期结果把 B 正在做的事标成"完成"          ✗
        两个 worker 同时对同一单写结果 → 版本可能落两版        ✗
```

**换了 token 之后**：B 领单时 token 变成 T′，A 手里还是 T。
A 之后提交的任何东西（心跳、完成、失败、取消）都带 `AND job_token = T` → **rowcount 0** →
写不进去。A 的心跳也会立刻拿到 `ok=false`，于是它**会在下一次心跳时自己停下来**
（`InternalJobController.heartbeat` 的 javadoc：`ok=false` 表示 token 已失效，
worker 应当**立即停止求解** —— 继续算下去的结果也不会被接受）。

所以换 token 这一个动作同时解决三件事：
① 旧 worker 的**结果**写不进去；② 旧 worker 的**心跳**失效 → 它自己收手；
③ 每个 attempt 的"结果归属"都是明确的，"一单只被一个人做"这条不变量
在**接管场景**下也继续成立。类注释的原话：**换 token 是故意的**。

> ⚠ 还有一个容易忽略的推论：**新 token 在 `markRunning` 之前就生成了**。
> `claim` 里 `String token = newJobToken();` 出现在 `capacityService.acquire(org, token)` **之前**
> —— 因为容量槽位也是**按 token 认持有者**的（`schedule_worker_slots.job_token`）。
> 一次领单只有**一个** token 同时代表"占着哪个槽位"和"哪次持有任务"。

##### `attempt` 怎么加

- `attempt = attempt + 1` **写在 SQL 里**，而不是"Java 读出来 1、加 1、写 2"。
  理由同 `lockForWaiting`/`UtcTimes` 那一类问题的思路：**所有状态迁移都在数据库里以条件 UPDATE 完成**，
  Java 侧只负责发起和判断 rowcount。如果先读后写，两个 worker 并发领单时后写的那个会覆盖，
  `attempt` 就丢计数了（虽然 `SKIP LOCKED` 已让这种并发不存在，但**不依赖"另一处机制刚好挡住了"**更稳）。
- 建表默认 `attempt int NOT NULL DEFAULT 0`；`enqueue` 显式 `setAttempt(0)`。
  所以**第一次领单后 attempt = 1**（不是 0），失败文案里说的"attempt 2"指第二次尝试。
- `claim` 回给 worker 的 `attempt` 是**在 Java 里自己算的**：
  `int attempt = (job.getAttempt() == null ? 0 : job.getAttempt()) + 1;`
  —— 用的是 `lockNextClaimable` 取回的**旧**值（`markRunning` 之后没有再 select），
  三元判空是因为 `BaseMapper` 反序列化理论上可能给 null。**两边算的是同一个数**，
  但这是"重复计算"：SQL 里算一次、Java 里算一次。改 `markRunning` 的加法时**必须同时改这里**。
- `attempt` 与 `max_attempts`（默认 3）的比较**发生在 `fail` 里**，不在领单里：
  领单不拒绝"已经试满"的任务，因为**能不能重试是失败那一刻的判定**（见 `fail`）。
- 人工 `retry` 会把 `attempt` **归零**（`requeue` 的 SET 里），所以人工重试是"重新给 3 次机会"。

##### `lease_until` 怎么算

`LocalDateTime leaseUntil = now.plusSeconds(leaseSeconds);`（在 `claim` 里算好传进来）。
`now` 是 `UtcTimes.now()`：**UTC + 截断到秒**。
于是 SQL 里的比较 `lease_until < #{now}` 与 Java 侧的时间是**同一个基准、同一个精度** ——
这正是第 1 册里 `UtcTimes` 存在的理由：
如果一边写东八区、一边比 UTC，租约会差 8 小时（本项目的"最难查的那一类 bug"）。

`leaseSeconds` 默认 300 秒，而心跳间隔默认 15 秒（`heartbeat-seconds`）——
**留了 20 倍余量**：worker 卡个十几秒（GC、慢 IO）不会立刻被判定死亡并发起接管。

##### `int` 返回值（rowcount）的含义

| 返回 | 含义 | 调用方（`claim`）怎么做 |
|---|---|---|
| `1` | 占单成功 | 继续：写事件、取快照、返回 `JobClaimResponse` |
| `0` | 状态在"选中"和"回写"之间被改动 → **当作没领到** | `log.warn` + `capacityService.release(slotId, token)`（把自己刚抢的槽位还回去）+ 返回 `null` |

`claim` 的注释说：**理论上不会发生**（行还锁在我们手里），但真发生了就
**当作没领到，别硬来**。这是这个项目反复出现的风格：**异常路径绝不假装成功**。

#### `heartbeat(id, jobToken, leaseUntil, now, progress)` —— 续租 + 带进度

```java
UPDATE schedule_jobs
   SET lease_until = #{leaseUntil}, heartbeat_at = #{now}, progress = #{progress}
 WHERE id = #{id} AND job_token = #{jobToken} AND status = 'running'
```

**逐句**：

| 片段 | 做什么 |
|---|---|
| `SET lease_until = now + leaseSeconds` | **把租约往后推**。这一步是"我还活着"的唯一证据 —— 也是接管机制能工作的前提：只有真的停止续租，租约才会过期 |
| `SET heartbeat_at = now` | 监控与运维用（"最后一次活着是什么时候"）。⚠ 它与 `lease_until` 信息重复，但口径不同：断点排查时看 `heartbeat_at` 的**间隔**是否均匀 |
| `SET progress = #{progress}` | 进度百分比（0-100）。由 `JobQueueService.heartbeat` 用 `Math.max(0, Math.min(100, progress))` **钳位后**传入 —— 用户在列表页看到的进度条不会出现 137% |
| `WHERE ... AND job_token = ? AND status = 'running'` | **token 不匹配 → rowcount 0 → 上层停止心跳**（javadoc 原话）。三个条件缺一不可：被别人接管了（token 换了）或任务已被取消/终结（status 不是 running），就不该再续租 |

**返回值**：`int` → `JobQueueService.heartbeat` 转成 `boolean`，
`InternalJobController` 再包成 `{"ok": false}`。

> ⚠ **`progress` 的口径是"估算"不是"真实"**：javadoc 在 `HeartbeatRequest` 里写明
> "OR-Tools 不直接给百分比，worker 会用『已耗时 / 时限』估算"。
> **本项目未在 `job/` 包里记录 `heartbeat` 事件的写入**（`ScheduleJobEventEntity.HEARTBEAT`
> 常量已定义，但全项目 `Grep HEARTBEAT` 只命中这个常量定义本身）。
> 建表脚本里却写着"看 heartbeat 事件的时间间隔"这一用途 ——
> **这是注释/常量与实际写入不一致的地方，不是本篇能解释的行为**（此处未完全理解，
> 代码行为是：心跳只更新行上的两个时间列，不写事件表）。
> 代价其实是**刻意的**：心跳每 15 秒一次，若每次写事件，`schedule_job_events` 会被心跳淹没。

#### `complete(...)` —— 完成：写摘要 + 置 done

```java
UPDATE schedule_jobs
   SET status = 'done', progress = 100,
       solver_status = #{solverStatus}, model_fingerprint = #{modelFingerprint},
       objective_value = #{objectiveValue}, version_id = #{versionId},
       entry_count = #{entryCount}, finished_at = #{now}, lease_until = NULL
 WHERE id = #{id} AND job_token = #{jobToken} AND status = 'running'
```

**SET 逐个**：

| SET | 含义 |
|---|---|
| `status='done'`、`progress=100` | 终态。进度直接钉到 100，不信任最后一次心跳的估算值 |
| `solver_status` | OR-Tools 的求解状态字符串（`OPTIMAL` / `FEASIBLE` / …） |
| `model_fingerprint` | **模型指纹**：把 `CpModelProto` 哈希成的一个值（架构说明 §6⑥） |
| `objective_value` | 软约束罚分（可选） |
| `version_id` / `entry_count` | 落库的课表版本与明细条数 |
| `finished_at = #{now}` | 终态时间 |
| `lease_until = NULL` | ⚠ **清空租约**。不清的话这一行是 `done` 但带着一个未来时间 —— 虽然 `lockNextClaimable` 只挑 `pending` / 过期 `running`（`done` 挑不到），但**留着会误导所有"按 lease_until 排查"的人**，也让"任务已终结还占着租约"成为脏数据 |

**为什么这些摘要字段存在**：`ScheduleJobEntity` 的注释说它们"诊断与列表页用，
**不必再去读版本表**"。列表页要显示"目标值 12、条目 480"，如果每次都要 join 版本表就重了。

**`WHERE` 三条件**（`id` + `job_token` + `status='running'`）：见下面统一那一节。

**返回值语义**：`1` = 采纳；`0` = **结果被丢弃，不是错误**
（javadoc 原话："token 不匹配 → 结果被丢弃（不报错，那是正确的）"）。
`JobQueueService.complete` 在 `0` 时打 `log.warn` 并返回 `false`，
`InternalJobController` 转成 `accepted=false` + `reason`。

#### `fail(...)` —— 失败：可重试就回 pending，否则 failed

```java
<script>
UPDATE schedule_jobs
   SET status = CASE WHEN #{retryable} = TRUE AND attempt &lt; max_attempts
                     THEN 'pending' ELSE 'failed' END,
       last_error = #{error}, solver_status = #{solverStatus},
       finished_at = CASE WHEN #{retryable} = TRUE AND attempt &lt; max_attempts
                          THEN NULL ELSE #{now} END,
       lease_until = NULL
 WHERE id = #{id} AND job_token = #{jobToken} AND status = 'running'
</script>
```

**逐句**：

| 片段 | 做什么 |
|---|---|
| `<script>` 包裹 + `&lt;` | MyBatis 的动态 SQL 需要 `<script>` 标签才解析 XML 实体；`&lt;` 就是 `<`。**这里没有 `<if>`** —— 分叉是用 SQL 的 `CASE WHEN` 做的，因为两个字段（`status` 与 `finished_at`）必须**同时**按同一条件取值，用 `<if>` 要写两遍且容易写歪 |
| `CASE WHEN retryable AND attempt < max_attempts` | **两条收场**：<br>• 真 → `status='pending'`：**退回队列**，别的 worker 立刻能领走（`lockNextClaimable` 第一个分支命中）。token 会在**下次领单时被换掉**，所以旧 token 也同时作废<br>• 假 → `status='failed'`：终态，等人工 `retry` |
| `attempt < max_attempts` | 用的是**行上的当前值**（已经被上一次 `markRunning` 加过 1）。例：`max_attempts=3`，第 3 次 attempt 失败时 `3 < 3` 为假 → `failed`。所以"最多试 3 次"成立 |
| `finished_at = CASE ... THEN NULL ELSE #{now}` | **退回队列时必须清空 `finished_at`** —— 否则会出现"pending 但已经 finished"的自相矛盾行。这与 `markRunning` 里 `finished_at = NULL` 是同一道防线 |
| `lease_until = NULL` | 两种收场都清空：退回队列的要让"别的 worker 能领"（其实 `pending` 本来就够，但清掉更干净）；`failed` 的更不该留 |
| `last_error = #{error}` | 失败原因。⚠ 建表是 `varchar(500)`，而 `JobQueueService.fail` 传进来之前做了 `truncate(error, 500)` —— **两个 500 必须一致**，否则长错误串会撞截断（MySQL 严格模式下会报错）。事件里的 detail 另用 `truncate(error, 300)` |
| `solver_status = #{solverStatus}` | 失败也可能有求解器状态（例如 `INFEASIBLE`、`UNKNOWN`） |
| `WHERE id AND job_token AND status='running'` | 同 `complete` |

> ⚠ **`retryable` 与"取消"是两件事**（架构说明 §5.8 的第三个设计决定）：
> 失败是"这次没排出来"（可能该重试），取消是"用户不想排了"（**绝不该重试**）。
> 如果混成一个字段，一次用户主动取消会被重新拉起来跑。
> 所以 `JobResultRequest` 里是两个字段，`InternalJobController.result` 里是**两个分支**：
> `cancelled=true` 优先判（走 `markCancelled`），然后才判 `error`（走 `fail`）。
> 判 `error` 时 `retryable` 由请求里的 `retryable` 字段决定。

#### `requestCancel(id, organizationId)` —— 打标记，不动状态

```java
UPDATE schedule_jobs SET cancel_requested = TRUE
 WHERE id = #{id} AND organization_id = #{organizationId}
   AND status IN ('pending', 'running')
```

- **只设一个标记**，`status` 一点都不改：正在跑的 worker **不碰数据库**，
  它只能从**心跳的响应**里知道"用户点了取消"（`HeartbeatRequest` 的注释：
  "这是取消请求到达 worker 的唯一通道"）。
- `WHERE` 带 `organization_id`：**多租户隔离**。用户只能取消自己学校的任务。
- `status IN ('pending','running')`：对已终结的任务置标记无意义。rowcount 0 表示"没什么可取消的"。
- **幂等**：重复调用再置一次 TRUE，无害。
- ⚠ 它**不是**终态路径：对外状态（`scheduling_state`）在这一步**不动**。
  真正的收尾发生在 worker 认领取消之后（`markCancelled`）——
  见 `JobQueueService.cancel` 里对 `running` 分支的处理。

#### `cancelPending(id, organizationId, now)` —— 直接终结还没被领走的任务

```java
UPDATE schedule_jobs
   SET status = 'cancelled', finished_at = #{now}, lease_until = NULL
 WHERE id = #{id} AND organization_id = #{organizationId} AND status = 'pending'
```

- **只有 `pending` 才允许直接终结**（javadoc 原话）。`running` 的行不在这里动 ——
  它可能已经算到一半，直接改状态会让 worker 的回写出现"上面写着 running 的活儿没了"，
  失败/完成的语义都会乱。所以 `pending` 走这条、`running` 走 `requestCancel`。
- `AND status = 'pending'` 同时是一个 **CAS**：如果这一瞬间 worker 刚好领走了它，
  rowcount 0，状态保持 `running` —— 于是 `JobQueueService.cancel` 已经做了这件事：
  它在调 `cancelPending` **之前**先 `requireJob` 读过一次状态（见 `cancel` 的分支），
  但**真正的竞态由这里的 WHERE 兜住**。⚠ 注意 `JobQueueService.cancel` **不检查**
  `cancelPending` 的返回值 —— 如果恰好被领走，`cancel` 仍会写一条 `cancelled` 事件并
  把对外状态置 idle，**而任务其实还在跑**（此处未完全理解设计意图，代码行为如上；
>  这属于"窗口极窄但真实存在"的竞态，本项目未在注释里记录它）。
- `finished_at = now` + `lease_until = NULL`：终态就该有终态时间、不该留租约。

#### `markCancelled(id, jobToken, now)` —— worker 察觉取消后主动交还

```java
UPDATE schedule_jobs
   SET status = 'cancelled', finished_at = #{now}, lease_until = NULL
 WHERE id = #{id} AND job_token = #{jobToken} AND status = 'running'
```

- 调用者是**正在跑的 worker**：它下一次心跳看到 `cancel_requested=true`，
  于是**主动停止求解**并 `POST /internal/jobs/{id}/result` 带上 `cancelled=true`。
- 与 `cancelPending` 的差别就在 `WHERE`：`cancelPending` 是**用户**发的（带 `organization_id`，
  只对 `pending`）；`markCancelled` 是 **worker** 发的（带 `job_token`，只对 `running`）。
  **两个入口、两种身份、两种允许的状态** —— 这是刻意分开的。
- `status='running'` 这个条件意味着：**已经被接管的任务不能自己标记取消**（正确：
  它已经不是持有者了，`job_token` 也换了，0 行）。
- javadoc 里说"（回到 pending 由上层置 cancelled）"—— **实际 SQL 是直接写 `cancelled`**，
  没有回 pending 这一步。这是**注释与代码不一致**的地方（此处未完全理解该 javadoc 的意图，
  代码行为是：一次 UPDATE 直接进终态）。

#### `requeue(id, organizationId)` —— 人工重试

```java
UPDATE schedule_jobs
   SET status='pending', attempt=0, progress=0, cancel_requested=FALSE,
       last_error=NULL, worker_id=NULL, lease_until=NULL, started_at=NULL, finished_at=NULL
 WHERE id = #{id} AND organization_id = #{organizationId} AND status IN ('failed','cancelled')
```

- 它是**唯一**一个把行从终态搬回 `pending` 的语句，**只给人工用**
  （`JobQueueService.retry`，对应运维界面上的"重试"按钮）。
- **9 个 SET 是一次彻底的"回到初始状态"**：连 `attempt` 都归零（重新给满 `max_attempts` 次机会）、
  `cancel_requested` 复位、`worker_id` / `started_at` / `finished_at` / `lease_until` 全清。
  ⚠ 它**不换 `job_token`**：token 会在下次 `markRunning` 时被换掉，
  所以"重试期间旧 token 也无效"这一点由领单路径保证。**这里不必也不该自己生成 token**
  （那需要应用层提供随机值，而 Mapper 只该写 SQL）。
- `WHERE status IN ('failed','cancelled')`：**`done` 的任务不能重试**（那会凭空多出一版课表）。
  `JobQueueService.retry` 用 rowcount != 1 抛
  `BusinessException.badRequest("只有失败或已取消的任务可以重试")`。
- `organization_id` 同样是多租户隔离。

---

#### 统一回答：**为什么所有回写都要带 `AND job_token = ?`**

把 8 个写方法按"带不带 token"排一下：

| 方法 | 带 `job_token` | 带 `status` 条件 | 身份 |
|---|---|---|---|
| `markRunning` | ✗（token 是它写进去的） | `IN ('pending','running')` | 持有行锁的领单者 |
| `lockForRunning` | ✓ | `='running'` | 已有 token 的 worker |
| `heartbeat` | ✓ | `='running'` | 同上 |
| `complete` | ✓ | `='running'` | 同上 |
| `fail` | ✓ | `='running'` | 同上 |
| `markCancelled` | ✓ | `='running'` | 同上 |
| `requestCancel` | ✗ | `IN ('pending','running')` + org | **用户**（按租户隔离，不是按持有者） |
| `cancelPending` | ✗ | `='pending'` + org | **用户** |
| `requeue` | ✗ | `IN ('failed','cancelled')` + org | **用户/运维** |

规律很清楚：**"worker 回写"一律用 token 认身份；"用户操作"一律用 `organization_id` 认租户**。
用户操作不能带 token —— 因为用户**不可能知道 token**（它是 worker 的秘密）；
也不该带，因为用户要取消的正是"不管谁在跑的那个任务"。

`job_token` 是**栅栏（fencing token）**的经典用法：
每次所有权变更就递增/更换一个值，**旧所有者的写请求全部失效**。
这里的妙处是它同时是**数据库里的一个普通列**，
所以"换所有权"和"作废旧所有权"是同一次 UPDATE 的两个效果 —— 原子、无额外组件。

**CAS 失败时返回什么**（这是本篇要回答的第二个问题）：

| 层 | CAS 失败（rowcount 0）的表现 |
|---|---|
| Mapper | 返回 `int 0` |
| `JobQueueService.heartbeat` | 返回 `false` → 控制器 `{"ok": false}` → **worker 立即停止求解** |
| `JobQueueService.complete` | `log.warn("完成任务被拒（token 已失效）")` → `false` → `{"accepted": false, "reason": "..."}` → **worker 不报错、不重试** |
| `JobQueueService.fail` | `log.warn("标记失败被拒（token 已失效）")` → `false` → `{"failed": false}` → 同样静默 |
| `JobQueueService.markCancelled` | `false` → `{"accepted": false, "cancelled": true}` |
| `JobQueueService.claim` 内 `markRunning` 0 | 释放槽位 + 返回 `null` → 204 |

**一句话**：CAS 失败**不是异常，是"你已经不是主人了"** ——
所有失败路径都返回一个**布尔假值**而不是抛异常。
架构说明 §5.8 第五个特色把这件事写成设计原则：
「"被接管"走的是**静默丢弃**而不是报错 —— 因为新任务会自己收尾」。

### 1.2 `JobQueueService` —— 任务队列业务逻辑

**一句话定位**：队列的**全部业务逻辑** —— 入队、领单、心跳、完成/失败、取消、重试、查询。
它是 `ScheduleJobMapper` 的唯一主要调用者，也是内部接口
`InternalJobController` 的下游。

**谁调它**：

| 上游 | 调什么 |
|---|---|
| `ScheduleRunService.trigger`（4a 册） | `enqueue(org, userId, ruleSetHash, snapshotId, maxAttempts)` |
| `InternalJobController.claim` | `claim(workerId)` |
| `InternalJobController.heartbeat` | `heartbeat` + `isCancelRequested` |
| `InternalJobController.result` | `markCancelled` / `fail` / `complete`（经 `JobResultWriter`） |
| `JobController`（用户接口） | `list` / `listByPage` / `requireJob` / `events` / `queuePosition` / `cancel` / `retry` |
| `DiagnosisHook` / P2 诊断 | `rulesOf` |

**它下游调谁**：`ScheduleJobMapper`、`ScheduleJobEventMapper`、`SnapshotService`、
`RuleSetService`、`CapacityService`、`ScheduleWorkerSlotMapper`、`ScheduleStateService`。

#### 构造器 —— 依赖与两个被钳位的配置

```java
public JobQueueService(..., @Value("${orbit.scheduling.lease-seconds:300}") int leaseSeconds,
                       @Value("${orbit.scheduling.heartbeat-seconds:15}") int heartbeatSeconds)
```

- 7 个依赖全是**构造器注入**（无 `@Autowired` 字段注入）—— 与全项目一致。
- 两个配置项都做了**下界钳位**：
  `this.leaseSeconds = Math.max(120, leaseSeconds);`
  `this.heartbeatSeconds = Math.max(1, heartbeatSeconds);`
  注释只解释了租约那条：**与容量槽位一致：租约不允许短于 120 秒**。
  （把租约配成 5 秒会让 worker 频繁被误判死亡 → 反复接管 → 同一个任务来回重启。）
  `heartbeatSeconds` 只钳下界 1，**没有上界校验**：配成 10000 秒会直接导致接管
  （晚于租约），这是一个**配置层面的坑**。
- `leaseSeconds()` / `heartbeatSeconds()` 两个 getter **存在的唯一原因**是
  把它们塞进 `JobClaimResponse` 告诉 worker"你该多久发一次心跳、租约多长"。

#### `enqueue(organizationId, createdByUserId, ruleSetHash, snapshotId, maxAttempts)`

```java
@Transactional
public ScheduleJobEntity enqueue(long organizationId, Long createdByUserId,
                                 String ruleSetHash, long snapshotId, int maxAttempts)
```

**逐行**：

| 行 | 做什么 |
|---|---|
| `new ScheduleJobEntity()` + 一系列 set | 手工构造一行。**没有用 MyBatis-Plus 的自动填充** —— `created_at` 显式 `setCreatedAt(UtcTimes.now())`，`status` 显式 `"pending"`，`attempt=0`、`progress=0`、`cancelRequested=false` |
| `job.setJobToken(newJobToken())` | ⚠ **入队就写一个 token**，但它是**占位用的**：`markRunning` 立刻会换掉它。为什么要先写？因为建表 `job_token varchar(64) NOT NULL` **且 UNIQUE** —— 不能留 null。所以入队时的 token 是一个"谁也不知道的随机值"，**它从生成那一刻起就注定无效**。这比"留空再由领单填"更安全：任何情况下表里都有一行合法的唯一 token |
| `job.setSnapshotId(snapshotId)` | 指向**入队前刚冻结**的快照（`ScheduleRunService` 第 137 行 `snapshotService.freeze` 的返回值） |
| `jobMapper.insert(job)` | 插入。`@TableId(type = IdType.AUTO)` → 插入后 `job.getId()` 由 MyBatis-Plus 回填（主键回写），所以下面能用 `job.getId()` |
| `eventMapper.insert(ScheduleJobEventEntity.of(org, job.getId(), ENQUEUED, null, 0, "任务入队"))` | 事件流的**第一条**。`workerId` 传 `null`（还没有 worker）、`attempt` 传 `0` |
| `log.info(...)` | 日志里把 hash 截到最多 12 字符：`ruleSetHash.substring(0, Math.min(12, ruleSetHash.length()))` —— **先判空再判长**，因为 `ruleSetHash` 在建表里是 `NOT NULL` 但 Java 侧签名允许 null（`? "-"` 分支）。这种"防御性的字符串截断"在本项目里出现多次（`claim` 里的 `previousToken.substring(0, 8)` 同理） |

**为什么整个方法是 `@Transactional`**：任务行与 `enqueued` 事件必须一起成功或一起失败。
如果事件插失败而任务留下，事件流就不完整（"这个任务从哪来的"没有记录）。

> ⚠ **快照在入队时冻结，不是领单时**（方法 javadoc 原话）：
> "因为『用户点下按钮的那一刻看到的数据』才是他要排的那份"。
> 但要精确地说：**冻结发生在 `enqueue` 之前**（`ScheduleRunService` 先 `freeze` 再 `enqueue`），
> 而 `enqueue` 只负责把 `snapshotId` 记下来。
> 这个顺序是关键：如果反过来（先入队再冻结），中间的时间差里教务数据被改，
> 排出来的就不是用户看到的那份。**而且冻结失败必须让入队失败** ——
> 4a 册记录了这个 try/catch：冻结抛异常时要把对外状态置 failed 并释放 Redis 锁。

**返回**：`ScheduleJobEntity`（含回填的 id）→ `ScheduleRunService` 用它写日志与返回给前端。

#### `claim(workerId)` —— ★ 领单（本篇最核心的方法）

```java
@Transactional
public JobClaimResponse claim(String workerId)
```

**逐段讲**（这是"三个机制在同一段代码里交汇"的地方）：

**① `LocalDateTime now = UtcTimes.now();`**
一次领单只取**一次**时间，后面 `leaseUntil` 和 `markRunning` 的 `heartbeat_at`
都用这个 `now`。副作用是：租约起点与心跳时间**完全一致**，
不会出现"心跳比租约起点晚几毫秒"这种排查时的困惑。

**② `ScheduleJobEntity job = jobMapper.lockNextClaimable(now);`**
拿行锁 + 跳过已锁的行。返回 `null` → `return null`（**什么都不写**）。
⚠ 这一步的锁**只有在本事务提交时才释放** —— 方法上的 `@Transactional` 是必需的（javadoc 原话：
"如果把它拆成'先查再改'，锁就白加了，两个 worker 会领到同一单"）。

**③ `boolean takeOver = "running".equals(job.getStatus());`**
**判定的全部内容**：`lockNextClaimable` 只可能返回 `pending` 或（租约过期的）`running`，
所以"回来的是 `running`" ⟺ "上一个持有者没续上租约" ⟺ **这是接管**。
判定依据是**领单那一刻读到的 status**，而不是"有没有人领过"（`attempt > 0`）——
因为一个任务完全可能被正常重试（`fail(retryable)` 回 pending）后再次被领，
那**不是接管**（上一个 worker 好好收尾了）。

**④ `String previousToken = job.getJobToken();`（带一大段 ⚠ 注释）**

```java
// 接管时，job 上还留着**上一个持有者的 token**（下面 markRunning 才换掉）。
// 必须先用它把那个死掉的 worker 占着的槽位释放掉 ——
// 否则槽位会永久泄漏：新 worker 完成时按**新** token 释放，释放不到旧的那份，
// 排课产能就被一次次崩溃慢慢吃光。
// （这个 bug 是"真 kill -9"故障注入跑出来才发现的，纯模拟租约过期看不到。）
```

**为什么必须"先用旧 token 释放"** —— 这是本篇要求讲透的第 4 个问题，逐层说：

- **槽位是什么**：`schedule_worker_slots` 是一张只有 `maxConcurrent` 行的表
  （`CapacityService.run` 启动时 `INSERT IGNORE` 预置 1..maxConcurrent 行）。
  一行被占 = 一份求解产能被用掉；`tryAcquire` 标 `WHERE id=? AND (job_token IS NULL
  OR lease_until IS NULL OR lease_until < now)`。**槽位的持有者身份就是 `job_token`**。
- **槽位怎么被释放**：`releaseByToken(token)` 是 `UPDATE ... WHERE job_token = ?`，
  即 **"按 token 找槽位并清空"**。所以**释放用的 token 必须等于占用时用的 token**。
- **泄漏是怎么发生的**：
  ```
  A 领单 #7：token=T1 → 槽位 3 的 job_token = T1
  A 被 kill -9（或宿主断电）→ 槽位 3 上的 lease_until 到期，但 job_token 仍是 T1
  B 接管 #7：生成 T2 → 抢到（可能还是槽位 3，因为它的 lease 过期了）→ 槽位 3 的 job_token 变成 T2
             ⚠ 此刻 T1 这个值已经不再出现在任何槽位上 —— 如果之前没释放，它就已经没了
  B 完成 #7 → releaseByToken(T2) → 清掉槽位 3 ✓
  ```
  看上去没问题？**问题在"B 抢到的不是同一个槽位"的时候**：
  ```
  A 占着槽位 3（job_token=T1，lease 到期但没清）
  B 领单 → acquire 从 slotId=1 开始试：槽位 1、2 都空 → **B 占的是槽位 1（T2）**
  B 完成 → releaseByToken(T2) → 清掉槽位 1
  结果：槽位 3 永远带着 T1 躺着 —— 它的 lease_until 会过期，所以还能被抢，
        看起来"没事"；但一旦槽位表被反复这样搞，就会出现
        **"实际可用槽位 < maxConcurrent"** 的慢性缩水
  ```
  ⚠ 更严重的一种形态：**如果 `releaseByToken` 是唯一清空 `organization_id` 的地方**，
  那么占用的槽位会带着"上一个组织的 organization_id"一直留着 ——
  而 `tryAcquire` 的判据只认 `job_token IS NULL / lease_until < now`，不认 organization_id，
  所以它**仍可被抢**。所以这段注释里"排课产能就被一次次崩溃慢慢吃光"的机制，
  **精确的失效路径与本项目的实际观测有关**：
  注释本身记录的是"**真 kill -9 故障注入跑出来才发现的**"，而纯模拟租约过期看不到 ——
  这说明**只有在进程真的被强杀（不走任何 Java 清理路径）时才会命中**。
  本篇照抄该注释的结论，并把它作为**"为什么不释放会泄漏"的官方答案**：
  **占用与释放必须成对，而"成对"的凭据是 token；接管换了 token，就产生了
  "旧 token 占着、新 token 是唯一能释放的人"这个缺口，所以必须在换 token 之前
  用旧 token 补上那一次释放。**
- **为什么 `freed > 0` 才打日志**：`releaseByToken` 是**幂等**的
  （`ScheduleWorkerSlotMapper` 的 javadoc："任务被接管后旧 worker 再来释放，会更新 0 行
  （token 已换），无害"）。`freed == 0` 的常见情形是**该组织已经用新 token 占过槽位**
  或旧槽位已被别的路径清掉 —— 不是错误，所以不打日志（避免刷屏）。

**⑤ `String token = newJobToken();` → `capacityService.acquire(org, token)`**

```java
// ⚠ 容量槽位在**这里**抢，不在入队时抢。
//   顺序也是刻意的：先试槽位、抢不到就**什么都不写**地返回 null
//   （事务提交时只有 FOR UPDATE 的行锁被释放，任务仍是 pending），
//   这样"没产能"不会把一个任务误标成 running。
Long slotId = capacityService.acquire(job.getOrganizationId(), token).orElse(null);
if (slotId == null) { log.debug(...); return null; }
```

三点必须理解：

1. **槽位挪到领单时抢**（架构说明 §5.8）：P1/P2 是"抢到槽位 → 立即求解"，
   槽位与任务同生共死；P3 里任务可能在队列躺几分钟，此时占着槽位等于**空占产能**。
2. **顺序**：抢槽位在 `markRunning` **之前**。抢不到 → `return null`，**一个字段都不写**。
   于是 `tryAcquire` 的写入（如果有）与任务状态**在同一个事务里一起提交或一起回滚** ——
   `acquire` 成功但 `markRunning` 失败时，代码显式 `capacityService.release(slotId, token)`。
   ⚠ 反过来说：**如果先 `markRunning` 再抢槽位，抢不到就只能"把刚标记的 running 改回 pending"**，
   那是一次多余的写、还可能被别的 worker 抢进来 —— 所以顺序是**为了少写一次、且不产生中间态**。
3. **`return null` 不释放行锁以外的东西**：`lockNextClaimable` 拿的行锁在事务提交时释放；
   任务仍是 `pending`，别的 worker 下次还能领。⚠ 但要注意：**"没产能"和"没任务"在 HTTP 上
   是同一个 204**（`InternalJobController.claim` 只看 `claim == null`）。
   所以 worker 分不清"队列空"和"产能满"—— 对它来说都是"过 2 秒再来问"。
   这是**可观测性的一个缺口**（只有 scheduling 的 `log.debug` 知道是哪种），
   本项目在注释里没有说明这一点。

**⑥ 接管释放（承接 ④）**

```java
if (takeOver && previousToken != null) {
    int freed = slotMapper.releaseByToken(previousToken);
    ...
}
```

- `previousToken != null` 是**防御性判空**：建表里 `job_token` 是 `NOT NULL`，
  正常不会为 null（理论上 `BaseMapper` 反序列化也可能给 null）。
- **为什么放在 `markRunning` 之前**：必须在**换 token 的那一次写之前**执行。
  如果放在 `markRunning` 之后，`previousToken` 变量还在手上，**功能上仍然正确** ——
  但那时行的 `job_token` 已经变了，代码读起来就必须靠"我手里留着旧值"来解释，
  而且一旦有人在两者之间加一句"重新 select 一行"就会踩空。
  现在这个顺序让"旧 token 的唯一用途"在代码上就是紧挨着的两行，更难改错。
  ⚠ 另外，`releaseByToken` 是**全表按 token 匹配**的 UPDATE，
  它可能碰到 `schedule_worker_slots` 上的一行，而 `acquire` 也可能刚碰过同一张表 ——
  **同一事务内对同一批行的加锁顺序是 `acquire`（slotId 从小到大试）→ `releaseByToken`（按 token 匹配）**。
  不同事务之间只要遵循同样的顺序就不会死锁，但这里**顺序并不完全由 id 决定**
  （`releaseByToken` 是全表扫匹配）。本项目未记录此处的死锁实测。

**⑦ `markRunning` + rowcount 检查**

```java
LocalDateTime leaseUntil = now.plusSeconds(leaseSeconds);
int affected = jobMapper.markRunning(job.getId(), token, workerId, leaseUntil, now);
if (affected != 1) {
    log.warn("领单失败（状态在锁定期间被改动）: job={}", job.getId());
    capacityService.release(slotId, token);   // 把刚抢的槽位还回去
    return null;
}
```

- 失败时**必须还槽位** —— 否则一次"领单失败"就永久吃掉一份产能（与 `fail`/`complete`
  里的释放是同一类问题，只是发生在更早的时刻）。
- 注意这里用的是 `capacityService.release(slotId, token)`（带 slotId），不是
  `releaseByToken` —— 因为**我们刚拿到 slotId**，直接按 id + token 释放更精确。

**⑧ `attempt` 的 Java 侧计算 + 事件写入**

```java
int attempt = (job.getAttempt() == null ? 0 : job.getAttempt()) + 1;
eventMapper.insert(ScheduleJobEventEntity.of(job.getOrganizationId(), job.getId(),
        takeOver ? ScheduleJobEventEntity.TAKEOVER : ScheduleJobEventEntity.CLAIMED,
        workerId, attempt,
        takeOver ? "接管：上一个持有者的租约已过期（attempt " + attempt + "）"
                 : "领单（attempt " + attempt + "）"));
if (takeOver) { log.warn("接管任务: job={} org={} 原 worker={} attempt={}", ...); }
```

- **`TAKEOVER` 事件**（架构说明 §5.8 的接管流程图把它列为关键一步）：
  它的用途不是"记一笔日志"，而是**故障注入与压测时统计"接管成功率"**
  （建表脚本注释：事件流的用途之一是"压测与故障注入时统计接管成功率"）。
  另外它回答了"**这个任务为什么跑了 3 次**"：看 `attempt` 与 `takeover` 事件。
- `CLAIMED` 与 `TAKEOVER` **互斥**，用同一个三元表达式决定 —— 一个任务每次被领
  恰好产生一条事件，事件流里 `claimed`/`takeover` 的条数 == `attempt`。
- `log.warn` 只在接管时打（正常领单是 `DEBUG` 级别的事 —— 事实上正常领单**根本不打日志**）。
- ⚠ 事件里的 `attempt` 是**领单后**的值（1、2、3…），而 `enqueue` 里是 `0`。
  所以"事件流里 attempt 跳变"不是 bug。
- ⚠ **`takeOver` 分支下不打"上一单往哪去了"**：日志只带 `原 worker`（`job.getWorkerId()`，来自旧行），
  不带旧 token —— 排查时需要它时得去数据库看。这是刻意的（日志里不出现秘密值的完整内容，
  对比 `enqueue` 里 hash 只截 12 位）。

**⑨ 取快照 + 取规则 + 返回**

```java
SchedulingSnapshotEntity snapshot = snapshotService.require(job.getOrganizationId(), job.getSnapshotId());
return new JobClaimResponse(job.getId(), token, job.getOrganizationId(), job.getSnapshotId(),
        snapshot.getFingerprint(), job.getRuleSetHash(),
        ruleSetService.rulesByHash(job.getOrganizationId(), job.getRuleSetHash()),
        snapshotService.toInput(snapshot), attempt, job.getMaxAttempts(),
        leaseSeconds, heartbeatSeconds, takeOver);
```

- 注释说"**快照读一次就够**：既要它的 fingerprint（给 worker 做溯源），也要它的 payload（求解输入）"
  —— 所以先 `require` 拿到实体，再从它身上取两个东西，而不是调两次。
  （`SnapshotService.payloadOf` 是给别的调用方的便利方法，这里没用它，就是为了只读一次。）
- `ruleSetService.rulesByHash(org, hash)`：**按任务入队时记下的 hash** 取规则，
  不是取"当前规则集"。这是"排课时用的是当时那套规则"的保证（详见 1.3 节末尾）。
- `snapshotService.toInput(snapshot)`：把 JSON payload 还原成 `ScheduleInput`。
  **这一步是 worker 拿到全部求解输入的地方** —— `JobClaimResponse` 的 javadoc 强调：
  worker 不需要碰数据库，铁律 ② 在 P3 仍然成立；代价是每次领单多传一份几 KB 的 JSON。
- ⚠ **`require` 会抛 404**：`BusinessException.notFound("排课输入快照不存在")`。
  在 `claim` 里抛出意味着**整个领单事务回滚** —— 任务留在 `pending`，
  而且**每次领都会被同一个坏快照挡住**（永久卡死，worker 只会一直拿到 5xx/404）。
  这是一种"快照行被删/被清库"后的**毒丸情形**，本项目未在注释里讨论它
  （此处未完全理解预期的运维处理，代码行为如上）。

**`claim` 的完整不变量检查清单**（读懂它 = 读懂三个机制）：

| 步骤 | 保证的东西 |
|---|---|
| `lockNextClaimable`（行锁 + SKIP LOCKED） | **一单只被一个人做**（并发安全，无应用层锁） |
| `previousToken` + `releaseByToken` | **接管不泄漏产能** |
| `acquire` 抢 slot | **全局并发上限**（跨组织，独立于队列） |
| 抢不到就 `return null`（不写任何东西） | **没产能不会误标 running** |
| `newJobToken()` + `markRunning` 写新 token | **旧持有者的所有回写立刻失效**（栅栏） |
| `leaseUntil = now + leaseSeconds` | **worker 死了任务会被接管，不会失踪** |
| `markRunning` rowcount != 1 时还槽位 | **失败不泄漏产能** |

#### `heartbeat(jobId, jobToken, progress)`

```java
public boolean heartbeat(long jobId, String jobToken, int progress) {
    LocalDateTime now = UtcTimes.now();
    int affected = jobMapper.heartbeat(jobId, jobToken, now.plusSeconds(leaseSeconds), now,
            Math.max(0, Math.min(100, progress)));
    return affected == 1;
}
```

- **不加 `@Transactional`**（注意：`claim` / `complete` / `fail` / `markCancelled` 都有它）。
  单条 UPDATE，自带原子性，不需要显式事务。
- 租约在**服务层**算（`now.plusSeconds(leaseSeconds)`），不在 SQL 里算 ——
  与 `claim` 保持一致，且用的是 `leaseSeconds()` 那个**被钳位过的**值。
- 进度**钳位 0..100**，`Math.max(0, Math.min(100, progress))`，两层套是为了
  `progress` 为负时也能纠正。
- 返回值：`true` = 续租成功（还是主人）；`false` = **token 失效**，
  worker 应当停止求解（`InternalJobController` 的 javadoc）。
- ⚠ **心跳不写事件**（见上面 `heartbeat` SQL 那一节的 ⚠）。

#### `complete(jobId, jobToken, solverStatus, modelFingerprint, objectiveValue, versionId, entryCount)`

```java
@Transactional
public boolean complete(...)
```

**逐行**：

| 行 | 做什么 |
|---|---|
| `jobMapper.complete(...)` | 那条 9 个 SET 的 UPDATE（见 Mapper 一节） |
| `if (affected != 1) { log.warn("完成任务被拒（token 已失效）: job={}", jobId); return false; }` | **早返回**：不写事件、不释放槽位、**不抛异常** |
| `ScheduleJobEntity job = jobMapper.selectById(jobId);` | 重新读整行 —— 需要 `organizationId` / `workerId` / `attempt` 来写事件。⚠ 这一次 `selectById` **不带 `FOR UPDATE`**，但它在**同一个事务**里，读的是自己刚提交前的写，所以拿到的一定是刚写的那一版；用整行而不是只 select 三列，是因为 `selectById` 是现成的 |
| `eventMapper.insert(... COMPLETED, job.getWorkerId(), job.getAttempt(), "完成：" + entryCount + " 条明细，求解状态 " + solverStatus)` | 事件 detail 里带了**条数**与**求解状态** —— 用户点开任务详情不用再去数版本表 |
| `slotMapper.releaseByToken(jobToken);` | ★ 让出求解槽位。**用 `jobToken`（新 token）释放** —— 与 claim 里用它抢 slot 是**同一个 token**，所以配对成功 |
| `return true;` | → `accepted: true` |

> ⚠ **`complete` 不碰 `scheduling_state`**（对外状态）。为什么？
> 因为对外状态的收尾不在这里，而在 `JobResultWriter.settle(jobId, persisted)` ——
> `InternalJobController.result` 在 `resultWriter.persistIfStillOwner` 之后调它，
> 且注释明确写"**事务之外**，见 JobResultWriter.settle 的注释"。
> 这样拆的理由是：**"写课表版本 + 标记任务 done"必须在一个事务里**（原子），
> 而"更新对外状态 + 释放槽位"是后续的收尾，失败重试的代价小。
> ⚠ 但注意 `slotMapper.releaseByToken` 在这里（`complete` 内），
> 而 `stateService.finishByOrganization` 在 `settle` 里 —— **槽位与对外状态被拆到了两处**。

#### `fail(jobId, jobToken, error, solverStatus, retryable)` —— ★ 带项目最值钱的一段 ⚠

```java
@Transactional
public boolean fail(...)
```

**逐行**：

| 行 | 做什么 |
|---|---|
| `jobMapper.fail(jobId, jobToken, truncate(error, 500), solverStatus, retryable, now)` | `truncate(error, 500)` —— 与建表 `varchar(500)` 对齐。**超长会被 MySQL 截断或报错，所以在应用层先截** |
| `if (affected != 1) { log.warn(...); return false; }` | 同 `complete`：静默早返回 |
| `ScheduleJobEntity job = jobMapper.selectById(jobId);` | 读回整行 |
| `boolean requeued = "pending".equals(job.getStatus());` | ★ **用"读回来的状态"判断这次失败是否被退回了队列**。这是**唯一**可靠的判据：`fail` 的 SQL 里那个 `CASE WHEN` 的取值取决于 `attempt < max_attempts`，而那个值是 SQL 内算的 —— Java 侧想知道结果，只能读回来。⚠ 这比"在 Java 里重算一遍 `retryable && attempt < maxAttempts`"更稳（不用重复日期/边界逻辑） |
| `eventMapper.insert(... FAILED, job.getWorkerId(), job.getAttempt(), (requeued ? "失败（可重试，已退回队列）：" : "失败（不再重试）：") + truncate(error, 300))` | 事件 detail 带**人类可读的两种收场**。⚠ 这里截 300、SQL 里截 500 —— **两个数字不一致是刻意的**（事件 detail 是长文本列，但列表页展示用，短一点更好看）。注释里没写这一点，是读代码看出来的 |
| `slotMapper.releaseByToken(jobToken);` | ★ **无论是否退回队列，都要让出槽位** —— 注释原话："否则一次失败就永久吃掉一份产能" |
| `if (!requeued) { stateService.finishByOrganization(job.getOrganizationId(), "failed", NO_SOLUTION_MESSAGE); }` | ★★ 见下面 |

##### `fail` 里那段 ⚠⚠ 注释（**必须逐字保留**）

```java
// ⚠⚠ 终态失败还必须**收尾对外状态**。
//   最初漏了这一步，症状是：任务已经 failed，而 scheduling_state 仍是 running，
//   于是**这所学校再也发不起新的排课**（每次 generate 都被 409
//   "某某正在排课，请稍后再试"挡住）—— 与"Redis 锁没人释放"是同一类事故。
//
//   退回队列的情况**不动**状态：那次任务还在进行中（只是换个人重做）。
if (!requeued) {
    stateService.finishByOrganization(job.getOrganizationId(), "failed", NO_SOLUTION_MESSAGE);
}
```

这段话解释了本项目一个反复出现的模式：**"漏掉收尾"不会崩，只会让某个学校永久发不起新排课**。
架构说明 §5.8 也点名："三处终态都必须收尾对外状态（失败 / 取消 / 完成）——
漏掉任何一处的症状都是『这所学校再也发不起新排课』，而不是崩溃。
这一点 P3 实测漏了三次"。

⚠ 注意 `fail` 只覆盖了"**终态失败**"这一处。另外两处分别在：
- **取消**：`cancel` 的 pending 分支显式 `stateService.finishByOrganization(..., "idle", "排课任务已取消")`；
  running 分支的取消由 `InternalJobController.result` 的 `cancelled` 分支补上。
- **完成**：`JobResultWriter.settle`（不在本篇）。
- **入队失败**：`ScheduleRunService` 的 catch 里 `stateService.finish(org, jobToken, "failed", "排课任务入队失败")`。

##### `NO_SOLUTION_MESSAGE` 常量

```java
/** 与 P1/P2 逐字一致的失败文案 —— 对外契约不能因为 P3 换了执行方式就改掉。 */
private static final String NO_SOLUTION_MESSAGE =
        "排课无解，请检查任教关系、周课时、固定时段和教师课时上限";
```

这是**"行为等价"铁律**（第 1 册 §0.3）在 P3 的落点：
换了执行架构（线程 → 队列 + 独立进程），**错误文案一个字都不能变**。
改这一行之前先读 `tools/contract-diff/compare.py` 里对应的用例。

#### `markCancelled(jobId, jobToken)`

```java
@Transactional
public boolean markCancelled(long jobId, String jobToken) {
    LocalDateTime now = UtcTimes.now();
    int affected = jobMapper.markCancelled(jobId, jobToken, now);
    if (affected != 1) { return false; }
    ScheduleJobEntity job = jobMapper.selectById(jobId);
    eventMapper.insert(... CANCELLED, job.getWorkerId(), job.getAttempt(), "worker 响应取消请求");
    slotMapper.releaseByToken(jobToken);
    return true;
}
```

- 结构完全与 `complete` / `fail` 同形（CAS → 读回 → 写事件 → 释放槽位），
  连"早返回时不释放槽位"都一样 —— ⚠ **这是一个刻意的选择**：
  token 失效意味着槽位已经不归你了（要么被别人释放了、要么被别人的新 token 占了），
  你去释放反而可能**误放别人的槽位**（虽然 `releaseByToken` 按 token 匹配，误放不了，
  但也不会有任何效果）。所以"CAS 失败就什么都不做"是正确且安全的行为。
- ⚠ **这里没有 `stateService.finishByOrganization`** —— 对外状态的收尾在
  `InternalJobController.result` 的 `cancelled` 分支里（`if (recorded) stateService.finish...`）。
  与 `fail` 把收尾放在 Service 里**不一致**，读的时候要注意"收尾到底在哪一层"。

#### `isCancelRequested(jobId, jobToken)` —— 取消请求的唯一通道

```java
public boolean isCancelRequested(long jobId, String jobToken) {
    ScheduleJobEntity job = jobMapper.selectOne(Wrappers.<ScheduleJobEntity>lambdaQuery()
            .select(ScheduleJobEntity::getCancelRequested, ScheduleJobEntity::getJobToken)
            .eq(ScheduleJobEntity::getId, jobId));
    return job != null
            && Boolean.TRUE.equals(job.getCancelRequested())
            && jobToken.equals(job.getJobToken());
}
```

- **`select(...)` 只取两列**（`cancel_requested` 与 `job_token`）—— 有这个 token 列
  是为了**在 SQL 之外做归属校验**（`jobToken.equals(job.getJobToken())`）。
  ⚠ 其实这个校验完全可以放进 `WHERE`（`AND job_token = ?`），写在这里是**等价但多传一行数据**的做法；
  差别是"任何不匹配都返回 false"，语义相同。
- `Boolean.TRUE.equals(...)` 而不是 `job.getCancelRequested()`：**防拆箱 NPE**
  （`tinyint(1)` 理论上可能为 null）。
- `jobToken.equals(...)` 而不是 `Objects.equals`：**调用方保证 jobToken 非空**
  （来自请求体 `@NotBlank`），所以用参数做 receiver 更省一次判空。
- ⚠ 它**不带 `status` 条件**：一个已经 `done` 的任务如果 `cancel_requested` 还是 true，
  这里会返回 true。但**不会造成危害**：`InternalJobController.heartbeat` 只在
  `ok=true`（即 status 还是 running 且 token 匹配）时才把它放进响应：
  `out.put("cancel_requested", ok && queueService.isCancelRequested(...))` ——
  `ok &&` 是短路的第一道闸。
- 为什么值得单独一个方法：worker **不碰数据库**，所以"用户点了取消"这件事
  **只能搭在心跳的响应里回去**（`HeartbeatRequest` 的注释：这是唯一通道）。

#### 查询与运维方法（表格说明）

| 方法 | 做什么 | 要点 |
|---|---|---|
| `list(org, status)` | 某组织的任务列表（不分页） | `status` 为空则不加条件（`.eq(cond, ...)` 的条件式用法）；`id DESC` |
| `listByPage(org, status, query)` | 分页列表 | ⚠ 用**数据库分页**而不是"全查出来再内存切片" —— 任务表是会长的那类表。排序**固定 `id DESC`，不接受前端传列名**（"让客户端传排序列名进 SQL 是不必要的攻击面"） |
| `requireJob(org, jobId)` | 按 id + org 取，取不到抛 404 | 多租户隔离靠 `organization_id`；`BusinessException.notFound("排课任务不存在")` |
| `requireJobById(jobId)` | 只按 id 取（内部接口用） | worker 只有 jobId、**没有租户上下文**，所以这个入口不做组织过滤 |
| `events(jobId)` | 事件流，`id ASC`（时间正序） | 与 `list` 的倒序相反 —— 事件流要按发生顺序读 |
| `queuePosition(org, jobId)` | "我前面还有几个" | ⚠ 统计的是 `status='pending' AND id < ?` 的**全局**行数（**不带 `organization_id`**，且 `organizationId` 参数实际未被使用）。因为容量槽位是跨组织全局的，所以排队名次按全局算才与领单口径一致；但这也意味着**参数 `organizationId` 是未使用的**（编译不会警告，读代码时别以为它在过滤）。注释写明了"口径与领单完全一致（都是 `ORDER BY id`）" |
| `cancel(org, jobId)` | 取消（分 pending / running 两条路） | 已终结 → `badRequest("该任务已经结束，无法取消")`。见下面的 ⚠ |
| `retry(org, jobId)` | 人工重试 | `requeue` rowcount != 1 → `badRequest("只有失败或已取消的任务可以重试")`；写 `RETRIED` 事件（`attempt` 传 0） |
| `isLeaseExpired(job, now)` | 派生字段：租约是否过期 | **不落库**（"它每时每刻都在变"）；`status='running' AND (leaseUntil == null OR leaseUntil < now)`。⚠ `leaseUntil == null` 也算过期 —— 与 `lockNextClaimable` 的 `lease_until < now` 语义**不同**（SQL 里 null 不满足 `<`，所以 SQL 不会挑走 `lease_until IS NULL` 的 running 行）。**两处口径不一致**：列表页会把这种行显示成"租约已过期"，但队列**不会**接管它。这是一个真实存在的边界不一致（建表 `lease_until datetime DEFAULT NULL`，`markRunning` 一定会写它，所以正常流程不会产生这种行） |
| `newJobToken()` (private) | `SecureRandom` 24 字节 → `HexFormat` 48 个十六进制字符 | 对应 Python 的 `secrets.token_hex(24)`；`SecureRandom` 实例是**字段级复用**的（不是每次 new） |
| `truncate(text, max)` (private static) | 超长截断（null 安全） | 两处调用：`truncate(error, 500)` 给 SQL、`truncate(error, 300)` 给事件 |
| `rulesOf(job)` | 这个任务用的规则集快照 | 供 P2 的诊断接口复用；就是对 `ruleSetService.rulesByHash` 的一行转发 |

**`cancel(organizationId, jobId)` 逐段**：

```java
ScheduleJobEntity job = requireJob(organizationId, jobId);        // ① 不存在 → 404
if ("done".equals(job.getStatus()) || "failed".equals(job.getStatus())
        || "cancelled".equals(job.getStatus())) {
    throw BusinessException.badRequest("该任务已经结束，无法取消");  // ② 已终结 → 400
}
if ("pending".equals(job.getStatus())) {
    jobMapper.cancelPending(jobId, organizationId, UtcTimes.now());  // ③ 直接终结
    eventMapper.insert(... CANCELLED, null, job.getAttempt(), "取消（尚未开始）");
    // ⚠ 取消一个还没开始的任务同样是"终态"，必须收尾对外状态 ——
    //   否则这所学校会一直显示"正在排课"，发不起新任务。
    //   （与失败路径是同一类问题，只是更容易被忽略：取消看起来"什么都没发生"。）
    stateService.finishByOrganization(organizationId, "idle", "排课任务已取消");
} else {
    jobMapper.requestCancel(jobId, organizationId);                   // ④ 打标记
    eventMapper.insert(... CANCELLED, job.getWorkerId(), job.getAttempt(),
            "取消请求已发出，等待 worker 收手");
}
return requireJob(organizationId, jobId);                             // ⑤ 读回最新状态返回
```

- ③ 里的 ⚠ 注释是本项目"三处终态收尾"的**第二处**，也是**最容易被忽略**的一处
  （"取消看起来什么都没发生"）。注意对外状态置的是 `"idle"` 而不是 `"failed"` ——
  用户主动取消**不是失败**，界面不该显示"排课无解"。
- ④ 的 `running` 分支**只打标记，什么都不改** —— 由 worker 通过心跳看到后自己收手，
  再经 `markCancelled` 进终态。**一轮完整的取消要经过 worker 的一次心跳间隔（≤15 秒）**。
- ⑤ 读回最新状态再返回：让前端立刻看到 `cancel_requested` 或 `cancelled`。
- ⚠ ③ 里 `cancelPending` 的**返回值没被检查**（见 Mapper 一节的 ⚠）；
  ④ 里 `requestCancel` 的返回值也没检查。与 `retry` 里严格的 `!= 1 → 400` 不同 ——
  取消**故意做成幂等/宽容**的，重复点取消不该报错。

### 1.3 `SnapshotService` —— 冻结 + 指纹 + 还原

**一句话定位**：**铁律 ③「排课输入用快照」的真正落地** ——
把 academic 的 7 张表**冻结**成 `scheduling_snapshots` 的一行（含指纹），
之后无论是排队中的任务还是事后审计，都用这一行。

**谁调它**：

| 上游 | 调什么 |
|---|---|
| `ScheduleRunService.trigger`（4a 册，第 137 行） | `freeze(organizationId)` —— **入队之前** |
| `JobQueueService.claim` | `require(org, snapshotId)` + `toInput(snapshot)` |
| `SnapshotService.payloadOf` 的调用方（诊断/试算） | 一步拿到 `ScheduleInput` |
| `snapshot/ScheduleInputLoader` | **它的下游**：真正去查那 7 张表 |

**类注释里两段必须理解的话**（照录结论）：

> **为什么 P3 才真正需要它**：P1/P2 时求解就发生在生成请求的同一条链路里，
> `ScheduleInputLoader` 现查一遍没问题。P3 之后求解挪到独立进程、
> **可能排队几分钟才开始跑** —— 期间教务数据完全可能被改。
> 不冻结的话：排出来的课表对应的是"另一份数据"，而且事后无法复现。

> **指纹怎么算**：与 `rule_set_hash` 同一套做法：**把 payload 规范化成键排序的紧凑 JSON 再 sha256**。
> 于是同一份输入 → 同一个指纹，可以写进课表版本一起进审计链
> （`snapshot_fingerprint` + `rule_set_hash` + `model_fingerprint` 三者合起来，
> 任何一版课表都能被精确复现）。

**静态字段 `CANONICAL`**（本类的技术核心）：

```java
private static final ObjectMapper CANONICAL = JsonMapper.builder()
        .configure(SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS, true)
        .build();
```

- `ORDER_MAP_ENTRIES_BY_KEYS = true` 是**指纹稳定的唯一关键**：
  `Map` 的迭代顺序默认是哈希顺序，而 `LinkedHashMap` 保留插入顺序 ——
  **两次调用只要字段插入顺序不同（例如 SQL 返回顺序变了），JSON 字符串就不同，指纹就不同**。
  打开这个开关后，序列化时**按键名字典序排**，于是"同一份数据 → 同一个字符串 → 同一个 sha256"。
  ⚠ 这是**必须靠配置而不是靠代码正确性**保证的东西：调用方只要往 payload 里塞一个
  顺序不同的 `LinkedHashMap`，"看起来一样"的两份输入就会得到不同指纹。
  这个坑**没有测试直接守着**（本项目未在注释里记录该开关系何时、因何被加上的）。
- 单独建一个 `ObjectMapper` 而不是复用 Spring 的：**默认的 Spring ObjectMapper 不带这个开关**，
  复用它会让指纹随"某处配置改了 JSON 序列化行为"而变化 —— 那就等于审计链失效。
- **`JsonMapper.builder()` 而不是 `new ObjectMapper()`**：前者带 `jackson-databind` 的
  模块自动发现（Java 8 时间类型等），是 Jackson 2.10+ 的推荐构造方式。

---

#### `freeze(long organizationId)` —— 冻结当前输入并存库

```java
public SchedulingSnapshotEntity freeze(long organizationId)
```

**逐行**：

| 行 | 做什么 |
|---|---|
| `ScheduleInput input = inputLoader.load(organizationId);` | **现查**那 7 张 academic 表（经 `snapshot/` 的 7 个 `*Ref` 只读映射） |
| `Map<String, Object> payload = toMap(input);` | `ScheduleInput`（record）→ `LinkedHashMap`，走 `CANONICAL.convertValue`。**这一步决定了 payload 的键名就是 record 组件名**（Jackson 的默认命名，全项目 record 的 JSON 形状都由它决定） |
| `entity.setPayload(payload)` | JSON 列（`SchedulingSnapshotEntity` 上 `@TableField(typeHandler = JacksonTypeHandler.class)`） |
| `entity.setFingerprint(fingerprintOf(payload));` | ★ 指纹 = **对 payload 算**（不是对 input 算）—— 因为"能被还原出来的那一份"才是审计对象 |
| 7 个 `setXxxCount(...)` | `input.grades().size()` 等。**存冗余的目的**：让"这次冻结的数据有多大"**不用解析 payload 就能看**（列表页/诊断只需 count）。⚠ **这 7 个数不参与指纹**（`fingerprintOf` 只吃 payload）—— 所以"只改了 count 列"不会改变指纹。这是正确的：count 是 payload 的派生数据 |
| `entity.setCreatedAt(UtcTimes.now())` | UTC + 秒级截断（第 1 册 `UtcTimes`） |
| `snapshotMapper.insert(entity);` | 插入，`IdType.AUTO` 回填 id → `ScheduleRunService` 用它做 `snapshotId` |
| `return entity;` | 返回给调用方（要 `getId()` 和 `getFingerprint()`） |

> ⚠ **`freeze` 没有 `@Transactional`**。它只写一张表的一行，`insert` 自带原子性。
> 但要注意调用方的语义：`ScheduleRunService` 把 `freeze` + `enqueue` 放在同一个 try 里，
> 而**它们各自是独立事务** —— 所以"快照插进去了但入队失败"会留下一行**孤儿快照**
> （没有任务引用它）。本项目未在注释里讨论清理策略（建表脚本里 `schedule_jobs.snapshot_id`
> 是外键指向快照，但反向没有约束）。孤儿快照不影响正确性，只占空间。

**为什么"入队时冻结"而不是"求解时现取"** —— 这是本篇要求讲透的第 5 个问题，四层理由：

1. **用户意图**：任务 javadoc 的原话"用户点下按钮的那一刻看到的数据才是他要排的那份"。
   用户在教务页面看到"六年级 8 个班、张老师 16 课时"然后点排课；
   如果排队 5 分钟后现取，而期间教务主任加了 2 个班，排出来的课表**不是他要的**，
   而且他**无法察觉**（课表本身看起来完全正常）。
2. **可复现**：快照 + 指纹写进审计链后，任何一版课表都能回答
   "它当时用的是哪份数据"。**现取的做法让这个问题永远答不出** ——
   数据已经被覆盖，先前的输入不可恢复。
3. **一致性**：`inputLoader.load` 是一次多表查询。求解时现取意味着"查询与求解之间"
   数据还可能变（甚至同一个 `load` 内部的 7 张表之间也可能不是同一时刻的快照）。
   冻结把"一次排课的输入"变成一个**不可变的字节串**。
4. **契约**：`JobClaimResponse` 一次把 `input` 交给 worker，于是 worker
   **不需要数据库连接**（架构说明 §5.8 的第一个设计决定：worker「拥有的表：无」）。
   这一条**依赖快照已经落库** —— 如果现取，worker 就必须自己去查 academic 的表。

#### `require(organizationId, snapshotId)` —— 取快照实体（不存在则 404）

```java
SchedulingSnapshotEntity entity = snapshotMapper.selectOne(
        Wrappers.<SchedulingSnapshotEntity>lambdaQuery()
                .eq(SchedulingSnapshotEntity::getId, snapshotId)
                .eq(SchedulingSnapshotEntity::getOrganizationId, organizationId));
if (entity == null) { throw BusinessException.notFound("排课输入快照不存在"); }
return entity;
```

- **两个 `eq`**：id + **organizationId** —— 多租户隔离的常规写法（同一个 id 在不同组织下不可见）。
- `selectOne` 而不是 `selectById`：正因为多了组织条件，`selectById` 用不上。
- **404 文案**"排课输入快照不存在"是一致性文案（与 `JobQueueService.requireJob` 的
  "排课任务不存在"同一风格）。
- ⚠ 返回的是**整行含 payload**（`payload` 是 JSON 列，可能几十上百 KB）。
  `claim` 需要 payload（要给 worker），所以这里不能只取摘要。
  反过来，任何**只需要 fingerprint** 的地方都不该调 `require` —— 那会把整个 payload 读进内存。

#### `payloadOf(organizationId, snapshotId)` —— 一步拿到 `ScheduleInput`

```java
public ScheduleInput payloadOf(long organizationId, long snapshotId) {
    return toInput(require(organizationId, snapshotId));
}
```

两行的便利方法：`require`（带租户校验的 404） + `toInput`（还原）。
给"诊断/规则试算"这类调用方用 —— 它们只想要 `ScheduleInput`，不关心实体。
**`JobQueueService.claim` 没用它**，因为 claim 还要 `fingerprint`，
所以它自己调 `require` + `toInput`（"快照读一次就够"的那条注释）。

#### `toInput(SchedulingSnapshotEntity entity)` —— 还原成求解输入

```java
public ScheduleInput toInput(SchedulingSnapshotEntity entity) {
    try {
        return CANONICAL.treeToValue(CANONICAL.valueToTree(entity.getPayload()), ScheduleInput.class);
    } catch (JsonProcessingException e) {
        throw new IllegalStateException("快照无法还原成 ScheduleInput", e);
    }
}
```

- **`valueToTree` → `treeToValue` 的两步是刻意的**：
  `entity.getPayload()` 的静态类型是 `Map<String, Object>`，
  直接 `convertValue(map, ScheduleInput.class)` 也可以，但先转成 `JsonNode` 树**再**转对象，
  能让 Jackson 的**类型强制规则完全走 JSON 语义**（数字/布尔/null 的转换与"读一份 JSON 文件"一致），
  避免 `Map<String,Object>` 里 `Integer`/`Long`/`String` 混用时出现
  "同一个值两条路径转出不同类型"的差异。⚠ 本项目未写明这个理由，
  这是对代码形状的解读（此处未完全理解作者的确切意图，代码行为是：经 `JsonNode` 中转）。
- **异常类型是 `IllegalStateException` 而不是 `BusinessException`**：
  快照无法还原 **不是用户错误**，是**系统不变量被破坏**（数据被手工改过、
  或 `ScheduleInput` 的结构变了而旧快照没迁移）。→ 500，不是 4xx。文案也不给用户看。
- **`entity.getPayload()` 为 null 时**：`valueToTree(null)` 得到 `NullNode`，
  `treeToValue(NullNode, ScheduleInput.class)` 返回 `null` ——
  **不抛异常，而是把 null 交给求解器**。⚠ 建表 `payload json NOT NULL`，
  正常不会为 null；但这是"坏数据静默通过"的一条路径（此处未完全理解是否符合预期，
  代码行为是：null payload 不会在这里被拦住）。
- 还原出来的 `ScheduleInput` **与冻结时的等价**，因为 `CANONICAL` 的键排序只影响
  序列化的**字节顺序**，不影响反序列化的语义。

#### `fingerprintOfInput(ScheduleInput input)` / `fingerprintOf(Map payload)`

```java
public String fingerprintOfInput(ScheduleInput input) {
    return fingerprintOf(toMap(input));
}

static String fingerprintOf(Map<String, Object> payload) {
    try {
        JsonNode node = CANONICAL.valueToTree(payload);
        return sha256Hex(CANONICAL.writeValueAsString(node));
    } catch (JsonProcessingException e) {
        throw new IllegalStateException("快照无法规范化", e);
    }
}
```

- **两个入口、一个实现**：`fingerprintOfInput` 是给"不落库时也用得上"的场景
  （javadoc 举的例子是**给诊断比对**：拿一份现查的输入算指纹，与某版课表记录的
  `snapshot_fingerprint` 比 → 直接回答"课表还是基于当前数据排的吗"）。
  `fingerprintOf` 是 `package-private`（**没有 `public`**）—— 只有本包能用，
  外部一律走 `fingerprintOfInput`。⚠ 注意 `freeze` 里调的是 `fingerprintOf(payload)`
  （已经是 Map，不必再 `toMap` 一次）。
- **`valueToTree` 再 `writeValueAsString`**（而不是直接 `writeValueAsString(payload)`）：
  绕一圈看似多余，但它保证了**和 `toInput` 走同一条规范化路径** ——
  指纹算的是"`toInput` 要读的那棵树"的字符串形式。⚠ `writeValueAsString(Map)` 与
  `writeValueAsString(JsonNode)` 在 Jackson 里输出**理论上是相同的**
  （同一套序列化器），所以这一步的收益主要是**代码意图的对称性**（此处未完全理解
  作者是否另有所图，代码行为是：先转树再序列化）。
- **异常同样是 `IllegalStateException`**（"快照无法规范化"）：序列化失败说明
  payload 里有 Jackson 表达不了的东西 —— 系统 bug，500。

#### `sha256Hex(String)` (private static)

```java
MessageDigest digest = MessageDigest.getInstance("SHA-256");
return HexFormat.of().formatHex(digest.digest(text.getBytes(StandardCharsets.UTF_8)));
```

- **显式 `StandardCharsets.UTF_8`**：不写字符集就会用平台默认编码，
  在 Windows（GBK）与 Linux（UTF-8）上同一份数据会算出**不同指纹** ——
  那会让审计链在两个环境之间完全对不上。这是本项目"跨环境一致性"的一个具体落点。
- `HexFormat.of().formatHex(...)`（Java 17）→ **64 个小写十六进制字符**，
  与建表 `fingerprint char(64)` 精确对齐。
- `NoSuchAlgorithmException` → `IllegalStateException("JVM 不支持 SHA-256")`：
  SHA-256 是 JDK 必须实现的，走到这里说明 JVM 坏了。
- ⚠ **指纹不是签名**：sha256 只保证"内容变了指纹就变"，不保证"没被人改过"。
  它防的是**漂移**（数据悄悄变了），不是**攻击**。

#### 为什么"排课时用的是当时那套规则" —— `rulesByHash` 在 `RuleSetService` 里

**`SnapshotService` 里没有 `rulesByHash`** —— 它在
[`RuleSetService`](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleSetService.java#L252)
（第 252 行）。之所以要说它，是因为**它和快照是同一个问题的另一半**：
冻结了"输入"，还得冻结"规则"，否则"排队期间管理员改了规则"照样会让
审计链自相矛盾（`rule_set_hash` 记的是旧指纹，而求解用的是新规则）。

它的保证机制（逐层）：

1. **P2 就把整份规则快照冻进了表**：`constraint_rule_versions.rules` 存的是
   **规则的完整内容**（`rule_type` / `params` / `hardness` / `weight` / `description`），
   而不是只存一个 hash。javadoc 说明了当时（P2）的理由：
   "审计链要求这版课表用的哪套规则任何时候都能点开" ——
   **到了 P3 它顺带解决了"排队期间规则被改"的问题**（javadoc 原话）。
2. **任务只记 hash**：`schedule_jobs.rule_set_hash`（`char(64) NOT NULL`），
   入队时由 `ScheduleRunService` 调 `ruleSetService.hashOf(org)` 取得并写入。
3. **领单时按 hash 取回**：`claim` 里
   `ruleSetService.rulesByHash(job.getOrganizationId(), job.getRuleSetHash())` ——
   `findByHash` 是 `WHERE organization_id = ? AND rule_set_hash = ? LIMIT 1`。
4. **取不到就 409**：
   ```java
   throw BusinessException.conflict(
           "规则集版本已不存在（指纹 " + hash + "）—— 该任务无法用当时的规则复现");
   ```
   注意用的是 **409 Conflict**（不是 404）："任务在，但它依赖的那版规则不在了"
   —— 这是**状态冲突**，不是"资源不存在"。而且**宁可让这个任务报错也不退回用当前规则**
   —— 那会静默地排出一份与记录不符的课表（比报错坏得多）。
5. **每一条规则都从 Map 手工重建**（`rulesByHash` 的 for 循环）：
   `String.valueOf(item.get("rule_type"))`、`RuleParams.of(...)`、
   `"hard".equalsIgnoreCase(...)` 决定 HARD/SOFT、`weight instanceof Number ? intValue : 1`。
   ⚠ 重建出来的第 5 个参数是**硬编码 `true`**（`ConstraintRule` 的某个 boolean 组件，
   按位置是"是否启用"一类），即**快照里的规则一律视为启用** ——
   因为 `snapshotOf(enabled)` 只冻启用的规则（`insertVersion` 的入参名就是 `enabled`）。
   第 4 个参数（`weight`）在快照里不是数字时**兜底为 1**。
6. **`@SuppressWarnings("unchecked")`**：`item.get("params")` 需要从 `Object`
   强转成 `Map<String,Object>`，`instanceof Map<?,?>` 模式匹配后强转 —— 类型安全靠**运行时检查**保证。

**合起来看**：`snapshot_fingerprint`（输入）+ `rule_set_hash`（规则）+
`model_fingerprint`（CP-SAT 模型）三者一起进审计链，
**任何一版课表都能被精确复现**（`SnapshotService` 类注释的原话）。
三者都由 `claim` 一次性交给 worker（`JobClaimResponse`），
其中前两者由 scheduling 侧记录，`model_fingerprint` 由 worker 算完回传
（`complete` 写进 `schedule_jobs.model_fingerprint`）。

### 2.2 `ScheduleJobEventEntity` —— `schedule_job_events`（116 行）

**它不是"日志"**（V3 建表脚本原话），而是**结构化的状态迁移记录**。三个用途：
①「这个任务为什么跑了 3 次」→ 看 `attempt` 与 `takeover` 事件；
②「求解到底卡在哪」→ 看 `heartbeat` 事件的**时间间隔**；
③ 压测与故障注入时统计**接管成功率**。
（②见前文 ⚠：`HEARTBEAT` 常量已定义但**全项目没有写入点**。）

| 字段 | 用途 |
|---|---|
| `id` | 主键；`events()` 按它 **ASC** 排（= 时间正序） |
| `organizationId` / `jobId` | 归属 |
| `event` | 事件名，**8 个常量**（见下） |
| `workerId` | 哪个 worker 干的（`enqueue` 时为 null） |
| `attempt` | 这次事件属于第几次尝试（`enqueue` = 0） |
| `detail` | 中文人读描述（"接管：上一个持有者的租约已过期（attempt 2）"） |
| `createdAt` | 由 `of(...)` 工厂**自动填** `UtcTimes.now()`（调用方不能传） |

**8 个事件名常量**：

| 常量 | 值 | 谁写 |
|---|---|---|
| `ENQUEUED` | `enqueued` | `enqueue` |
| `CLAIMED` | `claimed` | `claim`（正常领单） |
| `HEARTBEAT` | `heartbeat` | ⚠ **无写入点**（只有常量定义） |
| `COMPLETED` | `completed` | `complete` |
| `FAILED` | `failed` | `fail` |
| `TAKEOVER` | `takeover` | `claim`（**接管**：领到的是一条租约已过期的 running） |

**`of(...)` 静态工厂**：唯一推荐的构造方式 —— 8 个 set + 自动时间戳。
注释说明了为什么用常量而不是字面量：**"写成常量避免拼错，因为它是查询条件"**。

### 2.3 `SchedulingSnapshotEntity` —— `scheduling_snapshots`（138 行，11 列）

`@TableName(value = "scheduling_snapshots", autoResultMap = true)` ——

### 2.4 `ScheduleJobEventMapper` / `SchedulingSnapshotMapper`（各 9 行）

两个**空 Mapper**：`interface X extends BaseMapper<XEntity> {}`，只有 `@Mapper` 注解。
没有一条自定义 SQL —— 因为这两个表**只有"插入"和"按条件查询"**，而这些
MyBatis-Plus 的 `BaseMapper` 已经提供（`insert` / `selectList` / `selectOne` / `selectPage`）。

> ⚠ 与 `ScheduleJobMapper` 的对比正好解释了"什么时候需要自定义 SQL"：
> **当并发语义需要落在 SQL 里时**（`SKIP LOCKED`、`AND job_token = ?`、`CASE WHEN`、
> 条件式状态机），就必须自己写；**纯 CRUD 就别写**。
> 这也是本项目"Mapper 里只有条件 UPDATE 才是关键逻辑"这条读法的来源。
