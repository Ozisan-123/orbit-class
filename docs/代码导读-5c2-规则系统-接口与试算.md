# 代码导读 5c-2：规则接口、乐观锁与试算

> 本册接 [5c-1：类型与规则集](代码导读-5c1-规则系统-类型与规则集.md)。
> 5c-1 解释“规则怎样变成求解器输入”，本册解释“用户怎样安全地增删改查规则，以及保存前怎样试算”。

## 0. 先看整条调用链

```text
RuleManagement.tsx
  → /api/rules/**
  → RuleController（鉴权、取参、分发）
  → RuleService（CRUD、业务校验、乐观锁、版本留痕）
       → ConstraintRuleMapper（条件 UPDATE / DELETE）
       → RuleSetService（参数 schema、规则集版本）

保存前点“试算”
  → RuleTrialService
  → 同一份数据分别编译“当前规则集”和“当前规则集 + 草稿”
  → 比较能否编译、模型指纹和变量数；不求解、不落库
```

这组接口没有 Python 旧实现可做影子对比。正确性的证据来自两处：solver-core 的规则反例测试，以及默认 DB 规则集与 legacy 等价规则集排课时目标值相同。

## 1. `RuleController`：HTTP 边界

**源码**：[RuleController.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleController.java)

**定位**：只负责 URL、参数、管理员鉴权和调用 Service；规则语义与数据库更新不写在 Controller。

**上游**：前端 `api/index.ts` 的 `getRules`、`createRule`、`trialRule` 等函数。

**下游**：`RuleService`、`RuleSetService`、`RuleTypeCatalog`、`RuleTrialService`。

### 构造器

Spring 注入四个协作者。这里使用构造器注入，让依赖完整可见，也便于单元测试替换。

### `types(Boolean configurableOnly, SchedulePrincipal principal)`

对应 `GET /api/rules/types`。

1. `requireAdmin` 保证调用者已登录且是管理员。
2. `configurable_only=true` 时只返回用户可以新建的规则。
3. 不带参数时返回全部类型，包括三条不可关闭的不变量，供前端“系统规则说明”展示。

⚠ 规则类型清单来自注册表，不是 Controller 手写数组；新增 handler 后接口和动态表单会一起获得新类型。

### `list(SchedulePrincipal principal)`

对应 `GET /api/rules`。从登录主体取 `organizationId`，交给 `RuleService.list`。租户 id 不接受前端传入，避免越权读取别的学校。

### `versions(...)` 与 `version(Long versionId, ...)`

分别对应版本列表和版本详情。

1. 先 `ensureInitialized`，保证新组织也存在默认规则及首个版本。
2. 列表使用 `RuleVersionResponse.summary`，不带完整快照，控制响应大小。
3. 详情使用 `detail`，带当时全部启用规则，满足审计追溯。

⚠ 静态路径 `/versions` 放在 `/{ruleId}` 前面，避免阅读和路由维护时把 `versions` 误当 id。

### `current(SchedulePrincipal principal)`

对应 `GET /api/rules/current`。

返回 `version_no`、`rule_set_hash`、`rule_count`。使用 `LinkedHashMap` 固定字段插入顺序，便于日志与人工比对；当前版本不存在时明确返回 null/0，而不是空指针。

### `trial(RuleCreateRequest request, ...)`

对应 `POST /api/rules/trial`。它不加 `@Valid`，动态参数的真正校验由规则 schema 完成；随后调用 `RuleTrialService.trial`，全程不落库。

### `create(...)`

对应 `POST /api/rules`。`@Valid` 先检查请求形状，再由 Service 检查类型、参数与作用域。成功返回完整 `RuleResponse`，包含新规则的 `revision=1`。

### `get(Long ruleId, ...)`

对应 `GET /api/rules/{id}`。Service 的查询条件同时包含 id 和 organizationId；因此别的租户的规则也表现为“规则不存在”，不会泄漏其存在性。

### `update(Long ruleId, RuleUpdateRequest request, ...)`

对应 `PUT /api/rules/{id}`。请求必须带 `expected_revision`，Service 用单条条件 UPDATE 裁决并发写入。

### `setEnabled(...)`

对应 `PATCH /api/rules/{id}`。列表开关也走乐观锁，且 Mapper 只改 `enabled`、`version`、`updated_at`，不会顺手覆盖别人刚编辑的参数。

### `delete(Long ruleId, Integer expectedRevision, ...)`

对应 `DELETE /api/rules/{id}?expected_revision=...`。

⚠ revision 放查询参数，不放 DELETE body，因为不同客户端和代理对 DELETE body 的支持不一致。删除成功只返回 `{ok:true}`。

### `requireAdmin(SchedulePrincipal principal)`

统一权限闸门：未登录抛 401 `请先登录`；非管理员抛 403 `仅管理员可以执行此操作`。所有入口都复用它，避免某个新接口忘记权限。

## 2. 三个请求 DTO：把“形状校验”和“规则语义”分开

### `RuleCreateRequest`

**源码**：[RuleCreateRequest.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleCreateRequest.java)

| 字段 | 含义与默认值 |
|---|---|
| `ruleType` | 必填；必须存在且不能是 mandatory 类型 |
| `params` | 动态 Map；交给该类型的 `RuleParamSpec` 校验 |
| `hardness` | `hard` / `soft`；空值默认 hard |
| `weight` | 仅 soft 有效；空值或小于 1 时归一为 1 |
| `scope` | 当前仅接受 `org`；空值默认 org |
| `scopeId` | 为将来细粒度作用域预留；当前求解不使用 |
| `enabled` | 空值默认 true |
| `description` | 可选的人话说明；空时由 handler 根据参数生成 |

`@NotBlank`、`@Size` 只处理 JSON 形状，失败是 422。诸如“这个类型没有参数 max”属于业务语义，失败是 400。两层状态码不要混用。

### `RuleUpdateRequest`

**源码**：[RuleUpdateRequest.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleUpdateRequest.java)

更新不允许改 `ruleType`：换类型会让旧参数残留并产生歧义，正确操作是删除后新建。`expectedRevision` 用 `@NotNull` 强制客户端参与并发控制。

⚠ 当前实现把 `params=null` 解释为“空参数”，不是“保持原参数”；前端编辑时必须提交完整参数对象。

### `RulePatchRequest`

**源码**：[RulePatchRequest.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RulePatchRequest.java)

只有 `enabled` 和 `expectedRevision` 两项，二者都必填。独立 DTO 的意义是把 PATCH 的可写字段压到最小，防止开关接口被滥用成全量更新。

## 3. `RuleService`：CRUD 的业务主体

**源码**：[RuleService.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleService.java)

**上游**：`RuleController`。

**下游**：规则 Mapper、`RuleSetService`、类型目录，以及只读的年级/班级/教师/科目 Mapper。

写方法都有 `@Transactional`：数据行变化和规则集版本留痕必须一起成功或一起回滚。

### 构造器

除 CRUD 依赖外，还注入四个主数据 Mapper，仅用于把未来的 scope id 翻译为人名。它们不会写 academic 表。

### `list(long organizationId)`

1. `ensureInitialized` 懒初始化默认规则。
2. `listAll` 取得该租户全部规则。
3. 每行经 `toResponse` 补齐 handler 名、作用域名和人话描述。

### `get(long organizationId, long id)`

用 `requireOwned` 查询，再转响应。租户条件在查询阶段就生效，而不是查到后再判断。

### `create(long organizationId, RuleCreateRequest request)`

执行顺序是这段代码最重要的部分：

1. `catalog.handlerOf`：未知类型立即 400，防止写入永远不会生效的数据。
2. `rejectMandatory`：拒绝把系统不变量伪装成可关闭的数据规则。
3. `validateParams`：复用 solver-core 的 schema，不在接口层复制第二套校验。
4. 规范化 hardness、scope、weight 和 enabled。
5. `requireOrgScope`：当前明确拒绝未定义好叠加语义的细粒度 scope。
6. 构造 Entity；来源固定为 `manual`，revision 从 1 开始，时间统一取 UTC 秒精度。
7. 插入数据行。
8. `recordVersion` 冻结新的启用规则集合。
9. 返回响应。

⚠ 先校验后写入不是为了少报一个数据库错误，而是保证错误文案能直接给用户看。

### `update(long organizationId, long id, RuleUpdateRequest request)`

1. 查询本租户规则；不存在返回 404。
2. 校验新参数，保留或规范化 hardness、weight、description。
3. `updateWithRevision` 执行 `WHERE version = expectedRevision` 的单条 UPDATE。
4. 受影响行数不是 1 时返回 409，说明用户看到的版本已过期。
5. 再从数据库读取一次更新后的实体。
6. 冻结规则集版本并返回新响应。

⚠ 第 5 步不能省：revision 是 SQL 中 `version = version + 1` 得到的，内存 entity 仍是旧值。实测若直接返回它，前端下一次提交会立刻 409。

### `setEnabled(long organizationId, long id, RulePatchRequest request)`

先验证归属，再执行只更新启停字段的条件 UPDATE。成功后重读、记录“启用/停用规则”版本说明、返回新 revision。

### `delete(long organizationId, long id, int expectedRevision)`

先读实体是为了校验租户并保留描述；随后条件 DELETE。删除成功后仍要 `recordVersion`，因为“少了一条启用规则”同样是一个需要审计的规则集状态。

### `requireOwned(long organizationId, long id)`

查询条件同时带主键与租户。没找到统一抛 404 `规则不存在`。

### `toResponse(ConstraintRuleEntity entity)`

把数据库实体补成面向界面的 DTO：已知类型显示 handler 的中文名；未知历史数据至少退回原 `ruleType`，避免整个列表因一条脏数据崩溃。

### `descriptionOf(...)`

优先采用用户显式描述；为空时调用 handler 的 `describe(params)` 生成。这样规则列表始终是人能读懂的，不必展示内部类型名。

### `scopeName(String scope, Long scopeId)`

org 显示“全校”；其他 scope 用只读 Mapper 查真实名称。引用已删除时退化成“年级3”等可诊断文本，不返回 null。

### `hardnessOf(String raw, String fallback)`

空值用 fallback；其余去空格、转小写，只接受 hard/soft。非法值返回带原输入的 400。

### `scopeOf(String raw)` 与 `requireOrgScope(String scope)`

前者负责规范化，后者负责当前版本的能力边界。

⚠ 表结构虽然预留 grade/class/teacher/subject，但“多层规则如何叠加、冲突时谁覆盖谁”尚未定义，所以当前宁可拒绝，也不接受一个求解器实际忽略的参数。

### `positive(Integer weight)`

将 null 或小于 1 的权重归一为 1。hard 规则的权重也固定为 1，避免存一项看似有效、实际不会参与目标函数的值。

## 4. `ConstraintRuleMapper`：并发裁决必须落在 SQL

**源码**：[ConstraintRuleMapper.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/ConstraintRuleMapper.java)

### `lockOrganizationRules(long organizationId)`

执行 `SELECT ... FOR UPDATE`。首次懒初始化时，即便组织还没有规则，InnoDB 在 REPEATABLE-READ 下也会对索引范围加 gap lock，阻止两个请求各插入一套默认规则。

⚠ 这个保证依赖事务和隔离级别；把数据库切到 READ-COMMITTED 前必须重新设计初始化幂等。

### `updateWithRevision(ConstraintRuleEntity entity, int expectedRevision)`

一条 SQL 同时完成字段更新、revision 自增和并发比较。返回 rowcount；0 由 Service 翻译为 409。

⚠ 不能改成“先 SELECT version，再普通 UPDATE”，因为两个请求可能同时读到同一个旧值并都通过检查。

⚠ JSON 字段显式指定 `JacksonTypeHandler`。同时注解必须是 `@Update`，若误写 `@Select`，MyBatis 会把 UPDATE 当查询并拿不到 rowcount。

### `updateEnabledWithRevision(...)`

只更新 enabled、version、updated_at。刻意不接收 Entity，因而从类型层面阻止 PATCH 覆盖其它字段。

### `deleteWithRevision(...)`

DELETE 的 WHERE 同时包含 id、organization_id、version。它防止删除别的租户数据，也防止删除别人刚编辑的新版本。

## 5. 数据实体与响应 DTO

### `ConstraintRuleEntity`

**源码**：[ConstraintRuleEntity.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/ConstraintRuleEntity.java)

它映射 `constraint_rules`。`params` 是 MySQL JSON，使用 `JacksonTypeHandler`；类上的 `autoResultMap=true` 不能删除，否则会出现“写入正常、读出 null”。数据库字段 `version` 对外叫 `revision`，强调它是乐观锁而非业务版本号。

### `ConstraintRuleVersionEntity` / `ConstraintRuleVersionMapper`

**源码**：[ConstraintRuleVersionEntity.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/ConstraintRuleVersionEntity.java)、[ConstraintRuleVersionMapper.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/ConstraintRuleVersionMapper.java)

版本行不仅存 hash，还存全部启用规则的 JSON 快照。只存 hash 无法在规则被修改或删除后还原历史。Mapper 没有自定义 SQL，通用 CRUD 足够。

### `RuleResponse.of(...)`

**源码**：[RuleResponse.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleResponse.java)

Entity → API DTO 的唯一装配点。params 为 null 时返回空对象，数据库 version 映射成接口 revision，并补入 handler 显示名和 scope 名。

### `RuleVersionResponse.summary/detail`

**源码**：[RuleVersionResponse.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleVersionResponse.java)

两个工厂唯一差异是是否带 rules 快照：列表轻，详情可追溯。

## 6. `RuleTrialService`：保存前只编译，不求解

**源码**：[RuleTrialService.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleTrialService.java)

**上游**：`RuleController.trial`。

**下游**：`RuleSetService`、`RuleTypeCatalog`、`ScheduleInputLoader`、`OrbitSolver.compile`。

### 构造器

注入当前规则集、类型 schema 和排课输入加载器。试算使用真实组织数据，但不会改数据。

### `trial(long organizationId, RuleCreateRequest request)`

1. 完整复用保存时的类型、mandatory、参数、hardness、weight 校验，防止“试算通过但保存失败”。
2. handler 根据 params 生成人话描述。
3. 读取当前规则集，复制一份并追加草稿规则。
4. 加载当前组织的完整 `ScheduleInput`。
5. 编译当前规则集，取得基线指纹与变量数。
6. 编译追加草稿后的规则集。
7. 成功时比较指纹并返回变量数增量；失败时捕获 `ConstructionInfeasible`，把确定性冲突作为 `problem` 返回。

如果“当前规则集本身”就编译失败，方法直接返回 400，而不是把问题嫁祸给草稿。

⚠ 它故意不调用 `solve`：求解会占用容量槽位和分布式锁，用户每改一个表单数字就全校重排会拖垮系统。真正的排课差异必须走正式排课流程并产生版本与审计。

⚠ `modelChanged=false` 只表示对当前输入编译出的模型没有影响，不代表规则在所有学校数据上都无效。

### `variablesOf(String modelStats)`

从 OR-Tools 的统计文本中解析 `#Variables:` 后的数字，并兼容 `9'676` 这种千分位格式。找不到标记或传入 null 时返回 0。

⚠ 这是对 OR-Tools 输出文本格式的绑定；升级 OR-Tools 时应让相关测试显式失败并复核，而不是静默吞掉格式变化。

### `RuleTrialResponse`

**源码**：[RuleTrialResponse.java](../backend-java/orbit-scheduling/src/main/java/com/orbit/scheduling/rule/RuleTrialResponse.java)

| 字段 | 回答的问题 |
|---|---|
| `description` | “这条规则是不是我想表达的意思？” |
| `compiles` / `problem` | “它与当前数据和固定课是否存在确定性矛盾？” |
| `modelChanged` | “它是否实际改变了当前模型？” |
| `model` | 编译前后变量数及增量 |
| `note` | 明示“这里只评估编译影响，不是重排结果” |

`valid` 表示请求及规则语义有效；即使 `compiles=false`，规则草稿本身仍可能是合法的，只是与当前数据冲突。

## 7. 一次并发编辑会怎样

```text
甲、乙都读取 revision=3
甲 PUT expected_revision=3 → UPDATE 命中 1 行 → 数据库 revision=4 → 成功
乙 PUT expected_revision=3 → UPDATE 命中 0 行 → 409
乙刷新拿到 revision=4，再决定是否重做自己的修改
```

关键不是“检查 revision”这句话，而是检查和写入必须在同一条 SQL 的 WHERE 中完成。

## 8. 修改这块代码时的检查表

- 新接口是否经过 `requireAdmin`，租户 id 是否只从登录主体获取？
- 新规则参数是否复用 `RuleParamSpec`，而不是复制一套校验？
- 所有写操作是否同时记录规则集版本？
- UPDATE/PATCH/DELETE 是否都带 `expected_revision` 并检查 rowcount？
- SQL 自增 revision 后是否重新读库再响应？
- JSON 字段是否保留 `autoResultMap=true` 和 `JacksonTypeHandler`？
- 试算是否仍然“不落库、不求解、不占容量槽位”？
- 若开放细粒度 scope，是否先定义了叠加、覆盖和冲突语义，并让编译器真正消费它？
