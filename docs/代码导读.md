## 0. 先学会怎么读

### 0.1 三个贯穿全项目的约定

**① 包名 = 功能，不是层名。**
没有 `controller/` `service/` `mapper/` 这种按层切的包，而是 `version/` `swap/` `rule/` `job/`。
**理由**：改一个功能时你希望所有相关文件在一起。所以找"换课怎么实现的" → 看 `swap/`，
不要去找 `controller/`。

**② 类的角色看后缀。**

| 后缀 | 是什么 | 例子 |
|---|---|---|
| `*Controller` | HTTP 入口。**只做三件事**：取参数、调 Service、返回。不含业务逻辑 | `SwapController` |
| `*Service` | 业务逻辑都在这里 | `SwapService` |
| `*Entity` | **数据库表的一行**（字段与列一一对应） | `ScheduleVersionEntity` |
| `*Mapper` | 数据库访问（MyBatis-Plus）。有 `@Select`/`@Update` 注解的都是自定义 SQL | `ScheduleJobMapper` |
| `*Request` / `*Response` | **进出 HTTP 的 JSON 形状**，与 Entity **刻意分开** | `SwapRequest` |
| `*Ref` | 只读的跨服务表映射（只用来查询，从不写） | `TeacherRef` |

**③ 注释里的两个符号是"实测标记"，不是修辞。**

- **`⚠`** = 这里踩过坑，或者有反直觉的地方。**读代码时优先看带 ⚠ 的段落**。
- **"实测……"** = 这不是推测，是拿两个后端跑出来对比过的结果。
  例：`⚠ 实测踩过：POST 的响应带 7 位小数，而 Python 是干净的秒。`

### 0.2 怎么从"一个功能"找到"一段代码"

以「用户拖动课程换位置」为例，四步：

```
1. 前端点下去 → frontend/src/api/index.ts 里找 swapScheduleEntry
                  ↓ 它请求的 URL 是 /api/schedule/versions/{id}/entries/swap
2. URL 前缀 /api/schedule/** → Vite 分流到 8083（orbit-scheduling）
                  ↓
3. 在 orbit-scheduling 里搜 URL 片段 "entries/swap"
   → ScheduleVersionEntryController（@PostMapping("/{id}/entries/swap")）
                  ↓
4. 它调 SwapService.swap(...) → 业务逻辑全在这里
```

**关键词**：URL → Controller → Service。Mapper 只在 Service 里出现。

### 0.3 一个必须知道的背景：这个项目的目标是"行为等价"

P1/P2/P3 的每一行代码都受一条约束：**Java 侧的行为必须和 Python 侧一样**，
包括**错误文案**（`{"detail":"年级不存在"}` 里的每一个字）。

所以你会看到一些"明明可以写得更好、但故意没改"的地方，例如 422 的 `detail` 是**数组**而不是字符串。
**它们不是设计失误，是为对齐而付出的代价**。这类地方都写了注释说明原因，
改之前先读注释 —— 以及 `tools/contract-diff/compare.py` 里对应的用例。

### 1.1 `UtcTimes` —— 时间基准（53 行，1 个方法）

**为什么需要**：Python 侧写库用的是 `utcnow`（朴素 UTC）。Java 里顺手写
`LocalDateTime.now()` 拿到的是**东八区时间**，与 Python 差 8 小时 ✗
**不报错、不崩**，只在「按时间排序」「显示创建时间」时表现很怪 —— 最难查的那一类。

#### `static LocalDateTime now()`

| 它做的事 | 做三件事：取 UTC → **截断到秒** → 返回 |
|---|---|
| **谁调它** | 所有要写库的时间字段（`created_at` / `updated_at` / `lease_until` …） |
| **第一件**：`LocalDateTime.now(ZoneOffset.UTC)` | 取 UTC 而不是本地时间，对齐 Python |
| **第二件（容易忽略）**：`.truncatedTo(ChronoUnit.SECONDS)` | ⚠ **为什么必须截断**：MySQL 的 `datetime`（无精度声明）只存到秒，而 `LocalDateTime.now()` 带纳秒。不截断就会出现**同一个接口两次调用格式不一致**：<br>POST → `"2026-09-27T06:23:11.0585571"`（内存对象，带纳秒）<br>GET → `"2026-09-27T06:23:11"`（从库里读回，只有秒）<br>Python 侧没这问题，因为它在 commit 后 `db.refresh()` 重新读库。这里选择**写入前就截断**，比"再查一次库"少一次往返 |

> ⚠ 这是一个**临时对齐**措施。干净的做法是全程用带时区的 `Instant` / `OffsetDateTime`，
> 并在 JDBC 与 JSON 两层显式声明时区。那是一次涉及全部时间字段的改造，已记入 TODO。

**为什么是 `final` 类 + 私有构造器**：纯静态工具类，不允许被实例化或继承。

### 1.2 `PageQuery` —— 列表接口的查询参数（126 行）

**它解决的问题**：12 个列表接口都要"页码/条数/关键字/排序/方向"这 5 个参数 +
归一化 + 校验。**写在一个 record 里，而不是在 12 个 Controller 里各写一遍。**

前端这样传：`GET /api/teachers?page=1&size=20&keyword=张&order_by=name&order=asc`

```java
public record PageQuery(
        @BindParam("page") Integer page,
        @BindParam("size") Integer size,
        @BindParam("keyword") String keyword,
        @BindParam("order_by") String orderBy,
        @BindParam("order") String order)
```

#### 逐方法

| 方法 | 干什么 | 谁调它 |
|---|---|---|
| **紧凑构造器** `PageQuery { … }` | **归一化**：page≤0→1；size≤0→20 且**上限 200**；keyword 空白→null；order 只认 desc 否则 asc | Spring 绑定参数时**自动执行** —— 你在 Controller 里拿到的 `query` 一定已经归一化过了 |
| `static PageQuery of(int page, int size)` | 全量查询（只给页参数） | Service 内部需要分页拉数据时 |
| `int pageNumber()` | 归一化后的页码 | Service 构造 MyBatis-Plus 的 `Page` |
| `int pageSize()` | 归一化后的条数（**已截断到 200**） | 同上 |
| `boolean hasKeyword()` | 有没有关键字 | Service 决定要不要加 `LIKE` 条件 |
| `boolean desc()` | 是否倒序 | 少见（多数地方用 `ascending()`） |
| `boolean ascending()` | 是否升序 | ⚠ **给 MyBatis-Plus 用的**，见下面的坑 |
| `String likePattern()` | `"%关键字%"`；无关键字→null | 直接塞进 `like()` 条件 |
| `String orderColumn(Set<String> allowed, String fallback)` | **白名单校验**：不在 `allowed` 里 → 抛 400 | Service 取排序列 |

#### 三个 ⚠ 坑（都是实测踩出来的）

**坑 1：字段必须是包装类型 `Integer`，不能是 `int`。**

Spring 对 record 做构造器绑定时，请求里**没带** `page` 会把 `null` 传给构造器，
而 `null` 无法转成原始类型 `int` → **绑定失败**：

```
422 {"detail":[{"type":"value_error","loc":["query","page"],
     "msg":"Failed to convert value of type 'null' to required type 'int'"}]}
```

后果是**所有列表接口在"不带参数"时全部 422**，而带全参数时又正常 —— 很容易漏测。
（实测确实先漏了，是"走通全链路"这一步抓出来的。）

**坑 2：参数名必须显式 `@BindParam`，不能靠字段名。**

record 组件名是 camelCase（`orderBy`），查询参数是 snake_case（`order_by`）。
**两者对不上时 Spring 不报错，只是这个参数永远是 null** ✗
表现是「传了 `order_by` 但排序没变、白名单校验也没触发」。
（靠"传一个非法的 `order_by` 却没返回 400"才发现。）

**坑 3：`ascending()` 与 MyBatis-Plus 的参数名。**

MyBatis-Plus 的签名是 `orderBy(condition, isAsc, column)` —— 第二个参数叫 **`isAsc`**，
**不是 `isDesc`**。把 `desc()` 传进去会让语义**整个反过来**，而且**不报错**
（默认排序与显式排序都"有结果"，只是方向反了），只有拿数据核对时才发现。实测踩过一次。

**为什么 `orderColumn` 要白名单**：绝不允许把用户输入直接拼进 `ORDER BY`（SQL 注入）。
注意参数说明：`allowed` 里的值由各 Service **映射成类型安全的列引用**，
也不是直接拼进 SQL 的字符串。

### 1.3 `PageResponse<T>` —— 列表接口的统一响应（72 行）

```java
@JsonInclude(JsonInclude.Include.ALWAYS)
public record PageResponse<T>(List<T> items, long total)
```

响应长这样：`{ "items": [ ... ], "total": 123 }`

#### 为什么必须替换掉裸数组

Python 原版所有列表接口都是 `response_model=list[XxxOut]` —— 返回**裸数组**、
且**完全忽略分页参数**（实测：`GET /api/grades?page=1&size=1` 仍然返回全部 5 条 ✗）。
前端因此只能靠 antd 的**前端分页**：一次拉全量、在浏览器内存里切片。

现在数据规模是 4 个班，但目标是 160 班规模 —— 一个年级的课表条目就接近 4,800 行，
**必须真分页**。

#### 逐方法

| 方法 | 干什么 | 注意 |
|---|---|---|
| `PageResponse { … }`（紧凑构造器） | `items` 为 null → 空列表；并 `List.copyOf` 做**防御性拷贝** | copyOf 保证不可变，且**拒绝 null 元素**（早失败好过晚失败） |
| `static of(List<T>, long)` | 基本构造 | |
| `static of(List<T>, Number)` | **给 MyBatis-Plus 的 `Page` 用**（`getTotal()` 返回 `long`，但类型是 `Number`） | 刻意**不 import MyBatis-Plus**：common 是薄共享模块，让它依赖 MyBatis-Plus 会破坏"不给网关带 Servlet 容器"的约束。调用方写 `PageResponse.of(page.getRecords(), page.getTotal())` 即可 |
| `static empty()` | 空结果 | "查无数据"不是错误，别抛 404 |
| `boolean isEmpty()` | 当前页是否为空 | ⚠ **`@JsonIgnore` 不能省**，见下 |

#### ⚠ 坑：`isEmpty()` 会被 Jackson 当成字段输出

Jackson 会把任何 `isEmpty()` 当成属性 `empty` 的 getter，于是响应变成：

```json
{"items":[...],"total":6,"empty":false}
```

多出一个 **Python 侧没有的字段** ✗ 不是崩溃型错误，但会让契约测试产生噪音，
也可能让前端的类型校验失败。**它是 getter 形态，所以很容易忽略**。实测踩过一次。

**为什么 `@JsonInclude(ALWAYS)`**：`items` 为空数组时也要输出 `"items": []`，
不能因为"空"就省略字段 —— 否则前端读 `data.items.length` 会炸。

**刻意不做的事**：「有分页参数时包一层、无参数时返回裸数组」的混合形态。
同一接口两种返回结构会让前端必须写两个分支，契约测试也无法覆盖。

### 1.4 `BusinessException` —— 业务异常（91 行）

**对应 Python 的** `HTTPException(status_code=..., detail="人话")`。

```java
public class BusinessException extends RuntimeException {
    private final int status;
    private final Integer retryAfterSeconds;   // 仅 429 用
```

#### 为什么强调"传完整文案，而不是传错误码"

Python 原版有 20 多处 `HTTPException`，文案都是**面向用户的中文**，
而且**这些文案本身就是契约的一部分**（前端直接显示 `error.response.data.detail`）。
所以这里刻意要求传完整文案，而不是传错误码让上层去翻译。

实测到的原文（迁移时要**逐字保留**）：

| 状态码 | 文案 |
|---|---|
| 401 | `请先登录` / `用户名或密码错误` / `登录已失效，请重新登录` / `账号不存在或已停用` |
| 403 | `仅管理员可以执行此操作` / `仅平台管理员可以管理工作空间` |
| 404 | `年级不存在` / `班级不存在` / `老师不存在` / `课表版本不存在` |
| 409 | `只有草稿可以修改` / `本校已有排课任务正在运行，请稍后再试` |
| 429 | `登录失败次数过多，请在 N 秒后重试` / `服务器排课任务已满，请稍后再试` |

#### 逐方法

| 方法 | 干什么 |
|---|---|
| `BusinessException(int status, String detail)` | 基本构造。`detail` 通过 `super(detail)` 存进 `getMessage()` |
| `BusinessException(int, String, Integer retryAfterSeconds)` | 带 `Retry-After` 的重载 |
| `int status()` | 原始状态码 |
| `HttpStatus httpStatus()` | 转成 Spring 的枚举 |
| `Integer retryAfterSeconds()` | 有值时 `ApiExceptionHandler` 会写 `Retry-After` 响应头 |
| `String detail()` | 就是 `getMessage()` —— 语义化的别名，读代码时更清楚"这个是响应体里的那一段" |
| `static badRequest / unauthorized / forbidden / notFound / conflict` | 工厂方法，**推荐用它们**（比 `new BusinessException(404, …)` 更难写错） |
| `static tooManyRequests(String, int)` | 429 **带** `Retry-After`（登录限流用：它知道窗口还剩多久） |
| `static tooManyRequests(String)` | 429 **不带**（排课容量满用：确实给不出"还要等多久"，取决于别的任务何时跑完） |

**为什么继承 `RuntimeException` 而不是受检异常**：业务异常遍布各层，
强制 try-catch 会让代码充满噪音。由 `@RestControllerAdvice` 统一兜。

### 1.5 `ApiExceptionHandler` —— 全项目错误响应的唯一出口（278 行）

**这是 `orbit-common` 里最重要的一个类。** 所有异常最终都在这里变成 JSON。

**为什么必须有它**：Spring Boot 默认的错误体是 `ProblemDetail`：

```json
{"type":"about:blank","title":"Not Found","status":404,"detail":"...","instance":"/api/x"}
```

前端读 `error.response.data.detail` 虽然也能读到，但**多出的字段、不同的 `type` 语义、
以及 401/403 的默认行为**都会让契约测试产生大量噪音。方案 §9 明确要求不用它。

#### 状态码映射（都对着 Python 实测过）

| 捕获的异常 | 返回 | 依据 |
|---|---|---|
| `BusinessException` | 它自己的状态码 + `{"detail":"..."}` | 对应 Python 的 `HTTPException` |
| `MethodArgumentNotValidException` | **422** + `{"detail":[...]}` | FastAPI/Pydantic 的 422 |
| `ConstraintViolationException` | **422** + `{"detail":[...]}` | 方法参数级校验（`@Validated`） |
| `HttpMessageNotReadableException` | **422** + `[{"type":"json_invalid"}]` | 实测：body 非法 JSON 时 FastAPI 也是 422 |
| `MissingServletRequestParameterException` | **422** + `[{"type":"missing",...}]` | **必填查询参数没传** |
| `HttpRequestMethodNotSupportedException` | **405** + `{"detail":"Method Not Allowed"}` | 实测：`GET /api/grades/999999` → 405 |
| `Exception`（兜底） | **500** + `{"detail":"服务器内部错误"}` | 有意的偏离：Python 未捕获时 uvicorn 返回纯文本，这里给 JSON 更好用 |

> ⚠ **422 的 `detail` 是数组，其他错误的 `detail` 是字符串** —— 两种形状。
> 这不是笔误，是 Python 侧的既有形状。

#### 逐方法

**`handleBusiness(BusinessException ex)`** → 400/401/403/404/409/429
- 唯一做的事：把 `retryAfterSeconds` 写成 `Retry-After` 响应头，再包成 `ErrorResponse`
- 对应 Python：`raise HTTPException(429, detail, headers={"Retry-After": str(n)})`

**`handleBodyValidation(MethodArgumentNotValidException ex)`** → 422
- ⚠ **关键细节**：`loc` 的首段要区分 `"body"` 还是 `"query"`：
  ```java
  String location = ex.getParameter().hasParameterAnnotation(RequestBody.class)
          ? "body" : "query";
  ```
  因为参数可能来自请求体（`@RequestBody DTO`）也可能来自查询参数（`PageQuery` 这种 record 绑定）。
  **全写成 `"body"` 会让排查者找错地方。**
- `items.isEmpty()` 时的兜底（`"请求参数不合法"`）是为了避免返回 `{"detail":[]}` 这种空数组

**`handleParamValidation(ConstraintViolationException ex)`** → 422
- 处理 `@Validated` + 方法参数上的约束
- 取路径的**最后一段**作为字段名（`"list.page"` → `"page"`），再过 `jsonName()` 转成 snake_case

**`handleUnreadable(HttpMessageNotReadableException ex)`** → 422 `json_invalid`
- body 不是合法 JSON / 类型对不上
- 细节只写进 `log.debug`，**不外泄**给客户端

**`handleMissingParameter(MissingServletRequestParameterException ex)`** → 422
- ⚠ **它与"传了但值不对"是两条不同的路径**：
  - **没传** → 422（本条，`Field required`）
  - **传了但值非法** → 由业务代码给 400
- 最初把两者都写成 400，**被影子对比工具抓出来**。
  所以这里单独处理 —— 别把 `@RequestParam` 写成 `required = false` 再自己判空。

**`handleMethodNotSupported(...)`** → 405
- 实测 FastAPI 的 405 体就是 `{"detail":"Method Not Allowed"}`（英文，不是中文）

**`handleUnexpected(Exception ex)`** → 500
- ⚠ **这里一定要打日志**（`log.error("未预期的异常", ex)`）：否则 500 会变成
  「前端只看到一句服务器内部错误，后端什么都没有」，排查时非常痛苦

**私有工具方法三个**：

| 方法 | 作用 | 为什么需要 |
|---|---|---|
| `typeOf(String code)` | Jakarta 的约束码 → Pydantic 的 `type` 字符串 | Pydantic 数值边界用 `less_than_equal`/`greater_than_equal`，Spring 只给 `Max`/`Min`。**`type` 是响应体的一部分**，得按对端的取值输出 |
| `fieldPath(String location, String field)` | Spring 的字段路径 → Pydantic 的 `loc` 数组 | ⚠ Spring 给 `"items[0].weeklyHours"`（一串），Pydantic 要 `["body","items",0,"weekly_hours"]`（**下标单独一段**）。逐字符扫描：`.` 分段、`[n]` 变成整数元素。**实测就是这么发现两边对不上的** |
| `jsonName(String field)` | Java 属性名 → JSON 字段名 | ⚠ `FieldError.getField()` 返回**Java 属性名**（`adminDisplayName`），客户端发的是 **JSON 字段名**（`admin_display_name`）。直接用前者，前端拿它去表单里找字段会找不到。**实测：Java 报 `["body","adminDisplayName"]`，Python 报 `["body","admin_display_name"]`** —— 契约不一致。<br>**刻意复用 Jackson 的命名策略**（`PROPERTY_NAMING.nameForField(...)`）而不是手写 camel→snake 转换：序列化用什么策略，报错位置就用什么策略，**两者不可能漂移** |

**`UNPROCESSABLE_CONTENT` 常量为什么用数字**：`ResponseEntity.unprocessableEntity()`
在 Spring Framework 7 里**已过时** —— RFC 9110 把 422 的名字从 "Unprocessable Entity"
改成了 "Unprocessable Content"，Spring 跟着弃用了旧名字的方法。用数字不丢可读性
（常量名解释了它是什么），也不会随 Spring 改名再被弃用一次。

### 1.8 `ValidationErrorItem` —— 数组里的一项（76 行）

**刻意做成 FastAPI/Pydantic 的形状**：

```json
{"type":"missing","loc":["body","name"],"msg":"Field required","input":{}}
```

**为什么复刻这个别扭的结构**：P1 的目标是「**行为等价**」，不是「顺便改好」。
一旦这里改成字符串，契约测试就会红，然后要为每个差异写例外 —— **测试也就失去意义了**。

> ⚠ **文案不强求逐字**：Pydantic 的 `msg`（`"Field required"`）无法在 Spring 里复刻，
> 我们用 Jakarta Validation 的注解消息（`"不能为空"`）。契约测试比对的是
> **状态码 + 结构**（detail 是数组、每项有 type/loc/msg），不是文案。

#### 字段

| 字段 | 含义 |
|---|---|
| `type` | `missing`（缺字段）/ `value_error`（值不合法）/ `json_invalid`（body 不是合法 JSON） |
| `loc` | 出错位置，格式 `["body","字段名"]`，**首段是位置来源** |
| `msg` | 人话描述 |
| `input` | 触发错误的原始值；**拿不到时为 null 并省略该字段**（`@JsonInclude(NON_NULL)`） |

#### 逐方法

| 方法 | 用途 |
|---|---|
| `static missing(String field, String msg)` | body 里缺字段（`loc = ["body", field]`） |
| `static missing(String location, String field, String msg)` | 指定位置（`body` 或 `query`） |
| `static valueError(String field, String msg)` | body 里值不合法 |
| `static valueError(String location, String field, String msg)` | 同上，指定位置 |
| `static jsonInvalid(String msg)` | body 不是合法 JSON（`loc = ["body"]`，**只有一段**） |
| `static of(String type, List<Object> loc, String msg)` | **完全自定义** —— 用在嵌套路径等需要自己拼 `loc` 的场景 |
| `private static loc(String location, String field)` | 拼 `[location]` 或 `[location, field]` |

**为什么暴露 `of(...)`**：Python(Pydantic) 对**数组元素**的报错位置是把下标当成
**独立的一段**（`["body","items",0,"weekly_hours"]`），而 Spring 给的是一整串
（`"items[0].weeklyHours"`）。两者形状不同，必须在 `ApiExceptionHandler.fieldPath()`
里解析后重拼 —— 那就是用这个工厂造的。

**为什么 `loc` 的首段要区分 `body`/`query`**：分页参数来自 query，
要写成 `["query","page"]`；写成 `["body","page"]` 会**误导排查者**
（他会去请求体里找一个根本不存在的字段）。

### 1.9 `JwtService` —— 标准 JWT（95 行）

> ⚠ **与 Python 的 token 不通用，这是有意的。**
> Python 签的**不是**标准 JWT，而是自己拼的格式：
> ```
> base64url(json{"uid":..,"exp":..,"nonce":..}) + "." + base64url(HMAC-SHA256(SECRET, body))
> ```
> 没有 header、没有标准 claim。**两边 token 不通用 ⇒ 灰度切换时老 token 失效、
> 用户要重新登录一次。**
>
> **选择标准 JWT 的理由**：token 对前端是**不透明**的（只往 localStorage 存、原样回传），
> 所以**格式不属于契约**；而标准 JWT 在接网关、接 OAuth、用现成中间件时都省事。

#### 逐方法

| 方法 | 干什么 | 注意 |
|---|---|---|
| `JwtService(String secret, long ttlSeconds)` | 构造器：校验密钥长度、建 key | ⚠ HS256 要求密钥 ≥256 bit（32 字节）。**短于 32 字节直接启动失败**，而不是偷偷派生 —— 弱密钥是安全问题，静默"修好"会让人以为配置没问题。实测 `APP_SECRET_KEY` 是 49 字节 ✓ |
| `String issue(long userId)` | 签发 | `sub` = userId；`jti` = 随机 UUID（**对应 Python 的 `nonce` 字段**，标准 JWT 里叫 `jti`）；`iat`/`exp` = 现在 / 现在+ttl |
| `Optional<Long> userIdOf(String token)` | 校验并取出 userId | ⚠ **失败一律返回 `Optional.empty()`，不抛异常** —— 调用方（过滤器）要根据结果返回 401，而不是让异常冒到 500。`catch (JwtException \| IllegalArgumentException)` 覆盖：签名不对 / 过期 / 格式非法 / **subject 不是数字** |
| `long ttlSeconds()` | TTL 秒数 | |

**为什么 `AuthFailure` 要和它放在一个包**：见下。

### 1.10 `AuthFailure` —— 鉴权失败的原因与文案（38 行）

**它解决一个具体的对齐问题**：架构上过滤器（`JwtAuthenticationFilter`）
**只负责把 token 变成安全上下文，不负责写响应**；决定放行与否的是授权层，
未认证时由 `AuthenticationEntryPoint` 统一写 401。

**但 Python 的 401 文案不止一种**，取决于失败原因：

| 情况 | 文案 |
|---|---|
| 没带 token | `请先登录` |
| token 签名不对 / 已过期 / 格式非法 | `登录已失效，请重新登录` |
| token 有效，但用户已删除或停用 | `账号不存在或停用` |

**所以过滤器要把"为什么失败"记在请求属性上，入口点再据此选文案** ——
既保持职责分离，又能逐字对齐文案。

| 成员 | 用途 |
|---|---|
| `static final String ATTRIBUTE = "com.orbit.auth.failure"` | 请求属性名（**过滤器写、入口点读**）。用全限定名做 key，避免与其他框架属性冲突 |
| `static final String NO_TOKEN` | `请先登录` |
| `static final String INVALID_TOKEN` | `登录已失效，请重新登录` |
| `static final String UNKNOWN_USER` | `账号不存在或停用` |

> ⚠ 最初漏了这层，结果是"token 过期"也回 `请先登录`。
> **过期是 8 小时就会遇到的常见情况**，前端直接把这句话显示给用户，所以它值得做对。
> （靠影子对比工具比对多次请求才发现。）

**为什么常量放在 common 而不是各自的服务里**：academic 和 scheduling **都要**用
（一个签发+校验，一个只校验）。文案必须一致，所以必须共享。

## 本篇小结

`orbit-common` 这 10 个类回答的是一个问题的不同侧面：
**「两个服务要怎么表现才算同一个系统？」**

| 类 | 它守的一致性 |
|---|---|
| `UtcTimes` | 时间基准（UTC、截断到秒） |
| `PageQuery` / `PageResponse` | 列表接口的参数与响应形状 |
| `BusinessException` / `ErrorResponse` | 错误体形状 + **面向用户的中文文案** |
| `ValidationErrorResponse` / `ValidationErrorItem` | 422 的数组形状（复刻 Pydantic） |
| `ApiExceptionHandler` | 上述所有东西的**唯一出口**，含状态码映射 |
| `JwtService` / `AuthFailure` | 认证 + **三种 401 文案的区分** |

**读这一层的价值**：你以后看到的**每一个**错误响应、**每一个**分页响应、
**每一个**时间字段，都是这 10 个类决定的。看懂它们，后面的一大半"为什么这样"
就不用再问了。
